# MPG-307 — Share machine capacity across projects: research

Research ticket MPG-307R (#7620). Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (KTD-5, R2, A3). Contract:
MPG-307 in `docs/plans/2026-11-06-multi-project-gateways/tickets-m3.md`. Code read at `7d5cc6199` (main, 2026-11-06);
line numbers refer to that commit. No code changed. Focus: how a machine-wide grant composes with
`effective_concurrent_agents` (the load envelope) and with keep-agents adoption slots.

## Outcome

With `projects:` set in `~/.aiur/machine`, one `Aiur.Gateway.Capacity` process (one per VM, started before any project
tree) enforces three ceilings at once: running agents across all projects never exceed `capacity.max_agents`; each
project never exceeds `projects[].max_agents` and its own `agent.max_concurrent_agents`; and the load envelope still
shrinks admission when the host is busy, now once for the machine rather than once per project. With `projects:` empty
or `capacity.max_agents` unset, `Slots` behaves exactly as today (the existing `slots_test.exs` passes unchanged).

## Findings in the code (what the design must fit)

1. **One cap function feeds ~25 call sites.** `Slots.available_slots/1` (`slots.ex:349-353`) is
   `max(effective_concurrent_agent_limit(state) - used_slots(state), 0)`. Callers include `dispatcher.ex:463`,
   `dispatcher/candidates.ex:135`, `dispatcher/capacity.ex:231`, `dispatch_outcome.ex:19`, `retry_engine/lookup.ex:116`,
   `override_resume.ex:316`, `pr_anchored.ex:149`, `queue_set_slots.ex:68`, `feature_supply_snapshot.ex:18`. Three
   siblings do the same arithmetic against `effective_concurrent_agent_limit/1`: `dispatch_slots_available?/2`
   (`slots.ex:363`), `replacement_slot_available?/2` (`:325`), `resume_fleet_slot_available?/2` (`:333`). **A broker call
   inside each is a GenServer round trip on the orchestrator's hot path.** The design therefore makes the *read* side an
   ETS lookup and the *write* side a call at one place.
2. **The envelope is already a second ceiling.** `effective_concurrent_agent_limit/1` (`slots.ex:219-226`) is
   `min(state.effective_concurrent_agents, max_concurrent_agent_limit(state))`. The envelope (`load_envelope.ex:67-118`,
   `pressure_admission.ex:105-170`) is per orchestrator: it reads host load/CPU pressure, which is a *machine* signal,
   and compares it to that orchestrator's own `Slots.used_slots/1` (`load_envelope.ex:103,108`;
   `pressure_admission.ex:116`). Two orchestrators therefore each back off and each ramp from their own used counts.
3. **Single spawn site.** Every dispatch, retry and rework worker start goes through
   `spawn_issue_on_worker_host/6` (`orchestrator/dispatcher/launch.ex:212`). Resumes of paused entries do not spawn a
   new worker but are admitted by `resume_fleet_slot_available?/2`.
4. **Used slots are computed, not counted.** `used_slots/2` (`slots.ex:295-297`) is active running + pending rework
   claims + reserved paused entries + pending resumes. Paused CI-wait / dependency / duration-cap / usage-limit entries
   release their slot (#2329, #5788). A broker ledger that only counts `acquire`/`release` pairs will drift from this
   whenever an entry changes class without ending (running -> CI-wait pause releases a slot while the entry stays in
   `running`).
5. **`--max-agents` is a session override.** `cli.ex:403-415` puts it in `:max_concurrent_agents_override`;
   `lifecycle.ex:136` seeds `session_max_concurrent_agents`; `max_concurrent_agent_limit/1` (`slots.ex:205-216`)
   prefers it. `aiur set max-agents` writes the same field (`slots.ex:62-85`).
6. **Adoption ignores the envelope on purpose.** `Adopter.adoption_slot/3` (`handoff/adopter.ex:86-93`) compares to
   `Slots.max_concurrent_agent_limit/1` (static), not the effective limit, and `AdoptedBoot.restore/1`
   (`adopted_boot.ex:11-19`) then raises `effective_concurrent_agents` to at least `used_slots` so the adopted agents are
   not "over" the envelope. Adoption runs inside `Orchestrator.init/1` (`lifecycle.ex:174`), before the first poll.
7. **Machine settings already carry the keys.** `Aiur.Machine.Settings.Schema.Capacity` has `max_agents` (>= 1, nullable)
   (`machine/settings/schema/capacity.ex`); `Aiur.Machine.Settings.get/0` is the reader (`machine/settings.ex`). The
   per-project `max_agents` sits in the `projects` entries (MPG-002, #7703).

## Design

### D1. Broker state: a ledger of issue ids per project, mirrored to ETS

`Aiur.Gateway.Capacity` is a GenServer owning a `:protected`, `read_concurrency: true` ETS table
`:aiur_gateway_capacity`. State: `%{ceiling: pos_integer() | nil, projects: %{project_id => %{max: pos_integer() | nil,
holders: MapSet.t(issue_id), pid: pid(), ref: reference(), proposal: pos_integer() | nil}}}`. Rows in ETS:
`{project_id, held_count, project_max, proposal}` plus `{:machine, total_held, ceiling}`.

Why a ledger keyed by issue id and not a bare counter: `request(project_id, n)`/`release/2` in the contract cannot
repair itself. Keyed ids allow `sync/2` (D4) to replace the project's set with the orchestrator's truth, so drift heals
within one poll cycle. The contract names stay as thin wrappers (`request/2` with `n = 1` calls `acquire/2`).

### D2. Read side: `Slots` takes the minimum

```elixir
# slots.ex — one new private helper, used by the four functions in finding 1
defp machine_headroom(%State{project_id: pid}), do: Aiur.Gateway.Capacity.headroom(pid)  # :infinity | non_neg_integer()
def available_slots(%State{} = state),
  do: max(min(effective_concurrent_agent_limit(state) - used_slots(state), machine_headroom(state)), 0)
```

`Capacity.headroom(project_id)` is an ETS read, no call: `:infinity` when the broker is absent, `projects:` is empty or
the project is unknown (this is what keeps single-project behavior bit-for-bit); otherwise
`min(ceiling - total_held, project_max - held(project))`, floored at 0. `dispatch_slots_available?/2`,
`replacement_slot_available?/2` and `resume_fleet_slot_available?/2` apply the same `min`. A reserved-priority
`dispatch_slots_available?` (the `reservation_limit` branch, `slots.ex:364-367`) is still bounded by `machine_headroom`:
**the P1 pressure bypass raises the envelope for one project, never the machine ceiling.**

`State` gains one field, `project_id` (`nil` = legacy, headroom `:infinity`). Its source is the project context from
MPG-302/303 (`State.project_id` is `Aiur.Project.Context.current_id/0`, the MPG-302R name, which returns `String.downcase(repo)`; the broker keys every ETS row and holder map by that same id; see open question Q1). `Slots` must not call into
`Aiur.Project` itself; `lifecycle.ex` `init/1` copies the id into `State` once.

### D3. Write side: reserve at the spawn site, release by sync

`launch.ex` `spawn_issue_on_worker_host/6` calls `Capacity.acquire(project_id, issue.id)` immediately before
`runner.(...)` is started. `:ok` proceeds. `{:error, :machine_full | :project_full}` skips the spawn, logs at debug, and
returns state unchanged (the next poll retries; same shape as the existing `:no_worker_capacity` branch,
`launch.ex:131-137`). `acquire` is a synchronous `GenServer.call` (timeout 1 s; a timeout or dead broker counts as
`:ok` with a warning, so a broker fault degrades to today's per-project behavior rather than a stall). It is idempotent
per `{project_id, issue_id}`.

Release is **not** done per transition. It is done by `Capacity.sync(project_id, issue_ids)`, called once at the end of
each poll tick and after every `:DOWN` the orchestrator handles, with `issue_ids` = the ids that currently count in
`Slots.used_slots/1` (active + pending rework claims + reserved paused + pending resumes). This reuses the one
definition of "occupies a slot" (finding 4) and cannot drift from it. `sync` replaces the holder set and refreshes ETS.
Worst case a freed slot is visible to the other project one tick late (`polling.intervals.dispatch`); this is the
documented price of not threading a release through ~15 exit paths. To cut the latency for the common case, the
`:DOWN` handler for a finished worker also calls `sync` (one call, same function).

### D4. Crash safety

The broker `Process.monitor`s the orchestrator pid on first `acquire`/`sync`. On `:DOWN` it drops that project's
holders and updates ETS within the same message (well under the contract's 1 s). A restarted orchestrator re-registers
on its first `sync` (called at the end of `init/1`, after adoption). Runner tasks that survive an orchestrator-only
restart are stopped by `OrphanedWorkers.stop_untracked_runners` (`lifecycle.ex:174`), so a dropped grant matches reality.

### D5. The load envelope: one machine envelope level, taken from the orchestrators

Do **not** move the envelope computation into the broker in this ticket: it lives in `State`, is entangled with
`EnvelopeResume`, `PressureAdmission` and `AdoptedBoot`, and the ADR (MPG-301/302) decides which of those singletons
are per-project. Instead:

- Each orchestrator keeps computing its own `effective_concurrent_agents` exactly as today (still `<=` its static limit).
- After each envelope update the orchestrator publishes `proposal = Slots.effective_concurrent_agent_limit(state)` via
  `Capacity.sync/3` (third argument, `proposal:`).
- The broker's **machine envelope limit** is `max` over projects of `proposal` (ignoring projects with no proposal),
  clamped to `[1, ceiling]`. `headroom/1` then also bounds by `machine_envelope_limit - total_held`.

Why `max`, not `min` or `sum`: all orchestrators sample the same host, so under pressure they converge on similar
levels; `sum` would multiply the allowance by the project count (the failure this design avoids: two projects each at
level 4 admitting 8 on a host that asked for 4). `min` would let one idle project (whose envelope never ramps, because
ramping needs queued demand and its own `used_slots`) pin the whole machine low. `max` lets the busiest project's
envelope represent the host. Cost: a project with demand cannot be "ahead" of the host signal, which is correct.

Plain `max(proposals)` is wrong on a healthy host: ceiling 12, A and B static 8, both envelopes at 8, would cap the
machine at 8 instead of 12 (scenario 6). So each orchestrator publishes `{proposal, static_limit}`, and the machine
envelope limit is `max(proposals)` only while some project is backed off (`proposal < static_limit`); otherwise it is
`ceiling`. Q2 asks whether the owner prefers a true machine envelope.

### D6. Adoption (keep-agents restart)

Order of boot in `application/children.ex`: `Aiur.Gateway.Capacity` first, then project trees (MPG-306). Adoption runs
per project in `init/1`:

- `Adopter.adoption_slot/3` keeps its static comparison (`used > max_concurrent_agent_limit`) and adds one clause:
  `Capacity.adopt(project_id, issue_id)`, a call that **ignores the machine envelope limit and any hold, but not the
  hard ceiling or `projects[].max_agents`**. `{:error, :machine_full | :project_full}` maps to the existing
  `{:error, :max_concurrent_agents_reached}` fallback (a checked retry), so the existing fallback outcome and alert are
  reused.
- `AdoptedBoot.restore/1` is unchanged, and its raised `effective_concurrent_agents` reaches the broker through the
  first `sync` with `proposal`, so adopted agents are never over the machine envelope either.
- Projects adopt in `projects:` list order (each project's `init` is sequential under the gateway supervisor start
  order). If the operator *lowered* `capacity.max_agents` across the restart, the earlier-listed project keeps its
  agents and the later project's overflow agents fall back. This is deterministic and documented, and is the only
  case where a restart changes who runs. MPG-308 (per-project fingerprints) is independent: a fingerprint mismatch
  falls the agent back before `adoption_slot` runs.
- Adopted holds count in the ledger immediately, so project B's first poll cannot take the slots A's adopted agents
  occupy.

### D7. Ceiling sources and precedence

`ceiling = capacity.max_agents` from `Aiur.Machine.Settings.get/0`. `--max-agents N` becomes the **machine** ceiling in
multi-project mode (the contract says so): `cli.ex` `maybe_set_max_agents/1` additionally stores
`Application.put_env(:aiur, :machine_capacity_override, n)`; the broker reads it over `capacity.max_agents`. In
single-project mode `--max-agents` keeps writing only `:max_concurrent_agents_override`. `aiur set max-agents N` in
multi-project mode follows MPG-311R (PR 7721), which classifies `set max-agents` as project-scoped:
`aiur set max-agents N --project o/r` sets that project's runtime ceiling (today's `session_max_concurrent_agents`);
without `--project` on a multi-project gateway it exits 64 `pick a project`. A runtime machine-ceiling change is an edit
of `capacity.max_agents` in `~/.aiur/machine` followed by `aiur gateway reload`, which calls `Capacity.configure/1`.
There is no `Capacity.set_ceiling/1`. If `capacity.max_agents` is
nil and `projects:` is set, the ceiling is `sum` of the projects' static limits (nobody asked for a machine cap; the
envelope still protects the host).

Per-project limit = `min(projects[].max_agents, agent.max_concurrent_agents)` (the lower of the two wins; unset `nil`
is ignored). Config reload (MPG-306 `aiur gateway reload`) calls `Capacity.configure/1` with the new numbers; lowering
a limit below current holders never stops an agent (`draining?` already models this in `max_concurrent_agent_status`).

### D8. Status

`max_concurrent_agent_status/1` (`slots.ex:229-263`) gains `machine: %{ceiling, held, envelope_limit}` when the broker is
present, and `available` uses the new `available_slots/1`, so `aiur status` shows why a project with free local slots is
held (`dispatch_hold` reason `:machine_capacity`, added to `CapacityBinding`/`Dispatcher.Capacity` so the binding
constraint is named, never collapsed to `:unknown`). The gateway summary `capacity: {max, running}` (S6, MPG-407)
reads `ceiling` and `total_held` from the same ETS row.

### Alternatives considered

| Alternative | Why not |
|---|---|
| Broker computes the envelope for the machine | Needs `EnvelopeResume`/`PressureAdmission`/`AdoptedBoot` state to move out of `State`; that is MPG-301/302's call, and it breaks adoption's save/restore. Left as Q2. |
| Counter `request(n)` / `release(n)` only (contract wording) | Drifts from `used_slots` (finding 4) on every CI-wait pause; needs a release hook on ~15 exit paths. |
| `GenServer.call` from `available_slots/1` | ~25 call sites on the dispatch hot path; one slow broker stalls every orchestrator. ETS read avoids it. |
| Static split (ceiling / project count) | Violates A4: lower-priority work must use otherwise idle slots. |
| Sum envelopes | Multiplies host allowance by project count (D5). |

## Data and assets

- ETS table `:aiur_gateway_capacity`; row shapes in D1. No on-disk state: the ledger is rebuilt from the first `sync`
  of each orchestrator after a restart (adoption repopulates it; D6).
- Config names: `machine:capacity.max_agents` (existing), `machine:projects[].max_agents` (existing), app env
  `:machine_capacity_override` (new, internal). **No new config key**, so no new `check-config-docs` entry; docs change
  is behavioral (D7).
- Event/log names: `Logger` only. No new alert in this ticket (a full machine is normal). `system.dispatch.capacity_starved`
  already fires from `Dispatcher.Capacity` when ready work is held; the new `:machine_capacity` hold reason must reach
  it (unit 7).
- Known gap and fallback: if `Aiur.Project.Context.current_id/0` is not final when MPG-307 starts, `State.project_id` is
  populated from `Aiur.Config.settings!().tracker` repo identity (`Aiur.TrackerIdentity`) through `String.downcase/1`.

## Risks

| Risk | Detect | Fallback |
|---|---|---|
| Late `sync` leaves slots idle for up to one poll | scenario 9; `held` vs `used_slots` gauge in status | the `:DOWN` handler also syncs (D3); lower poll interval is unaffected |
| `sync` called with wrong id set double-frees | scenario 9 with a pending-rework-claim id included | the id set comes from one function (`Slots.slot_holder_ids/1`, extracted from `used_slots/2`); never built ad hoc |
| Broker is a single point of failure for all dispatch | scenario 12 | calls time out to `:ok`; reads are ETS and survive a broker restart only until the table owner dies, so the ETS table is created by a `Gateway.Supervisor`-owned heir, or `headroom` returns `:infinity` on `ArgumentError` |
| `max(proposals)` hides one project's pressure | scenario 5 | Q2 true machine envelope |
| state.ex / launch.ex / slots.ex line limits (500) | `scripts/check-pr-structure.py` | new code goes in `machine_grant.ex`; slots.ex has 104 lines of headroom |
| Adoption order decides who loses when the ceiling is lowered | scenario 8 | documented; Q3 |
