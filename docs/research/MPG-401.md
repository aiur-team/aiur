# MPG-401: Allocation and scheduling policy

Date: 2026-11-06. Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579). The contract is in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m4-m7.md`. Prior art:
`docs/research/multi-gateway/priority-reconciliation.md`, section "Focus with borrowing has direct scheduler
precedent". Consumer: MPG-402. It adds `gateway/allocation.ex`, which `Aiur.Gateway.Capacity` calls on every
request and release.

**Interfaces.** Callers: `Aiur.Gateway.Capacity` (MPG-402) on every slot request and release. Implementation:
`Aiur.Gateway.Allocation.allocate/5` in `gateway/allocation.ex` (MPG-402). Producer of `priorities`: the reconciled
scheduler slot (MPG-403, MPG-405).

## Summary

A gateway runs one pure function each time a slot may change hands. The function walks the work groups in priority
order. It gives each group as many new slots as the group can use, up to the group's hard maximum and its project's.
Slots a group cannot use go to the next group. Nothing that is running is ever stopped. Priority decides only the
order of the walk. Limits decide only how far each group may fill. Neither input changes the other.

## Decisions on the mechanisms the scope delegates

| Mechanism | Decision | Why |
|---|---|---|
| Hard maximum vs flexible target | **Hard maximum only.** A limit caps running agents for a project or a feature. No target or nominal share exists. | A target either holds slots back, which makes it a reservation, or is advisory, which makes it priority order. |
| Reservations | **None.** No slot is held for a project with no ready work. | A held slot is an idle slot, and decision 24a forbids idle slots while eligible work exists. Tickets reserved for an offline owner (KTD-2) are another matter: they are left out of `demands`. |
| Borrowing | **Implicit, up to the borrower's own maximum.** A lower group gets every slot the groups above it cannot use. No separate borrowing limit exists. | A borrowing limit idles slots while the focus feature is briefly blocked. To cap a side lane, set that lane's maximum. |
| Preemption | **Never.** Grants are new starts only. A higher group gets slots back by waiting for running agents to finish. | KTD-5 and decision 25: first access to slots, not exclusive use. Kubernetes `preemptionPolicy: Never` draws the same line. |
| Fair share | **None. Strict priority, no usage decay.** | Decision 24a asks for one feature to finish at a time. A lower project waits while higher groups have ready work and headroom. The operator's lever is a maximum on the higher group. Revisit decay only after a measured starvation case. |
| Named queues | **None inside the allocator.** A build-queue entry orders work inside its project's feature order. It has no capacity share. | Project, then feature, is the whole priority model (decision 1). |

## Contract

```elixir
@type project_id :: String.t()
@type feature :: String.t() | :none
@type group :: {project_id(), feature()}
@type capacity :: non_neg_integer()
@type demand :: %{ready: non_neg_integer(), promoted: non_neg_integer()}
@type demands :: %{optional(group()) => demand()}
@type priorities :: [group()]
@type limits :: %{optional(project_id() | group()) => non_neg_integer()}
@type running :: %{optional(group()) => non_neg_integer()}
@type grants :: %{optional(group()) => pos_integer()}

@spec allocate(capacity(), demands(), priorities(), limits(), running()) :: grants()
```

- `capacity` is the machine's agent capacity: L1 `capacity`, or `--max-agents`.
- `demands` counts this gateway's dispatchable tickets per group. A ticket counts in `ready` when it can start now.
  This gateway owns it or may claim it, its blockers are satisfied, it is not paused, and it is not in retry backoff.
  `promoted` counts the promoted tickets among them, so `promoted <= ready`. A promoted ticket is one the operator
  has explicitly moved to the front; MPG-402 maps the existing signals onto it. `:none` holds a project's tickets
  with no feature.
- `priorities` is the full group order, highest first. The caller builds it from effective priority. Projects come in
  cross-project order: shared intent (L4), else L1 `projects[].priority`. Within each project come its features in
  `build_order.feature_order` order, then `{project, :none}`. Groups in `demands` but not in the list follow the listed
  ones in ascending term order, so the result is total and deterministic.
- `limits` maps a project id or a group to a hard maximum of running agents. A missing key means no limit beyond
  `capacity`. The caller resolves a project's limit as `min(projects[].max_agents, agent.max_concurrent_agents)`.
  Priority never feeds this map.
- `running` counts agents running now per group, including groups with no demand. Every running agent uses
  `capacity` and its project's limit.
- `grants` is the number of **new** agents each group may start now. Groups granted 0 are omitted. The caller picks
  the tickets within a group: promoted tickets first, then by ticket priority.

## Algorithm

1. `free = max(capacity - sum(running), 0)`.
2. **Promotion pass.** Walk the order. Each group gets
   `min(promoted, ready, free, group headroom, project headroom)`.
3. **Priority pass.** Walk the order again. Each group gets
   `min(ready - already granted, free, group headroom, project headroom)`.
4. Headroom is `max(limit - (running + granted), 0)`, or unlimited without a limit. Project headroom counts all the
   project's groups.

The walk is the focus rule. The first feature of the first project fills before the second feature gets a slot. Any
slot a group cannot use falls through to the next feature or project. A group cannot use a slot when it has no more
ready work or has reached a maximum.

Reference implementation. It produces the expected grants for every case below:

```elixir
def allocate(capacity, demands, priorities, limits, running) do
  unlisted = demands |> Map.keys() |> Enum.reject(&(&1 in priorities)) |> Enum.sort()
  order = priorities ++ unlisted
  free = max(capacity - Enum.sum(Map.values(running)), 0)
  {grants, free} = pass(order, &promoted/2, demands, limits, running, {%{}, free})
  {grants, _free} = pass(order, &ready/2, demands, limits, running, {grants, free})
  grants
end

defp promoted(d, _granted), do: min(d.promoted, d.ready)
defp ready(d, granted), do: d.ready - granted

defp pass(order, want_fun, demands, limits, running, acc) do
  Enum.reduce(order, acc, fn {project, _} = group, {grants, free} ->
    d = Map.get(demands, group, %{ready: 0, promoted: 0})
    granted = Map.get(grants, group, 0)
    used_group = Map.get(running, group, 0) + granted
    used_project = used(running, project) + used(grants, project)

    n =
      Enum.min([
        want_fun.(d, granted),
        free,
        headroom(limits, group, used_group),
        headroom(limits, project, used_project)
      ])

    if n > 0, do: {Map.put(grants, group, granted + n), free - n}, else: {grants, free}
  end)
end

defp used(counts, project), do: for({{^project, _}, n} <- counts, reduce: 0, do: (acc -> acc + n))

# :infinity sorts above every integer, so Enum.min ignores a missing limit.
defp headroom(limits, key, used) do
  case Map.fetch(limits, key) do
    {:ok, limit} -> max(limit - used, 0)
    :error -> :infinity
  end
end
```

## Rules

**Worked example.** There are 12 slots. A has priority 1 and maximum 3. B has priority 2 and maximum 5. C has
priority 3 and maximum 8. All three have plenty of ready work. The walk gives A 3, then B 5, then C
`min(8, 12 - 8) = 4` (case 1).

**No eligible work in a high-priority project.** A group with `ready: 0` gets nothing, and the walk moves on. The lower
groups borrow every slot it leaves, up to their own maximums (case 2). When the high-priority group gains ready work,
it gets the next slots that free up. It never takes back running ones (cases 17 to 19).

**Promoted ticket.** The promotion pass serves promoted tickets before any other work, whatever their project's
priority, so a promoted ticket wins the next free slot (case 9). It is still a new start, so it waits when no slot is
free (case 10). Promotion never raises a limit. A promoted ticket whose project is at its maximum waits, and the slot
goes to other work (case 11).

**Hysteresis against oscillation.**

- H1. Grants are never negative, and the allocator never stops an agent. A slot changes group only when its agent
  ends, so it is reassigned at most once per agent. Allocation alone cannot make agents flap.
- H2. The function is stateless and deterministic. The stable group key breaks ties, never recent usage, so equal
  inputs cannot alternate.
- H3. `priorities` arrives already reconciled by MPG-403 and MPG-405. Rank damping belongs to the writer of the
  scheduler slot there: promote now, demote after a window, ignore small score gaps. `allocate` adds no second layer,
  because a priority change already moves only future starts (H1).
- H4. A start that fails at once re-enters `ready` only after the dispatcher's retry backoff. Without that, one
  failing ticket could loop through grant, fail and release. The caller owns this rule.

**Priority stays separate from allocation.** `limits` and `capacity` are computed without reading priority, and the
function uses priority only to order the walk. MPG-402 should test the properties that follow:

- P1. `sum(grants)` does not depend on the order of `priorities`. A priority change alters who gets slots, never how
  many (case 3 against case 1).
- P2. For every limited group and project, `running + grant <= max(limit, running)`, in any priority order.

**Never idle.** P3. If `sum(grants) < free`, every group with ungranted ready work is at a group or project maximum.
Slots stay idle only when every group with ready work is at a maximum (case 15). In case 5 the focus feature cannot
use every slot, and the rest go to the next project, so none stays idle.

The property check below runs P1, P2, P3 and `sum(grants) <= free` on 2,000 seeded random inputs. Each input has
3 projects of 3 groups and random demand, limits, running agents and capacity, in two priority orders. It is plain
ExUnit, ready for MPG-402's `allocation_test.exs`, and passes against the reference implementation above:

```elixir
test "P1, P2, P3 and the free-slot bound hold on random inputs" do
  :rand.seed(:exsss, {401, 402, 403})
  groups = for p <- ~w(A B C), f <- [:none, "f1", "f2"], do: {p, f}
  sum = fn counts, p -> for({{^p, _}, n} <- counts, reduce: 0, do: (acc -> acc + n)) end
  total = fn grants -> grants |> Map.values() |> Enum.sum() end
  at_limit? = fn limits, key, used -> Map.has_key?(limits, key) and used >= limits[key] end

  for _ <- 1..2000 do
    demands = Map.new(groups, &{&1, (r = Enum.random(0..4); %{ready: r, promoted: Enum.random(0..r)})})
    running = Map.new(Enum.take_random(groups, 3), &{&1, Enum.random(0..3)})
    limits = Map.new(Enum.take_random(~w(A B C) ++ groups, 3), &{&1, Enum.random(0..4)})
    capacity = Enum.random(0..14)
    free = max(capacity - total.(running), 0)
    g1 = Allocation.allocate(capacity, demands, groups, limits, running)
    g2 = Allocation.allocate(capacity, demands, Enum.shuffle(groups), limits, running)

    # P1 and the bound: priority changes who gets slots, never how many.
    assert total.(g1) == total.(g2)
    assert total.(g1) <= free

    for g <- [g1, g2] do
      # P2: no group or project ends above max(limit, running).
      for {key, limit} <- limits do
        {r, n} =
          if is_tuple(key),
            do: {Map.get(running, key, 0), Map.get(g, key, 0)},
            else: {sum.(running, key), sum.(g, key)}

        assert r + n <= max(limit, r)
      end

      # P3: a slot stays free only when every group with ungranted ready work is at a limit.
      if total.(g) < free do
        for {{p, _} = grp, d} <- demands, d.ready > Map.get(g, grp, 0) do
          assert at_limit?.(limits, grp, Map.get(running, grp, 0) + Map.get(g, grp, 0)) or
                   at_limit?.(limits, p, sum.(running, p) + sum.(g, p))
        end
      end
    end
  end
end
```

## Risks

- **Starvation.** Strict priority with no decay lets a low project wait for as long as higher groups have ready work
  and headroom. The operator's lever is a maximum on the higher group. Open question (a) sets the revisit trigger.
- **Slow reclaim.** A higher group gets slots back only when running agents end (no preemption). When agents run for
  hours, a newly ready focus feature can wait that long. A promotion moves one ticket to the next free slot, but it
  does not shorten the wait for that slot either.
- **Dispatch races.** Two concurrent `allocate` calls on the same `running` snapshot can both grant the same free
  slot. `Aiur.Gateway.Capacity` must serialize calls (one process owns the counts) and count a grant as running
  before the next call, so the function stays pure and the race stays out of it.

| c | Which module owns the retry backoff in H4? | The dispatcher's existing retry engine (`Aiur.Orchestrator.RetryEngine`). The caller leaves a ticket out of `ready` while it holds a pending retry; `allocate` never sees backoff. | MPG-402 |
