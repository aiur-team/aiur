# MPG-208 — Enrol a peer with a one-time invite: research

Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579). Contract: MPG-208 in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m2.md`. Research ticket: MPG-208R (#7591). Abbreviations:
`E/` = `packaging/npm/aiur-cli/libexec/`, `S/` = `src/lib/`, `T/` = `src/test/`.

## Outcome

On gateway B, `aiur gateway invite --grant read,message [--ttl 10m]` prints one line, the code. On gateway A,
`aiur gateway join <code> --name <n>` contacts B, checks B's identity against the code, sends A's gateway id and
label together with the single-use secret, receives a peer-bound token, and writes A's registry entry for B (token
file mode 0600, `gateway_id`, and `tls_pin_sha256` when the code carries one). B, in the same step, burns the
invite, writes its entry for A with the invited categories and stores the token's hash. A reused, expired or
mismatched code leaves both machines unchanged. `gateway register` is the same result without B's help, and
`gateway rotate` replaces the token with a 10 minute overlap.

## Design

### D1. Code encoding (answers the focus question)

`aiur-invite:` + base64url (no padding) of one line of JSON:

```json
{"v":1,"url":"https://b.example.ts.net","gateway_id":"<26 base32>","fp":null,"id":"<8 hex>","secret":"aiur_inv_<43 base64url>","exp":1793998800}
```

- `fp` is the SPKI SHA-256 of B's own TLS certificate, lower-case hex, or `null` (D2).
- `exp` is unix seconds. B enforces it; A only uses it to fail fast with a clear message.
- The code carries **no grants**. B holds them in its invite record, so a joiner cannot widen what it will get by
  editing the code, and the code stays short (about 260 characters).
- `v` is checked first; an unknown version exits 64 `unsupported invite version`.

Why this and not the alternatives:

| Option | Verdict |
|---|---|
| `aiur-invite:` + base64url JSON (plan default) | **Chosen.** No shell metacharacters (`& # ? ;`), so it survives copy-paste into an unquoted shell, chat and a QR. Extensible by field. Decoding needs `node`, which `E/engine/remote.sh` already requires. |
| `aiur-join://host#sha256=…&t=…` (the k3s-style string in `docs/research/multi-gateway/gateway-enrollment-and-permissions.md`) | Rejected. Same information, but `&` and `#` are shell hazards unquoted, and a URL-shaped string invites being opened in a browser, which would send the secret to the server in a `GET` log. |
| Short human code over SPAKE2 | Rejected for MVP, as that report concludes: a new crypto dependency for a convenience. |
| Joiner passes `--url` and a short secret, no code | Rejected: nothing carries B's identity, so the joiner cannot check B before sending the secret. |

### D2. TLS fingerprint source (answers the focus question)

Finding: the daemon never terminates TLS. `grep` of `S/aiur_web/endpoint*.ex` finds no `https:`, `certfile` or
`:ssl` option; HTTPS in front of it is always `tailscale serve`, a Cloudflare tunnel or another proxy. So the daemon
has no certificate of its own to fingerprint, and the `tls_fingerprint_sha256` field MPG-207 puts in hello cannot be
computed by the daemon in the common deployment.

Decision:

1. `invite` takes the pin from, in order: `--tls-pin <hex>` (operator supplies it), else
   `server.tls_pin_sha256` (new optional config key, see Interfaces), else `null`.
2. When the pin is `null`: **pin disabled, token only, with a warning** on both sides. `invite` prints
   `warning: no TLS pin; the joiner will trust whatever certificate answers at <url>`; `join` prints the same and
   writes no `tls_pin_sha256`. The secret is single-use and short-lived, so a man in the middle on first contact
   can enrol only himself, and B's grants for him are read-only by default.
3. When a pin is present, `join` passes it to curl as `--pinnedpubkey sha256//<base64>` (the hex is converted to
   base64 in the shell) for both hello and enrol, and writes `tls_pin_sha256` into A's entry. (This is `join`'s own first-contact use of the pin, before any registry entry exists; enforcement on later calls is MPG-201's.) The pin is the SPKI
   hash, not the whole-certificate hash. MPG-207 must document that `tls_fingerprint_sha256` has this meaning and is
   `null` unless `server.tls_pin_sha256` is set.
4. `remote.sh` today does not pass any pin to curl (lines 428-438 call plain `curl`). Honouring a stored
   `tls_pin_sha256` on every later call is owned by **MPG-201**, which adds `--pinnedpubkey` to `remote.sh`. MPG-208
   only writes the key; it depends on MPG-201 so the written pin is never ignored.

Hex-to-base64 and the S2 field name stay as the plan defines them (`tls_pin_sha256`, hex).

### D3. Protocol

```text
B: gateway invite   -> invites.json += {id, secret_sha256, exp, grants, created_at, used_at: null}
                       prints aiur-invite:<b64>
A: gateway join     -> decode; reject expired; GET  B/api/v1/gateway/hello   (pinned if fp)
                       require hello.gateway_id == code.gateway_id and hello.enrollment == "open"
                    -> POST B/api/v1/gateway/enroll
                       {id, secret, gateway_id: A's, label: A's, url: A's (optional)}
B: enroll           -> constant-time compare sha256(secret); not used; not expired; gateway_id not already enrolled
                       in ONE locked step: mark invite used, create client token {name, scope, peer: A's id},
                       write registry entry for A (allows.categories, allows.credentials)
                       respond 200 {gateway_id, label, token, granted: [...], pending: [...]}
A: join             -> check response gateway_id == code.gateway_id; write token file 0600, then registry entry
                       (temp file + rename, same pattern as Aiur.ClientTokens.write_records/2)
```

Properties that follow:

- **Verify before disclosing.** The secret leaves A only after hello matches the code's `gateway_id`, and, with a
  pin, only over the pinned channel.
- **Single use, atomic.** The `used_at` write and the token and registry writes happen under one file lock on B.
  Two concurrent joins with one code: one gets 200, the other 410 `invite_used`, and B holds exactly one entry.
- **Refusals write nothing.** Order of checks on B: rate limit, id lookup, secret hash, expiry, used, duplicate
  `gateway_id`. Failure responses are identical in body for unknown id and wrong secret (`401 invalid_invite`) so a
  caller cannot probe ids. Every refusal is an audit line (`outcome: "refused"`, reason, remote IP) and no state
  changes. On A, nothing is written until the 200 arrives.
- **Rate limit.** 5 failed enrol attempts per minute per remote IP, then 429, so a code cannot be brute-forced
  within its TTL. The secret has 256 bits, so this is defence in depth.
- **Direction.** Only B gets a grant row for A. A's entry for B has no `allows` block (read only by default, per
  S2), so the reverse direction needs its own invite from A, which is Kevin's Q5 decision: full mutual trust is one
  command per side.
- **Failure after B commits** (the response is lost, or A crashes while writing): B has an entry and a token A never
  received. Recovery is `aiur gateway remove <peer>` on B and a new invite. `join` prints that sentence when the
  response is lost. This is acceptable because the entry is read-only until confirmed and the token is useless
  without being known.

### D4. Write categories need a signed-in human

`message` and every category above `read` is a write category in MPG-206. At enrol time B writes the entry with
`allows.categories: [read]` and passes the remainder of the invite's grants to the MPG-206 grant-request path
(`Aiur.Gateway.Grants.request/3`, raising the human-required Decision). The entry gains those categories only when
a dashboard session signed in on B answers it. `join` therefore prints `granted: read` and
`pending on <B>: message (confirm in the dashboard)`. An invite that names only `read` writes at once. The invite
command is refused over `--gateway` (D6) and `trust` in `--grant` is rejected as in MPG-206.

### D5. Token shape and rotation

- `Aiur.ClientTokens` records gain an optional `"peer"` (the peer gateway id). `create/3` takes `peer:`; `list/0`
  returns it; `authenticate/1` returns it so `control_controller.ex` can call `Grants.allowed?/3` (MPG-206). Token
  scope is `"read"` when the invited categories are `[read]`, else `"write"`; the category check, not the scope, is
  the real gate.
- Token name is `peer-<local name>-<n>` where `n` increments on rotation. It matches the existing name rule
  `\A[A-Za-z0-9][A-Za-z0-9._-]{0,63}\z`.
- `gateway rotate <peer>` is run on the side that owns the token's hash (B). It mints a new token, keeps the old
  record valid with `"expires_at"` ten minutes ahead (new optional field, checked in `authenticate_records/2`), then
  removes it. It prints the new token once; the operator moves it to A with `gateway register <name> --url <u>
  --token-file <f>`. The entry's `allows.credentials` lists the current and, during the
  overlap, the old id.
- `gateway remove <peer>` deletes the registry entry, revokes every token whose `peer` equals the entry's id, and is
  local only.

### D6. Local-only commands

`invite`, `join`, `register`, `remove` and `rotate` are not on the remote allowlist and, like MPG-206's grant
commands, exit 64 `<cmd> is local to the gateway it changes` when given `--gateway`/`--instance`. The enrol route is
the only way a remote caller touches the registry, and it can only add an entry whose secret it holds.

## Prior art

Everything needed is in the existing reports, so no `deep-research` run was made.

- k3s secure token carries the cluster identity hash plus credentials, and expiring bootstrap tokens: "enables the
  client to authenticate the identity of the cluster it is joining, before sending credentials"
  (`docs/research/multi-gateway/gateway-enrollment-and-permissions.md`, "Enrolment is a pinned, one-time join string").
  Used for the verify-before-disclose order.
- Syncthing pins a device identity by certificate hash; its introducer re-adds removed devices, which is why D3 gives
  the joined peer only a read-only entry on one side.
- Behind a tunnel the peer's certificate pin checks the edge, not the daemon (same report, "Without a tailnet…"),
  so the bearer token is the real credential and the pin is optional. That is the basis of D2.

## Implementation units

1. **Invites store.** `S/aiur/gateway/invites.ex` (new). `create(grants, ttl_seconds)` returns `{:ok, %{code_fields}}`;
   `redeem(id, secret, peer_id, now)` returns `{:ok, grants}` or `{:error, :invalid_invite | :expired | :used |
   :duplicate_peer}`. File `gateway-invites.json` under `Aiur.Config.Paths.decision_state_dir/0`, mode 0600, atomic
   write like `Aiur.ClientTokens`. Secrets stored as sha256 only, compared with `Plug.Crypto.secure_compare/2`.
   Default TTL 10 minutes, maximum 24 hours. Done when `T/aiur/gateway/invites_test.exs` passes.
2. **Token fields.** `S/aiur/client_tokens.ex`: optional `"peer"` and `"expires_at"` in `create`, `list`,
   `authenticate`, `valid_record?/1`. Done when old stores still load and an expired record fails `authenticate/1`.
3. **Enrol route.** `S/aiur_web/controllers/gateway_enroll_controller.ex` (new) and a route in
   `S/aiur_web/routes/api.ex` outside the bearer pipelines, plus the failed-attempt limiter (ETS counter in the
   controller module, 60 s window). Refuses when `server.gateway_hello` hides the gateway (404, same as hello).
   Done when `T/aiur_web/controllers/gateway_enroll_controller_test.exs` passes.
4. **Config key.** `S/aiur/config/schema/server.ex`: `tls_pin_sha256` (optional, 64 hex). Docs
   `website/docs-app/reference/configuration-daemon.md`. Done when `scripts/check-config-docs.py` passes.
5. **CLI.** `S/aiur/gateway/cli.ex` (`invite`, `register`, `remove`, `rotate`; created by MPG-206, extended here),
   `E/aiur-gateway.sh` and `E/aiur-engine.sh` dispatch (`join` runs in the shell because A needs no running daemon),

## Data and assets

- Invites file: `gateway-invites.json` in the decision state dir, list of `{id, secret_sha256, exp, grants,
  created_at, used_at}`. Used invites are kept 24 hours for the audit trail, then dropped on the next write.
- Registry entry written on A: `instances.<name>: {gateway_id, label, url, token_file: ~/.aiur/peers/<name>.token,
  tls_pin_sha256?}` (S2). On B: `{gateway_id, label, allows: {categories, credentials}}`, no `url` unless A sent one.
- Known gap: the daemon cannot read its own certificate when a proxy terminates TLS (D2). Fallback: token only.

## Risks

- **First-contact interception without a pin.** Detect: `join` always prints the warning. Fallback: an operator who
  needs the pin sets `server.tls_pin_sha256` or passes `--tls-pin`. Impact is bounded: read-only entry.
- **Code leaked in shell history or chat.** TTL 10 minutes default, single use, and the enrolled peer starts
  read-only, so a stolen code before use costs one revocable read-only peer.
- **Lost response leaves B enrolled.** Documented recovery above; `gateway list` (MPG-209) shows the peer as never
  reached.
- **Pin conversion bug** (hex SPKI vs curl's base64). Covered by the pin mismatch test against a local TLS stub; a
  match test with the right pin must also pass.
- **MPG-207 naming drift.** Hello's field must be the SPKI hash and may be `null`; confirm before MPG-207 merges.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| Should the daemon terminate TLS itself so a pin is always available? | No; pin is optional, operator-supplied | A TLS listener, certificate generation and rotation become a separate ticket; `fp` is then always set |
| Should `join` refuse when there is no pin on a non-loopback `http` url? | Refuse plain `http` (already enforced for non-loopback in `remote.sh`); allow `https` without a pin with the warning | Stricter would break every tunnel deployment |
| Should the invite carry the grants so A can show them before joining? | No; B states them in the response | Grants in the code would make the code longer and let a joiner see, not change, them |
| Are write grants confirmed at `invite` time or at enrol time? | At enrol time (D4); read lands immediately | At invite time would block the CLI on a human or print a code that is unusable until confirmed |
| Token overlap on `rotate` | 10 minutes, fixed | A flag `--overlap` is a later addition |
| Can one invite enrol several peers? | No, single use | Multi-use invites reintroduce a shared fleet secret, which the enrolment report rejects |
