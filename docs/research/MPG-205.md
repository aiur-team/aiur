# MPG-205 — Split write scope into permission categories bound to a peer: research

Research for #7634 (MPG-205), plan `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579), contract in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m2.md`. Ticket #7588 (MPG-205R). No code change.

## Outcome

Every remotely reachable `Aiur.ControlCall.Allowlist` entry carries one category: `read`, `message`, `executor`,
`agents`, `tickets` or `config`. `trust` exists as a name, but nothing remote maps to it. A client token may carry
`peer` (a 26-character gateway id) and `categories`. `POST /api/v1/control` refuses a call whose category is not in
the token (403 `category_not_granted: <category>`). MPG-206 adds the second check, the peer's grant in
`remote-instances.yaml`. Existing tokens keep working: `read` becomes `[read]`, `write` becomes every category except `trust`.

## Design

### Today (verified in the checkout)

- `allowlist.ex` has 112 entries (100 `@agent_rows` plus 12 other rows). Each row's `class` is `:read`, `:write`, `:deny`, or a
  one-argument function (`watch_scope/1`, `queue_scope/1`, ...) that decides from the parsed arguments.
- `ControlCall.parse/2` computes `scope in [:read, :write, :deny]` (`control_call.ex:45`). `:deny` is refused when
  `remote: true`. `ControlCall.run/3` recomputes `classify(entry.class, args) == scope` before running
  (`control_call.ex:152`), so the class is checked twice and must stay deterministic.
- `control_controller.ex:62-63` is the only token check: `token_scope == "write"` and `max_scope: write`. The token store
  (`client_tokens.ex`) holds `name`, `scope`, `hash`, `created_at`.
- `engine_census_test.exs` pins read/write per wrapper command. It will keep passing if `scope_of/1` is kept.

### Decision 1: the row keeps its shape; the third element becomes a category

Each row's third element becomes a category atom, a category function, or `:deny`. A function returns a category or
`:deny` (for example `watch_scope/1` returns `:read` or `:executor`). The scope is derived:

```elixir
@spec scope_of(category | :deny) :: :read | :write | :deny
def scope_of(:read), do: :read
def scope_of(:deny), do: :deny
def scope_of(c) when c in [:message, :executor, :agents, :tickets, :config], do: :write
```

`:trust` is not a legal result of any row, so no call can be gated on it. The census test makes that an assertion.
`ControlCall.parse/2` returns `%{..., category: c, scope: scope_of(c)}`. The existing scope users (`max_scope/2`,
`allow_remote/2`, `validate_run_entry/4`) are unchanged. Rejected: a second `category:` key beside `class`. The two
could disagree, and a read category with a write class would pass review.

The existing `*_scope/1` helpers (`watch_scope`, `estimate_scope`, `feature_scope`, `lane_scope`, `epic_scope`,
`queue_scope`, `sweep_scope`, `experiment_scope`, `history_label_scope`, `listen_mode_scope`, `wait_scope`,
`alerts_scope`) are renamed `*_category/1` and return categories. Rename and search `src/test/` for each old name
(`rg -n --fixed-strings`). `src/test/aiur/control_call_test.exs` and `engine_census_test.exs` reference several.

`queue_scope/1` can never return `:write`: every enum verb is either `:deny` or `:read`. So no `queue` call needs a
write category. The ticket's "`queue` → tickets" has no remote effect today. Keep `queue_category/1` returning `:read`/`:deny`,
and map the write branch to `tickets` so a future remote queue verb lands in the right place.

### Decision 3: entries that do not fit (the ticket's explicit ask)

`take`/`release` here are ownership ops on ticket ids, not `executor-claim`/`executor-release` (those are wake-stream
claims and stay `executor`). The launcher wrapper `cmd_executor_ownership take 123` calls `take/2`.

### Decision 4: where `peer` and `categories` live

- Tokens: add optional keys `"peer"` (26-char base32 id or `nil`) and `"categories"` (list of category strings or absent)
  to the record in `client-tokens.json`. `valid_record?/1` accepts records without them (old stores stay valid) and rejects
  unknown categories and `trust`. `authenticate/1` keeps returning `{:ok, name, scope}` for existing callers; add
  `authenticate_full/1` returning `{:ok, %{name, scope, peer, categories}}` and have `ClientTokenAuth` assign
  `:token_peer` and `:token_categories`.
- Legacy mapping happens on read, not by rewriting the file: absent `categories` with `scope: "read"` means `["read"]`; with
  `scope: "write"` means `~w(read message executor agents tickets config)`. A token created with `--categories` stores both
  `categories` and a derived `scope` (`"write"` unless the list is exactly `["read"]`), so a version-1 reader of the same file
  still refuses writes it should refuse. Rejected: migrating the file in place, which breaks a rollback.
- `aiur token create <name> --peer <id> --categories a,b` and keeps `--scope`. Giving both `--scope read` and a
  write category is an error. `--categories` without `--peer` is valid (a local token). `--peer` without `--categories`
  defaults to `["read"]`. `token list` adds `peer` and `categories` columns.
- Controller: in `execute_expression/5`, after `ControlCall.parse` and before the `allowed_scope?` check, call
  `category_granted?(conn.assigns.token_categories, call.category)`; a miss refuses with `403`,
  code `category_not_granted`, and `error.category` set (body text `category_not_granted: agents`). The existing
  `scope_denied` check stays for tokens without categories and for `max_scope: read` requests. The peer grant (MPG-206) will
  be a second guard in the same `cond`; leave an obvious seam (`peer_allows?/2`, returning `true` until MPG-206).
- Audit: MPG-205 writes `category` and `peer` into the existing audit record (`control_controller.ex` already builds the
  audit map around line 127). `request_id`, `origin_gateway` and `actor` belong to MPG-204.

### Alternatives rejected

- Per-category separate tokens. Multiplies secrets; a gateway needs one credential per peer.
- Categories computed from the module name. The classification is per function and per argument (`feature show` vs `feature
  edit`); a module rule cannot express it.
- Deriving write/read from the category in the launcher. The launcher only forwards `max_scope`; the daemon decides.

## Risks

- A mis-categorised write silently widens or narrows a legacy `write` token. Legacy tokens get all six categories, so no
  existing token narrows; the new narrow tokens are the only exposure. The census test is the early signal.
- `ControlCall.run/3` rechecks the class; if category functions are not pure, `parse` and `run` disagree and a call is
  refused as unauthorized. Keep them pure and covered by the double-check test.
- `allowlist.ex` is 320 lines on main, under the 500-line gate. The helpers move to `allowlist/categories.ex` so the
  security table stays small; if a projected count shows the change would cross 500, that becomes a second reason.
- Token file rollback: old binaries ignore `categories` and use `scope`, which is why `scope` stays derived and stored.
