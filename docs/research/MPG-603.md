# MPG-603 — Show every project on one home screen: research

Research for [MPG-603](https://github.com/aiur-team/aiur/issues/7655) (research ticket MPG-603R, #7630), milestone M6
of [the multi-project gateways plan](../plans/2026-11-06-multi-project-gateways.md) (PR #7579). It builds on the
decisions in [MPG-601](MPG-601.md) (D1-D7, the wireframe, the state tables) and does not reopen them. It refines
MPG-603's file list and settles what MPG-601 left to this ticket (Q1, Q3, Q5, the lazy-load endpoint, E3, E4).

## Outcome

Open `/` on a gateway with `dashboard.projects_home: true` and the browser shows, in the MPG-601 order: projects with
their focus features, current agents, queue entry, gateway health and pending Decisions, for this gateway and every
peer gateway whose summary the browser can read. The page paints from the local gateway at once. Each peer card fills
in as its summary arrives, and a peer that does not answer within 3 s reads `unreachable · last seen 5m ago` with its
workload marked `last known`. Totals that leave a gateway out say so (`Running 7 of 12+ · 1 gateway unknown`). Every
project and feature row links to the existing Build page. With the flag off (the default), `/` is the Build page as
today.

## Design

### Mounting (C1)

1. Add `AiurWeb.ProjectsHomeLive` at `live("/projects", ..., :projects)` inside the existing `live_session :dashboard`
   (`dashboard_pages.ex:41`), so it gets the same auth and `DashboardPagesGate`.
2. Add `AiurWeb.ProjectsHome.Gate`, an `on_mount` module in that live session. On the `:build` live action at path
   `/`, when `Aiur.Config.settings!().dashboard.projects_home` is `true`, it returns
   `{:halt, push_navigate(socket, to: "/projects")}`, but only when the request has no query string (Risks, deep
   links). Any other action or path continues. `/build` never redirects,
   so the Build page stays reachable and every existing test that visits `/build` is untouched.
3. A navigation entry `projects` (label "Projects", path `/projects`) is added to `RouteRegistry` with `nav?: true`
   only when the flag is on. The registry is a compile-time list (`route_registry.ex:4`), so give the entry
   `availability: :available` and filter it in `RouteRegistry.routes/1` on the flag. When the flag is on, the Build
   entry's path becomes `/build` (it is `/` today), so "Build" in the nav does not bounce through the redirect.

Why not a second `live("/")`: Phoenix compiles one route per path and verb. A runtime flag cannot pick between two
module names, and a wrapper LiveView that delegates `render` to one of two modules would re-run every BuildLive test.

### Where the data comes from (D2)

- **Local gateway: server-rendered, no HTTP.** `ProjectsHomeLive.mount/3` calls the same function MPG-602's
  controller calls to build S6 (assumed `Aiur.Gateway.Summary.build/0`; MPG-602R fixes the name). The result renders
  as the first card and as the local rows of every section. The page therefore paints without waiting for the
  network, and it works with zero peers.
- **Peers: browser-side fetch.** The LiveView puts the peer list on the hook's root element as
  `data-peers='[{"gateway_id","label","url"}, ...]'`, read from the registry (S2) through the reader MPG-602 adds for
  the D5 origin list (assumed `Aiur.Gateway.Registry.peers/0`). A peer with no `url` (inbound-only) is omitted. A peer
  whose URL is not `https` or not on a tailnet host gets `off_tailnet: true` and renders the link-out card with no
  fetch (D7).
- **Hook.** `projects-home-hook.js` (registered as `Hooks.ProjectsHome` in `layouts.ex`) owns one container with
  `phx-update="ignore"`, so LiveView patches never wipe peer cards. It fetches
  `GET <peer.url>/api/v1/gateway/summary` with `{credentials: "include", signal}` where the signal aborts at 3000 ms,
  all peers in parallel. It renders into the container with `textContent` and `createElement`, never `innerHTML`: a
  peer's labels and titles are data from another machine.
- **Pure model.** All decisions live in `projects-home-model.js`, a no-DOM ES module exporting functions the hook
  calls and `node --test` can run (below). The hook only does fetch and DOM.

### The model (`projects-home-model.js`)

```text
classifyResult({ok, status, body, expectedGatewayId, timedOut, threw}) -> {connectivity, reason}
  timedOut or threw                                  -> {unknown, null}            // no cause named
  status 401 | 403                                   -> {error, "signed out"}
  status >= 500                                      -> {error, "server " + status}
  2xx but body.gateway_id != expectedGatewayId       -> {error, "gateway id mismatch"}
  2xx but body fails validateSummary                 -> {error, "unreadable summary"}
  2xx and valid                                      -> {online, null}

displayState(connectivity, reason, lastKnown, now) -> {connectivityText, workloadText, ageText}
  online       -> "online", live workload, "seen Ns ago"
  unknown      -> "unreachable · last seen <age>", "last known: <workload> <age>"      // never "idle", never "0"
  unknown, no cache -> "unknown · never seen on this device", workload "unknown"
  error        -> "error: <reason>", last-known workload with age if cached, else "unknown"
  connecting   -> "connecting…", workload "unknown"

totals(gateways, now) -> {running, capacity, unknownGateways, text}
  online gateways add running and capacity.max. A gateway not online adds nothing and increments unknownGateways.
  text: "Running 7 of 12+ · 1 gateway unknown" when unknownGateways > 0, else "Running 7 of 12".
  A fresh cache entry never makes a gateway "known": stale numbers are shown on its card, not summed.
```

Rules that carry over from MPG-601 and AGENTS.md:

- `unreachable` is display text for `unknown`, never a sixth state. The collapse of "timeout / TLS / CORS / blocked
  / mixed content" is made at the source with `_ -> unknown` and no cause (AGENTS.md, "collapsed causes").
- The age is rendered wherever it is computed (AGENTS.md rule 1): the card shows `seen Ns ago` from `age_ms` plus the
  time since the fetch, and an `unknown` card shows the cached `observed_at` age.
- Q5 (is `offline` needed): **no.** `offline` needs the MPG-408 liveness read. Ship `unknown` alone. The model keeps
  `offline` out of `classifyResult` and adds no dead branch for it.
- Q3 (cache life): **7 days.** `localStorage` key `aiur.projectsHome.v1.<gateway_id>` holds
  `{observed_at_ms, summary}`. An entry older than 7 days, unparsable, or failing `validateSummary` is deleted and
  treated as never seen. `localStorage` access is wrapped in `try`, since private-mode Safari throws. A throw means
  "no cache", not an error state.
- Cache is written only from an `online` result, so an `error` body is never stored as last-known.

### Page sections (order from MPG-601)

| Section | Server-rendered part | Hook-rendered part |
|---|---|---|
| Header totals | none (the model computes them from all cards) | `totals().text`, pause-all link disabled with title "Pause arrives with gateway views" until MPG-604 |
| Projects | rows for local projects with feature rows, counts, `Build ›` link, disabled `⠿` handle | peer projects append under the same repo row when the repo matches, else as their own row; gateways chip list per row |
| Current agents | local agents (from S6 `agents`) | peer agents, prefixed with the gateway label; an `unknown` peer shows its cached agents under `last known <age>` |
| Queue entry | local `queue_head` | peer `queue_head`, merged by the same order MPG-401 gave (each summary arrives ordered; the page does not reorder across gateways, see below) |
| Gateway health | the local card | one card per peer: connectivity text, workload text, age, `Open ›` link to the peer's own dashboard |
| Pending Decisions | local `decisions` | peer `decisions`; each row opens on its own gateway (MPG-601 note 10) |

- **Cross-gateway queue order.** MPG-601 says order across gateways uses shared intent (S4) when known. S6 does not
  carry it, and the MPG-603 acceptance does not need it. The page lists each gateway's queue head in a block per
  gateway, in the order that gateway sent. Merged global order is a later ticket (Q5).
- **Existing Build pages.** Each project row links to `/build?repo=<repo>` and each feature row to
  `/build?feature=<id>` using the URL parameters `build_live_url_test.exs` already covers. The implementer reads that
  test for the exact parameter names before wiring the links (open item in Implementation unit 5).
- **Phone.** One column below 640 px, gateway health collapses to one chip per gateway in the header (MPG-601). Use
  tokens from `packages/aiur-style`, not copies.
- **Icon slots.** Render `<span data-icon-slot="gw-conn-<state>">` and `gw-load-<state>` before each state text, empty
  and 16 px, exactly as MPG-601 specifies.

### What the page does when things go wrong

| Situation | Page shows |
|---|---|
| Peer request aborted at 3 s | `unreachable · last seen 5m ago` (cached) or `unknown · never seen on this device` |
| Peer answers 401 or 403 | `error: signed out` and a `Sign in` link to `<peer>/auth/google?return_to=<this page>` (the `return_to` parameter is MPG-602's) |
| Peer's origin missing from its `dashboard_origins` | browser throws on CORS, so `unknown`; the card does not claim a cause. MPG-602 logs the refused origin on the peer (MPG-601 risk) |
| Peer returns a different `gateway_id` than the registry pinned | `error: gateway id mismatch`; its numbers are discarded |
| Peer returns a summary that fails `validateSummary` (missing `observed_at`, `age_ms` non-numeric, negative counts) | `error: unreadable summary` |
| Local `Aiur.Gateway.Summary.build/0` raises or times out | The server-rendered card reads `local summary unavailable` with `data-empty-reason="local_summary_unavailable"`; peers still load. Never a zero |
| `localStorage` unavailable | Works without cache; every `unknown` card reads `never seen on this device` |
| Mixed content (page `https`, peer `http`) | The browser blocks the fetch, which the model sees as `unknown`. The registry reader marks `http` peers `off_tailnet: true`, so they get the link-out card instead |

### Evidence gathered for E3 and E4

MPG-601 marked these two claims pending evidence and assigned them to this ticket. A prior-art report from
`docs/research/multi-gateway/` does not cover browser policy, so a `standard` web search was run on 2026-11-06. The
result is below. Nothing here is a lab run: no browser was launched, so a claim stays "unverified" until the
post-deploy check records a browser, version and date.

| # | Claim | Result | Source |
|---|---|---|---|
| E3a | Chrome 142 ships the Local Network Access permission prompt | **Supported.** Chrome 142 (28 Oct 2025) added the prompt. From Chrome 145 the site setting splits into "Apps on device" (loopback) and "Local Network" | [Chrome blog](https://developer.chrome.com/blog/local-network-access), [Dynamsoft FAQ](https://www.dynamsoft.com/web-twain/docs/faq/chromium-142-local-network-access-issue.md) |
| E3b | Firefox 151 ships LNA | **Not supported as written.** Sources disagree: Mozilla's design note is undated, and one vendor FAQ cites Firefox 153 and 154 for enforcement, including WebSocket blocking. No source names 151. Use "Firefox is rolling out LNA enforcement; the version is unconfirmed" | [Mozilla bug 1919889](https://bugzilla.mozilla.org/show_bug.cgi?id=1919889), [Dynamsoft FAQ](https://www.dynamsoft.com/web-twain/docs/faq/chromium-142-local-network-access-issue.md) |
| E3c | Safari prompts for LNA | **Unconfirmed.** The only source is a 2024 Mozilla bug saying macOS Safari grants it implicitly. No current Safari or iOS statement was found | [Mozilla bug 1919889](https://bugzilla.mozilla.org/show_bug.cgi?id=1919889) |
| E3d | Tailnet-to-tailnet requests raise no prompt | **Unverified.** It follows from the spec's address classes only if the page itself is served from a local-class address. Chrome's own docs describe the prompt as firing when a public site reaches a less-public address. The page here is served from a tailnet name, which resolves to a `100.64.0.0/10` address | [WICG LNA spec](https://wicg.github.io/local-network-access/) |
| E4a | Safari blocks cross-site cookies | **Supported.** Safari's Intelligent Tracking Prevention has blocked third-party cookies in full since March 2020 | [CPO Magazine](https://www.cpomagazine.com/data-privacy/apple-updates-safaris-intelligent-tracking-prevention-to-block-all-third-party-cookies/) |
| E4b | Firefox partitions cross-site cookies | **Supported.** Total Cookie Protection keeps a separate cookie jar per top-level site; default for all users since June 2022. A limited exception exists for login providers | [Mozilla support](https://support.mozilla.org/en-US/kb/third-party-cookies-firefox-tracking-protection/revision/287101), [AppleInsider](https://appleinsider.com/articles/22/06/14/firefox-joins-safari-in-controlling-cross-site-browser-cookies) |

Consequences for the design:

- E4 holds, so the rejection of a public `aiur.dev` page calling gateways directly stands (D1, D7).
- E3b and E3c change nothing in MPG-603's code: under D1 the page and the peers are all tailnet names. They do change
  the wording MPG-601 left in "Private Network Access / Local Network Access": drop "Firefox 151" and say "version
  unconfirmed". MPG-603 owns that edit to the docs page it writes, and the post-deploy check is where iOS Safari
  and Firefox are finally exercised.
- One point MPG-601 does not state: the cookie argument for D3 holds whether or not `ts.net` is on the Public Suffix
  List (E1). If it is, `<host>.<tailnet>.ts.net` shares the registrable domain `<tailnet>.ts.net` and so one site. If it
  is not, every `*.ts.net` name shares the site `ts.net`. Both put the gateways of one tailnet on one site, so the
  `SameSite=Lax` argument does not depend on E1. E1 stays MPG-602R's to verify, because it bears on whether another
  tailnet's page counts as same-site (an isolation question, not an availability one).

## Prior art

- `docs/research/multi-gateway/gateway-enrollment-and-permissions.md` (PR #7579) proposes proxying peers through the
  page's own gateway. MPG-601 D2 and Q6 declined that. MPG-603 follows D2 and adds no proxy route.
- `docs/research/multi-gateway/priority-reconciliation.md` supplies the order rules the queue block depends on. MPG-603
  displays what MPG-401 produced and computes no order (C3, "Cross-gateway queue order").
- The existing Instances page (`instance_roster_live.ex`) is the nearest in-repo precedent: it already renders
  `observed_at`, `age_ms`, a per-instance `state` and a `data-empty-reason` for each unavailable branch. MPG-603 copies
  that discipline, with `data-empty-reason` on each non-online card.
- Web search for E3 and E4: see "Evidence gathered". No deep-research run was needed beyond it.

## Interfaces

- **Consumes from MPG-602:** `GET /api/v1/gateway/summary` (S6) with CORS for listed origins, the D5 origin list, the
  registry reader, `return_to` on Google sign-in. **Additive S6 keys MPG-603 requires** (C3), all bounded and all
  carrying the same `observed_at`/`age_ms` as the rest:
  - `projects[].focus_features`: `[{id, title, done, total, running, ready}]`, at most 20 per project.
  - `agents`: `[{identifier, repo, state, percent, age_ms}]`, at most 50 (`percent` is the progress emit, nullable).
  - `queue_head`: `[{identifier, repo, feature, lane}]`, at most 10, in allocation order.
  - `decisions`: `[{id, identifier, title, kind}]`, at most 20, where `kind` is `human_required` or `question`.
  MPG-602R must add these to its field list and to `state-schemas.md`; this doc does not edit the plan.
- **Consumes from MPG-407:** the heartbeat `projects` key (feeds `projects[]` counts) and `executor_present`.
- **Consumes from MPG-601:** D1-D7, the wireframe, the state tables, the `localStorage` rule.
- **Provides to MPG-604:** `projects-home-model.js` (`classifyResult`, `displayState`, `totals`), the `Hooks.ProjectsHome`
  container, the `data-icon-slot` ids, and the disabled pause-all control it enables. MPG-604 adds
  `gateway_live.ex` and filters on top; it must not fork the model.
- **Provides to the separate icon work:** the `data-icon-slot` ids, unchanged from MPG-601.

## Risks

- **A peer's cookie policy breaks the fetch.** If Safari or Firefox refuse the Lax cookie on the cross-origin fetch,
  every peer reads `error: signed out`. Detect it in the post-deploy check. Fallback is MPG-601's Q6, reopened.
- **S6 lacks the keys the sections need (C3).** The largest risk to this ticket. It surfaces at MPG-602R. Fallback is
  the `not in this gateway's summary` text above.
- **Stale cache read as live.** The cache is the one place a number can outlive its truth. Every cached figure carries
  its age text and is excluded from totals; the browser spec and the model test both pin it.
- **`phx-update="ignore"` hides a server bug.** Peer cards do not change on LiveView patches. The patch scenario
  guards it.
- **The `/` redirect breaks deep links.** `/?feature=...` style Build URLs would be redirected and lose their query.
  The gate redirects only when the query string is empty; a request with a query string stays on Build. Add that to
  the gate test (not in the table above because it depends on Q6).
- **Config doc length gate (C4).** `check-config-docs.py` and the file-size gate fail the PR if
  `configuration-daemon.md` passes 400 lines. Count lines before pushing.
