# MPG-304 — Register the workflow, queue, feature and snapshot stores per project: research

Research ticket MPG-304R (#7617). Plan: [multi-project gateways](../plans/2026-11-06-multi-project-gateways.md).
Contract: `tickets-m3.md` MPG-304. Reads [MPG-301](MPG-301.md) (the ADR) first. Code references are to `src/` at
`7d5cc6199`; paths under `lib/aiur/` are written relative to that. No questions were put to the user; each open
question carries a recommended default.

Brainstorm and plan phases were run inline for this complexity-2 spike. No `deep-research` run: nothing here is an
external question, and the prior-art reports in `docs/research/multi-gateway/` cover coordination, not ETS or
`Registry` mechanics.

## Outcome

With two project trees in one VM (MPG-306 boots them; MPG-304 is tested with the `Aiur.ProjectCase` helper from the
ADR §7), each project owns its own `WorkflowStore`, `BuildQueue.Server`, `BuildOrder.Features`,
`Orchestrator.TrackedSet`, `SnapshotCache`, `SnapshotStore` and `SnapshotPublisher`. Each registers under
`{:via, Registry, {Aiur.ProjectRegistry, {project_id, Module}}}`, and each ETS table is unnamed and found through the
`{Aiur.Project.Table, project_id, name}` `:persistent_term` lookup. Adding item `#5` to project A's queue leaves
project B's `queue.json` byte-identical. With no project context every module behaves as today: same registered
name, same named tables, same paths, and the existing tests pass unchanged.

## Design

### Project identity (Executor decision, binding on MPG-302, MPG-304 and MPG-306)

A project id is `String.downcase(repo)` for the `owner/name` repo. GitHub names are case-insensitive and MPG-002
already rejects case-insensitive duplicate repos. The original-case repo is kept only for display and API calls. Every
`project_id` in this document (Registry keys, `Aiur.Project.Table` keys, `via/1`) is that downcased string. Each
project's `state_root` is built from its own downcased id with the same leaf rule as today's `decision_state_dir/0`
(`paths.ex:469-473`: last path segment, sanitized), so the daemon's own repository resolves to exactly today's leaf.
Two entries whose ids resolve to the same leaf (for example `a/x` and `b/x`, which share leaf `x` today) are a boot
error, raised by MPG-306 before any tree starts; MPG-304 relies on that and does not re-check it.

### Findings that change the ticket

The contract names seven modules and ~10 files. Reading the code turns up five things the contract does not say.

1. **The queue's `queue.json` path is not per-project today.** `BuildQueue.Store.resolve_path/0`
   (`build_queue/store.ex:75`) calls `Config.Paths.build_queue_dir/0` → `decision_state_dir/0`
   (`config/paths.ex:55`), which builds `<root>/<AIUR_INSTANCE_KEY>/<leaf>` from `System.get_env/1` and
   `safe_project_identity()` (`paths.ex:448-473`): process environment, not a project context. The ADR row says the
   file "lives in the project's state leaf"; that is true only for a one-project daemon. The same function feeds
   `build_features_state_dir/0` (`paths.ex:145`) and `epic_overrides_state_dir/0` (`paths.ex:154`). Without a change
   here, the acceptance test ("A's queue leaves B's `queue.json` unchanged") fails for the right reason: both
   servers write the same file. **MPG-304 must add `config/paths.ex` to its files**, but must not change
   `decision_state_dir/0` itself: it is called from 25 files outside `paths.ex` (`rg -l decision_state_dir src/lib`), and most are
   machine-level files (`client_tokens.ex:70`, `github/access_settings.ex:111`, `dispatch_budget_store.ex:75`,
   `orchestrator/global_pause_store.ex:91`, `dashboard_auth/passkeys.ex:176`). A context-aware `decision_state_dir/0`
   would move them into a project directory whenever a control call carries a project context (MPG-311). See D3.
2. **The queue owns three ETS tables, not one.** `Hints` (`build_queue/hints.ex:11-12`) names
   `:aiur_build_queue_hints` (created by the server, `server.ex:343`) and `:aiur_build_queue_sets` (created lazily by
   `Hints.publish_sets/1`, `hints.ex:19`). `LastRead` (`build_queue/last_read.ex:10`) names
   `:aiur_build_queue_last_read`. The dispatcher reads the hints table from the orchestrator process
   (`dispatch_candidates`, `dependency_gate`, `eligibility`, `queue_set_slots`, `waiting_reason`, `optimistic_dispatch`,
   `decision_escalation`: 7 callers). Two projects creating a named table both crash the second `:ets.new` with
   `ArgumentError` (`server.ex:343` has no `whereis` guard). All three move to the project table lookup.
3. **`WorkflowStore` is the hardest of the seven, and MPG-302 already starts it.** MPG-302's "Next action" keys
   `workflow_store/cache.ex` by project id. MPG-304 must not redo that. The boundary (D1): **MPG-302 owns the cache
   *table and its keys*; MPG-304 owns the *process* (registration, `init`, polling, `force_reload`).** The cache
   table is also used by `ReloadRejection` (`workflow_store/reload_rejection.ex:44,62,69`) through `Cache.table/0`, so
   that module changes too. `WorkflowStore` also has seven `Process.whereis(__MODULE__)`/`GenServer.call(__MODULE__)`
   sites (`workflow_store.ex:72,90,109,157,189,193-204`), and the timeout-exit patterns at 193-204 match on
   `[__MODULE__, :force_reload, _]`, which a via-tuple name will not match.
4. **`SnapshotStore`, `SnapshotPublisher` and `SnapshotCache` are already keyed by the orchestrator's name.**
   `Lifecycle` passes `snapshot_key = Keyword.get(opts, :name) || self()` (`orchestrator/lifecycle.ex:110`) and every
   `persistent_term` key and ETS row includes it (`snapshot_store.ex:447-449`). After MPG-303 the name is a via-tuple
   `{:via, Registry, {Aiur.ProjectRegistry, {id, Aiur.Orchestrator}}}`, which is unique per project, so these three
   would not collide on data. They collide on **process and table names** only. The cheap, correct move is to keep the
   key shape and register the processes per project; do not re-key the data.
   One trap: `SnapshotStore.read(Orchestrator, 15_000)` is called with the bare atom in three places
   (`current_run_membership/reconciler.ex:169`, `current_run_projections/state.ex:119` via default, `orchestrator/client.ex:281`
   default `server \\ Aiur.Orchestrator`). MPG-303 rewrites those defaults to `Aiur.Project.whereis(Aiur.Orchestrator)`
   (a pid or via-tuple). `SnapshotStore` must accept both forms for the same orchestrator without splitting the key,
   or one project's snapshot is published under the via-tuple and read under the pid. See D5.
5. **`SnapshotCache` is shared with an unrelated module family.** `Aiur.Orchestrator.SnapshotCache` is the target.
   `GitHub.Quota.SnapshotCache` and `ExecutorSweep.SnapshotCache` are different modules and stay machine-level. The
   only lib caller of the orchestrator one is `orchestrator/status_cli/sections.ex:9,74,79` (plus `SnapshotStore`). Its
   `{:status_section, name}` key has no project in it, so after the move it is per-project because its table is.

### Decisions

**D1. One mechanism for processes.** Each of the seven `start_link/1` functions builds its name with a single helper,
`Aiur.Project.via(module)`:
`{:via, Registry, {Aiur.ProjectRegistry, {id, module}}}`, where `id` is the downcased `id` of the `%Aiur.Project{}` returned by `Aiur.Project.Context.current/0`; with no context it returns the
module atom, which is today's `name: __MODULE__`. This keeps the single-project daemon byte-identical and puts the
"which name?" logic in one place (MPG-303 adds `whereis/1`; MPG-304 adds `via/1` next to it in `project.ex`).
`BuildQueue.Server` and `Features` already accept `name:` in opts (`server.ex:40`, `features.ex:16`); the default
changes from `__MODULE__` to `Aiur.Project.via(__MODULE__)` and an explicit `name:` still wins, so every existing test
that passes `name:` is untouched.

**D2. One mechanism for tables.** A new `Aiur.Project.Table` module (the ADR §3 name) with three functions:
- `new(name, opts)` → creates an **unnamed** table when a project context is set, a `:named_table` called `name`
  when not; records the tid in `:persistent_term` under `{Aiur.Project.Table, project_id, name}` for the project case;
  returns the tid-or-name.
- `ref(name)` → the tid for the current project's table, or `name` itself with no context. This is what readers call.
- `drop(project_id)` → erases that project's `persistent_term` keys; called from the owner's `terminate/2` is not
  reliable, so the project supervisor (MPG-306) calls it on project stop. MPG-304 provides the function and tests it.
Readers keep `rescue ArgumentError` (the existing "table is gone" behaviour). A `persistent_term` write triggers a
global GC only when a key is *replaced or erased*; one write per project boot is the ADR's accepted cost, and the
restart path (a store crashing and being recreated) replaces the key. Mitigation in D6.

**D3. A new `Paths.project_state_dir/0`; `decision_state_dir/0` is unchanged.** `project_state_dir/0` returns
`{:ok, project.state_root}` when `Aiur.Project.Context.current/0` returns a project, and otherwise delegates to
`decision_state_dir/0` (today's env-derived value). `Aiur.TestRunState.decision_state_override/1` keeps priority in
the fallback. MPG-304 switches only the three per-project paths it needs, `build_queue_dir/0`,
`build_features_state_dir/0` and `epic_overrides_state_dir/0`, from `decision_state_dir()` to `project_state_dir()`.
Every other `Paths` function and all other callers keep calling `decision_state_dir/0` and stay machine-level. The
remaining per-project paths (conversations, spend caps, optimistic starts and the rest) are classified one by one by
MPG-305; this ticket does not decide them. With no context the result is byte-identical to today, because MPG-302
defines the implicit project's `state_root` as the same path.

**D4. `TrackedSet` uses `Table.new/ref` for two tables** (`@table`, `@identity_table`). `member?/1` and
`tracker_identity/1` run in caller processes (dispatcher, `Orchestrator.tracked_issue?/1`), so they use `ref/1` and
inherit the caller's project through `$callers`/`$ancestors` (ADR §3). Its private `call/2` does
`Process.whereis(__MODULE__)`; it becomes `Aiur.Project.whereis(__MODULE__)`.

**D5. `SnapshotStore` key normalisation.** Add `defp key(orchestrator)` that maps a registered name, a via-tuple, or
the orchestrator pid for the *current project* to one canonical value: the via-tuple when the pid resolves to a
`Registry` entry, else the input. All eight `persistent_term` key builders (`snapshot_store.ex:447-449` and the
warning keys at 61, 403, 418) call it. Alternative: re-key everything by `project_id`. Rejected, because the three
unnamed-orchestrator test modes (`self()` key, `discard_unnamed_snapshot`, `lifecycle.ex:237`) rely on pid keys and the
change would touch ~40 test files that call `SnapshotStore.publish/2` with literals.

**D6. Restart-safe `persistent_term`.** A store restart under its supervisor recreates its tables; rewriting the
`persistent_term` key triggers a global GC. `Table.new/2` therefore **reuses the key's tid when the table still
exists** (`:ets.info(tid) != :undefined`) and only writes when the tid changed. A crash always changes the tid, so
the write is unavoidable; it is the same cost the ADR accepts and is rare. Unit-tested (T9).

**D7. `BuildQueue` module-level helpers.** `BuildQueue.status/0` (`build_queue.ex:14`) and `child/1` (`:10`) use
`Process.whereis(Server)` / `GenServer.call(Server, ...)`; both change to `Aiur.Project.whereis(Server)`.
`BuildQueue.show/1`, `build_queue_cli.ex:27` and `mutation_cli.ex:358` default `server` to the atom `Aiur.BuildQueue.Server`;
change those two defaults to `Aiur.Project.whereis(Aiur.BuildQueue.Server)`. `Features` already routes every public
function through `call/3` with `Keyword.get(opts, :server, __MODULE__)` (`features.ex:215`); that default becomes
`Aiur.Project.whereis(__MODULE__)`. These defaults are evaluated in the caller's process, so a control call that ran `Context.put/1` (MPG-311R) reaches that project's server; no new argument is needed, and MPG-304 and MPG-311R agree on this. No other `Features` caller is edited: the ~35 files that mention it call the public
functions.

### Alternatives considered

- **Keep the named tables and make table names project-suffixed atoms** (`:"aiur_build_queue_hints_#{id}"`).
  Rejected: creates atoms from config at runtime (atoms are never collected; project ids are operator-supplied) and
  gives readers a string-building step on the dispatch hot path.
- **One shared table keyed `{project_id, key}`.** Rejected for `WorkflowStore` cache and `TrackedSet`: a project stop
  must delete exactly its rows, and `:ets.delete_all_objects` plus a `match_delete` over a shared table is O(table); an
  owned unnamed table disappears with its owner for free. Rejected also because ADR §3 already decided unnamed tables.
- **Thread `project_id` through every store function.** Rejected by the ADR: 142 `Config.settings/0` callers and the
  `Features` callers would all change, breaking the "fewer than 40 files" budget.

## Prior art

None needed. The mechanism (`Registry` via-names, unnamed ETS plus a lookup) is fixed by KTD-4 and ADR §1/§3. Erlang
`persistent_term` update cost (global GC on replace/erase) is documented in the OTP reference and accepted by the ADR;
D6 limits it.

## Risks

- **Hot-path cost of `Table.ref/1`.** `Hints.sort_key/1` runs per candidate per dispatch. A `persistent_term.get` plus a
  context lookup in the process dictionary is sub-microsecond, but measure: run the existing `dispatch_candidates`
  benchmark if any, or time 100k `Hints.sort_key/1` calls before/after in the PR body. Fallback: cache the tid in the
  caller's process dictionary keyed by project.
- **`$callers` does not reach every reader.** The ADR says bare `spawn/1` and Ports inherit nothing. Any reader that
  runs from one (the dashboard LiveView reading `SnapshotStore`) has no project, so it reads the wrong table or none.
  Detect early: T4/T5 call from `Task.async` and from `spawn` and assert the second falls back to the no-context table
  (documented behaviour) rather than crashing. Dashboard readers become explicit-project in MPG-601/603.
- **`persistent_term` global GC on restart loops.** A crash-looping store replaces its key each restart. Detect: log the

- **`WorkflowStore` timeout-exit patterns** match on the literal server name (`workflow_store.ex:193-204`); a missed
  rewrite makes a timeout propagate as an exit instead of `{:error, :timeout}`. T10 includes a forced timeout on a
  stopped server.
- **MPG-302/304 overlap on `WorkflowStore`.** If MPG-302 also edits `workflow_store.ex`, the PRs conflict. D1 splits by
  file region; the implementer rebases on the merged 302.
