## Outcome

With `projects:` set in `~/.aiur/machine`, the daemon starts the machine-level children, then one
`Aiur.Project.Supervisor` per entry under a `DynamicSupervisor` named `Aiur.Project.Supervisors`. Each project tree
holds that project's orchestrator and the per-project stores. A project whose config does not parse, or whose tree
keeps crashing, raises `system.project.boot_failed` and the other projects keep polling.
`aiur status --json` prints a `projects` list. `aiur gateway reload` starts added projects and stops removed ones and
touches no other tree. With `projects:` empty or absent, `Children.child_specs/1` returns the same list as at
`7d5cc6199`, and nothing else changes.

## Design

### D1. Two lists, one function

`Aiur.Application.Children.child_specs/1` (`application/children.ex:34`) stays the one boot-order authority and the
only public entry (`lib/aiur.ex:190` delegates to it). It gains one branch:

```elixir
projects = Keyword.get_lazy(opts, :projects, &Aiur.Project.Config.configured/0)   # [] when unset or invalid
children = machine_specs(opts, projects)                                           # today's list body, see D2
if projects == [], do: children, else: children ++ [Aiur.Project.Registry.child_spec([]), Aiur.Project.Supervisors, Aiur.Project.Watcher]
```

Reason: the 400-line function body keeps its order comments (they are load-bearing: #2531, #2557, #4664). Moving the
whole body would lose the blame trail. The per-project modules come out of that body and into one list (D2).
`:projects` is an `opts` key so `children_test.exs` can pass fixtures without touching `~/.aiur/machine`.

Alternative rejected: a second `child_specs_for_projects/1`. Two entry points mean `Aiur.start/2` and the tests
choose, and the empty-list equality check (Acceptance 1) cannot be one assertion.

### D3. The project tree: `Aiur.Project.Supervisor`

```elixir
defmodule Aiur.Project.Supervisor do
  use Supervisor
  def start_link(%Aiur.Project{} = project, opts) # name: Registry.via(project.id, __MODULE__)
  def init({project, opts}) do
    Aiur.Project.Context.put(project)          # MPG-302: children started from init inherit it via $ancestors anyway
    Supervisor.init(Aiur.Project.Children.specs(project, opts), strategy: :rest_for_one, max_restarts: 3, max_seconds: 5)
  end
end
```

- `:rest_for_one`, because the list is in dependency order exactly as the machine list is (`lib/aiur.ex:116-137`).
- `max_restarts: 3, max_seconds: 5` is `Supervisor`'s default, made explicit so it is visible and testable.
  Reason: a project that crashes four times in five seconds is crash-looping, and a longer window would keep a
  broken project retrying against GitHub.
- The root registers itself in `Aiur.ProjectRegistry` (a `Registry`, `keys: :unique`) under `{project.id, Aiur.Project.Supervisor}`.
  ADR §3 resolves context through that registration.
- `Aiur.Project.Registry` (`project/registry.ex`) is a small module, not the registry itself: `child_spec/1`
  (`Registry.child_spec(keys: :unique, name: Aiur.ProjectRegistry)`), `via(project_id, module)`, `root_pid(project_id)`,
  `project_ids/0`. The ticket asks for this file name; the registry process name is `Aiur.ProjectRegistry` as in the ADR.

### D4. Starting, stopping and failure isolation: `Aiur.Project.Supervisors`

`Aiur.Project.Supervisors` is a `DynamicSupervisor` registered under its own module name (it is machine-level, so the
ADR's singleton rule does not apply). It exposes the ADR §10 API; MPG-306 implements the first three and
`which_projects/0`; `restart_project/2` is MPG-308's.

| Function | Behaviour |
|---|---|
| `start_project(%Aiur.Project{})` | `DynamicSupervisor.start_child(__MODULE__, %{id: project.id, start: {Aiur.Project.Supervisor, :start_link, [project, opts]}, type: :supervisor, restart: :temporary})`. Returns `{:ok, pid}` or `{:error, reason}`; on error calls `Watcher.report_failed(project, reason)`. |
| `stop_project(project_id)` | `DynamicSupervisor.terminate_child/2` on the root pid. Stops that tree only. Runner tasks are under the machine-level `Aiur.TaskSupervisor`, so they survive (ADR §11); the orchestrator's `terminate/2` reaps only its own project's agents once MPG-305 keys `ProcessReaper` by project. |
| `which_projects()` | `[%{id, repo, pid, state: :running}]` from the dynamic supervisor's children. |
| `reload/1` | Diff `Machine.Settings.load/0` `.projects` against `which_projects/0` by `Project.id`: start the missing, stop the removed, leave the rest. Returns `%{started: [...], stopped: [...], failed: [{id, reason}], unchanged: [...]}`. A changed `config:` path for an existing id is `unchanged` plus a warning; rebuilding it is MPG-308. |

**Deviation from the ADR: `restart: :temporary`, not `:transient`.** The ADR §6 says each root is `:transient`. With
`:transient` an abnormal root exit (intensity exhausted) makes the `DynamicSupervisor` start the root again, and
`DynamicSupervisor` has its own intensity, default 3 restarts in 5 seconds. A crash-looping project then exhausts the
*dynamic supervisor's* intensity and takes every other project with it. That is the opposite of the contract's "leaves
the others running". `:temporary` never restarts the root; `Aiur.Project.Watcher` raises the alert instead.
The ADR's own sentence ("stops alone and raises `system.project.boot_failed`") is what this implements. Record the
change in the ADR table in the MPG-306 PR (Open question 2 proposes the exact wording).

`Aiur.Project.Watcher` (`project/watcher.ex`, a `GenServer`, machine-level): `monitor(project, pid)` after every
successful start; on `{:DOWN, ..., reason}` with `reason not in [:normal, :shutdown]` it calls
`Aiur.Alerts.emit_system("system.project.boot_failed", message: ..., needs_attention: true, severity: "warning")`,
the same call `lease_store.ex:477-480` uses. The message names the repo and `inspect(reason)` truncated to 200 bytes,
never the `config:` path (MPG-002 keeps the path out of messages). A `:shutdown` from `stop_project/1` raises
nothing. There is no automatic retry in this ticket; the operator edits the config and runs `aiur gateway reload`,
which starts any project in `projects:` that is not running (so a failed project is retried by reload; `reload/1`
treats "in `projects:` and not running" as "missing"). A `.resolved` alert fires when a later start succeeds.

### D5. Boot order and the start of `Aiur.start/2`

`Aiur.start/2` (`lib/aiur.ex:30-150`) builds `child_specs(...)` once and starts `Aiur.Supervisor` as `:rest_for_one`.
In projects mode the project trees come last in the machine list, after `Aiur.Project.Supervisors`:

1. The machine children, in today's order (ADR §6; open question A re-checked in "Prior art").
2. `Aiur.Project.Registry` and `Aiur.Project.Supervisors` and `Aiur.Project.Watcher`.
3. A one-shot `Task` child (`Aiur.Project.Boot`, `restart: :temporary`) that calls `Supervisors.start_project/1` for each
   configured project, in `projects:` order, then exits `:normal`.

Why a boot task and not static children of `Project.Supervisors`: a `DynamicSupervisor` has no static children, and
starting from a task keeps `start_project/1` the only code path, so boot and `reload` behave the same (and a boot
failure is the same alert).

Because everything sits behind `:rest_for_one`, a crash of a *machine* child restarts every project tree after it.
That is today's behaviour for the orchestrator and is accepted by decision 24. The Watcher and `Boot` are after the
dynamic supervisor, so a machine-child crash re-runs `Boot` and re-reads `projects:`.

**`Aiur.start/2` itself.** It reads `Aiur.Config.settings_uncached()` (`lib/aiur.ex:39`) from the working directory's
`.aiur/config` or `~/.aiur/config`. In projects mode that config still configures the machine-level children (server,
GitHub credentials, `instance`, telemetry). Nothing in `start/2` changes except `child_specs(projects: ...)`.
`StartupChecks.validate_hosted_mode!/1` and `log_base_branch/1` still read the daemon config. Whether project configs
get the same checks is Open question 3.

### D6. Context for the empty-list default (the equality test)

`Aiur.Project.Config.configured/0` returns `[]` when: `Machine.Settings.get/0` is `{:error, _}`, or `projects` is `[]`,
or `Application.get_env(:aiur, :projects_enabled?, true)` is false. An invalid machine file in projects mode must not
silently fall back to the single-project tree and dispatch the wrong repository. So `{:error, {:invalid, errors}}`
**aborts boot** with the key paths (never values) and `{:error, {:unreadable, _}}` for a file that exists but cannot be read
does the same. Only a missing file (`{:ok, defaults}`) means "no projects". Decision, reason: today a daemon with
no machine file works; a daemon whose machine file is broken has been told something and should say so.

### D7. `aiur status --json` and `aiur gateway reload`

`aiur status --json` does not exist: `engine/commands.sh:55` dies with `status --json requires --handoff`. MPG-306's
acceptance needs it. Change:

- `engine/commands.sh` `cmd_status`: accept `--json` alone and send `Aiur.AgentControlCLI.status(json: true)`.
  `--handoff --json` keeps its path. Text `aiur status` is unchanged.
- `Aiur.Orchestrator.StatusCLI.status/1` (`status_cli.ex:33`): when `json: true`, print one JSON object
  `{"observed_at": iso8601, "projects": [...]}` through `Aiur.Project.StatusRows.rows/0` (new, `project/status_rows.ex`) and return.
  A row is `{"id", "repo", "state": "running"|"failed"|"stopped", "running": int|null, "observed_at", "age_ms", "freshness"}`.
  `running` is the length of that project's snapshot `running` list, read with the project's `SnapshotStore`; it is `null`
  (never `0`) when the project is not `running` or its snapshot is unavailable. `age_ms` and `freshness` are rendered, per
  AGENTS.md ("If a surface computes an age, it renders the age"). In single-project mode `projects` is `[]`.
  The status allowlist entry already accepts a keyword (`allowlist.ex:50-51`) but its constraint map has no `json:`
  key; add `json: :boolean` or the remote call is refused.
- `aiur gateway reload`: a local-only verb. `engine/gateway.sh` (new) defines `cmd_gateway`, which accepts only `reload`
  and runs `run_control_rpc "Aiur.Gateway.CLI.reload()"`; `--instance` is refused ("local to the gateway's host") like
  `stop`. `Aiur.Gateway.CLI.reload/0` (`gateway/cli.ex`, new) calls `Supervisors.reload/1` and prints
  `started: o/a`, `stopped: o/b`, `failed: o/c (<reason>)`. `aiur-engine.sh` is exactly 500 lines (`wc -l`). **Adding a `gateway)`
  case there makes an oversized file longer, which AGENTS.md forbids.** Put the dispatch in a file that already sources
  per-verb handlers (`engine/commands.sh` is 427 lines) and make the one-line `gateway)` case in `aiur-engine.sh`
  replace a line, not add one; if no line can go, move one existing case body into `commands.sh` first. The pickup agent
  checks `wc -l` before and after.

`gateway/cli.ex` will also hold MPG-209's `list` and `status`. MPG-209 does not depend on MPG-306, so whichever merges
second rebases onto the first; each creates the file only if absent and adds its own functions. No shared function.

## Data and assets

- Project id: `String.downcase(repo)` (`o/a`), per the Executor decision binding on MPG-302, MPG-304 and MPG-306. GitHub names are case-insensitive and MPG-002 rejects case-insensitive duplicate repos. The original-case `repo` is kept only for display and API calls. Each state leaf is built from the downcased id; two entries resolving to one leaf are a boot error.
- Mixed-case edge: `sanitize/1` keeps case, so a daemon repo `Owner/MyRepo` has today's leaf `MyRepo` while the downcased leaf is `myrepo`. `project_leaf/1` fails closed (boot error naming both paths, test 21) when the existing mixed-case directory is present and the downcased one is not. MPG-302R records the same rule.
- Naming: `Project.Registry.via/2` is for code holding an explicit id (the tree builder, `Supervisors`); MPG-304R's `Aiur.Project.via/1` (id from `Context.current_id/0`) is for a store starting inside a project tree. `Project.Children.specs/2` passes no `name:` for the seven MPG-304 modules; they derive it from the context `Project.Supervisor.init` already set.
- `state_root`: `Paths.project_leaf(id)` under the existing instance-key root (unit 1); MPG-306 does not move any state (MPG-309 does).
- Alert names: `system.project.boot_failed`, `system.project.boot_failed.resolved`.
- No fixtures outside `tmp_dir`. The two memory-tracker configs are written by `Aiur.ProjectCase`.

## Risks

- **The names are paper until MPG-302..305 merge.** Mitigation: unit 1 starts by reading the merged `Aiur.Project` and `whereis/1`; any renamed function changes this doc's names, not its design.
- **A machine child secretly needs an orchestrator.** Detect: test 4 plus booting the real tree (`aiurdev --bg` with two projects) before opening the PR. Fallback: move that child to after `Aiur.Project.Supervisors` (D5 last paragraph).
- **`rest_for_one` cascade.** A machine-child crash restarts all project trees (and `Boot` re-starts them). Accepted by decision 24, but each re-boot polls GitHub once per project; budget impact is bounded by the existing read cache. Not measured here; no saving is claimed.
- **Unclassified children misfiled.** A per-project child left in the machine list would serve one repo only; a machine child moved into the tree would run N times (for example two `DecisionExpiry` timers). Detect: test 8, plus MPG-305's inventory test reading `modules/0`. Fallback: edit `Project.Children` only.
- **`aiur-engine.sh` at 500 lines.** Growing it fails the file-size gate. See D7.
- **Allowlist drift.** `status` with `json: true` is refused remotely until `allowlist.ex` is edited; the remote tests (`launcher-remote*.test.mjs`) must still pass.
