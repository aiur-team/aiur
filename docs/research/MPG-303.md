# MPG-303R — Register the orchestrator per project: research

Plan: `docs/plans/2026-11-06-multi-project-gateways.md`. Contract: MPG-303 in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m3.md`. Reads the ADR `docs/research/MPG-301.md` (§2, §3, §5).
All line numbers are at commit `7d5cc6199` under `src/`. Re-run the counts at pickup (§Pickup commands).

## Outcome

`Aiur.Orchestrator` can be started once per project under a via-Registry name, and every place that names the
orchestrator resolves the orchestrator of the *current project* through one function, `Aiur.Project.whereis/1`.
With no project context (an empty `projects:` list, or any process outside a project tree) the function returns the
atom `Aiur.Orchestrator`, so today's boot, today's registered name and the roughly 57 test files that name
`Aiur.Orchestrator` behave exactly as before.

## Design

**Names, not pids.** `Aiur.Project.whereis(module, project_id \\ current_project_id())` returns a
`GenServer.server()` term and never a pid:

- `project_id` is `nil` → the atom `module` (today's name).
- otherwise → `{:via, Registry, {Aiur.ProjectRegistry, {String.downcase(project_id), module}}}`.

**Project id is the downcased repo** (binding for the MPG-30x set). `%Aiur.Project{}.id` is `String.downcase(repo)`
(`owner/name`); the original-case `repo` is for display and API calls only. `name/2` and `whereis/2` downcase an explicit
id (CLI `--project`, a webhook's repo, MPG-307's broker), the same rule MPG-306R gives `Registry.via/2` and `root_pid/1`.
The default id is `Context.current/0`'s `.id` (`nil` with no context), read through the private `current_project_id/0`;
MPG-303 does not depend on a `current_id/0` helper.

A name works in a function-head default (`server \\ Aiur.Project.whereis(Aiur.Orchestrator)`, evaluated per call), in
`GenServer.call/3`, `GenServer.whereis/1` and `Process.whereis/1`-style liveness checks that go through
`GenServer.whereis`, and it survives an orchestrator restart. A cached pid goes stale. A function-head default
evaluates its expression on every call, so the project is read at call time, not at compile time.

**One function for both sides, and the only tuple builder.** `Aiur.Project.name/2` owns the
`{:via, Registry, {Aiur.ProjectRegistry, {id, module}}}` tuple; MPG-306's `Aiur.Project.Registry.via/2` delegates to it
(merge order 303, 304, so 303 lands first). `name/2` is the start side (`children.ex` today, `Aiur.Project.Supervisor`
in MPG-306); `whereis/1,2` is the lookup side. They share one implementation so a registered name and a looked-up
name cannot drift. `whereis/1` is therefore an alias of `name/1` with the current project; it is kept under the name
the ticket contract fixes.

**No context means the legacy atom, even in projects mode.** A machine-level process (HTTP request, CLI RPC, webhook,
Phoenix channel) has no project. In MPG-303 it keeps resolving to `Aiur.Orchestrator`, which in projects mode is not
registered, so calls exit `:noproc` and the existing `:unavailable` branches run. That is fail-closed. It is not
silent: MPG-311 (`--project`) and the MPG-6xx dashboard tickets pass an explicit `project_id` to `whereis/2`. The sites
this affects are marked **M** below so each owner can find them.

**Why rewrite the 0-arity wrappers.** MPG-301 §5 says plain callers (`Orchestrator.pause_agent(id)`) are not edited
because "public functions resolve their own server". That is true, but the resolving code is the set of 0-arity
wrappers such as `def pause_agent(id), do: pause_agent(Aiur.Orchestrator, id)`. Those wrappers are the sites. Callers
of them stay untouched.

**What stays untouched.** The three `config :aiur, ... Aiur.Orchestrator` entries (`config/config.exs:30,31,42`:
`github_poll_owner`, `github_quota_recovery_target`, `pause_containment_result_target`) are read by machine-level
code (`github/access_settings.ex:55-56`, `pause_containment.ex:352`, `github/transport.ex:264`, `github/quota.ex:422`).
In default mode they stay correct. In projects mode the broker must be told which project's orchestrator to notify;
that is a per-request `project_id` (MPG-301 §4) and belongs to MPG-307 (see Open question 3). MPG-303 changes none of
those four files.

**Atom assumptions (projects mode only).** A via name is not an atom, and `Process.info(pid, :registered_name)`
returns `[]` for it. Code that assumes an atom name:

| Site | Assumption | MPG-303 action |
|---|---|---|
| `agent_runner/handoff.ex:350-357` | `registered_name/1` → atom, else `nil`, becomes `orchestrator_name` | none in default mode; recorded for MPG-306 |
| `agent_runner/workspace_guard.ex:126-133` | same | same |
| `orchestrator/orphaned_workers.ex:116,141` | `owned_by_this_orchestrator?` needs an atom name | same |
| `orchestrator/state/process_liveness.ex:6` | `alive?(name) when is_atom(name)` | same |
| `orchestrator/lifecycle.ex:110` | `snapshot_key = Keyword.get(opts, :name) \|\| self()` | works (a via name is a valid key for `GenServer.whereis`, `tracker_tasks.ex:18`); `SnapshotStore` keying is MPG-304 |
| `orchestrator/lifecycle.ex:440` | `Keyword.get(opts, :name) == Aiur.Orchestrator` gates `AgentPubSub.subscribe_prewarm()` | compare against `Aiur.Project.name(Aiur.Orchestrator)` so a project orchestrator also subscribes |

These six are the reason MPG-303 does **not** switch default mode to a via name. They need a project-aware
"orchestrator identity" that is one decision (Open question 1), and it is cheaper to take it once in MPG-306/308 than
to thread it through six modules now.

**How the project reaches a site (MPG-301 §3).** P = the caller runs in a project tree or in a task started from one
(`$ancestors` / `$callers`), so `current/0` resolves. M = the caller is machine-level and needs an explicit
`project_id` later; in MPG-303 it still gets the legacy atom.

**Alternatives rejected.**

- *Mint one atom per project* (`:"Elixir.Aiur.Orchestrator.o/a"`). It keeps the atom-name sites working, but atoms are
  never collected, a project removed by `aiur gateway reload` leaks one, and MPG-301 KTD-4 already chose Registry names.
- *Pass the orchestrator through opts everywhere.* 181 occurrences in 97 files (`code-evidence.md` §5). Too wide.
- *Resolve through `:persistent_term`.* It would bypass the Registry's monitor-based cleanup of dead names.

## Prior art

None needed. The registration pattern (a `via` tuple over a unique `Registry`) is OTP's documented mechanism, and
the ticket raises no external question. The reports in `docs/research/multi-gateway/` were not read for this ticket.

## Risks

- **A missed site silently returns the wrong project's data** in projects mode. The mitigation is the zero-match
  regex test (MPG-303 acceptance) with the stricter pattern in §Pickup commands; the plain-argument form is the one
  MPG-301's regexes miss.
- **Default arguments hide cost.** Each call now runs `Context.current/0`, a process-dictionary read with a cached
  result. It is only visible on the hot paths `Client.snapshot/0` and `SnapshotStore.read`; benchmark one tick.
- **A machine caller later "works" by accident** if it happens to run under a project's `$callers`. M sites must be
  given an explicit `project_id` by their owning ticket, not rely on inheritance.
- **Atom-name sites** (table in Design) break only in projects mode; MPG-306's crash test (kill project A's
  orchestrator) detects them.
