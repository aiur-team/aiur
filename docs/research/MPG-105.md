# MPG-105 — Stop a stale owner before pushes and pull requests: research

Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (KTD-2, S1, "Ownership protocol" step 6).
Contract: MPG-105 in `docs/plans/2026-11-06-multi-project-gateways/tickets-m0-m1.md`.
Depends on MPG-101 (GO: `refs/aiur/owners/<ticket>`, `updateRefs` compare-and-set; see `docs/research/MPG-101.md`),
MPG-102 (ref read/write adapter) and MPG-103 (`Aiur.Ownership.ensure_owned/2`). Neither MPG-102 nor MPG-103 is in the
tree yet (`src/lib/aiur/ownership*` does not exist), so every name below that belongs to them is marked *assumed*.

No external question: this is a local shell/Elixir protocol question. Prior art needed: none beyond
`docs/research/multi-gateway/github-claim-protocols.md`, which the plan already cites for the epoch (fencing token).

## Outcome

With `instance.ownership: github`, an agent whose ticket moved to another gateway (or was released) cannot run
`git push`, `gh pr create`, `gh pr ready`, or any other fenced `gh` call. The guard exits non-zero with a message
containing `ownership moved` (or `ownership unverifiable` when the daemon cannot say), the daemon stops that agent
through the normal teardown path **keeping the workspace**, and one alert `system.ownership.stale_agent` fires per
ticket. With `instance.ownership: off` (default) none of this is active and existing guard tests pass unchanged.

## Design

### D1. The daemon, not the agent, records the epoch at spawn

The agent environment is agent-writable, so an epoch passed in env could be forged or stale after a resume. The daemon
keeps the truth.

- Module `Aiur.Ownership.Fence` (new, `src/lib/aiur/ownership/fence.ex`) is a GenServer owning one ETS table
  `:aiur_ownership_fence` keyed by **workspace path** (absolute, as in `AIUR_AGENT_WORKSPACE`), value
  `%{ticket: "123" | "pr-45", repo: "owner/name", gateway_id:, daemon_key:, epoch: 4, registered_at_ms:}`.
- Registration happens where MPG-103 learns the claim result: `Aiur.Ownership.ensure_owned/2` returns
  `{:ok, %{epoch: 4, ...}}` *(assumed shape; MPG-103 must return epoch, gateway_id, daemon_key — open question Q1)*.
  The dispatch path that spawns the agent calls `Aiur.Ownership.Fence.register(workspace, owned)` **before** the
  agent process starts, and `Fence.unregister(workspace)` from the same teardown that ends the run
  (`Aiur.Orchestrator.AgentTeardown`). Spawn is after claim in the plan (step 5-6), so the epoch is the one the claim
  returned, never a later read.
- Restart: the table dies with the BEAM. A resumed agent goes through `ensure_owned/2` again (uncached read, MPG-103),
  so it re-registers with the *current* epoch; if ownership moved while the daemon was down it is not dispatched at
  all. An unregistered workspace asking the fence gets `unknown no_registration` and the guard fails closed.

### D2. Socket protocol: reuse the line-JSON transport, second socket instance

Existing transport (`src/lib/aiur/github/agent_budget_socket.ex`): Unix socket, `packet: :line`, request
`{"args":[...up to 64 strings]}\n`, response `{"status":0,"output":"..."}\n` or `{"status":1,"error":"..."}\n`; the
shell client is `src/priv/github_budget_socket.py` (`python3 -I client SOCKET args...`; exit 0 and prints `output`;
exit 75 when the socket is unreachable; exit 1 with `aiur daemon budget error: <reason>` on a status-1 reply). It
already strips `--db/--token-key/--identity-key` and ignores unknown args, so it is reusable unchanged.

Constraints found in code:

1. `AgentBudgetSocket` is started only `if LeaseStore.configured?()` (`src/lib/aiur/application/children.ex:353`,
   `dashboard_final_children/2`), and `AIUR_GITHUB_BUDGET_SOCKET` is exported only under the same condition
   (`src/lib/aiur/github/agent_environment_contributor.ex`, `budget_socket_env/0` and `budget_socket_export/1`). A
   fence on that socket would silently vanish without Postgres — wrong for KTD-3 (claims work with the store down).
2. `AgentBudgetSocket.init/1` already takes `:name`, `:socket_path`, `:command_fun` options, so a second instance
   needs no new transport code. Only `socket_path/0` hard-codes `@socket_name`.

Decision: **start a second `Aiur.GitHub.AgentBudgetSocket` instance** with
`name: Aiur.Ownership.FenceSocket`, `socket_path: Aiur.Ownership.Fence.socket_path()`
(`<runtime_state_dir>/ownership-fence.sock`, same fallback shape as `socket_path/0`), and
`command_fun: &Aiur.Ownership.FenceCommand.execute/1`. It is started when `instance.ownership == "github"` (not when
the lease store is configured). `children.ex` is 414 lines; the child is one short entry in the same function.

Request/response (all on `args`):

| Request args | Output (status 0) | Meaning |
|---|---|---|
| `["fence","--workspace",W,"--action",A]` | `ok epoch=4 age_ms=1200\n` | still the owner at the registered epoch |
| same | `moved owner=<gateway_label> epoch=5 state=owned\n` | ref shows another gateway/daemon or a higher epoch |
| same | `moved owner=- epoch=5 state=released\n` | ref was released |
| same | `unknown <reason>\n` | `no_registration`, `read_failed`, `invalid_ref`, `timeout` |

`A` is one of `push`, `pr-create`, `pr-ready`, `pr-merge`, `api-pr-write` (closed set, validated; anything else is
`{:error, :invalid_request}` which the socket maps to status 1). Moved/unknown are **status 0 output lines** on
purpose: the client turns status 1 into a generic stderr line and exit 1, which the guard could not tell from a
daemon bug. The guard branches on the first word.

The socket is mode 0600 in a 0700 directory and is not authenticated per caller: any process of the same uid can ask.
That is fine because the answer reveals nothing secret; the only forgeable input is `--workspace`, and asking about
another workspace only yields that workspace's status.

### D3. The check (daemon side)

`Aiur.Ownership.Fence.check(workspace, action, opts)` returns `{:ok, info} | {:moved, info} | {:unknown, reason}`:

1. Look up the registration; none -> `{:unknown, :no_registration}`.
2. Read the owner record through the MPG-102 adapter *(assumed `Aiur.Ownership.Ref.read(repo, ticket, uncached: true)`
   -> `{:ok, %{state:, gateway_id:, daemon_key:, epoch:}} | :absent | {:error, _}`)*, with a **30 s freshness
   window**: a previous read for that ticket whose monotonic age is `<= 30_000` ms is reused, anything older is
   refreshed. The window is a module attribute `@max_age_ms 30_000`, with `now` injectable via `opts[:now_ms]` for tests
   (AGENTS.md time rule). Not a config key (no docs surface; open question Q4).
3. Concurrent checks for one ticket share one in-flight read (call serialised in the GenServer per ticket via a
   `Task` map) so a burst of pushes costs one read.
4. Verdict: `state == "owned"` and `gateway_id`/`daemon_key` equal the registration's and `epoch` equal -> `ok`.
   Anything else readable -> `moved`. Read error/absent -> `unknown`.
5. On the first `moved` for a ticket the fence casts `{:stale_owner, workspace, info}` to the orchestrator
   (see D5) and emits the alert once (dedupe key `{ticket, epoch}`; process memory is enough, restart repeats at most
   once).

Epoch comparison is `==`, not `>=`: the same gateway re-claiming after a release gets a new epoch and the old agent
is stale by design (a fresh dispatch spawned a fresh agent).

### D4. The guards

Two shell fragments, same check, both fail closed.

**Gating (identical in both):** the fence runs only when `AIUR_OWNERSHIP_FENCE_SOCKET` is set and non-empty *and*
`AIUR_AGENT_WORKSPACE` is set. The contributor exports the socket path only when `instance.ownership == "github"`.
`ownership: off`, host-level (Executor) git/gh, and non-agent contexts therefore never reach the fence. This is the
reason the existing guard tests should keep passing without edits.

**Shell helper** (defined once in the gh fragment and once, duplicated, in the git fragment; the two guards are
separate installed scripts and cannot share code):

```sh
ownership_fence() { # $1 = action
  [ -n "${AIUR_OWNERSHIP_FENCE_SOCKET:-}" ] && [ -n "${AIUR_AGENT_WORKSPACE:-}" ] || return 0
  fence_client="$(dirname "$0")/aiur-github-budget-socket"
  fence_out=$(python3 -I "$fence_client" "$AIUR_OWNERSHIP_FENCE_SOCKET" fence --workspace "$AIUR_AGENT_WORKSPACE" --action "$1" 2>/dev/null); fence_rc=$?
  case "$fence_rc:$fence_out" in
    0:ok\ *) return 0 ;;
    0:moved\ *) printf 'aiur: ownership moved (%s); this ticket now belongs to another gateway; stop and leave the workspace as is\n' "${fence_out#moved }" >&2; exit 77 ;;
    *) printf 'aiur: ownership unverifiable (%s); refusing %s\n' "${fence_out:-daemon fence socket unreachable, exit $fence_rc}" "$1" >&2; exit 75 ;;
  esac
}
```

Exit codes follow the existing guards: 77 = policy denial (merge/approve, update-branch), 75 = infrastructure
unavailable (budget socket) — so existing alert/log classifiers treat them the same way. The acceptance text only
needs "non-zero with `ownership moved`".

The git guard locates the client as `$(dirname "$0")/aiur-github-budget-socket`; check that the installed `git`
and client share `.aiur-runtime/bin` (they do: `wrapper_test.exs` lists `gh git aiur-github-budget-socket` in one
`bin_dir`). Remote worker installs use `RemoteInstall.script(workspace, @relative_bin_dir, @scripts, opts)` over the
same `@scripts`, so the client is present there too, but the daemon's Unix socket is not reachable from a remote
host; for remote workers `AIUR_OWNERSHIP_FENCE_SOCKET` is not exported by `shell_exports/2` and the fence is skipped
in v1 (open question Q2 — this is a real gap, not a pass).

**git fragment** `src/priv/github_guard/git/20-ownership-fence.sh`: runs after the push block of
`10-worktree-push.sh` (variables `git_command`, `push_command`, `competing_context` are already defined there). Fence
when `push_command = true` and no `--dry-run`/`-n` argument. It must come **before** the `@aiur-merge-queue-push-guard@`
substitution point? That marker sits inside `10-worktree-push.sh` and is replaced by other code; placing the fence
in its own later fragment avoids touching that marker (check in implementation: `grep -rn aiur-merge-queue-push-guard
src lib ../.claude` to see who substitutes it — open question Q6). Fenced git subcommands: `push` only. Not fenced:
`fetch`, `commit`, `merge`, `rebase` (local or read-only toward GitHub) — they are reversible and the agent needs
them to finish its report.

**gh fragment** `src/priv/github_guard/gh/20-c4-ownership-fence.sh`, listed in `parts.tsv` as
`aiur-policy	20-c4-ownership-fence.sh` directly after `20-c3-agent-gate.sh`. Name order matters:
`.claude/hooks/issue-disposition.py:295` assembles the gh guard by `sorted(glob("*.sh"))`, and `script.ex` comments that
list order and name order must agree. `20-c4` sorts after `20-c3-agent-gate` and before `20-d-budget`, so a fenced
refusal happens **before** budget admission and costs no GitHub quota. It runs only when `agent_guard -eq 1` (set in
`20-a-context.sh`).

The contract names only the git fragment; the gh fragment is an addition required by "Add the same check to the `gh`
guard" and is listed in Files below.

### D5. Which `gh` subcommands are irreversible (fenced)

Classification already exists in `10-a-classify.sh` (`"pr create"|"pr merge"|"pr review"` -> graphql write,
other `pr *` -> core write) and `20-b-merge-functions.sh` (`merge_or_approve_command`, `approve_flag_in_arguments`,
`api_command_endpoint`, `graphql_body_is_hidden`). Fenced set:

| Command | Action | Why fenced | Note |
|---|---|---|---|
| `gh pr create` | `pr-create` | creates a second PR for a ticket another gateway owns (plan "duplicate PR" risk) | contract |
| `gh pr ready` | `pr-ready` | marks a draft ready, which is the handoff the new owner never asked for | extra; recommended |
| `gh pr merge` | `pr-merge` | contract names it | already denied to agents by `20-c3-agent-gate.sh` (exit 77) first, so unreachable for agents; kept so a future relaxation of the gate stays fenced |
| `gh pr reopen` | `pr-ready` | revives a PR the new owner may have closed | extra; open question Q3 |
| `gh api` write to `.../pulls` (POST, REST PR creation) | `api-pr-write` | same effect as `pr create` | detect with `api_command_endpoint`, `direction = write`, endpoint `*/pulls` |
| `gh api graphql` with `createPullRequest` or `markPullRequestReadyForReview` | `api-pr-write` | same effect | body scan loop copied from `merge_or_approve_command`; hidden body (`graphql_body_is_hidden`) is already rejected for agents by the existing denial |

Explicitly **not** fenced: `pr comment`, `pr edit`, `pr close`, `issue comment`, label changes, workpad edits, `gh pr
checks/view/diff`. They are reversible or read-only, and the stale agent must still be able to report that it was
stopped. Plan risk "Unfenceable writes" stays: labels, comments and PR creation by tools other than `gh`/`git` (e.g.
the Aiur MCP tools such as `aiur_set_ticket_state`, which run in the daemon) are out of this guard's reach and are
covered only by D6.

### D6. Daemon stops the agent, keeps the workspace

The Outcome requires "its daemon stops it, keeps the workspace and alerts". The guard only refuses; stopping is the
daemon's:

- `Fence.check` on the first `moved` sends `{:stale_owner, ticket, info}` to the orchestrator, which calls
  `Aiur.Orchestrator.AgentTeardown.terminate_running_issue(state, issue_id, false, {:ownership_moved, info})`
  (`cleanup_workspace = false` keeps the workspace; signature at `agent_teardown.ex:55`) and must not schedule a
  retry/continuation for it (a stale owner redispatching is the bug). The retry suppression is the part to read
  carefully in the orchestrator before implementing (unit 6).
- Alert: topic `system.ownership.stale_agent` through `src/lib/aiur/alerts/` with the ticket, old epoch, new owner label.
  Name chosen to sit beside MPG-104's `system.ownership.ambiguous`.
- No periodic ref polling of running agents in this ticket: cost is one read per running agent per poll, for
  an event (transfer) that is rare, and the guard catches the stale agent at its first irreversible call anyway.
  Proactive stop on transfer is MPG-106's job (the transfer command knows the old agent; open question Q5).

### Alternatives rejected

- *Epoch in env* (`AIUR_OWNERSHIP_EPOCH`): agent-writable, and wrong after a resume.
- *Guard reads the GitHub ref itself*: agents hold no GitHub credential (the `gh` guard injects it per governed call),
  and a raw read would bypass the shared budget; the daemon already has the read path and cache.
- *Extend `AgentBudgetCommand`* with a `fence` verb: that module is token-and-budget specific (`agent_token/0` in
  front of every verb) and 197 lines; keep ownership out of it.
- *Fence in the `aiur_set_ticket_state` MCP path*: valuable but separate, and not what the contract lists.

## Risks

- **Guard is advisory.** An agent that runs the real `git` by absolute path skips the fence. The existing guards have
  the same property (identity guard comment in `00-destructive.sh`); credentials still come from the tracker token
  helper. Do not describe the fence as a sandbox in docs.
- **Remote workers unfenced** in v1 (Q2). Detect early: the contributor test asserts the unset export, and the docs
  paragraph says so.
- **Fail-closed lockout.** A GitHub outage makes every push return `ownership unverifiable` after the 30 s window. This
  is what the contract asks ("Fence query failure refuses the push"); the message names the cause so the agent can
  wait rather than loop. A cached `ok` under 30 s still passes during an outage.
- **Hash freeze.** `aiur-gh.sha256` is labelled a pre-extraction freeze; a reviewer may object to bumping it (Q7).
- **MPG-102/103 shape drift.** Names marked *assumed* may change; unit 1 must be re-based on the real adapter.
- **Retry loop.** If unit 6 misses retry suppression, the daemon redispatches the stale ticket, which `ensure_owned`
  then declines — harmless but noisy; the test above catches it.
- **Budget.** Each refreshed read costs one GitHub read per ticket per 30 s window while the agent is pushing; negligible,
  not measured (MPG-102 owns read cost).
