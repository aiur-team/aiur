# MPG-203 — Close the remote command gate gaps: research

Research deep dive MPG-203R (issue #7586). Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579),
contract `tickets-m2.md` § MPG-203, inventory `code-evidence.md` §3.3. Every claim below was re-read in the code on
`main` at `26ec6e00d`; file and line references are to that tree.

## Outcome

`aiur --instance x redispatch 12`, `aiur --instance x ticket estimate 12 [hours]` and
`aiur --instance x operator-relay-answer …` reach the remote control endpoint and run the same expression a local call
runs. A new ExUnit test fails when an allowlisted function has no CLI command mapping, or when a mapped command is
neither in the client gate nor on an explicit local-only list. A new client test proves each newly opened command makes
one HTTP request and each still-refused one makes none.

The research found **four** gaps, not three: `history label-writes` is also allowlisted and also refused (see Design,
finding F1).

from one to the other, and the parity test needs exactly that.

### What the three ticket commands need beyond a gate arm

1. **`redispatch`.** Add the word to the accept arm. The wrapper sends
   `Aiur.AgentControlCLI.redispatch(["12"], nil)` or `…(["12"], "codex")` — a string list and a nullable string, both in
   the row's positional constraints (`allowlist.ex:193`). `parse_issue_targets` is pure shell (no local state), so the
   expression is identical local and remote. Write scope applies.
2. **`ticket estimate`.** Add the word `ticket`. The wrapper accepts only `estimate` as the next word
   (`ticket.sh:3`) and refuses anything else with exit 64 before any RPC, so the gate need not look at the
   subcommand. Scope is dynamic: `ticket estimate 12` is a **read** (works with a read token); with hours or `--clear`
   it is a **write**. `by` defaults to `cli:$USER` (client user name); `by` is not in the forbidden remote keys
   (`control_call.ex:110-119` forbids `who, actor, set_by, owner, env`), so it is accepted. Attribution on the
   daemon is the token in the audit line, not `by`; this is recorded as an open question, not changed here.
   `--instance all ticket estimate` stays refused (`remote_all.sh:37` list excludes it) — keep, since the `all`
   path is out of scope.
3. **`operator-relay-answer`.** Add the word. The row requires `decision_id, expected_version, idempotency_key,
   quote, relayed_by` style keywords with the option constraints at `allowlist.ex:115-126`, all produced by the
   wrapper. It is a write with an idempotency key, which makes a client retry after exit 124 safe at the decision
   level. The daemon-side relay config gate still applies and its refusal comes back as HTTP 422 mapped to exit 64
   (`remote.sh` 422 arm), so no client change is needed.
4. **`history label-writes` (F1).** Add a gate arm for `history` that accepts only the `label-writes` subcommand
   and refuses `export` with `aiur: history export is local to the instance's host`. Server-side
   `history_label_scope` already makes `start`/`resume` deny and `pause` write; no server change. The wrapper's
   agent-workspace refusal for `start`/`resume` reads the client's env, which is the right place.

### Closing the class: the mapping and the parity test

The plan says "add a `cli_command` field per entry" to `allowlist.ex`. Recommendation: **do not put it in `@rows`**.
`@rows` has about 118 entries in 320 lines; a field per row grows an already dense file toward the 500-line gate and
couples a documentation fact to the security table. Put the mapping in a new small module instead:

`src/lib/aiur/control_call/allowlist/cli_commands.ex`, module `Aiur.ControlCall.Allowlist.CliCommands`:

```elixir
@spec for_entry({[atom()], atom(), non_neg_integer()}) :: {:remote, [String.t()]} | {:local_only, String.t()}
@spec entries() :: %{ {[atom()], atom(), non_neg_integer()} => {:remote, [String.t()]} | {:local_only, String.t()} }
```

Keyed by the same `{segments, function, arity}` as the allowlist. `{:remote, ["redispatch"]}` names the gate word(s);
`{:local_only, "TTY confirmation"}` carries the reason for deny rows and for read rows the client chooses not to send
(`executor_listen_validate`). Keep the facade pattern: one function-per-name map written as a literal so a reviewer
sees one line per entry.

`src/test/aiur/control_call/gate_parity_test.exs` (module `Aiur.ControlCall.GateParityTest`, `async: true`, no daemon):

1. Read `packaging/npm/aiur-cli/libexec/engine/remote.sh` (path relative to `__DIR__`, as
   `engine_census_test.exs` does). Extract the accept arm: the text between `case "$command" in` inside
   `ensure_remote_command_allowed` and the first `;;`, split on `|`, trim. Assert it is non-empty and contains
   `status` and `pause` (guards the parser against matching nothing).
2. `Allowlist.entries()` minus the `Mix.env() == :test` probe modules (`Aiur.ControlCallTestProbe`,
   `Aiur.ControlControllerTestProbe`) must all be keys of `CliCommands.entries()`, and `CliCommands.entries()` must
   have no key absent from `Allowlist.entries()`.
3. For every `{:remote, words}` entry each word is in the gate accept list. For every `{:local_only, reason}` entry
   the reason is a non-empty string.
4. For every `:deny` row the mapping must be `{:local_only, _}` (so a deny row cannot silently become a gate word).

The fail-without property: remove `redispatch` from the gate list and assertion 3 fails naming `redispatch`;
remove a `CliCommands` row and assertion 2 fails naming the function.

Limits, stated plainly. The test proves the lists agree on **names**. It does not prove the wrapper emits an expression
that parses; `engine_census_test.exs` already does that (it runs 77 wrapper cases through `ControlCall.parse`,
including `redispatch`, `ticket estimate` and `operator relay answer`). The two tests cover different halves; do not
merge them.

## Risks

- **Gate parser drift.** The test reads shell text with a regex. If someone reformats the `case` arm (for example one
  word per line), the extractor may mis-split. Detect: assertion 1 (non-empty, contains `status` and `pause`). Fallback:
  move the word list to a sourced file `engine/remote_commands.list` read by both the shell and the test. Rejected for
  now because it changes the shell loading order for no present benefit.
- **`operator-relay-answer` is the sensitive one.** It records an operator's words relayed by an Executor. Remote, the
  `--relayed-by` value is whatever the client typed. A write token holder can already call every write in the
  allowlist (`executor-revoke`, `set`), so this adds no new capability class; MPG-205 categories are the right place
  to narrow it. State this in the PR body.
- **Opening `ticket` opens the word, not only `estimate`.** Safe today because `cmd_ticket` rejects other
  subcommands before RPC and the server allowlist has only `ticket_estimate`. If a later ticket adds `ticket frob` to
  the wrapper without an allowlist row, the server refuses it with `unknown_on_build`. Acceptable.
- **Plan-doc edits depend on #7579 merging.** See unit 6.
- **Saving claim:** none. This is a correctness and consistency change; no quota or cost claim is made.
