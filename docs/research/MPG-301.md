# MPG-301: the multi-project process model

Status: **decided** (2026-11-06). Plan: [multi-project gateways](../plans/2026-11-06-multi-project-gateways.md)
(KTD-4, decision 24). Contract: `tickets-m3.md` MPG-301. Every M3 research ticket (MPG-302R..311R) reads this first.

Code references are to `src/lib/aiur/` at `26ec6e00d` unless a path says otherwise. The `name: __MODULE__`
inventory below re-runs the `code-evidence.md` §5 command (`grep -rlE 'name: __MODULE__' lib`) on that commit: 27 files,
the same set the evidence counted.

## Decision

KTD-4 is **confirmed**. One BEAM per machine (the *gateway*) runs one supervision tree per project. The changes
below make it buildable:

1. **Per-project processes register under `{:via, Registry, {Aiur.ProjectRegistry, {project_id, Module}}}`.** Their
   public functions find their own server with `Aiur.Project.whereis(__MODULE__)`, so callers keep calling
   `Module.fun(...)` and do not change. Only callers that name the process directly (`GenServer.call(Module, ...)`,
   `Process.whereis(Module)`, a `\\ Module` default) are migrated.
2. **The project context lives in the process dictionary and is inherited, not threaded** (§3).
3. **Machine-level processes are called with an explicit project id.** A machine process serves every project, so it
   never reads an ambient context. Any output it writes about a project carries that project's id (§4).
4. **An empty `projects:` list boots exactly today's tree** (§6).
5. **The planned `machine-gateway` process stays a separate OS process** (§8).

## 3. How the project context reaches each kind of process

`Aiur.Project.Context.current/0` (MPG-302) resolves the project in this order, and caches the answer in the calling
process:

1. an explicit `Aiur.Project.Context.put/1` value in the process dictionary;
2. otherwise, the first pid in `$callers` that resolves to a project;
3. otherwise, the first pid in `$ancestors` that resolves to a project;
4. otherwise `nil`, which means today's single-project behaviour.

A pid "resolves to a project" when it is a project root supervisor registered in `Aiur.ProjectRegistry`, or a process
that has already cached a project.

How each kind of process gets its project:

- **`GenServer` and `Supervisor` children of a project tree** get it from `$ancestors`, which `proc_lib` sets. No
  per-module code is needed.
- **`Task` and `Task.Supervisor` children** get it from `$callers`, which `Task` sets to the caller. This holds even
  when the task runs under the machine-level `Aiur.TaskSupervisor`, so agent tasks started by a project's orchestrator
  carry that project. `Aiur.Project.Task.async/1` exists only for a machine process that starts work *for* a project:
  it puts the given project explicitly.
- **ETS readers** run in the caller's process, so they read with the caller's context. Per-project tables are unnamed.
  Their tid is stored in `:persistent_term` under `{Aiur.Project.Table, project_id, name}` at boot (written once per
  project, read in constant time). With no context, readers use today's named table.
- **Bare `spawn/1` and `Port` owners** inherit nothing. Code that spawns raw processes for a project must call
  `Context.put/1`. MPG-302R lists these sites.
- **Machine-level processes** never call `current/0` on their own behalf. Every request from a project to a machine
  process carries `project_id` as an argument.

`Aiur.Config.settings/0` reads `current/0`. That is how the 142 files that call it (`code-evidence.md` §5) become
project-correct without being edited.

## 6. The single-project default

With `projects:` absent or empty in `~/.aiur/machine`, nothing changes:

- `Aiur.Application.Children.child_specs/1` returns today's list unchanged.
- `Aiur.ProjectRegistry` has no project roots, so `Context.current/0` returns `nil`.
- `Aiur.Project.whereis(Module)` returns `Module`, the name every singleton registers under today.
- Table lookups fall back to today's named tables.

MPG-306 asserts this with a test: `child_specs/1` with `projects: []` equals the list at the parent commit. Rollback
of projects mode is therefore "empty the list" (plan, rollout).

With `projects:` set, the list is split. Machine children start first, in today's relative order. They are followed by
`Aiur.Project.Supervisors`, a `:one_for_one` `DynamicSupervisor` with one `Aiur.Project.Supervisor` per entry, each
`:transient`. A project tree that exhausts its restart intensity stops alone and raises `system.project.boot_failed`;
other projects keep running. Today some machine children (`HttpServer`, the opencode supervisors, `TokenRegistry`)
start *after* `Aiur.Orchestrator` under `:rest_for_one`. MPG-306R must confirm that none of them depends on starting
later.

## 7. Test helper for two project trees in one VM

**`Aiur.ProjectCase`**, at `src/test/support/project_case.ex`, introduced by MPG-302 and used by MPG-302..306:

```elixir
use Aiur.ProjectCase
%{a: a, b: b} = start_projects!(["o/a", "o/b"], children: [Aiur.WorkflowStore])
```

`start_projects!/2` writes a memory-tracker `.aiur/config` for each repository under a `tmp_dir` state root. It starts
one root supervisor per project with `start_supervised!`, registers each as a project root in `Aiur.ProjectRegistry`,
and returns the `%Aiur.Project{}` structs. Each ticket passes the children it migrates. MPG-306 replaces the plain
root supervisor with `Aiur.Project.Supervisor`. The helper never touches `~/.aiur`.

## 8. The `machine-gateway` process stays separate

`machine-gateway` (MP-N2, `docs/research/aiur-mobile-and-platform/`) owns the `~/.aiur/machine` `gateway`, `pairing`
and `transport` sections, `~/.config/aiur/machine/`, and the pairing HTTP listener. **It is kept as its own lean OS
process, and is not folded into the gateway daemon.** The reasons:

- **Pairing must work with no daemon running.** MP-N2-C4-T01 boots it without the `:aiur` application, because
  `Aiur.Application.start/2` reads a workflow config, resolves GitHub credentials and starts an orchestrator before
  any child runs. A phone must be able to pair and discover while every project is stopped, or before any is
  configured.
- **Daemon restarts must not drop paired devices.** Keep-agents restarts and `aiur gateway reload` restart the daemon
  or its project trees. The pairing listener and its device store lock outlive both.
- **The single-writer rule is already the gateway's.** `machine-gateway` is the one writer of the machine store.
  Folding it into a BEAM that can be restarted for a config change would move that writer into the most frequently
  restarted process on the machine.

The gateway daemon is a client of `machine-gateway`. It reads `identity.json` and the machine store through the
`aiur_machine` library, and registers itself in the instance registry. Both share one identity (KTD-1: `gateway_id` =
`machine_id`). "Gateway" in this plan means the daemon; MP-N2 keeps the name `machine-gateway` for the pairing process.

## 9. Alternative evaluated: one OS daemon per project behind a machine coordinator

Each project keeps today's daemon unchanged, and a new coordinator process grants capacity and serves the machine
surfaces.

- **For:** no singleton migration (none of the 229 project-reading files, none of the 30 hard-coded orchestrator
  files). A crash in one project cannot stop another.
- **Against:**
  - Capacity (MPG-307), the GitHub budget broker, the usage ledger and the alert feed would each need a cross-process
    protocol and a failure mode for "coordinator unreachable". They are in-process calls today.
  - There would be N tmux sessions, N HTTP listeners and N dashboards, so the "one dashboard per machine" surface
    becomes a proxy.
  - Remote control would need per-project `--instance` addresses again, which undoes KTD-6.
  - The GitHub credential is per machine, so N daemons contend for one budget through IPC instead of one broker.
- **Conflict:** it contradicts plan decision 24 / KTD-4, "one daemon per machine", which was taken firm *knowing* that
  a crash pauses all local projects. **Rejected.** Its one real advantage, crash isolation, is recovered inside the
  BEAM by §6: one `:transient` project tree per entry under a `:one_for_one` supervisor, so a crashing project stops
  alone. A crash of the BEAM itself still stops every project; decision 24 accepts that.
