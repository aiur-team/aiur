# MPG-104 — Project ownership as a gateway label and skip ambiguous tickets: research

Research ticket MPG-104R (#7607). Inputs: `docs/plans/2026-11-06-multi-project-gateways.md` (KTD-2, S1, "Ownership
protocol"), `tickets-m0-m1.md` (MPG-102, MPG-103, MPG-104), `docs/research/MPG-101.md`, and the code read below. The plan
files come from PR #7579. No code change. Focus: label colour and creation, alert dedupe key, budget cost.

## Outcome
After a gateway wins a claim (`:won`) it adds `gateway:<slug>` to the issue, and once per poll it compares the ref
(authority) with the labels on every owned or labelled ticket. When they disagree, or the ref is unreadable, the ticket is
not dispatched by this gateway and one `system.ownership.ambiguous` alert names it, at most once per ticket per hour per
daemon. A ticket with a `gateway:` label, no ref and no state label is logged as a human assignment request and not
dispatched.

## Design

**Authority.** The ref (KTD-2) decides. The label is a projection for people and for GitHub search. The projection module
never changes who owns a ticket and never removes a label it did not add.

**Pure classifier, then effects.** `Aiur.Ownership.Projection.reconcile/2` is pure: `(ref_read, issue_view) -> decision`.
Effects (label ensure, label add, alert, log) are in `Aiur.Ownership.Projection.apply/3`, so the AC scenarios are table
tests on the classifier and one stub test per effect.

`ref_read` is the MPG-102 read result mapped to: `{:owned, record}` (S1 `state: "owned"`), `:unowned` (no ref),
`:released` (S1 `state: "released"`), `{:unreadable, reason}`. `issue_view` is `%{labels: [String.t()], has_state_label?: boolean}`
taken from the issue the poll already fetched (no extra read). `self` is `%{gateway_id, daemon_key, slug}`.

Gateway labels on the issue = labels matching `^gateway:(.+)$`, compared case-insensitively.

| # | Ref | Gateway labels | Has state label | Decision |
|---|---|---|---|---|
| 1 | `{:owned, r}`, `r` is self | none | any | `{:project, self.slug}` |
| 2 | `{:owned, r}`, `r` is self | exactly `[self.slug]` | any | `:consistent` |
| 3 | `{:owned, r}`, `r` is self | any other set (another slug, or 2+ labels) | any | `{:ambiguous, :label_disagrees}` |
| 4 | `{:owned, r}`, `r` is another gateway or daemon_key | none, or exactly `[slug(r)]` | any | `:foreign` (skip, no alert) |
| 5 | `{:owned, r}`, `r` is another gateway | a set that is not `[slug(r)]` and not empty | any | `{:ambiguous, :label_disagrees}` |
| 6 | `:unowned` or `:released` | none | any | `:unlabelled` (dispatch proceeds to claim, MPG-103) |
| 7 | `:unowned` or `:released` | `[self.slug]` | true | `:unlabelled` (claim proceeds; the label is a hint that agrees) |
| 8 | `:unowned` or `:released` | `[other]` | true | `{:hint_other, slug}` (skip this poll, log, no alert: that gateway will claim it) |
| 9 | `:unowned` or `:released` | one or more | false | `{:assignment_request, slugs}` (log once, never dispatch) |
| 10 | `{:unreadable, _}` | any | any | `{:ambiguous, :ref_unreadable}` |
| 11 | `{:owned, r}` where `r.gateway_id == self.gateway_id` but `r.daemon_key != self.daemon_key` | any | any | `:foreign` (two daemons on one machine, S1 "self" rule) |

Rows 3 and 5 are the KTD-2 "ref and label disagreeing = skip and alert". Row 10: the plan says unreadable ref means
skip; MPG-103 already holds dispatch with attention `ownership_unknown`. MPG-104 alerts under its own name only for the
projection pass, so a ticket skipped for an unreadable ref raises `system.ownership.ambiguous` too. See open question 4.

**Slug.** `slug(label)`: downcase the registry `gateway_label`, replace each run of characters outside `[a-z0-9]` with
`-`, trim leading and trailing `-`, cut to 42 characters (GitHub caps a label name at 50, and `gateway:` is 8). An empty
result falls back to the first 8 characters of the lowercased `gateway_id`. The slug is derived in one place
(`Projection.slug/1`); the S1 record keeps `gateway_label` verbatim, and the classifier compares `slug(record.gateway_label)`
with the label, never the raw label text. Two gateways whose labels slug-collide would look consistent to the classifier;
the ref still decides ownership, and registry validation (MPG-2xx) should reject a duplicate slug. See open question 3.

**Label creation.**
- `gateway:*` labels are dynamic, like `agent:executor:<owner>` (`Aiur.GitHub.Labels` header comment, "Owner-valued ...
  labels ... ensured by `aiur take`"). They are not added to `Labels.label_set/2`, so `aiur init` does not create them.
- Today `Labels.ensure/5` posts `%{"name" => label}` only (`create_label/4` in `src/lib/aiur/github/labels.ex`), so GitHub chooses the
  colour and there is no description. MPG-104 needs a colour and a description, so add `Labels.ensure_with/5`
  (`owner, repo, token, [%{name:, color:, description:}], opts`) that reuses `create_label/4`'s status handling (2xx and
  422 `already_exists` are success) and posts `name`, `color`, `description`. `ensure/5` keeps its signature and callers
  (`main_fixer.ex`, `init/labels.ex`).
- **Order matters.** `POST /issues/:n/labels` with a label that does not exist creates it with a GitHub-chosen colour and
  no description (documented GitHub behaviour; not re-verified in this ticket, see "Evidence to produce"). So the
  projection must `ensure_with` first, then `add_label`, or the colour and description are lost for good (a later 422
  `already_exists` never repairs them).
- Ensure at most once per slug per daemon lifetime: an ETS or `Agent` set keyed `{repo, slug}` marks "ensured". Failure to
  ensure is not fatal: log, skip the add this poll, retry next poll.
- `Labels.describe/1` must get a clause before the generic `[_prefix, suffix]` one. Today `describe("gateway:pc")` splits
  to `["gateway", "pc"]` and falls to `state_description("pc")`, which returns `"pc"`. New clause:
  `describe("gateway:" <> slug)` returns `"Owned by gateway #{slug}: mirrors the ownership ref, which is authoritative"`.
- **Colour: one fixed colour, `1d76db` (blue), for all `gateway:*` labels.** Rationale: the label tells a person which
  gateway holds the ticket; the name is already distinct, and a per-gateway hash palette adds a mapping that must stay
  stable across machines for no decision value. Constant `@gateway_label_color "1d76db"` in `labels.ex`. I could not check
  colours already in use in the target repository from this workspace (no repository read); open question 1.
- The `gateway:` prefix is not the tracker prefix (`agent:`/`nuc:`/`aiur:`), so one gateway label name is shared by all
  instances of a repository. That is wanted: a label written by PC reads the same on Nook.

**Label add.** Reuse `Aiur.GitHub.IssueState.add_label/3` (`issue_state.ex:49`; `Client.add_label/3` delegates). It already
writes through `WriteThrough.issue_labels/2`, so the next poll sees the label without a re-read. Do not use
`update_issue_state`; this is not a lifecycle state, and `Labels.state_labels/1` must not include `gateway:*` (dispatch
refuses contradictory state labels).

**Never remove.** On a mismatch the projection skips and alerts and does not delete the other gateway's label. Fixing a
stale label after a transfer belongs to MPG-106 (`aiur ticket assign` writes the new label in the same flow).

**When it runs.** (a) Immediately after each `:won` claim (plan step 4, best effort: a failed add does not undo the claim
and the next poll retries). (b) Once per poll in the orchestrator's candidate pass for tickets that are owned by this
gateway or carry a `gateway:` label. Tickets with neither are not touched, so an un-migrated repository with
`instance.ownership: off` pays nothing and sees no behaviour change.

**Alert.**
- Name `system.ownership.ambiguous`, plus `system.ownership.ambiguous.resolved` emitted when a previously ambiguous ticket
  classifies as `:consistent`, `:foreign` or `:unlabelled` (same pairing as `system.instance.ownership_unknown`).
- Register both in `src/lib/aiur/events/catalog/system_entries.ex` with category `"config"`, source comment
  `# aiur/ownership/projection.ex`, in the file's existing alphabetical order among the `system.*` entries.
- Emit with `Aiur.Alerts.emit_system/2` (same call `lease_store.ex` uses), `needs_attention: true`, `severity: "warning"`,
  `dedup_key: {:ownership_ambiguous, repo, ticket}`, and `bypass_contamination: true`.
  - **Why `bypass_contamination: true`:** `Events.Publisher.rejection/3` returns `:filtered` for any event with an
    `issue_number` that `tracked?/1` does not know. A skipped ticket is by definition one this daemon is not tracking, so
    without the bypass the alert is dropped silently (`publisher.ex:136`, `:334`). `publication_result(:filtered)` is also
    `:ok`, so the caller cannot tell. A test must cover an untracked ticket.
  - **Why the key has no label or epoch in it:** the AC says once per ticket per hour. A key that includes the label value
    or epoch would re-alert on every flap. The Publisher's replay window is 1 hour (`@default_ttl_ms 3_600_000`,
    `publisher.ex:45`), which is exactly the AC window, so no new timer is needed.
  - **Limits, stated:** the window is an ETS table owned by the Publisher, so it empties on daemon restart: one extra alert
    per ambiguous ticket after a restart. PC and Nook each run their own Publisher, so each alerts once; the Executor of
    each gateway sees its own. Accepted; open question 2.
  - Message: `"Ticket #<n> in <repo>: ref says <gateway-label or unreadable>, labels say <labels>. Skipped."` Payload
    carries `repo`, `ticket`, `reason` (`label_disagrees | ref_unreadable`), `ref_gateway_id` (or `nil`), `labels`.
    `reason` is a specific atom only for the two causes the classifier actually knows; any other classifier outcome is
    `:unknown` (AGENTS.md "collapsed causes").

**Budget cost.** Counted from the code paths, not measured; MPG-104 claims no saving and only adds writes.
- Per `:won` claim: 1 REST `POST /repos/:o/:r/issues/:n/labels` (endpoint family `labels`, resource `core`, billable
  in `Aiur.GitHub.EndpointPolicy`) = 1 Core point. Zero when the label is already present (row 2).
- Per daemon lifetime per slug per repo: 1 REST `POST /repos/:o/:r/labels` (same family) = 1 Core point. A 422
  `already_exists` still costs the call.
- Per poll: 0 requests. The classifier reads labels already in the polled issue payload and the ref read that MPG-103
  performs for dispatch. Projection adds no ref read; if MPG-103 reads only for dispatch candidates, tickets that are not
  candidates (for example `agent:done` with a label) are classified from labels only with `ref_read = :not_read`, which
  must map to no decision (no alert, no write). See open question 5.
- Attribution: the broker ledger names callers; use ledger callers `ownership_label_ensure` and `ownership_label_add`
  (same pattern as `history_label_backfill_ensure` and `history_label_backfill_post` in
  `website/docs-app/apis/github-budgets.md`, "History label writes") so `aiur github-cost` ranks them separately.
- Pacing: GitHub applies secondary limits to content-creating writes; the label POST goes through the broker, which paces
  and defers writes on a hold. A hold makes the add fail with `{:github, :local_hold, _}` (`label_error/2` in `labels.ex`);
  the projection treats any add error as "retry next poll" and does not alert.
- Population (AGENTS.md item 5): the cost scales with claims per hour. A gateway doing N claims/hour spends N Core points
  /hour plus one per boot; the live claim rate is unmeasured here because `instance.ownership: github` does not exist yet
  (MPG-103). Re-measure with `aiur github-cost` filtered to the two callers after MPG-109's live run, and state the date
  and count there.

**Alternatives rejected.**
- Per-gateway label colours: more mapping, no decision value (above).
- Making the label authoritative (no ref read when a label exists): the label is writable by anyone with triage rights and
  has no compare-and-set; KTD-2 forbids it.
- Deleting a stale `gateway:` label on mismatch: it would hide the very disagreement the alert reports and race with a
  transfer in flight.
- A new dedupe timer or table: the Publisher window already equals the AC.
- A label per project (`project:<x>`): the ticket's outcome is the gateway label only; project routing is another lane.

## Risks
- **Silent alert loss** if `bypass_contamination` is dropped (see Alert). Detect: the untracked-ticket test.
- **Wrong authority**: a future change that lets the label short-circuit the ref read. Detect: row 3/5 tests.
- **Slug collision between two gateways** makes disagreement invisible to the classifier. Mitigated by registry
  validation (open question 3); the ref still decides ownership.
- **Alert storm after restart** with many ambiguous tickets: one per ticket. Bound it by capping alerts per poll at 20
  (the remainder logged with a count). Add if the live run shows more than that; not built now.
- **Transfer window** (MPG-106): between the ref moving and the label rewrite, the ticket is ambiguous and is skipped
  for at most one poll; accepted.
- **Label write by a human** (adding `gateway:nook` to a PC-owned ticket) is indistinguishable from drift; it alerts, which
  is the intent.

## Open questions
| # | Question | Recommended default | What changes if answered differently |
|---|---|---|---|
| 1 | Which colour for `gateway:*` labels? | One fixed `1d76db`; implementer checks the target repository's existing label colours at build time and picks the nearest unused blue if it clashes. | Per-gateway colours add a stable slug-to-palette function in `labels.ex`; no other unit changes. |
| 2 | Should only the ref owner alert, rather than both daemons? | Each daemon alerts for its own view, once per ticket per hour. | An owner-only rule needs the other daemon's skip to be silent, and a ticket whose ref is unreadable would alert from nobody. |
| 3 | Where is a duplicate gateway slug rejected? | In registry validation (MPG-205/206), with the error naming both gateways; MPG-104 only documents the assumption. | If not rejected, two same-slug gateways could not be told apart by label; ownership remains correct. |
| 4 | Does an unreadable ref raise `system.ownership.ambiguous` as well as MPG-103's `ownership_unknown`? | Yes, but only from the per-poll projection pass for tickets that carry a `gateway:` label, so a store-style outage on unlabelled tickets does not double-alert. | If both always fire, one outage raises two alerts per ticket; dropping MPG-104's row 10 removes that. |
| 5 | Does the per-poll pass read refs for non-candidate tickets? | No. Only candidates and owned tickets are read; others get `ref_read = :not_read`, which yields no decision. | Reading refs for every labelled ticket costs up to one GraphQL call per labelled ticket per poll; measure before adopting. |
| 6 | After a human transfer, should the new owner repair the stale label? | No; MPG-106's transfer writes the label itself. A gap between ref and label is ambiguous and is skipped. | Repair on mismatch would make the new owner delete another gateway's label, which this design forbids. |
| 7 | Is `1 Core point per claim` acceptable without a measured rate? | Yes: it is additive, bounded by the claim rate, and claims no saving; measure after MPG-109. | A budget gate on claims would need a number first. |
