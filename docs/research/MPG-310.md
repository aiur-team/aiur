# MPG-310 — Explain where each config value comes from: research

Plan: [multi-project gateways](../plans/2026-11-06-multi-project-gateways.md) ("Config precedence and provenance").
Contract: `tickets-m3.md` MPG-310. Reads: [MPG-301](MPG-301.md) (process model), `code-evidence.md` §4,
`state-schemas.md` S3. Code references are to this checkout (`main` at `7d5cc6199`).

Brainstorm questions were not put to a user; each is recorded under Open questions with a recommended default.
**No external research was needed:** the ticket raises no question the codebase or the prior-art reports in
`docs/research/multi-gateway/` leave open (the design is a read-only report over files Aiur already parses).

## Outcome

`aiur config explain <key> [--project owner/repo] [--json]` prints, for one dotted config key: the effective value, the
layer that owns it (L0-L6), the file or store it came from, and every lower layer that also set the key and lost.
Secret-valued keys print `<redacted>`. A key set nowhere prints the built-in default with layer L0. The command is
read-only, allowlisted as `:read`, and works against the local gateway and (through the existing remote selector)
a remote one.

## Design

### What exists today (verified in code)

- **There is no merge between a project file and the global file.** `Aiur.Workflow.resolve_config_path/1`
  (`src/lib/aiur/workflow.ex`) returns the *first existing* of `<cwd>/.aiur/config`, then `~/.aiur/config`. So L2 and
  L3 are alternatives for one project, not stacked. `explain` must say so: when L3 exists, L2 is not an "overridden"
  layer, it is "unused" and is omitted from `overridden`.
- **Overrides (L5) are file-backed and narrow.** `Aiur.Config.Overrides` (`config/overrides.ex`) accepts exactly eight
  keys (`@settings`): `agent.max_concurrent_builds`, `agent.max_concurrent_agents_by_state`, `agent.priority`,
  `agent.routing`, `build_queue.max_active_sets`, `instance.ignore.tickets`, `instance.owns`, `instance.pool`. Entries
  carry `value`, `revision`, `set_by`, `set_at`, `build`, and are merged after YAML by `Overrides.apply/1`
  (`Workflow.load/1` = `load_base/1` + `Overrides.apply/1`). `Overrides.list/0` already returns
  `source: "override"` per key.
- **`agent.max_concurrent_agents` is NOT an `aiur set <key>` key.** `aiur set max-agents <n>` is a different path: it
  calls `Aiur.AgentControlCLI.set_max_agents/1` -> `Orchestrator.set_max_concurrent_agents/1`
  (`orchestrator/slots.ex:33`) and is session-only orchestrator state, not in the overrides file. `--max-agents` at
  launch (`cli.ex:403 maybe_set_max_agents/1`) uses the same call. The MPG-310 acceptance example ("`agent.max_concurrent_agents` set in
  the project file and overridden by `aiur set`") therefore needs the session cap to count as L5 for that one key
  (see Open question 1).
- **Machine file (L1)** is `Aiur.Machine.Settings` (`machine/settings.ex`): `projects`, `capacity`, `coordination`,
  plus mobile/gateway/pairing/transport. `load/0` re-reads the file; `get/0` is cached.
- **Secrets:** config secrets are `$NAME` env references (`Aiur.Config.EnvRef`), e.g. `tracker.linear.api_key`,
  `elevenlabs.api_key` (`config/schema.ex:286-331`). A literal secret may also be present.
- **L4 (shared intent) and L6 launch flags** do not exist yet as readers (S4 lands with the intent tickets; L6 is
  `--max-agents`/`--host`/`--pause` handled in `cli.ex`).

### Algorithm

`Aiur.Config.Provenance.explain(key, opts) :: {:ok, report} | {:error, reason}`.

1. Validate `key` against the set of known dotted keys. Source of truth: the keys the schema accepts, derived by
   walking `Aiur.Config.Schema` (embedded schemas under `config/schema/*`) plus the `Aiur.Machine.Settings.Schema`
   keys prefixed `machine:` (the same convention `scripts/check-config-docs.py` uses). Unknown key ->
   `{:error, {:unknown_key, key, suggestions}}`, exit 64, suggestions by Jaro distance >= 0.8, max 3.
2. Resolve the project (MPG-301's `Aiur.Project.Context`, falling back to the cwd repo when the gateway has one
   project; `--project` selects explicitly; unknown project -> exit 64 listing the known ones). Until MPG-306 lands the
   only project is the single legacy one.
3. Read each layer **separately** into a `%Layer{id, label, source, value | :unset}`, never through the merged
   `Aiur.Config.settings/0` (a merged read cannot say who set what):
   - L0: struct defaults of the schema field (`Ecto` `default:`), read by building the schema with an empty map.
   - L1: `Aiur.Machine.Settings.load/0`, keys under `machine:` and the `projects[]` entry for the project
     (`max_agents` caps `agent.max_concurrent_agents`).
   - L2: `~/.aiur/config` via `Workflow.load_base/1` when it is the file `resolve_config_path` would *not* choose;
     reported as `unused` if L3 exists, as the owning layer if L3 does not.
   - L3: the project's `<repo>/.aiur/config` via `Workflow.load_base/1` (this is `Workflow.workflow_file_path/0`
     for the single-project gateway; MPG-304 supplies the per-project path later).
   - L4: `:unavailable` with reason `intent_store_not_implemented` until the intent store exists (never `:unset`;
     see the collapsed-cause rule in AGENTS.md).
   - L5: `Overrides.list/0` entry for the key, else, for `agent.max_concurrent_agents` only, the session cap read
     from the orchestrator (`Aiur.Orchestrator.Slots` snapshot field for the configured vs live cap) when it differs
     from the configured value.
   - L6: `:unavailable` unless the launch recorded a flag; recorded flags are out of scope for MPG-310 (Open question 2).
4. Winner = highest-numbered layer whose value is set, **except** the cap rule from the plan: when the key is
   `agent.max_concurrent_agents` and L1 `projects[].max_agents` is lower than the winner, the effective value is the L1
   cap and the report names L1 as owner with `capped_by: "L1"`. Everything below the winner that was set goes in
   `overridden`, highest first.
5. Redact: a key is secret when it is on `Aiur.Config.Provenance.@secret_keys` (a literal list: every key whose schema
   field is passed through `EnvResolver.resolve_secret_setting/…`, plus `*.token`, `*.secret`, `*.password`, `*.api_key`
   suffixes). Redaction applies to `value` and to every `overridden[].value`. A `$NAME` reference is shown as the
   reference text for non-secret keys and `<redacted>` for secret keys; the env var's resolved value is never read.

Report shape (also the `--json` body, one object, keys in this order):

```json
{"key":"agent.max_concurrent_agents","project":"o/a","value":4,"layer":"L5","label":"runtime",
 "source":"session cap (aiur set max-agents)","capped_by":null,
 "overridden":[{"layer":"L3","label":"project","source":"/repo/.aiur/config","value":8}],
 "unavailable":[{"layer":"L4","reason":"intent_store_not_implemented"}],
 "observed_at":"2026-11-06T16:00:00Z","age_ms":0,"freshness":"live"}
```

`observed_at`, `age_ms`, `freshness` are emitted and **rendered** in the text output (AGENTS.md "computed ages"
rule); `freshness` is `live` for local reads and the remote envelope's value for a remote gateway.

Text output, one block:

```
agent.max_concurrent_agents = 4
  owner   L5 runtime   session cap (aiur set max-agents)
  overrode L3 project  /repo/.aiur/config = 8
  unavailable L4 shared intent (intent_store_not_implemented)
  as of 2026-11-06T16:00:00Z (age 0 ms, live)
```

### Alternatives rejected

- **Instrument the merge path** (record the source on each merged key). Rejected: touches ~142 files that read
  settings (`code-evidence.md` §4) or the hot `Config.settings/0` memo; a separate read-only loader changes nothing
  that runs in production.
- **Diff the merged result against each layer.** Rejected: cannot tell "set to the default" from "unset".

## Risks

- **Drift between the explainer and the real merge.** The explainer re-implements precedence. Mitigation: one test
  loads a fixture through the real `Workflow.load/1` and asserts `explain(key).value` equals
  `Aiur.Config.settings/0`'s value for five keys (one per layer L0, L1-cap, L3, L5, and a secret's redaction).
  Detect early: that test fails the moment someone adds a merge step.
- **Overrides file is per instance, not per project** (`Overrides.path/0`). In a multi-project gateway an L5 value
  would appear for every project. Mitigation: follow MPG-304/306 when they key overrides by project; until then the
  report states the override source file so the sharing is visible.
- **Secret leakage by key-list omission.** A new secret key not on `@secret_keys` prints. Mitigation: derive the list
  from the schema's secret fields plus the suffix rule and add a test that walks the schema for `api_key`/`token`/
  `secret`/`password` field names and asserts each redacts.
- **Remote use.** Over the remote selector, values from another machine are shown to the caller; the `:read` category
  grants this, so the redaction is the only guard. Keep redaction server-side (it is).
