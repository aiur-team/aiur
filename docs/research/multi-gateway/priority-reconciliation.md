# Give each writer its own priority slot

A small fleet of 2 to 10 machines should not reconcile shared priority state by asking "which write is newest". It should ask "whose write is this, and did they mean to override someone else". The recommended design stores every priority attribute (rank, override, pause) as a **per-item priority array with one slot per writer class** (human, Executor, scheduler, default), in the style of BACnet's 16-level array. The effective value is the highest non-empty slot. Each slot is a last-writer-wins (LWW) register ordered by a **hybrid logical clock (HLC) plus node ID**, with a small **version vector** beside it to detect real concurrent conflicts. Order is a **fractional-index sort key** in the slot, so a move is one register write. Changes travel as immutable operations that keep their original `(origin_node, hlc)` identity, so applying a remote change never mints a new one, and replay is a no-op. A human's dashboard edit survives every automatic adjustment because the scheduler writes only its own lower slot. An Executor beats a human pin only through an explicit, audited `force` with a reason, never through recency. Oscillation is removed by construction (one writer per slot, one lease-elected scheduler) and then damped with a tolerance band and an asymmetric stabilization window. The "focus one feature, never leave slots idle" goal maps onto the guaranteed-quota-plus-borrowing model of Kueue and YARN.

## Why recency alone fails this problem

The three requirements pull against plain LWW. "Deterministic and idempotent" favours LWW, because an LWW register converges and a re-delivered operation that is not newer has no effect ([Shapiro et al., RR-7506](https://hal.inria.fr/inria-00555588/document)). But "a human's edit is not undone by automatic adjustment" is a statement about **authority**, not time: a scheduler that recomputes rank every 15 seconds is always the newest writer, so under LWW it erases any human edit within one cycle. And LWW under clock skew favours whichever machine runs fast. Jepsen found that **"even one-second skews caused lost updates"** in Scylla ([Jepsen, Scylla 4.2-rc3](https://jepsen.io/analyses/scylla-4.2-rc3)), and an earlier Riak test saw LWW drop **30 to 70% of writes** under contention ([aphyr, Jepsen: Cassandra](https://aphyr.com/posts/294-jepsen-cassandra)). Those are high-contention tests; no source measured anomaly rates for a workload of a few edits per hour, so the real risk at this scale is probably small but not zero. The point that matters is qualitative: a pause flag silently cancelled by an agent with a fast clock is a safety failure, however rare.

Control systems that already solved "human beats automation" do not use timestamps for it. Kubernetes Server-Side Apply records a **field manager** for every field, and a write that changes a field another manager owns fails with a conflict unless the writer sets `force=true` ([Kubernetes SSA](https://kubernetes.io/docs/reference/using-api/server-side-apply/)). The Horizontal Pod Autoscaler documentation names the failure this design must avoid: if a manifest keeps `spec.replicas` while the autoscaler is active, every apply scales back and the result is **"thrashing or flapping behavior"**; the fix is to give the field one owner ([Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). The rest of this report therefore uses time only to order writes **within** one authority level, and uses ownership to order writes **between** levels.

## HLC plus node ID orders writes; version vectors reveal conflicts

### The clock

An HLC timestamp is a pair `(l, c)`. `l` is the largest physical time seen, and `c` is a counter that breaks ties inside one `l`. On a send or local event, `l := max(l_old, pt)` and `c` increments if `l` did not move, else resets to 0. On receive, `l := max(l_old, l_msg, pt)` with matching counter rules. Timestamps compare lexicographically ([Kulkarni et al., 2014](https://cse.buffalo.edu/tech-reports/2014-04.pdf)). The paper proves that happened-before implies a smaller timestamp, that `l` never falls below physical time, and that **`|l − pt| ≤ ε`**, the clock-sync uncertainty. In its AWS measurement, with a 9 ms average NTP offset, the worst `l − pt` was **107.9 ms**, and `c` stayed at 4 or less for over 99% of events ([Kulkarni et al.](https://cse.buffalo.edu/tech-reports/2014-04.pdf)). It fits in 64 bits and only reads the system clock. The paper itself notes that masking skew this way "makes it especially useful for last write wins (LWW) database systems."

Two `(l, c)` values from different nodes can be equal, so the total order needs a node-ID tiebreak: compare `(l, c, node_id)`. The Elixir `hlclock` package does exactly this ([hlclock README](https://preview.hex.pm/preview/hlclock/show/README.md)); the algorithm is about fifteen lines, so a hand-written TypeScript version for the dashboard is reasonable. One property is not in the paper and must be engineered: monotonicity across restarts. A node that restarts after a backward clock step and has not persisted its last `(l, c)` can issue lower timestamps than before. Mint from `max(wall_clock, persisted_l)` and persist `l` on every write.

### What the clock cannot tell you

An HLC gives a total order, but it cannot say whether two writes were **concurrent** or one was **newer**. Shapiro et al. state it directly: "To detect concurrency, a scalar timestamp ... is insufficient" ([RR-7506](https://hal.inria.fr/inria-00555588/document)). A version vector can, and with at most ten known machines it costs at most ten integers per record. Dotted version vectors refine this when one node proxies several clients, which a dashboard served by one daemon to several browsers does; a plain per-node vector there produces false concurrency ([Riak, Dotted Version Vectors](https://riak.com/posts/technical/vector-clocks-revisited-part-2-dotted-version-vectors/); [Preguiça et al., 2010](https://asc.di.fct.unl.pt/~nmp/pubs/tr-corr-2010.pdf)). The recommended use is diagnostic: LWW by HLC still picks the deterministic winner, but when the vectors show the losing write was concurrent rather than superseded, the system records a **conflict marker** that the dashboard can surface. That turns "two humans reordered the same feature offline" from a silent loss into a visible one.

### Bounding skew on consumer machines

The HLC paper bounds damage from bad clocks with a constant `∆` on `l − pt`, which "can be set to a constant factor of ε, and even on the order of seconds depending on the application semantics." A message that would push `l` too far past local time is ignored, logged and raised to the administrator ([Kulkarni et al.](https://cse.buffalo.edu/tech-reports/2014-04.pdf)). CockroachDB applies the same idea with a default **500 ms** maximum offset and self-terminates a node whose mean offset exceeds about 80% of it ([Netdata guide](https://www.netdata.cloud/guides/cockroachdb/cockroachdb-clock-synchronization-error-500ms/)). Consumer machines are looser than a datacenter: default Windows time sync targets only Kerberos-grade agreement ([Microsoft](https://learn.microsoft.com/en-us/windows-server/networking/windows-time-service/configuring-systems-for-high-accuracy)), and chrony may step the clock at startup and slews at up to one twelfth of a second per second by default ([chrony.conf](https://chrony-project.org/doc/4.6/chrony.conf.html)). A laptop resumed from sleep can be seconds or more off before it resyncs.

The recommended rule is to accept a remote change when `remote.l ≤ local_pt + ∆`, with **`∆` around 60 seconds**, and otherwise hold it in a **quarantine** that the dashboard shows. The 60-second figure is engineering judgement, not a measured value; no source measured post-resume laptop skew. Two details matter for determinism. Never **clamp** a future timestamp, because each node would clamp to a different value and the total order would diverge. And never **drop** the change permanently: a quarantined change is re-checked as local time advances and becomes acceptable once the clocks catch up, so convergence is delayed, not lost. Since every node applies the same rule against its own clock, a far-future change can be applied on one node and held on another for a short time; that window is bounded by `∆` and is visible.

## Per-field registers, with multi-value only where loss is unsafe

Treat each attribute as its own register: the rank key, the override, the pause flag, and (for a hierarchy) the parent. Concurrent edits to different fields then never conflict. Figma uses this per-property model, with the last value the server received winning, and says plainly that it "isn't using true CRDTs" ([Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Without a central server, the HLC order stands in for server arrival order.

LWW is acceptable for low-stakes fields once skew is bounded. For the pause flag and for overrides, the cost of silently losing a concurrent write is higher, and there are two sound choices. A **multi-value (MV) register** keeps every concurrent value as `(value, version_vector)` pairs and drops only values the other side has already seen ([Shapiro et al.](https://hal.inria.fr/inria-00555588/document)); the dashboard then asks a human to resolve the sibling. Or a **deterministic non-temporal bias** resolves concurrency without asking: "pause wins over unpause when concurrent", the add-wins idea behind `DeltaCrdt.AWLWWMap` in Elixir ([delta_crdt](https://hexdocs.pm/delta_crdt/0.3.1/DeltaCrdt.html)). The recommendation is the bias for pause (stopping work is the safe direction, and a human can always resume) and the slot model below for overrides, which already makes most of these conflicts impossible because humans and automation never write the same register.

## A fractional sort key makes "move" a single write

Priority order is a list, and lists are where naive replication breaks. Implementing a move as delete-then-insert duplicates the item under two concurrent moves: the two deletes collapse into one, but the two inserts each re-add it. Kleppmann's motivating example is precisely a to-do list "where the order may reflect the relative priority of tasks", reordered on a laptop and an offline phone ([Kleppmann, Moving Elements in List CRDTs](https://martin.kleppmann.com/papers/list-move-papoc20.pdf)). His fix is to give each element **one LWW register holding its position**, with "any deterministic method of picking the winner", or an MV register if losing a concurrent move is unacceptable.

The position should be a **fractional index**: a string key strictly between its neighbours. Figma stores each child's index as an arbitrary-precision fraction between 0 and 1, inserts at the average of the neighbours, and notes that reordering "only involves editing a single value" and that "normal usage patterns never generate prohibitively-large index lengths" ([Figma, ordered sequences](https://www.figma.com/blog/realtime-editing-of-ordered-sequences/)). The `rocicorp/fractional-indexing` library provides `generateKeyBetween(a, b)` in base-62, with byte-compatible ports to several languages; keys must be compared with plain byte order, not locale-aware comparison ([rocicorp/fractional-indexing](https://github.com/rocicorp/fractional-indexing/)). No Elixir port was found, so the daemon would need a small port checked against the JavaScript output. Two offline machines can generate the **same** key between the same neighbours, so sort by `(key, item_id)` to keep the order identical everywhere, and optionally add jitter at generation, which `jittered-fractional-indexing` does with 30 random bits ([README](https://unpkg.com/jittered-fractional-indexing@1.0.0/README.md)).

Sequence CRDTs built for text (RGA, Logoot, LSEQ) solve a harder problem than a list of tens to hundreds of items that move a few times an hour, and are not needed. The project, feature and ticket hierarchy is a tree, but with fixed depth a reparent cannot create a cycle, so a `parent` field in the same register is enough. Kleppmann et al.'s verified tree-move algorithm, which undoes and redoes logged operations around each insertion, is only needed for arbitrary-depth reparenting ([Kleppmann et al., move-op](https://martin.kleppmann.com/papers/move-op.pdf)).

## An immutable change identity stops the echo

"Applying a remote change never republishes it" is a property of the change log, not of the merge function. Use **op-based sync where each change carries a globally unique identity**: `change_id = (origin_node, hlc)`, plus `slot`, `author`, `field`, `value` and an optional `supersedes` reference. Remote apply writes the register directly with the remote HLC and origin; it never goes through the local edit path that would mint a new HLC. The outbound feed sends only changes whose `origin_node` is this node, or forwards remote changes byte-for-byte under their original ID; it never re-mints. A per-origin high-water mark (or a set of applied IDs) makes apply idempotent, and the LWW comparison already ignores older operations, so re-delivery is harmless ([Shapiro et al.](https://hal.inria.fr/inria-00555588/document)). Merging a received HLC into the local clock is required and is not republishing; only minting a new change ID is forbidden.

Prior art shows where this goes wrong in practice. Yjs marks each transaction with an origin so a listener can tell local edits from remote ones, but "it is up to the provider to set local and origin correctly", and at least one storage provider reported loaded data as local ([Yjs forum](https://discuss.yjs.dev/t/determining-whether-a-transaction-is-local/361)). The lesson is to make the origin a **field of the stored change**, not a property of the code path that delivered it, so a reload from disk cannot reclassify a remote change as local. Figma also discards incoming server changes that conflict with the client's own unacknowledged writes, which avoids flicker while a dashboard edit is in flight ([Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)); the dashboard should do the same for its optimistic edits.

Compaction follows from the known, small replica set. Keep the latest HLC seen from each peer; the minimum across peers is the **causally stable threshold**, and operations at or below it can be folded into state and discarded ([Kleppmann et al., move-op](https://martin.kleppmann.com/papers/move-op.pdf)). A laptop that stays offline for a week blocks that threshold, so pair it with a bounded retention window and a full-state resync for any peer that falls behind it. Elixir's `delta_crdt` shows a middle path between op and state sync, diffing keys with a Merkle map ([delta_crdt 0.5.5](https://preview.hex.pm/preview/delta_crdt/0.5.5)); it is a reasonable transport if its add-wins map semantics fit, but the slot model below needs custom resolution, so a small op log is simpler to reason about.

## A priority array lets the human win without fighting

### Slots instead of overwrites

BACnet's commandable properties carry a **16-level priority array**. The present value is the non-NULL entry at the highest level, and if all are NULL a relinquish default applies ([Chipkin](https://store.chipkin.com/articles/bacnet-what-is-a-bacnet-priority-array); [OPC/BACnet](https://reference.opcfoundation.org/specs/OPC-30030/3.2.1)). Manual operator override conventionally sits at level 8, above schedules and automation ([Johnson Controls Metasys](https://docs.johnsoncontrols.com/bas/r/Metasys/en-US/Controller-Tool-Help/15.0/Input-and-Output-Objects/Command-Priority-Levels)). Lower-priority writers keep writing their own slots and **never overwrite the operator's slot**; the operator releases by writing NULL, and control falls back to the next level ([Chipkin, why present value does not change](https://store.chipkin.com/articles/bacnet-why-doesn039t-the-present-value-change)). LaunchDarkly evaluates flags the same way, through an ordered source list in which "targets take priority over rules" ([LaunchDarkly](https://launchdarkly.com/docs/sdk/concepts/flag-evaluation-rules)).

Applied here, every item has four slots, highest first: **human** (dashboard), **executor** (a deliberate agent decision), **scheduler** (continuous automatic ranking), **default** (creation order or config). Each slot is an independent LWW register as described above. The scheduler can recompute its slot every cycle and never touches the human's, so the requirement "a human's dashboard edit is not undone by automatic adjustments" holds by construction, regardless of clocks. The same value means different things in different slots, which Kubernetes also needed: the autoscaler records a separate `ScaledToZero` condition so it can tell a zero it set from a human's deliberate zero, and a human zero puts the autoscaler into maintenance mode until a human changes it back ([Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). Slurm behaves alike: once a privileged user sets a job's priority, "it is fixed and the priority plugin will no longer modify it" until the job is held and released ([Slurm scontrol](https://slurm.schedmd.com/scontrol.html)).

### Expiry: release, event or timer

A human slot needs a lifetime. Slurm uses explicit release; thermostats offer holds of 2 or 4 hours, "until next scheduled activity", or indefinite ([ecobee hold guide](https://www.techsolutions.support.com/how-to/how-to-set-hold-action-duration-on-ecobee-thermostat-12337), a vendor-adjacent source). The recommended default is **hold until released or until the pinned item completes**, with an optional time-to-live chosen in the dashboard. Expiry must be deterministic across nodes, so store `expires_at` as an HLC value in the slot and evaluate it against the same HLC order, and record the release as an ordinary change from the node that observed it, so every peer drops the pin at the same logical point instead of at its own wall-clock moment.

### Deliberate supersession is explicit, not recent

The requirement "a later deliberate Executor change can still win" is met by **explicitness**. In SSA, a writer that wants a field another manager owns must set `force=true`, which moves ownership visibly to the forcing manager ([Kubernetes SSA](https://kubernetes.io/docs/reference/using-api/server-side-apply/)). Argo CD with server-side apply always forces, and so overrides other owners unless ignore rules exclude those fields ([Argo CD Sync Options](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/)); that is the anti-pattern for a system where the human must win. Here, an ordinary Executor write lands in the executor slot and has no effect while a human pin exists; the API returns a conflict so the Executor knows. To supersede, the Executor sends `force: true` with a mandatory `reason`. That change **clears the human slot** and writes the executor slot in one operation, carrying `supersedes = <human change_id>`, and the dashboard shows the takeover. The scheduler is never allowed to force. If the human pin and the force were concurrent (the version vector says neither saw the other), the force applies only to the pin it names in `supersedes`, so a human pin written after the force, or concurrently with it on another machine, survives. That one check is what keeps "deliberate Executor change wins" from turning back into "newest write wins". A rate limit on forces, for example one per item per hour, stops two Executors from thrashing through repeated takeovers; that limit is a design choice with no cited precedent.

Who may hold which slot is itself access-controlled, as Kubernetes restricts high PriorityClass values through ResourceQuota ([K8s priority and preemption](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/)). The human slot should be writable only from authenticated dashboard sessions, never from agent credentials.

## One writer per slot first, then damping

Slots stop the human and the scheduler fighting, but two scheduler instances on two machines can still fight inside the scheduler slot. Kubernetes fixes the autoscaler-versus-GitOps fight with a single owner per field, not with a timer ([Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). The same applies here: run the scheduler as a **single lease-elected writer** for the fleet, so the slot has one automated author at a time. Executors are deliberate actors rather than control loops, but several can exist, so the executor slot holds one entry per Executor and the effective executor value is the newest by HLC.

Damping then handles a single controller reacting to noisy inputs. The autoscaler documents the toolkit: a **10% tolerance** band below which changes are ignored, a **300-second stabilization window** for scale-down with none for scale-up, and rate policies that cap change per period, with the loop running every 15 seconds ([Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)). Nomad applies hysteresis to priority directly: a job preempts only jobs whose priority is **at least 10 lower**, which prevents cascading preemption among near-equal jobs ([Nomad preemption](https://developer.hashicorp.com/nomad/docs/concepts/scheduling/preemption)). For a priority queue, that becomes: the scheduler promotes immediately but does not demote an item it changed within a window of minutes; it does not reorder two items whose scores differ by less than a threshold; and it acts **at most once per intent version**. Argo CD encodes that last rule as "only attempt one synchronization per unique combination of commit SHA1 and application parameters" ([Argo CD automated sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)): if a human overrides the scheduler's decision, the scheduler does not reassert it until its inputs change. These tuning defaults come from large clusters; no source validates them for 2 to 10 machines, so treat the numbers as starting points to measure against.

## Focus with borrowing has direct scheduler precedent

"Focus one feature, but never leave a slot idle" is the guaranteed-share-plus-borrowing model every major batch scheduler uses. YARN's Capacity Scheduler gives each queue a guaranteed fraction, lets "free resources ... be allocated to any queue beyond its capacity", caps elasticity with `maximum-capacity`, and reclaims over-capacity containers by preemption when the owner needs them ([YARN Capacity Scheduler](https://hadoop.apache.org/docs/stable/hadoop-yarn/hadoop-yarn-site/CapacityScheduler.html)). Kueue gives each ClusterQueue a `nominalQuota`, lets queues in a cohort borrow idle quota up to a `borrowingLimit`, keeps a reserve with `lendingLimit`, and chooses with `reclaimWithinCohort` whether the owner preempts borrowers; in its example, a team with 9 CPU can use 21 when a neighbour is idle, or only 10 with `borrowingLimit: 1` ([Kueue ClusterQueue](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/)). Kubernetes `preemptionPolicy: Never` separates jumping the queue from evicting running work ([K8s priority and preemption](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/)), and Slurm's fair-share decays usage with a 7-day default half-life so heavy consumers drift down without starving forever ([Slurm multifactor](https://slurm.schedmd.com/priority_multifactor.html)).

Mapped onto agent slots: the focus feature holds a nominal quota of most slots, other features are borrowers with a per-feature borrowing limit, and reclaim is **wait, not preempt**, so running agents are never killed and the focus feature takes the next free slot. Idle slots always go to the next-ranked ready work, which is the never-idle property. A borrowing limit stops a side lane from filling the machine while the focus feature's ready work is briefly blocked by dependencies. A decay term is the counterweight that stops a permanent focus from starving everything else. Importantly, this allocation runs on the **effective** priority from the slot array, so a human pin changes allocation immediately and the scheduler's continuous re-ranking cannot undo it.

## Recommended rule set and alternatives

| # | Rule | Rationale |
|---|------|-----------|
| 1 | Every change is an immutable op `{change_id=(origin_node,hlc), item, field, slot, value, author, reason?, supersedes?, expires_at?}`. | Stable identity makes apply idempotent and echo-free. |
| 2 | Timestamps are HLC `(l, c)` with node-ID tiebreak; persist `l`; mint from `max(wall, persisted_l)`. | Total order consistent with causality; no regression after restarts. |
| 3 | Accept a remote op only if `l ≤ local_pt + ∆` (∆ about 60 s); otherwise quarantine, log and show it; never clamp. | Bounds skew damage without breaking determinism. |
| 4 | Remote apply writes registers with the remote identity; only `origin_node == self` ops are published as new; forwarding keeps the original ID. | Applying a remote change never republishes it. |
| 5 | Each item field (`rank_key`, `override`, `paused`, `parent`) has four slots: human > executor > scheduler > default. Effective value = highest non-empty slot. | Human edits cannot be undone by automation; writers never overwrite each other. |
| 6 | Within a slot, LWW by `(hlc, node_id)`; a per-record version vector flags concurrent losers as visible conflicts. | Deterministic winner, no silent loss. |
| 7 | `paused`: under concurrency, pause wins. | Stopping is the safe default. |
| 8 | Order = fractional-index key in the slot; sort by `(key, item_id)`; optional jitter. | Move is one write; equal keys sort the same everywhere. |
| 9 | Human slot lives until released or the item completes; optional TTL stored as HLC. | Explicit release, deterministic expiry. |
| 10 | Executor non-forced writes to a human-pinned field return a conflict. `force` requires `reason` and names `supersedes`; it clears only that pin; rate-limited. | A later deliberate Executor change can win, but only explicitly. |
| 11 | The scheduler never forces, runs as one lease-elected writer, and acts once per (intent version, inputs). | One automated writer per slot; no reassertion loops. |
| 12 | Scheduler damping: promote now, demote only after a window; ignore score gaps below a tolerance. | Prevents flapping on noisy inputs. |
| 13 | Capacity: focus feature has a nominal slot quota; others borrow idle slots up to a limit; reclaim by waiting; usage decays. | Focus without idle slots or starvation. |
| 14 | Compact below the causally stable threshold; full-state resync for peers beyond retention. | Bounded log with long-offline peers. |

| Decision | Recommended | Alternative | When to choose the alternative |
|----------|-------------|-------------|--------------------------------|
| Ordering clock | HLC + node ID | Lamport clock + node ID | Wall-clock meaning is never needed for TTLs or audit display. |
| Ordering clock | HLC + node ID | Single sequencer (server-assigned order, as Figma and the reverse-engineered Linear engine do) | One machine is always reachable; offline edits can wait to be sequenced ([reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine), secondary). |
| Concurrent writes in a slot | LWW + conflict marker | MV register shown on the dashboard | Several humans edit the same items often enough that silent picks would annoy them. |
| Pause conflicts | Pause wins | MV register | The cost of a wrong pause is higher than the cost of asking. |
| Human pin lifetime | Until released or done | Fixed TTL (thermostat style) | Operators forget pins and stale pins cause harm. |
| Executor supersession | Force + reason clears named pin | Executor writes a higher slot above human | Executors are trusted more than the dashboard; loses the human-first guarantee. |
| Scheduler writers | One lease-elected writer | Per-machine scheduler slots, merged by max or median | Lease infrastructure is unavailable; accept more churn. |
| Transport | Small op log | `delta_crdt` AWLWWMap | Slot semantics can be expressed as separate map keys and add-wins suffices. |

## What remains uncertain

Three numbers in the rule set are judgement, not measurement: the 60-second skew bound, the demotion window, and the force rate limit. No source measured clock jumps on consumer laptops after suspend, or LWW anomaly rates at a human editing rate. The scheduler damping constants come from large clusters. A first implementation should log quarantined changes, conflict markers and forced takeovers, and use those counts to tune the constants. The CockroachDB offset figures rest on a third-party guide rather than current official documentation, and the thermostat hold options rest on vendor-adjacent sources; neither changes the design, only the cited defaults.

## Conclusion

The core finding is that this problem splits cleanly into two orders that should never be confused: **authority order between writer classes** and **time order within one class**. Most reconciliation bugs in this space come from letting time decide authority, which hands control to the busiest writer or the fastest clock. Once the slot array settles authority, the remaining machinery is small and well understood: an HLC with a skew guard, per-field LWW registers with version-vector conflict flags, fractional keys, and an op log whose identity never changes in transit.

The less obvious implication is that "deliberate" must be a property of the message, not of the actor. The same Executor can make a routine write and a forced takeover, and only the second may beat a human; naming the pin it supersedes is what keeps a concurrent human edit from being swept away. Designing for that from the start is cheaper than retrofitting it, because the audit trail it produces (who forced, why, over which pin) is also the evidence needed to tune every judgement-based constant above.
