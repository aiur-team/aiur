# Pin identities, grant per direction, keep trust local

A small gateway fleet should separate three things that existing tools also keep apart: **transport identity** (who is on the other end), **admission** (an explicit operator decision to enrol that identity) and **authorization** (a per-direction grant table that each receiving gateway holds and enforces). Discovery, whether from the Tailscale peer list or an mDNS hint, only produces *candidates*. It never admits a peer and never grants a scope. The recommended design gives every gateway a self-generated Ed25519/TLS key whose SPKI SHA-256 is its gateway ID (the Syncthing model). Enrolment uses a k3s-style join string that carries the target's fingerprint and a one-time, short-TTL secret, so the joiner verifies the target before it sends anything. Each receiver keeps a deny-by-default table `peer_id → scopes` that starts empty or at `status:read`. On a shared tailnet, WireGuard plus LocalAPI `WhoIs` supplies the transport identity and makes app-layer mTLS redundant. Off the tailnet, a pinned self-signed certificate plus a per-peer bearer token does the same job. Self-elevation is blocked by structure, not by token cleverness. `trust:admin` is a tier that no remote principal can hold. Trust-bearing config sits outside `config:edit`. Executors are distinct principals from the human operator. A remote request can at most *propose* a trust change, which then waits for confirmation over a channel the Executor does not control. Capability-token formats (macaroons, Biscuit, UCAN) do prevent widening a held token, but they do not stop a holder from calling a grant endpoint. Biscuit and UCAN have no Elixir library. At 2-10 machines they cost more than they return.

## Discovery yields candidates; only a pin and an operator decision admit a peer

The two discovery channels differ sharply in what they prove. On a tailnet, every inbound connection maps through LocalAPI `WhoIs(remoteAddr)` to a `WhoIsResponse` whose `Node` and `UserProfile` "are never nil" on success, plus a `CapMap` of application capabilities ([apitype](https://pkg.go.dev/tailscale.com/client/tailscale/apitype); [local client](https://pkg.go.dev/tailscale.com/client/local)). An embedded `tsnet` node exposes the same thing: "Use the WhoIs method on the client returned by Server.LocalClient to identify who is making a request" ([tsnet](https://pkg.go.dev/tailscale.com/tsnet)). That is a strong, unforgeable identity, but it is still only identity. A node on the tailnet is not a node the operator has chosen to trust with control.

mDNS proves nothing at all. `.local.` names are "meaningful only on the link where they originate", any host may claim an unused name, and the conflict algorithm "assumes cooperating participants". **"A malicious host could masquerade as" another name** through an mDNS answer ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html)). Advertising also leaks presence: Syncthing notes that an eavesdropper "can deduce which machines are running Syncthing" from its LAN broadcasts ([Syncthing security](https://docs.syncthing.net/users/security.html)). A DNS-SD record such as `_aiur-gateway._tcp` can therefore carry an endpoint and a fingerprint *hint*, but the client must check that hint against an enrolled pin and must never take it from the record. Make LAN advertising opt-in. mDNS does not cross subnets or VPNs, so on a tailnet the tailnet peer list is the better source.

The admission rule follows from this. On a tailnet, a discovered node becomes an **enrolment candidate** only if its `WhoIs` `CapMap` holds a fleet-specific capability. Even then, the receiver records and pins the peer's stable node ID and gateway key at an explicit accept step. Syncthing's model is the right shape: a device ID is "a SHA-256 hash of the device certificate", and fingerprints are "compared to a preset list" on every connection ([Syncthing security](https://docs.syncthing.net/users/security.html)). Do **not** copy Syncthing's *introducer*. Its own docs say a manually removed device "will be automatically re-added as long as the introducer device is still marked as such", and introducer status passes down the chain ([Syncthing introducer](https://docs.syncthing.net/users/introducer.html)). That is the exact failure the requirement forbids: one gateway's knowledge silently grants trust on another.

### Use tagged nodes and a custom app capability on a tailnet

Gateways should join the tailnet as **tagged nodes** (for example `tag:gateway`). "Applying a tag to a device removes any user-based authentication", only tag owners or admins can apply tags, and a tagged device's identity is the union of its tags ([Tailscale tags](https://tailscale.com/kb/1068/tags)). Authorization should not rest on the tag string. Grant a custom capability under a domain the project controls instead, in the form the KB shows: `{"src":["tag:gateway"],"dst":["tag:gateway"],"app":{"<owned-domain>/cap/gateway":[{"role":["peer"]}]}}`. Names are `{domain}/{path}`, `tailscale.com` and `tailscale.io` are reserved, and apps read the values through LocalAPI or tsnet ([app capabilities](https://tailscale.com/kb/1537/grants-app-capabilities)). Removing the grant then disqualifies a node at once, with no daemon change.

Three Tailscale details constrain the build. First, **tagged nodes have key expiry disabled by default** ([tags](https://tailscale.com/kb/1068/tags)), so node-key expiry gives no revocation. Revocation must come from removing the node, the tag, or the grant, or from the gateway's own table. Second, if the daemon sits behind `tailscale serve` rather than tsnet, it must bind to localhost only. Serve strips and re-adds identity headers, but a direct caller "could trivially provide their own values for these HTTP headers". Serve also sends no identity headers for tagged sources, and app-capability headers only with `--accept-app-caps` ([Serve](https://tailscale.com/kb/1312/serve)). For gateway-to-gateway calls between tagged nodes, LocalAPI `WhoIs` is therefore the only reliable path, and the headers are not. Third, **never put the control API on Funnel**. `ListenFunnel` by default also listens on the tailnet, so connections "can come from either inside or outside your network" ([tsnet](https://pkg.go.dev/tailscale.com/tsnet)), and Funnel traffic "does not include identity headers" ([Serve](https://tailscale.com/kb/1312/serve)). If a public listener is ever needed, give it a separate `FunnelOnly` listener and treat every request on it as anonymous.

One point is unverified. The notes did not confirm that a peer's `CapMap` holds only capabilities whose `dst` is the *receiving* node. The KB implies it, but design tests should check it before relying on it for direction.

## Enrolment is a pinned, one-time join string, not a shared fleet secret

The surveyed systems show which bootstrap shapes fail. A k3s server token is effectively root: "Anyone with access to the server token essentially has full administrator access to the cluster". The agent token "does not expire", and `k3s token rotate` needs every node that joined with the old token to restart ([k3s tokens](https://docs.k3s.io/cli/token)). A Consul gossip key is one symmetric 32-byte secret for every member, and rotating it is a staged install → list → use → remove across a live cluster ([Consul gossip](https://developer.hashicorp.com/consul/docs/secure/encryption/gossip/enable)). **A fleet-wide shared secret makes every member an admin and turns rotation into a coordinated restart.** The gateway fleet should have none.

k3s does get one thing right, and the design should copy it. Its *secure* token is `K10` + the cluster CA hash + `::` + credentials, and this "enables the client to authenticate the identity of the cluster it is joining, before sending credentials". A short token without the hash "implicitly trusts the CA bundle presented by the server" and is open to MITM. Its bootstrap tokens expire, with a default TTL of 24 h ([k3s tokens](https://docs.k3s.io/cli/token)). Applied here, the target gateway B prints a join string of the form `aiur-join://<endpoint>#sha256=<B's SPKI pin>&t=<one-time secret>&exp=<ttl>`. The operator carries it to gateway A. A connects, checks B's certificate against the pin, and only then presents the secret together with its own public key. B burns the secret, records A's pin, and creates A's inbound grant row at the default posture. The exchange gives both sides each other's pins. It gives **only B** a grant table entry for A. The reverse direction needs its own join string or an explicit operator grant on A.

For interactive LAN pairing with no copy-paste channel, a short code over a PAKE is the alternative. SPAKE2 lets two parties "derive a strong shared key without disclosing the password", with MAC key confirmation over the transcript ([RFC 9382](https://www.rfc-editor.org/rfc/rfc9382.html)). It is not augmented, the RFC points to OPAQUE for that, and it was not selected in the CFRG competition, so it adds a cryptographic dependency for a convenience. A simpler fallback is trust on first use with the fingerprint compared by eye on both screens. Prefer the join string, and add PAKE only if users need it.

Nomad's ACL bootstrap supplies the model for the first operator credential. `nomad acl bootstrap` creates one management token, default-deny starts at once, and bootstrap "cannot be performed again unless the reset procedure is complete", which needs a reset file in the leader's data directory ([Nomad ACL bootstrap](https://developer.hashicorp.com/nomad/docs/secure/acl/bootstrap)). Each gateway should do the same: the first operator principal is created only from a local session (CLI on the host, Unix socket), and any reset needs filesystem access on that host.

| Bootstrap option | Verifies target before sending secret | Fleet-wide secret | Rotation cost | Fit for 2-10 gateways |
|---|---|---|---|---|
| Pinned one-time join string (recommended) | Yes, by SPKI pin | No | Per peer | Best default, works on any network |
| Tailscale grant + explicit accept | Yes, by WireGuard node key | No | Policy edit | Best on a shared tailnet |
| SPAKE2 pairing code | Yes, by key confirmation | No | Per peer | Optional LAN convenience |
| Shared cluster token or gossip key | Only if a hash is embedded | Yes | Restart every node | Reject |

## Pinned keys beat a private CA, and both beat SPIFFE at this scale

There are three credible ways to authenticate gateway-to-gateway TLS. **Pinned self-signed certificates** have no CA to protect. The identity is the certificate hash, as in Syncthing, revocation is deleting a pin, and rotation needs a "next pin" announced over the already-authenticated channel with an overlap window. The weakness is the same as Syncthing's: "Anyone who can access the Syncthing TLS keys and config file on your device can impersonate your device" ([Syncthing security](https://docs.syncthing.net/users/security.html)). Key files therefore need host-level protection and must stay out of agent-readable paths.

**A private CA with mTLS** follows Nomad. It uses a CA from `nomad tls ca create`, which "should be a _private_ CA and not a public one like Let's Encrypt". Certificates encode role and region instead of hostnames, `verify_server_hostname` stops other services signed by the same CA from posing as agents, `verify_https_client` requires client certificates on the HTTP API, and certificates reload on SIGHUP ([Nomad TLS](https://developer.hashicorp.com/nomad/docs/secure/traffic/tls)). Adding a node is easier. In exchange, revocation needs a CRL or short-lived certificates, and the CA key becomes the crown jewel. For under ten nodes, per-peer pins are simpler and fail more narrowly.

**SPIFFE/SPIRE** provides short-lived SVIDs, node and workload attestation, and a Workload API "for automatic rotation" ([SPIFFE overview](https://spiffe.io/docs/latest/spiffe-about/overview/)). That is a server-plus-agent system built for many workloads. Borrow only its naming, `spiffe://<trust-domain>/gateway/<id>` in a URI SAN, if a standard ID format is wanted. The operating cost estimate is judgment; SPIRE's deployment docs were not reviewed.

On a tailnet, WireGuard already authenticates both nodes, and `WhoIs` is the identity. Gateways there can speak plain HTTP over a `tsnet` `Listen`, or use `ListenTLS` for browser-facing names. App-layer mTLS adds nothing. Off the tailnet, the caller authenticates the server by pin. The receiver authenticates the caller either by client-certificate pin (mTLS) or by a **per-peer bearer token** sent over the pinned channel. The receiver stores only a hash of each token and accepts two tokens at once during rotation. The bearer form survives TLS-terminating proxies, which matters for the next section.

## Reachability off the tailnet moves TLS to an edge you must account for

Without a tailnet, at least one side of each peer pair needs a reachable listener: a public address, an inbound port forward, or an outbound tunnel. **Port forwarding exposes the control API to the internet**, so every route must require auth, and "discovered" must never fall back to "trusted". Cloudflare Tunnel avoids inbound ports: `cloudflared` makes outbound-only connections, and operators can "allow only these outbound connections and block all inbound traffic". But "Authenticated Origin Pulls has no effect on hostnames routed through Cloudflare Tunnel", and origin traffic is authenticated by the connector's credentials ([Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)). Funnel, the tailnet equivalent, is public, limited to ports 443, 8443 and 10000, needs MagicDNS and HTTPS certificates, and works only with `*.ts.net` names ([Funnel](https://tailscale.com/kb/1223/funnel)).

The consequence is the same for both edges. The edge terminates public TLS, so **a peer's client certificate does not reach the daemon end to end**, and the SPKI pin the caller checks is the edge's certificate, not the gateway's. Peer authentication behind an edge must therefore happen at the application layer. The minimum is the per-peer bearer token. A stronger option is a signed request, where the caller signs method, path, body digest, timestamp and request ID with its enrolled Ed25519 key, so that a compromised edge can relay but not forge. HTTP Message Signatures (RFC 9421) standardizes that shape, but it was not reviewed for this report. Cloudflare Access service tokens and edge-enforced mTLS could add a second layer, but neither was verified here, so the design should not depend on them. NAT traversal without a relay (UPnP, NAT-PMP, hole punching) was not researched.

| Path | Peer identity at the daemon | End-to-end TLS pin | Notes |
|---|---|---|---|
| Shared tailnet (tsnet) | `WhoIs` node + `CapMap` | Not needed (WireGuard) | Recommended where available |
| Direct, public address or port forward | Client-cert pin or bearer token | Yes | All routes authenticated, no anonymous surface |
| Outbound tunnel or Funnel | Bearer token or signed request only | No, the edge terminates TLS | Use request signing to survive a hostile edge |

## The browser dashboard must proxy peers through its own gateway

A dashboard served by one gateway that calls *other* gateways' APIs directly hits three walls: CORS, mixed content, and certificate trust. Browsers do not honour an application-level SPKI pin, so a peer reachable only by pinned self-signed certificate is unreachable from the page. Off-tailnet tunnels would also mean placing peer credentials in browser storage. The design therefore routes every cross-gateway action as **browser → own gateway → peer**. The local gateway authenticates the human with its existing dashboard auth, then calls the peer with its own peer credential and pin. Peer credentials never reach the browser. The receiving peer sees the call as coming from the origin gateway, acting for a named principal (`operator@A`).

Two consequences follow. First, the dashboard's own HTTPS must be a certificate the browser trusts. On a tailnet, `tsnet` `ListenTLS` with the node's certificate domain does this. Repeated certificate requests can hit Let's Encrypt rate limits ([Funnel](https://tailscale.com/kb/1223/funnel)), so cache them. Second, the proxy makes the local gateway a confused-deputy risk. It must forward the authenticated principal and must never upgrade it. A browser session belonging to an Executor-reachable account must arrive at the peer as an Executor principal, not as the operator.

## Receivers hold a deny-by-default table per direction, and trust administration is never remote

Every mature system surveyed has the same shape: an identity, policies keyed on it, and deny-by-default evaluation by the receiver. Tailscale grants define "which source devices (`src`) can access which destination devices (`dst`)" and carry app capabilities whose parameters are "opaque JSON objects" that the destination application enforces itself ([Tailscale grants](https://tailscale.com/kb/1324/grants)). That is the closest existing analogue to "A may do X to B". Nomad's ACLs add that "deny takes precedence when multiple policies are associated with a token" and split rules by surface ([Nomad ACL policies](https://developer.hashicorp.com/nomad/docs/secure/acl/policies)).

The recommended model is a table that each receiver holds locally: `(peer_id, principal_kind) → scopes [+ constraints] , expires_at`. The six scope tiers are `status:read`, `agents:message`, `agents:manage`, `tickets:edit`, `config:edit` and `trust:admin`. Constraints are optional, such as an agent name or a queue. A missing row means deny. A row on B about A says nothing about A's row about B. **Do not use wildcard scopes.** Kubernetes warns that wildcards also grant "all object types which are created in the future" ([RBAC good practices](https://kubernetes.io/docs/concepts/security/rbac-good-practices/)), so a later `workspace:delete` tier would arrive pre-granted. **Fail closed on unknown fields**, as OpenSSH does: "unknown critical options will cause the certificate to be refused" ([ssh-keygen](https://man.openbsd.org/ssh-keygen#CERTIFICATES)). An older gateway that meets a constraint it cannot parse must refuse the call, not ignore the constraint.

A local table is preferred over pushing policy into Tailscale app-capability values. Tailscale policy works only when every gateway is on the tailnet. It makes the tailnet admin console the authority, and it adds an external dependency. Use the tailnet grant only as the coarse gate ("is a fleet gateway"), and keep fine-grained scopes in each receiver's own table.

### Default posture for a new peer

A new peer gets nothing, or at most `status:read`, with an expiry such as 30 days unless renewed. This mirrors Tailscale's deny-by-default grants ([grants](https://tailscale.com/kb/1324/grants)) and OpenSSH's `clear` option, which drops default permissions so that only listed ones apply ([ssh-keygen](https://man.openbsd.org/ssh-keygen#CERTIFICATES)). Fly.io states the same principle for tokens: "Tokens with no caveats should not be honored" ([Fly.io](https://fly.io/blog/macaroons-escalated-quickly/)). Promotion up the tiers is an explicit operator action on the receiving host, and each step is audited. The pairing UX can stay symmetric for identity exchange. Authorization is always recorded per direction, so pairing never implies mutual write access.

### Five structural rules stop an Executor from elevating itself

Kubernetes shows how escalation hides in scopes that look harmless. `system:masters` "bypasses all RBAC rights checks", and the right to create workloads implicitly grants any service account's rights in that namespace ([RBAC good practices](https://kubernetes.io/docs/concepts/security/rbac-good-practices/)). The gateway equivalents are a config key that lists trusted peers, and an agent whose environment holds a credential. The design closes these routes with five rules, which are synthesis rather than any one source's prescription.

First, **`trust:admin` never appears in a row for a remote principal**. Trust changes are accepted only from a local operator session on the receiving host. Second, a remote request can at most **propose** a trust change. The receiver queues it, and it takes effect only after the human confirms over a channel the Executor does not control, such as a push approval, a TOTP, or a FIDO touch. OpenSSH's `verify-required` option is a precedent for requiring physical user verification on a credential ([ssh-keygen](https://man.openbsd.org/ssh-keygen#CERTIFICATES)). Third, any endpoint that issues grants checks `requested ⊆ caller_scopes ∖ {trust:admin}`, which is the Kubernetes no-escalation rule. The exact Kubernetes wording on the `escalate` and `bind` verbs was not retrieved, so treat that attribution as the general principle. Fourth, **Executors are distinct principals** (`executor@A`), never the operator's token (`operator@A`). The receiver can then deny `config:edit` and `trust:admin` by principal kind, and the audit log can tell the two apart. Fifth, **trust-bearing state lives outside `config:edit`**: peer lists, grant tables, pins and keys. Otherwise "edit config" becomes trust administration by another route.

A confirmation step is only as strong as its channel. If the Executor can read the TOTP seed, or can reach the approval UI with its own credential, the step is not a second factor. The approval secret must therefore live outside every agent-readable path and environment.

### Capability tokens solve a narrower problem than they appear to

Macaroons, Biscuit and UCAN all allow attenuation only. UCAN states that each delegation "MUST either directly restate or attenuate" ([UCAN spec](https://github.com/ucan-wg/spec)), and Fly.io notes that adding caveats "can only weaken a token" ([Fly.io](https://fly.io/blog/macaroons-escalated-quickly/)). But **attenuation stops a holder from widening a token, not from asking a grant endpoint for a wider one**. The self-elevation guarantee comes from the five rules above whatever the token format. The library picture for an Elixir and Node stack is also thin. Biscuit has Rust, WASM, Python and Haskell implementations at spec v3 ([biscuit README](https://github.com/eclipse-biscuit/biscuit)) and a Node WASM package at 0.6.0 ([npm](https://registry.npmjs.org/@biscuit-auth/biscuit-wasm)), but a Hex search found no Elixir package ([hex.pm](https://hex.pm/api/packages?search=biscuit)). The generic Elixir `macaroon` package was last updated in 2021 and needs libsodium ([hex.pm](https://hex.pm/packages/macaroon)). UCAN has Node libraries ([iso-ucan](https://registry.npmjs.org/iso-ucan)) and no Hex package. Fly.io's experience adds two warnings: "Anyone who can verify a Macaroon can also mint one", and "Pure restrictive caveats are an awkward way to express some roles" ([Fly.io](https://fly.io/blog/macaroons-escalated-quickly/)).

The right moment to revisit is when one gateway must hand another an *offline-delegable* slice of its rights, for example an Executor on A passing B a token to act on C with no round trip. Macaroons then fit "B decides what A may do to B" best, because B mints and verifies its own inbound tokens with its own key. Biscuit fits if the operator's public key must be the single root of trust.

## Short credentials, receiver-side deletes, idempotent writes and a daemon-owned audit log

**Revocation** at this scale is a row delete on the receiver. Because the receiver checks its own table on every call, revocation takes effect on the next request, and no distributed revocation list is needed. Set `revoked_at`, close live connections, and on a tailnet also remove the node from the capability grant. Token systems that do keep lists bound them with expiry. Biscuit says "All tokens should come with an expiration date, to prevent the revocation list from growing indefinitely" ([Biscuit revocation](https://www.biscuitsec.org/docs/guides/revocation/)), and Fly.io finds that "Revocation is rare, so just keeping a revocation list and invalidating caches wholesale seems fine" ([Fly.io](https://fly.io/blog/macaroons-escalated-quickly/)). No source compared revocation latency across systems.

**Rotation** follows the pattern every surveyed system uses: install the new credential, verify, switch, then remove the old one. Consul warns that "unused keys in the keyring are a potential security risk" ([Consul gossip](https://developer.hashicorp.com/consul/docs/secure/encryption/gossip/enable)). The peer requests a new token, or announces a next pin, over the authenticated channel. The receiver accepts both until the new one is first used or a TTL passes, then drops the old one. Because credentials are per peer, rotating one never forces a fleet restart. Join secrets are single-use with a TTL of hours, and grants expire unless renewed. Biscuit's guidance on refresh tokens adds a theft signal: reuse of a single-use token should revoke all of that client's tokens ([Biscuit revocation](https://www.biscuitsec.org/docs/guides/revocation/)). Apply the same rule to join secrets and rotation tokens.

**Replay and idempotency** share one field. Every write call carries a client timestamp, which the receiver accepts within ±N seconds, and a request ID, which the receiver remembers for longer than N seconds and uses as the idempotency key. The IETF Idempotency-Key draft (still a draft, revision 08) requires the key to be unique and not reused "with another request with a different request payload". It suggests a payload fingerprint and specifies 400 for a missing key, 422 for a reused key with a different payload, and 409 while the original is in flight ([IETF draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)). Stripe's production rules settle the edge cases. It saves the status and body once execution begins, so a 500 replays. It does not save validation failures or concurrency conflicts, so the client can retry them. It compares parameters to the original, and it prunes keys after 24 hours ([Stripe](https://docs.stripe.com/api/idempotent_requests)). Apply this to `agents:message` and every higher tier, but not to `status:read`. Over WireGuard or mTLS, network replay is already blocked, so the nonce mainly guards against application retries. Behind a TLS-terminating edge it is the replay defence.

**Audit** is one record per remote call, written by the daemon to a path that no agent can write. The record holds receiver, origin gateway ID, actor principal and kind, credential ID, scope exercised, target, request ID, outcome (allowed, denied with reason, or replayed) and timestamp. OpenSSH sets the precedent of logging the certificate key ID on each authentication, which ties every record to a specific credential ([ssh-keygen](https://man.openbsd.org/ssh-keygen#CERTIFICATES)). **Log denials as carefully as successes.** A denied `trust:admin` or out-of-scope call from an Executor principal is exactly the self-elevation attempt the design exists to catch, and it should raise an operator alert, not only a log line.

## Recommended design and the alternatives it rejects

| Concern | Recommendation | Alternative and when to choose it |
|---|---|---|
| Identity | Self-generated key; gateway ID = SPKI SHA-256; tailnet node ID also pinned on a tailnet | Private CA with role SANs once the fleet outgrows hand pinning |
| Discovery | Tailnet peers carrying `<owned-domain>/cap/gateway`; opt-in DNS-SD hints on a LAN; manual endpoint anywhere | None. Never auto-admit, never introducer chains |
| Admission | Explicit operator accept, via a one-time pinned join string with TTL | SPAKE2 code or eyeball fingerprint for interactive LAN pairing |
| Transport auth | Tailnet: WireGuard + `WhoIs`. Direct: pinned TLS + per-peer hashed bearer token or client-cert pin | Signed requests (Ed25519) when a TLS-terminating edge sits in the path |
| Authorization | Receiver-local, deny-by-default `(peer, principal_kind) → scopes` table, per direction, with expiry, no wildcards, fail closed | Tailscale app-capability values as policy, only if every gateway is always on one tailnet |
| Self-elevation | `trust:admin` local-only; remote proposals need out-of-band human confirmation; no-escalation check; Executor ≠ operator principal; trust state outside `config:edit` | Biscuit or macaroons, only when offline delegation is needed, and still with these rules |
| Dashboard | Browser → own gateway → peer; peer credentials stay server-side; forward the principal, never upgrade it | Direct browser calls only with publicly trusted certificates and CORS, which is not recommended |
| Revocation | Delete or mark the row; close connections; remove the tailnet grant | Revocation list keyed by token ID, if tokens become offline-delegable |
| Rotation | Per-peer overlap window, single-use join secrets, expiring grants, reuse treated as theft | CA-issued short-lived certificates if a CA is adopted |
| Replay and idempotency | Timestamp window + request ID used as Idempotency-Key, with Stripe-style storage semantics for 24 h | RFC 9421 message signatures binding both fields |
| Audit | Daemon-owned record per call, including denials, alerting on denied trust or out-of-scope attempts | None. This one is not optional |

## Conclusion

The question of how gateways should trust each other turns out to be mostly about *where authority lives*, not about cryptography. Every primitive the design needs (pinned keys, one-time join strings, receiver-side grant rows, idempotency keys) is ordinary and already proven in Syncthing, k3s, Nomad, Stripe and Tailscale. The failures the surveyed systems document come from authority leaking to places it should not reach: a shared token that makes every node an admin, an introducer that re-adds removed peers, a wildcard that pre-grants future verbs, a config scope that quietly edits the trust list. Making each receiver the sole authority over its own inbound grants, and putting trust administration beyond the reach of any network credential, removes those leak paths. That makes an Executor's credential safe to issue, even though it cannot be made safe to trust.

The main open risks are verification gaps, not design gaps. Before implementation, confirm that a peer's Tailscale `CapMap` reflects only grants whose `dst` is the receiving node. Settle whether request signing (RFC 9421) is required or optional for tunnel-fronted peers. Decide which out-of-band confirmation channel the operator actually has, because rule two is only as strong as that channel.
