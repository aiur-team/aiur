# MPG-206 — Grant, revoke and inspect peer permissions on the receiving gateway: research

Research spike MPG-206R (#7589). Contract: MPG-206 in `docs/plans/2026-11-06-multi-project-gateways/tickets-m2.md`
(plan PR #7579). Schema: S2 in `state-schemas.md`. Decisions already made by Kevin and not reopened: 34, 34a, 34b, 34c
(read-only default; only the target gateway grants write; grants live in the receiver's registry file; no remote writer).

## Outcome

On a receiving gateway (B), a human can run `aiur gateway permissions [<peer>]`, `gateway grant <peer> <categories>`,
`gateway revoke <peer> [<categories>]` and `gateway trust <peer> --full`. They edit the `allows` block of B's own
`~/.aiur/remote-instances.yaml` entry for that peer. `read` is written at once. Any write category, and `trust --full`,
is written only after a human signed in with Google or a passkey on B's dashboard confirms a pending Decision. Calls
arriving over `/api/v1/control` with a peer-bound token are allowed only when the peer's `allows.categories` and the
token's `categories` both contain the call's category. No remote call can change a grant.

## Design

### D1. Registry module (`Aiur.Gateway.Registry`)
- `get/0` returns `{:ok, %{peers: %{gateway_id => peer}}} | {:error, reason}`; cached in `:persistent_term` keyed on
  the file's `{mtime, size, inode}`, the same pattern as `Aiur.Machine.Settings.get/0` (`src/lib/aiur/machine/settings.ex:31`).
  Hand edits apply on the next call, which is "applies on reload" with no daemon restart.
- A file that fails validation keeps the **last good** parsed value (the `fallback(load(), cached)` shape in
  `Settings`); the error is surfaced by `gateway permissions` and logged once per stat identity. With no last good value
  (first boot), every peer-bound call is refused (`grants_unavailable`, 403) and unbound tokens are unaffected.
- Validation (error names the key): reject keys `token`, `secret`, `password` anywhere under a peer; reject category
  `trust` and any category outside `read message executor agents tickets config`; reject duplicate `gateway_id`;
  reject `credentials` entries that are not client-token names; `categories` absent means `[read]`; `categories: []`
  means no access at all.
- `write/2` (`write(fun, actor)`) is the only writer: read file → apply `fun` → validate → write temp file mode 0600 in
  the same directory → `File.rename/2`, under a `:global.trans` lock so the CLI and the dashboard cannot interleave.
  It preserves keys it does not own (comments are lost; stated in the docs). It appends an audit line (D6).
- Keep the awk parser in `engine/remote.sh` and `packages/streamdeck/src/instances.ts` untouched: MPG-201 already makes
  them ignore `allows`. MPG-206 adds a launcher test that a file with `allows` parses identically.

### D2. Enforcement (`Aiur.Gateway.Grants.allowed?/3`)
`allowed?(peer_id, token_id, category) :: :ok | {:error, {:category_not_granted, category} | :unknown_peer | :grants_unavailable}`.
`control_controller.ex` calls it in `execute_expression/5` after the existing scope check and before `execute_call/5`,
only when `conn.assigns` carries a token `peer` (set by MPG-205's `ClientTokens.authenticate/1` extension). Grant check
order: token categories (MPG-205) → peer `allows.categories` → `token_id in allows.credentials` when that list is
non-empty. Refusal is 403 `category_not_granted: <category>` and writes an audit line with `peer`, `category`.
Tokens without a `peer` keep today's behaviour (scope only); MPG-205 owns that mapping.

### D3. Grant-changing calls are local only
- CLI: `gateway grant|revoke|trust` are not added to `Aiur.ControlCall.Allowlist` at all, so the remote parser returns
  `unknown_on_build`. To make the refusal explicit and audited, add one deny entry list in
  `src/lib/aiur/control_call/allowlist.ex`: `@grants_local [:gateway_grant, :gateway_revoke, :gateway_trust]` checked in
  `ControlCall.parse/2` when `remote: true`, returning `:grants_are_local`; `control_controller.ex` maps it to
  403 `grants_are_local` and audits it. This is the **[fails without]** case: a token whose peer holds every grantable
  category is still refused.
- Launcher: `aiur-gateway.sh` rejects grant verbs when `--gateway`/`--instance` selects a remote: exit 64,
  `grant changes are local to the receiving gateway`.
- Guard against a future allowlist entry reaching the writer: a test runs `mix xref graph --sink
  Aiur.Gateway.Registry` and fails if any module named in `Allowlist` (transitively) calls `Registry.write/2`.

### D4. Decision kind for pending grants
- New kind `gateway_grant`, `authority: :human_required`, `reversibility: :reversible` (a grant can be revoked). Add it to
  `Aiur.DecisionCommandType` `@classifications` (`src/lib/aiur/decision_command_type.ex`) so authority/reversibility are
  data, not request defaults. `:human_required` already excludes the Executor and supervisor (`DecisionAuthority.evaluate/2`
  returns `:human_required`), so an Executor or supervising agent cannot answer it through delegation.
- Options (structured, recommendation first): `approve` ("Grant <categories> to <peer label>"), `deny`. Question text
  names the peer label, gateway id (first 8 chars), categories, and the consequence ("<peer> will be able to <verbs>
  on this gateway until you revoke").
- Request is raised by `Aiur.Gateway.Cli.grant/1` through the in-process decision store
  (`Aiur.DecisionStore` request path used by `Aiur.Commands`), with `idempotency_key = "gateway_grant:<peer_id>:<sorted categories>"`
  so repeating the command returns the same pending Decision rather than a second one.
- The Decision payload carries `gateway_id` of **this** gateway and a `request_digest = sha256(peer_id|categories|this_gateway_id)`.
  Confirmation re-derives the digest from the current file state and refuses a mismatch (`stale_grant`), which also
  covers "a Decision raised on another gateway cannot be confirmed here": a Decision store is per gateway, and a
  digest from another gateway id never matches.
- A pending grant is **not** stored in the registry file. Pending state is the open Decision; the file changes only on
  approve. (Alternative rejected: a `pending:` key in the file. It makes a hand edit ambiguous and S2 would need a
  second state.)
- Expiry: none for MVP. A pending Decision uses the store's standard Command expiry; an expired Decision writes nothing.
  An approved grant has no end date (`expires_at` is not in S2; adding it later is an optional key).

### D5. How the dashboard session proves a human
Facts from the code (read, not assumed):
- Google and passkey sign-in both set `:google_authenticated_at` / `:passkey_authenticated_at` and `:google_email` in the
  signed session (`dashboard_auth_controller.ex:60-62,113-114`). Basic Auth sets only the `financial_data_access` marker, so
  a Basic Auth session has neither timestamp. A client token sets no session at all.
- The generic dashboard answer path passes `actor: DecisionCommands.actor()` with `actor_source: :dashboard_session`
  (`decision_answer_commands.ex:79`) for every signed-in dashboard session, Basic Auth included, and
  `ActorSource` documents that "source never grants authority". So `actor_source` cannot be the proof.
- Other write paths can answer Decisions as an operator: the allowlisted `operator_relay_answer`
  (`allowlist.ex:115`, flagged "gap" in code-evidence), `Commands.HostApi.answer/4` (`actor: %{kind: :operator}`), and the
  Stream Deck answer path. Each would satisfy a naive "actor.kind == :operator" check.

Decision: **`gateway_grant` Decisions are answerable only through a dedicated confirmation function,
`Aiur.Gateway.GrantConfirmation.confirm/3`, and every generic answer path refuses that kind.**
1. `Aiur.Commands.Answering.submit/4` (the single funnel behind dashboard, relay, host API, Stream Deck and executor
   CLI) returns `{:error, :grant_requires_session_confirmation}` for a Decision of kind `gateway_grant`. This is one
   guard in one place, so a new answer surface cannot bypass it.
2. The LiveView event handler for the grant card (`AiurWeb.OperatorControlCenter.GatewayGrantCommands`, new, called from the
   existing decision card) reads the session via `Plug.Conn.get_session` equivalent in the LiveView mount (the session map
   is already passed to LiveView), requires **either** `google_authenticated_at` or `passkey_authenticated_at` to be an
   integer within the last 900 seconds (`@fresh_seconds 900`), and `FinancialDataAccess.authorize/1` to still pass
   (current auth generation). It then calls `GrantConfirmation.confirm(decision_id, answer, proof)` where `proof` is
   `%{method: :google | :passkey, subject: email_or_credential_id, authenticated_at: integer}`.
3. `confirm/3` re-checks freshness against `System.system_time(:second)` (so the proof is verified in core code, not
   trusted from the web layer), re-derives the digest (D4), calls the internal answer function with a private option
   `grant_confirmation: proof` that `Answering.submit/4` accepts only for this kind, then on `approve` calls
   `Registry.write/2`. Registry write failure leaves the Decision answered but reports `write_failed` in the card and
   audit; re-running `gateway grant` raises a new Decision (new digest generation via `reason: retry`).
4. Basic Auth-only sessions see the card read-only with the text "Sign in with Google or a passkey to confirm". When
   neither Google nor passkeys are configured, write grants cannot be confirmed at all; the CLI prints the exact
   hand-edit alternative (a hand edit is valid, decision 34c). This is deliberate: the file owner can always edit it.
5. Fresh-session window 900 s: balance of "human is at the screen" against making someone log in again to approve two
   categories in a row. Open question Q1 records the default.

### D6. Audit
`Aiur.ControlCall.Audit.append/1` (`src/lib/aiur/control_call/audit.ex`) already writes `control-audit.ndjson` under the
daemon log root, outside agent workspaces. Add S5 fields (`actor`, `category`, `peer`) and these event names:
`grant_requested`, `grant_confirmed` (with `method`, `subject`), `grant_denied`, `grant_written`, `grant_revoked`,
`token_revoked`, `grants_are_local_refused`, `category_not_granted_refused`. Each names the **actor kind**: `cli_local`,
`dashboard_google`, `dashboard_passkey`, `file_edit_detected` (emitted by `Registry` when the stat identity changes and the
diff of `allows` is non-empty, `actor: unknown_local_editor`).

### D7. Revocation also revokes tokens
- `gateway revoke <peer> <categories>`: removes just those categories from `allows.categories` (a reduction needs no
  Decision). Tokens stay; they now hit D2 and are refused for the removed categories.
- `gateway revoke <peer>` (no categories): sets `categories: []` **and** revokes every client token whose `peer` equals
  the peer's gateway id plus every name in `allows.credentials`, via `Aiur.ClientTokens.revoke/1`
  (`client_tokens.ex:36`), then clears `credentials`. Token revocation deletes the hashed record, so it takes effect on
  the next request. A revoke in which the registry write succeeds but token deletion fails reports exit 1 with the
  unrevoked token names; the peer is already blocked by D2, so the failure is fail-closed.
- `revoke` of an unknown peer: exit 66 `no such peer`. Nothing is written.
- `Aiur.ClientTokens` needs `list_for_peer/1` (returns names for a gateway id) because `list/0` returns only
  name/scope/created_at; this depends on MPG-205 adding `peer` to the record.

### D8. `gateway trust <peer> --full`
Equivalent to `grant <peer> read,message,executor,agents,tickets,config`. One Decision with consequence text listing all
six. "Full" never includes `trust`, and `--full` rejects a `trust` argument. Mutual trust is one command per side (Q5).

### D9. `gateway permissions [<peer>]`
Read-only, local. Without a peer: table of `name, label, gateway_id (8), categories, credentials count, pending`.
With a peer: the same plus last 5 audit lines for that peer and any open `gateway_grant` Decision id. `--json` emits
`observed_at`, `age_ms`, `freshness` as the AGENTS.md age rule requires (the file's mtime is the observation time).

### Alternatives considered
- Grants in a separate `grants.yaml`: rejected by decision 34c.
- Dashboard confirmation by Basic Auth: rejected; a script holding the machine password could self-grant.
- Putting the proof in the Decision answer's `actor`: rejected, `actor_source` is attribution only and the relay paths
  can forge `kind: :operator`.
- Expiring grants: deferred (no S2 key); revoke covers the need.
- Macaroon/Biscuit attenuation: out of scope; see Prior art.

## Prior art

No new external research was run; the prior-art report answers it. `docs/research/multi-gateway/gateway-enrollment-and-permissions.md`
and `notes/gateway-enrollment/permissions.md` (PR #7579) cover capability tokens: Fly.io's lesson that "revocation is
rare, so keeping a revocation list and invalidating caches wholesale seems fine" supports D7 (delete the hashed token
record, no distributed revocation). The same report finds no maintained Elixir Biscuit/UCAN library and a receiver-mints
macaroon model that matches "B decides what A may do to B"; the plan chose a file-based grant table instead, which this
design keeps. Claims taken from those reports are theirs; the code facts in D5 were read from this repository.

| Write is pending | `gateway grant nook agents`; peer calls `pause` | CLI prints Decision id; file unchanged; `pause` 403 |
| Approve via Google session | confirm with session `google_authenticated_at = now-60` | file `categories: [read, agents]`; `pause` succeeds; audit `grant_confirmed method=google` |
| Approve via passkey | same with `passkey_authenticated_at` | same, `method=passkey` |

| Basic Auth session | no google/passkey timestamp | `{:error, :human_session_required}`; file unchanged |
| Client token answers | `operator_relay_answer`, `HostApi.answer`, Stream Deck, executor CLI each with the grant Decision id | each `:grant_requires_session_confirmation`; file unchanged |
| Supervisor/Executor delegation | `DecisionAuthority.evaluate` on the kind | `allowed: false`, `reasons: [:human_required, ...]` |
| Foreign gateway | Decision payload `gateway_id` differs from this gateway, or digest mismatch | `:stale_grant`; file unchanged |
| Deny | answer `deny` | file unchanged; audit `grant_denied` |
| Trust full | confirm `trust nook --full` | categories exactly `read message executor agents tickets config`; no `trust` |

| Bad file: trust | `categories: [read, trust]` | rejected naming `trust`; last good kept |

## Risks
- A new answer surface added later bypasses D5. Mitigation: the guard sits in `Answering.submit/4`, the single funnel; a
  test enumerates `actor_source` values and the answer entry points.
- Comments in the YAML file are lost on write. Mitigation: documented; file is machine-edited by design.
- `control_controller.ex` and `answering.ex` size limits (500 lines). Check before editing; add logic only in new modules.
- MPG-205 not merged: D2/D7 depend on the token fields. Fallback: blocked-by link already exists (MPG-205).
- Session timestamps are in the signed cookie and could outlive a sign-out; mitigated by `FinancialDataAccess.authorize/1`
  and the 900 s window. A server-side session store would be stronger but is out of scope.

## Open questions
| Question | Recommended default | What changes if answered differently |
|---|---|---|
| Freshness window for the signed-in proof | 900 s | A shorter window adds re-login friction; a longer one widens a stolen-cookie window. One constant. |
| Should Basic Auth ever confirm when Google/passkeys are not configured? | No; print the hand-edit instructions | Yes would let the machine password self-grant; a single `if` in `GrantConfirmation`. |
| Does `revoke <peer>` with no categories also delete the entry? | No; keep entry with `categories: []` so identity pinning stays | Delete loses the pin and the peer reverts to unknown. |
| Grant expiry | None for MVP (Kevin's default) | Adds an optional `allows.expires_at` and a check in `Grants.allowed?/3`. |
| Hand-edit audit attribution | Log `file_edit_detected` with unknown editor | Without it, hand edits grant silently. |
| New component file name | `components/gateway-trust.json` | Rename only. |
| Amend the MPG-206 file list to include Decision, session, audit, token, component files | Yes | Without it the implementer misses D4-D6. |
