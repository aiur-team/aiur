# MP-E8 Continuous build history: operator decisions

The operator, Kevin, settled these during the MP-E8 brainstorm on 2026-10-06.

| ID | Decision |
|---|---|
| E8-D1 | **Epic model:** a fixed list of general epics plus short-lived epics for each feature. Every ticket belongs to exactly one epic. While the operator scrolls, epic columns appear and hide based on the tickets in view. |
| E8-D2 | **Feature tagging:** tickets can be tagged with a feature name. A feature is a package of tickets plus the part of the DAG that built it, and it can grow over time (for example, 50 tickets becomes 60 within a build of 100). The feature filter highlights the feature's tickets with the existing grey-out/focus UI. A compact mode pulls them into a shorter vertical span without the unrelated tickets. |
| E8-D3 | **Time axis:** past tickets are ordered by real time, and planned tickets are ordered by the MP-E1 queue order. Below them is a separate section of open tickets that are not queued. |
| E8-D4 | **Gantt mode:** an extra view where tickets expand and map to time on the Y axis, like [gantt-reference.webp](gantt-reference.webp): <ul><li>columns are epic lanes, and a day/time axis runs on the left;</li><li>each card's height is its duration from start to end;</li><li>each card shows its start and end time, an estimate badge (hours) and points;</li><li>dependency arrows run between cards.</li></ul> |
| E8-D5 | **Units merge:** the build view shows which tickets have active agents. The Units page's columns move into the ticket/agent modal. Filters for ticket type, agent type and other fields use the existing grey-out/focus UI. |
| E8-D7 | **Gantt planned section:** Gantt mode is most pronounced in the historic view, where real start and end times set card height. Planned tickets get an *anticipated* height and duration, taken by default from their complexity points. The Executor's planning agent can override the default height or duration for a ticket when it has a strong reason. An override is recorded with its reason and who made it, and the planned card is drawn so it is never mistaken for real history. |
| E8-D8 | **Home page:** the continuous build page becomes `/`. On load, a sticky "now" band keeps every active agent in view. The Units nav item is retired. Its columns move into the ticket/agent modal, which gets a shareable `?ticket=` URL. The Stream Deck and the MP-N3 meta-dashboard counts are unchanged. |
| E8-D9 | **General epics.** The aiur default general epics are **Bugs, Design, Infra, Docs**. A project overrides them through aiur config (a default-epics key, per repository). The aiur skills (aiur-build, aiur-run, aiur-agent and the planner prompts) **strongly encourage** planning agents to give every ticket a category, overriding the defaults where a feature needs its own epics. Retroactive categorisation must be easy for an agent: a single CLI or tool call, with batch support, that sets or changes a ticket's epic or category and records who made the change and when. |
| E8-D10 | **History backfill.** An agent classifies past tickets into epics and features. It runs as a slow, budget-capped background job near the end of the MP-E8 build or after it, never during it. It reads from the one-time census, which is about 30 GraphQL points, and records results locally with the source `backfill-agent`. Any GitHub label writes are optional. If they happen, they are paced inside an explicit hourly API ceiling that stays well below the agent core budget, and they can be paused and resumed. A ticket ships the measured cost before it runs, per AGENTS.md "A claimed saving must be measured". |
| E8-D11 | **Feature membership.** Each ticket has at most one owning feature. The owning feature sets the ticket's feature-epic column and counts the ticket toward its progress. A ticket can also carry optional "also affects" links to other features. In those features' focus views it shows outlined, not filled, and it never counts toward their progress, so totals are never counted twice. |
| E8-D12 | **Agent indicators on ticket cards** make agent state clear in the build view. <ul><li>A **circular model logo** sits in the corner of any ticket that has an agent, showing the agent's model or harness.</li><li>**Active:** a gentle background glow that slowly rotates.</li><li>**Stuck:** a red glow and shadow. Covers error, retry-exhausted, and blocked on a human Command.</li><li>**Paused or parked:** a grey, static glow. Nothing animates.</li></ul> Animations respect `prefers-reduced-motion` with a static equivalent. The colours come from aiur-style tokens. State is never shown by colour alone: the logo carries a state glyph or label for accessibility. Exact visuals are part of DESIGN-E8 (Claude Design). |
| E8-D13 | **Epic columns.** All columns are dynamic, general and feature alike, and the columns follow the tickets on screen. Zooming changes which tickets are visible, so it changes the columns too: zooming out shows more epics, zooming in shows fewer. **Focusing on a feature locks its epic columns:** the feature's epics, and the general epics its tickets use, stay fixed while you scroll. Clearing the feature focus returns the columns to viewport-driven. Kevin accepts that general columns move as you scroll. The design must keep transitions smooth (debounce, animate width, keep a stable relative order), and DESIGN-E8 owns the motion details. |
| E8-D14 | **Sequencing.** MP-E1 ships first and is CLI-only: its C8 read-only dashboard view is folded into MP-E8, and no throwaway panel is built. MP-E8 follows in **wave 0b**, before the refactor and on a seam, like E1. MP-E8 becomes the build queue's dashboard view, and the refactor moves it rather than rewriting it. |
| E8-R1 | *Recommended, confirmed in DESIGN-E8:* past tickets include all closed tickets, with `not_planned` closures collapsed by a default filter (PQ-5). Feature headers show the complexity-weighted completion figure, labelled "weighted" (PQ-7). The MP-R1-C10 public planned-features list keeps its own store, with an optional link to the feature registry (PQ-8). |
| E8-D6 | **Gate:** implementation is blocked on a Claude Design owner task (DESIGN-E8). |

## Questions the Gantt mode raises (for research and for the owner)

- **What "start" and "end" mean for a past ticket.** Options are first dispatch or the first `agent:in-progress` label for start, and PR merge or issue close for end. Paused time and rework rounds either show as gaps inside the bar or are folded into it.
- **How planned tickets get times.** The proposal: project them from a duration estimate (the historical median by complexity or model, or an explicit estimate) and simulate the queue against agent capacity, so the future part of the chart becomes a forecast. The open question is whether a forecast is wanted at all, or whether planned tickets stay unscaled in queue order.
- **Where points and estimates come from.** Today there are only `complexity:N` labels, so points would map from complexity unless a new estimate field is added.
- **How the time scale handles idle spans.** Nights and idle days can collapse into compressed gap markers, as in compact mode.
