## Identity and outcome

- Bucket 2, feature MP-E8 (continuous build history), chunk C11 (ticket modal
  and agent chat).
- **User value.** When an agent waits on a Command, the operator answers it in
  the ticket modal, next to the conversation that asked it, with one click. The
  operator does not leave the page for `/commands`. The answer goes through the
  same durable path as the Commands page, so it is versioned, idempotent and
  attributed.
- **Deliverable.**
  1. The `#bd-cmd.cv-cmd` card in the conversation foot (J:1406): the question,
     one button per option, and the `recommended` badge on the recommended
     option.
  2. A server read: the open Command of the modal's ticket, loaded from
     DecisionStore through `DecisionCommands` (PROPOSED
     `DecisionCommands.ticket_command/1` and `DecisionCommands.command_detail/1`).
  3. The answer write: the card's button calls
     `DecisionCommands.record_answer/4` with `%{"choice" => "option:<id>"}`.
     BuildLive sets the `selected_decision`, `selected_decision_id` and
     `decision_actions` assigns that function needs. The version check, the
     idempotency key and the error copy are reused, not rewritten.
  4. The success path of the design (J:1501–1506) without its optimism: the card
     is removed and an `Answered: <option>` `cv-op` row is appended **after** the
     server accepts the answer.
  5. Settled, failed, read-only and unavailable states (EC-15, EC-12, EC-08).
  6. Live refresh: an answer recorded elsewhere (Commands page, CLI, another tab,
     the Executor) settles the open card within one Decision signal or one
     10-second tick.
- **Non-goals.**
  - No custom response, rationale, defer or dismiss. The design card has only
    option buttons. The Commands page keeps those actions.
  - No resume logic. The orchestrator resumes a self-paused worker when the
    correlated answer arrives (#2738); the card never resumes the agent.
  - No agent-state or typing change on the client. Those come only from the
    server diff (C8-T01) and the C11-T05 typing indicator.
  - No `cmd` event row ("Asked a blocking question", J:1336). That is C11-T04.
  - No MP-E2 authority or supersede rules. That is C14-T04.
  - No delivery status on the card. The Commands page shows delivery and retry.

## Chosen design

### Server: one read, one write, one refresh

**Read.** PROPOSED `DecisionCommands.ticket_command(identifier)` and
`DecisionCommands.command_detail(decision_id)`:

```elixir
@spec ticket_command(String.t()) :: {:open, map()} | :none | {:unavailable, atom()}
def ticket_command(identifier) when is_binary(identifier) and identifier != "" do
  params = %{"ticket" => identifier, "lifecycle" => "open", "limit" => 100}

  case DecisionProvider.list(params, decision_store: decision_store()) do
    {:ok, %{decisions: [_ | _] = rows}} -> {:open, pick(rows)}
    {:ok, %{partial_results?: true} = page} -> {:unavailable, page.partial_reason || :partial}
    {:ok, %{pagination: %{next_cursor: c}}} when is_binary(c) -> {:unavailable, :page_truncated}
    {:ok, _complete_empty_page} -> :none
    {:error, _reason} -> {:unavailable, :invalid_query}
  end
end

@spec command_detail(String.t()) :: {:ok, map()} | {:unavailable, atom()}
def command_detail(decision_id) do
  case DecisionProvider.detail(decision_id, decision_store: decision_store()) do
    {:ok, %{decision: row}} -> {:ok, row}
    {:error, :not_found} -> {:unavailable, :not_found}
    {:error, {:indeterminate, _}} -> {:unavailable, :indeterminate}
    {:error, _} -> {:unavailable, :store_unavailable}
  end
end
```

- The store already matches the ticket exactly (`query_plan.ex:73, 88`) and
  `lifecycle: "open"` returns only `:open | :deferred` rows (`query_plan.ex:67`),
  so no client-side filter is added. Settled Commands of the same ticket can no
  longer push an open one off the page.
- `pick/1`: the rows sorted blocking first, then oldest `created_at`, then
  `decision_id`; the first one.
- An empty page counts as `:none` only when it is complete:
  `partial_results?: false` and `pagination.next_cursor: nil`. **A partial or
  unreadable page is never `:none`.**
- `limit: 100` is the maximum (`params.ex:8`). More than 100 open Commands on one
  ticket returns a non-empty page, so `pick/1` still finds an answerable one; the
  "blocking, oldest" order is then exact only within those 100 (recorded in
  Decisions, item 2).
- **Race view.** When a card is already showing decision X and X is not in the
  open read, `CommandCard` calls `command_detail(X)`: a settled X becomes the
  `settled` card; `{:unavailable, _}` becomes the `unavailable` card. When the
  open read returns another open Command, that one replaces X's card (the
  operator gets X's outcome through the click reply when they clicked; see N1).
  A newly opened modal never shows a settled card.

**State in BuildLive.** C11-T01 pushes `open-ticket` on every modal open (the
reply carries the row only when it was not loaded), and C11-T03's open hook
fires on every open. The card load hangs off the point where C11-T03 pins the
open conversation on the server (its first view: Server flow steps 1–2, `conversation-page` with
`before: nil`). There, for a ticket whose section is not `hist`, and on every
reload, BuildLive calls PROPOSED `AiurWeb.Build.CommandCard.load(socket,
identifier)`, which:

1. calls `DecisionCommands.ticket_command/1` (and `command_detail/1` for the race
   view above);
2. for `{:open, row}` assigns `selected_decision: row`,
   `selected_decision_id: row.decision_id`;
   for anything else assigns `selected_decision: nil` and keeps
   `selected_decision_id` as the shown card's decision id (so a settled race is
   shown for the right decision); after an `accepted` reply it sets
   `selected_decision_id: nil`, so the following refresh does not push a settled
   card for an answer the operator just gave;
3. builds the card payload (below), stores it in the `command_card` assign, and
   pushes `push_event(socket, "modal:command", card)`. Only `load/2` and
   `refresh/1` push; `reload/1` (inside a click) stores without pushing, and the
   reply carries the card.

`decision_actions: %{}`, `selected_decision: nil`, `selected_decision_id: nil`
and `command_card: nil` are initialised in BuildLive `mount/3` and reset on
C11-T03's `conversation-close`.

**Card payload** (server → hook, JSON):

```text
nil                                              # no card (state :none, or a hist ticket)
| { state: "open",
    decision_id, version,
    question,                                    # untrusted text
    options: [{ id, label, title, recommended }],# label/title untrusted; title = description or null
    writable: true | false,
    disabled_reason: null | "Read-only dashboard" }
| { state: "settled", decision_id,
    kind: "answered" | "expired" | "dismissed" | "moot",
    option_id: null | id,                        # the winning option, for "answered"
    text: "Answered: Keep process-local · dashboard",   # built on the server, no time
    at_ms: null | integer }                      # answer.accepted_at; the client appends " · HH:MM"
| { state: "unavailable", decision_id: null | id, text, href: "/commands" }
```

`unavailable` text: "This agent is waiting on a Command this page cannot load."
when the agent state is `command` and no card was showing; "This Command cannot
be loaded right now. Its outcome is not confirmed." when a card for
`decision_id` was showing and its read failed.

- `recommended` is `option.id == row.recommendation.option_id`. With
  `recommendation: nil`, no option is recommended.
- The option order is the stored order. The design's fixture has the
  recommended option first; the product does not reorder.
- Settled text (server-built without a time; the client formats local time from
  `at_ms` with the design's `fmtT` and appends ` · HH:MM`):
  - `decided | acknowledged | resolved` with `answer.selected_option_id` →
    `Answered: <option label>`, then ` · <actor id>` when the actor is known.
    Unknown actor or `at_ms: null`: that part is left out, never filled. An
    option id with no matching label (option removed in a later version) →
    `Answered: option <id>`.
  - with `answer.custom_response` → `Answered with a custom response · <actor>`.
    The response text is not repeated on the card (it may be long; `/commands`
    shows it).
  - `expired` → `This Command expired.`
  - `dismissed` → `Closed without an answer.`
  - `moot` → `No longer needed.`
- The `unavailable` state is sent when the agent state in the payload is
  `command` and the read is `{:unavailable, _}` **or** `:none`. A `command`
  agent with no loadable Command is a disagreement between two sources. The card
  says so; it never hides, and it never shows an empty card.
  When the agent state is not `command`, no card was showing and the read is
  `{:unavailable, _}`, no card is shown (nothing says a Command exists). When a
  card **was** showing, an unavailable read always gives the `unavailable` card
  for that `decision_id`, whatever the agent state: a Command is known to exist
  and its outcome is unknown, so the card must not vanish.
- When the read is `{:open, row}` the card is shown even if the agent state in the
  payload is not yet `command`. The store is the authority; the agent state diff
  follows.
- Past tickets (`hist`) never load a card: the design's foot is `.cv-end`.

**Write.** BuildLive PROPOSED handler:

```elixir
def handle_event("answer-decision", %{"decision_id" => id, "answer" => %{"choice" => "option:" <> _} = form}, socket) do
  if socket.assigns.writable and dashboard_writable?() do
    socket = DecisionCommands.record_answer(socket, id, form, &CommandCard.reload/1)
    {:reply, CommandCard.reply(socket, id), socket}
  else
    {:reply, %{status: "error", message: "This dashboard is read-only."}, assign(socket, :writable, false)}
  end
end

def handle_event("answer-decision", _params, socket),
  do: {:reply, %{status: "error", message: "The submitted answer was incomplete. Try again."}, socket}
```

- `form` is passed through unchanged; `record_answer/4` `normalize_form/1` keeps
  only its four keys, so a forged `custom_response` cannot sneak through: the
  card's clause matches only `"option:" <> _`.
- `CommandCard.reload/1` re-runs the read for the modal's ticket (it re-reads the
  store after the write, as `/commands` does) and updates the assigns, but does
  **not** push `modal:command`: the clicking client gets the new card in the
  reply, so a push and a reply never race in the hook. The `command_card`
  assign keeps the payload and the row it was built from.
- `CommandCard.reply/2` reads `socket.assigns.decision_actions[id]` and adds
  `card: <the reloaded payload>` to every reply:
  - `:notice` present → `%{status: "accepted", text: "Answered: <label>", at_ms: <answer.accepted_at or null>, action_id: <answer.action_id>}`,
    read from the reloaded (settled) row. A `:duplicate` store result would
    also be `accepted`, but it is not reachable from the card: after a success
    the reload makes `selected_decision` settled, so a second submission takes
    the `:error` branch of `record_answer/4` (`:29`) before any key is used.
  - `:error` present and the reloaded card is `settled` →
    `%{status: "settled", message: <command_error text>}`; the hook then renders
    the settled card it received in the same round trip.
  - `:error` present and the card is still `open` →
    `%{status: "error", message: <command_error text>}`.
  - `:error` present and the card is `unavailable` →
    `%{status: "error", message: <command_error text>}`; the reply's
    `unavailable` card then replaces the card (its text says the outcome is not
    confirmed).
- The reply uses LiveView's `{:reply, map, socket}` and the hook's
  `pushEvent(event, payload, onReply)` (LiveView `1.1.33`, `mix.lock`).

**Refresh.** C3-T01's BuildLive clauses for `{:decision_changed, _, _}` and
`:awaiting_commands_tick` also call `CommandCard.refresh/1`: when a modal is open
on a non-`hist` ticket, it re-runs `load/2` and pushes `modal:command` only if the
payload changed (compare with the `command_card` assign). So a missed
broadcast leaves the card wrong for at most 10 s. No new subscription and no new
timer.

### Invariants

- The card never changes `t.agent.state`, never unhides `#cv-typing` and never
  starts a stream (the J:1502, 1505 lines are not ported).
- The `cv-op` row appears only after `accepted`.
- Every value on the card comes from the store read in the same server process
  that will validate the answer. The client sends only a decision id and an
  option id.
- Idempotency keys behave exactly as on `/commands`: `ensure_action_key/2` makes
  one per attempt; `put_error/3` drops it, so a retry after an error is a new
  attempt; after a success the decision is settled and no further answer is sent.

**Security and privacy.** The card shows the question, option labels and
descriptions, the answer's actor id and time. `/commands` shows the same data
under the same dashboard auth. The actor is trusted runtime identity
(`DecisionCommands.actor/0`); the client cannot set it. The client can name any
decision id, but `record_answer/4` answers only the `selected_decision` that
BuildLive loaded for the open ticket. Every write re-checks
`dashboard_writable?()` on the server (EC-12).

**Resume.** An accepted answer is delivered as a correlated message. If the
worker paused itself on the Command, `self_pause_ends_on_input?/3` resumes it,
unless a global pause or a tracker pause label holds it. A parked agent
(`:usage_limit_exhausted`, #2742) is not an input pause, so it stays parked. The
card shows no resume claim; the agent state changes only by diff.

## Decisions made without the owner

1. **Read through `DecisionProvider.list/2` with `ticket` and `lifecycle: "open"`,**
   not `open_blocking_decision_ids/3`. C8-T01 shows `command` for any open
   Command, blocking or not, so the card must find non-blocking ones too. The
   store's ticket match is already exact, so no second filter is added.
2. **One card at a time:** blocking first, then oldest. The next one appears after
   the first is answered. The design shows one card; no "1 of N" counter is added.
   With more than 100 open Commands on one ticket the order is exact only within
   the 100 the page returns; any of them is answerable.
3. **No custom response, rationale, defer or dismiss on the card.** The design
   has option buttons only. A Command with no options links to `/commands`.
4. **The store decides whether a card shows,** not the agent state. A `command`
   agent with no loadable Command shows an explicit "cannot load" card, never
   nothing; a card that was showing never disappears because a read failed
   (AGENTS.md: unknown is never a plausible default).
5. **Settled cards keep the question and disable the buttons,** and mark the
   winner with the design's own `.rec` badge reading `answered`. The state line
   uses the `.cv-end` type with `--muted` / `--block-ink`, the "muted/bad tones"
   S-7 names; `--muted` instead of `--faint` for contrast.
6. **Unknown actor or time is left out** of the settled text and the `cv-op`
   `time`, never filled with "now".
7. **No reordering of options;** the recommended one gets `btn sm`, the others
   `btn secondary sm`; with no recommendation all are secondary, so the card does
   not suggest an answer the agent did not recommend.
8. **Option descriptions go in `title`** (no pixels), so the information the
   Commands page shows is still reachable on enabled buttons. The read-only reason
   is also visible text, because a disabled `.btn` shows no tooltip.
9. **Refresh reuses the existing decision signal and the 10 s AwaitingCommands
   tick;** no new subscription or timer.
10. **The 60 s store call blocks the LiveView process,** as it does on
    `/commands`. Making it async is out of scope; a change there belongs to the
    Commands page owner.
11. **`clear_stale_action_state/2` is not moved or reused.** In BuildLive an
    idempotency key survives only after a success (`put_error/3` drops it on
    every error), and after a success the decision is settled, so no stale key
    can be sent. Moving the helper would change `dashboard_live.ex` for no
    behaviour in this ticket (smallest correct change).
12. **When another open Command exists, it replaces a card settled elsewhere,**
    instead of showing the settled card first. A waiting agent's next question
    matters more than the outcome of one already answered; the outcome is still
    in the conversation and on `/commands`.
