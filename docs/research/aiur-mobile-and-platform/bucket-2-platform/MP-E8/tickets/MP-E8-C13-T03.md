## 4. Chosen design (Part A)

### 4.1 What "confirmed" means

`confirmed: false` means exactly one thing: **the value came from the
backfill agent and no operator has accepted it.** Every other source
(`cli:<who>`, `agent:<ticket>`, `label:…`, `import:…`) is `confirmed: true`
when written, as C5-T03 and C6-T01 already decide. Confirming does not change
the stored epic, the feature or the feature epic. It records who accepted the
guess and when, and it changes the value's `source` to `cli:<who>`.

Two effects follow from neighbour rules, not from new code here:

- **Column.** Under C13-T04 G-5/G-6, an unconfirmed override loses to a label
  match and a confirmed one wins. So for a ticket that has an unconfirmed
  `infra` override and a `bug` label, a confirm moves the card from Bugs to
  Infra. A ticket with no label match, or one owned by a feature (C5-T02
  step 1 decides first), does not move.
- **Protection.** After a confirm the source is no longer `backfill-agent`, so
  C13-T04 G-1/G-3 keep any later backfill write off it (`:kept_existing`).

### 4.2 Epic confirm — no new journal op

PROPOSED `Aiur.BuildOrder.EpicOverrides.confirm/3`:

```elixir
@spec confirm([pos_integer()], %{actor: String.t(), source: String.t()}, keyword()) ::
        {:ok, %{generation: non_neg_integer(), results: [result()]}} | {:error, term()}
# opts: :expect_epic (String.t() | nil), :server, :now
# result :: %{number: n, status: :changed | :unchanged, epic: key, previous: Override.t()}
#   (same result shape as C5-T03 set/4 plus `epic`; consumers must not assume
#   only two statuses, C5-T03 §4.3)
```

Inside one `GenServer.call` (so it is atomic with every other write, EC-13):

1. Refuse unless the store is healthy (C5-T03 §4.4 table; same refusals, for
   example `{:error, :epic_overrides_unavailable}` on a corrupt file and
   `{:error, :epic_overrides_not_running}` when the store is down).
2. Dedupe ids. More than 200 → `{:error, {:too_many_ids, 200}}`.
3. Read the catalog the same way C5-T03 `set/4` does (`settings_fun.()`,
   `settings.build_order.epics |> Enum.map(& &1.key)`). A config error →
   `{:error, :epic_config_unavailable}`, nothing written; never fall back to
   the default four keys (C5-T03 §4.2).
4. For every id, check, and collect all failures before writing anything:
   - no current override → `{:no_override, n}`;
   - override epic not in the catalog → `{:not_a_configured_epic, n, key}`;
   - `expect_epic` given and different from the current epic →
     `{:epic_changed, n, current_epic}`.
   Any failure → `{:error, {:confirm_refused, failures}}`, nothing written.
5. Already `confirmed: true` → `:unchanged`, no entry.
6. Otherwise append a normal **`set`** entry with the **same epic**,
   `actor` and `source` = the confirmer (`cli:<who>`), `confirmed: true`.
   The previous `backfill-agent` entry stays in the journal, so the guess and
   its acceptance are both on record. Write, ETS update and broadcast follow
   C5-T03's write path (`Fs.atomic_write/3` with fsync, then state, then the
   `build-order-epic-overrides:changed` message).

**Why a `set` entry and not a new `confirm` op.** C5-T03 §4.1 says a loader
that sees an unknown `op` treats the whole file as a newer version and refuses
it. A new op would make a rollback to a release before this ticket lose every
override (store unavailable) after the first confirm. A `set` entry is already
valid for every release that has the store. C5-T03 V-7 already defines "same
epic, new source" as a journaled change that sets `confirmed: true`, so the
fold needs no change. (Interface mismatch with C5-T03 §4.1 and §11, which
expect a `confirm` op; §10 decision 1.)

The journal entry is the same one `aiur epic set <same-epic> <id>` would
write. What `confirm` adds is the refusals: it never creates an override
(`no_override`), it never changes an epic, and `--epic` makes it refuse a
value that changed since the operator read it.

### 4.3 Feature confirm

PROPOSED `Aiur.BuildOrder.Features.confirm/3`:

```elixir
@spec confirm(String.t(), [pos_integer()], meta()) :: result()
# meta and result are C6-T01's types (§4.4): meta = [source:, actor:, …];
# result = {:ok, %{generation, changed, slugs, pairs}} | {:error, reason}
```

Inside the store's one writer (the same `GenServer.call` path, 60 s timeout,
validate-then-append, as every C6-T01 write):

1. Store not usable → the same error every C6-T01 write returns (for example
   `:features_not_running`, `:features_corrupt`); nothing appended.
2. More than 1,000 numbers → `{:error, :batch_too_large}` (C6-T01 limit; the
   CLI already caps at 200).
3. Unknown slug → `{:error, {:unknown_feature, slug}}`.
4. Every id must be owned by `slug` → else `{:error, {:not_member, [n]}}`
   (same atom as C6-T01 `remove/3`). The whole batch is refused.
5. Owner already `confirmed: true` → unchanged (not in `changed`).
6. Otherwise one journal record, with the confirmer's `source`/`actor`
   (`cli:<who>`), and one `member.added` event per id carrying the owner's
   **current** `epic` and `confirmed: true`. C6-T01's update rule keeps
   `joined_at` and `at_basis`, so a confirm never makes a ticket look "added
   after the baseline" (C6-T05 scope figures stay the same). The owner's
   `source` becomes `cli:<who>`, so C13-T04 G-3 then keeps a later backfill
   write off it, and C13-T02 sees a non-backfill owner.
7. A confirm writes no label and does not start C6-T02 projection (a
   `confirmed` change is not a membership change; C6-T02's `:held_backfill`
   state for a backfill join is left for C13-T02 to release).

`confirm` is done in the store, not as `add(slug, ids, confirmed: true)` from
the CLI. `add/3` defaults `epic` to the feature's first epic
(`MP-E8-C6-T01.md` §4.4), so a CLI that forgot to pass the current epic would
silently move the ticket to another feature epic; and a CLI read-then-write
races the backfill agent.

### 4.4 CLI

```text
aiur epic confirm <ids…> [--epic <key>] [--as <who>] [--json]
aiur epic show [<ids…>] [--unconfirmed] [--json]          # --unconfirmed is new
aiur feature confirm <slug> <ids…> [--as <who>] [--json]
aiur feature show [<slug>] [--unconfirmed] [--json]       # --unconfirmed is new
```

- **Engine.** `cmd_epic` (C5-T03) gains the `confirm` verb and the
  `--unconfirmed` flag; `cmd_feature` (C6-T04) gains `confirm` and
  `--unconfirmed`. Same validation as their siblings: ids
  `^#?[1-9][0-9]{0,9}$`, 1..200, duplicates collapsed; `--epic` must match
  C5-T03's key shape `^[a-z0-9][a-z0-9_-]{0,63}$`; `--as` and the empty-`$USER`
  rule as C5-T03 / C6-T04; `--unconfirmed` only on `show`; no `--source` on
  `confirm`; anything else is exit 64. Text values go through
  `encode_control_value` (`:2861`). RPCs:
  `Aiur.AgentControlCLI.epic([action: :confirm, ids: [...], expect_epic: …, who: …, json: …])`
  and `Aiur.AgentControlCLI.feature([op: :confirm, slug: …, ids: [...], who: …, json: …])`
  (each sibling's own keyword: C5-T03 uses `action:`, C6-T04 uses `op:`).
- **Actor.** Both verbs record `actor` and `source` `cli:<who>` (C5-T03 §4.2,
  C6-T04 "Source and actor"). There is no `--source` on `confirm`: a confirm is
  always a human CLI act.
- **Human output, `confirm`:**
  - `confirmed infra: #12 #14 (was backfill-agent), #13 unchanged (already confirmed)`
  - The output does not predict a column move (that needs the History labels
    and the resolver, which this CLI does not read). The column effect of
    §4.1 is stated in `cli.md` and in the review procedure (§4.5) instead.
  - refused: `aiur: epic confirm: refused, nothing written: #15 has no override; #16 is now design, not infra`
    on stderr, exit 1.
- **Human output, `show --unconfirmed`** (healthy store only):
  - one line per row, the C5-T03 / C6-T04 line format, with the literal token
    `unconfirmed` and the source `backfill-agent`;
  - `aiur feature show --unconfirmed` without a slug lists unconfirmed owner
    memberships across every feature, one line each
    (`#12  events-pagination  f-pag-api  backfill-agent  unconfirmed  <joined_at>`),
    not the per-feature summary that plain `show` prints;
  - a last line `N unconfirmed`. `0 unconfirmed` is printed **only** when the
    read was `{:ok, …}`.
  - Unavailable store: `aiur: epic show: epic overrides unavailable (<failure>)`
    (C5-T03 wording) or `feature registry unavailable`, exit 1. Never a count.
- **JSON.** `confirm` returns the C5-T03 / C6-T04 envelope with
  `"command": "epic confirm"` / `"feature confirm"` and per-id
  `{"number"|"id", "status"|"outcome": "confirmed"|"unchanged", "epic", "previous": {"source", "actor", "at"}}`.
  A refusal is `{"ok": false, "refused": [{"number": 15, "reason": "no_override"}, {"number": 16, "reason": "epic_changed", "current": "design"}]}`,
  exit 1. `show --unconfirmed --json` is the normal `show` JSON filtered to
  `confirmed == false`, plus `"unconfirmed_count"`; when unavailable it is
  `{"ok": false, "health": {…}}` with no count key at all.

### 4.5 Review procedure (goes in `cli.md`)

1. `aiur epic show --unconfirmed --json` and `aiur feature show --unconfirmed --json`.
2. Accept: `aiur epic confirm 12 14 --epic infra` (the `--epic` guard makes sure
   you accept what you read), `aiur feature confirm events-pagination 12 14`.
   An accepted epic now outranks the ticket's type labels: a ticket that showed
   in Bugs because of a `bug` label moves to the confirmed epic's column
   (C13-T04 G-5/G-6). A ticket owned by a feature does not move.
3. Reject: `aiur epic clear 13`, `aiur feature remove events-pagination 13`.
   A rejected ticket goes back to its label epic or Unsorted.
4. Re-run step 1 to see what is left.

### 4.6 Invariants

- A confirm never changes the stored `epic`, owning feature, feature epic or
  `joined_at`. It can change the resolved column of a labelled ticket (§4.1).
- A confirm on a batch is all or nothing.
- `confirmed` flips only `false → true` through this ticket, and does not go
  back: a later backfill write on a confirmed value is `:kept_existing`
  (C13-T04 G-1, G-3; the guard is in the store, so it holds for the CLI's
  `--source backfill-agent` too). A new guess is possible only after a reject
  (`clear` / `remove`).
- An unknown or unavailable store never shows as `0 unconfirmed`, `confirmed`
  or "no override".

## 10. Decisions made without the owner

1. **Confirm writes a `set` entry, not a new `confirm` op.** C5-T03 (§4.1,
   §11) expected a new op. A new op makes a rollback lose every override,
   because C5-T03's loader refuses unknown ops
   (`:epic_overrides_version_unsupported`). The `set` entry gives the same
   record (who, when, same epic) and the guess stays in the journal. The cost:
   a confirm cannot be told apart from an operator re-`set` of the same epic in
   the journal. Both mean "a human accepted this epic", so nothing reads the
   difference.
2. **Feature confirm is included.** The row names only `aiur epic confirm`, but
   C13-T04 also writes unconfirmed feature memberships, and C6-T04 defers
   "a confirm command for unconfirmed classifications" to this ticket. Without
   it a feature guess can never be accepted.
3. **`--epic` guard on `epic confirm`.** It costs one comparison and stops an
   operator from accepting a value the backfill agent changed after they read
   it (EC-13). It is optional so batch scripts can omit it.
4. **No reject verb, no confirm-all.** `clear` and `remove` already reject. A
   confirm-all would turn the review into a rubber stamp.
5. **"Also affects" links are not confirmed.** C6-T01 stores no `confirmed`
   flag on also-links, and they never count toward progress (E8-D11). The
   C13-T04 runbook should not write also-links (interface note below).
6. **`confirmed` means "not an unaccepted backfill guess".** It does not mean
   "a human approved it". Agent and label writes are confirmed when written
   (C5-T03, C6-T01 already decide this).
7. **Placement rules are not changed here.** C5-T02 §10 decision 8 kept
   `confirmed` out of the resolver, but C13-T04 (step 7, G-5/G-6) changes that:
   an unconfirmed override ranks below a label. This ticket takes that rule as
   given, so a confirm can move a labelled ticket (§4.1). It documents the
   effect instead of predicting it in the CLI output, because the CLI does not
   read History labels. If Kevin wants guesses kept out of columns entirely
   until confirmed, that is a resolver change in C5-T02, sized there.
9. **`feature show --unconfirmed` without a slug lists members, not
   features.** Plain `show` without a slug prints one line per feature
   (C6-T04); a review needs the unconfirmed tickets across all features, so the
   filter changes the listing to member lines.
10. **No CLI cap change for features.** The CLI keeps C6-T04's 200-id cap; the
    store refuses above its own 1,000 cap as every C6-T01 write does.
8. **Part B is not guessed.** The row says the design has nothing to default
   to; inventing a chip or an outline would be a design change without Kevin.
   §9 lists the elements a treatment would most likely reuse, as input to the
   S-8 answer only.
