### Two kinds of check

1. **Parity checks (product = design).** These are screenshots through
   `expectDesignParity`, motion through `runOn` + `compareRecords`, and geometry
   values read on both pages with the same `evaluate`. Any difference fails,
   unless the C1-T02 allowlist covers it.
2. **Absolute checks (the requirement itself).** They run on both pages:
   - no page scroll sideways;
   - the bottom nav does not cover the last control;
   - the age stays visible when offline;
   - a tap opens the modal.

   If the product fails and the design passes, it is a port bug: fix it. If
   both fail, it is a design gap: the test is `test.fail()` with the PS-item id
   in its title, and it is listed for C12-T08. The test then still fails when
   the design or the product starts to pass, so the marker cannot go stale.

### Geometry the spec asserts (on both pages, then equal)

- **Gutter.** In `#bd-sec-hist .bd-layer > .bd-card`, the minimum `left` is
  `46`, at `p390` and `p430`, in flow and in non-flow mode.
- **Right edge.** The maximum `left + width` is `≤ #bd-vp.clientWidth − 14`.
- **Flow.** `#bd-content` has class `flow` when the design has it. In flow:
  - `.bd-lane` count is 0;
  - `.bd-lane-g` text is "Colour = epic";
  - `#bd-edges` has class `hide`;
  - the distinct `left` values of history cards (rounded to 0.5 px) number
    `≤ K`, and `K` is computed on the design page from J:649 with the design's
    own `vp.clientWidth`.
- **Band.** The distinct `left` values of `#bd-now .bd-layer > .bd-card` equal
  the design's. Precondition: the dataset has at least 2 band items
  (`BL.length ≥ 2`), or `BK = min(BL.length, …)` (J:491) is 1 whatever the
  width rule says, and the check proves nothing. The spec fails with "band
  check needs ≥ 2 band items" when no dataset has them.
- **Precondition guard.** The fixture must reach the branch it tests. At each
  of `p390` and `p430`, at least one dataset puts the design in flow mode, and
  at least one does not. The spec finds these datasets at run time and fails
  with "no flow dataset at <cell>" when there is none. Estimate from J:646-648
  with the root widths above: `avail` ≈ 289 px at 390 and ≈ 330 px at 430
  (minus the `.bd-vp` border), so flow needs `nEst ≥ 5` distinct epics over
  `now ∪ plan` at 390 and `nEst ≥ 6` at 430. The spec reads the real values
  from the design page; the estimate only tells the implementer what to look
  for in the fixtures. The implementer records
  in the PR which datasets go into flow at each width. If no fixture reaches
  flow at 430 px, the row's "in flow mode" cannot be proven; the implementer
  stops and raises it (see Non-happy paths N3).

### Touch rules the spec asserts

- `locator.tap()` on a history card opens `#tk-backdrop.show`, and the modal
  shows that ticket's id.
- After the tap, with `?trees=1`, no element has `.hl` or `.hdim`, and
  `#bd-content` has no `.hovering`. This is C9-T11's touch filter (§7 there:
  `pointerover` plus a return on `pointerType === "touch"`), checked here at
  the page level. **Product only.** The design listens to `mouseover` (J:618)
  with no touch filter, and a mobile engine fires a compatibility `mouseover`
  on a tap, so the design page does show the chain after a tap. T2 does not
  compare with the design; it is C9-T11's intended deviation.
- **Scroll freeze (C:353).** A tap within 200 ms of the last scroll event does
  not open the modal on either page. A tap after 250 ms does. The design does
  this, so both pages must agree. Three rules keep this test honest:
  - **Tap by coordinates** (`page.touchscreen.tap(x, y)` at the card's centre),
    not `locator.tap()`. `locator.tap()` waits until the element can receive
    pointer events, so it would wait out the 200 ms freeze and then open the
    modal; the test would pass for the wrong reason.
  - **Use the C1-T03 fake clock** (`page.clock.install`, then
    `clock.runFor(100)` for the early tap and `clock.runFor(150)` more for the
    late one), not real sleeps.
  - **Use a scroll that does not start a snap:** the `snap.pinned` input
    (C1-T03: lower `scrollTop` by 1 px from the top pin, `y ≤ topY + 2`, J:597).
    Any larger scroll can make `snapLive` start a 420 ms glide at +200 ms,
    which sets `.scrolling` again, and the +250 ms tap would then miss on both
    pages.
- **Usage popover.** A tap on `.ax-ln` shows `.ax-pop.show` on both pages, as
  the design does (C10-T04). This is a parity check, not a new rule.

## Decisions made without the owner

1. **Proof only; gaps become PS-items.** The row says the design defines phone
   behaviour. So this ticket adds no breakpoint, `dvh`, `viewport-fit`,
   `(hover: hover)` guard or 44 px overlay. Each of these is a PS-item with
   "as designed" as its default.
2. **A 360 px structure-only cell is added.** DV-P6 asks for "the narrowest
   device width", and 360 px is a common Android CSS width. It runs only the
   absolute checks (no parity screenshots), to keep the CI cost small.
3. **WebKit is a manual run, not a CI gate.** CI installs only Chromium
   (`ci.yml:644`, `:747`), and Playwright WebKit on Linux is not iOS WKWebView.
   The manual run catches engine differences cheaply; the device check is the
   real proof.
4. **Engine proxies are allowed for the device check.** MP-E8 ships in wave 0b,
   probably before the MP-N1 app. iOS Safari and Android Chrome use the same
   engines as WKWebView and Android System WebView. The PR names what was used,
   and MP-N1's own DV-P6 run is still required.
5. **No sideways scroll is checked against the cell width, not `innerWidth`.**
   With `isMobile`, the browser can zoom out to fit content that is too wide,
   and then `innerWidth` grows with the content. The existing helper
   (`browser-helpers.mjs:26-29`) would then pass on a broken page. The spec uses
   its own one-line assert with the constant.
6. **The composer's dropped `font` declaration is kept.** It is a design bug
   (C:558). Fixing it would change the computed size and break parity, so it is
   S-45.2.
7. **The tests are named as regression guards** (`phone guard:`). The
   behaviour they guard ships in predecessor tickets, so the mutation names the
   predecessor's line, as AGENTS.md allows for guards.
8. **Complexity 3,** as in the row. The spec is mostly reuse of C1-T02 and
   C1-T03. The risk is the device findings, and those become PS-items, not
   work in this ticket.
9. **Product-only checks are labelled as such.** T2 (chain hover after a tap)
   and S10 (unknown values) cannot be compared with the design: the design
   has no touch filter and no unknown values. They assert fixed expected
   values on the product and are never counted as design parity (C1-T03's
   `productOnly` rule).
10. **The scroll-freeze test taps by coordinates under the fake clock.**
    `locator.tap()` waits for the card to accept pointer events, which hides
    the freeze. Real sleeps around a 200 ms window flake in CI.
