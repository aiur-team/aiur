## 4. Chosen design

### 4.1 Port the functions as they are

`features.js` copies J:1074–1090 and J:366–379 with mechanical edits only
(`setFeature`, J:1091–1096, is C10-T02's):

- `D`, `S`, `$`, `$$`, `esc`, `I`, `writeURL`, `relayout`, `setFeature` → reads
  from C9-T01's `ctx` and `fx`.
- `featStats(f.key)` → `D.features[k].stats` (C6-T05 §4.6). The client never
  recomputes a figure from loaded rows: they are a paged subset.
- Every `onclick` is registered through `ctx.life` (C9-T01), so it ends with the
  hook.
- Text goes through `esc`; `hue` is written as `+f.hue` (C3-T02 validates it as an

- A `f.epics` key with no `D.epics` entry is skipped, not dereferenced (the design
  throws at J:1086).

### 4.2 `activeFeature()`: one rule for "is a feature focused"

```js
export const activeFeature = () =>
  (S.feature && D && Object.hasOwn(D.features, S.feature) ? S.feature : null);
```

The design checks `D.features[S.feature]` in `renderFeatures` and `visibleCols`,
but not in `computeLayout` (J:366) or `decorate` (J:869). With a slug that does
not exist, compact mode then folds the whole board into gap markers and focus
mode greys every card. `Object.hasOwn`, not a truthiness read: C3-T03 accepts
any `[A-Za-z0-9._-]{1,64}` slug, so `?feature=constructor` or `toString` would
find `Object.prototype` members through `D.features[k]` and the header would
read `f.label` and `f.stats` of a function. `S.feature` keeps the URL value (a shared link stays the
same; C3-T03 shape-checks only), and every consumer reads `activeFeature()`:
`layoutExt`, `renderFeatures`, `cards.js` `decorate` (one line), `list.js` dim (one
line), and C9-T04's `visibleCols` (J:679, J:690), which this ticket switches from
the design's truthiness read to `activeFeature()` in its PR (one line). A feature that appears later through a diff becomes
active with no other code: C9-T01 `defaultDataChanged` re-renders the chrome and
relayouts when `set.features` arrives.

### 4.4 Figures: known, unknown, absent

### 4.5 Focus with no loaded tickets: `loadFeatureSpan(k)`

History is paged by day (C9-T03). In the design the browser holds all of history,
so a focused feature's members always exist for the lock columns (J:681) and for
the ghosts. In the product they may be older than `S.histFrom`.

This reuses C9-T03's `ensureFrom(ms, keep)` (`while (S.histFrom > ms && H.more &&
keep() && await loadEarlier())`), whose stop predicate is settled (Interface note 5):

```js
let spanRun = 0;
export function loadFeatureSpan(k) {
  const run = ++spanRun, f = activeFeature() === k ? D.features[k] : null;
  const to = f ? f.oldest : null;                              // ms | null (Interface note 2)
  if (to == null) return Promise.resolve();                    // nothing closed to load
  return ensureFrom(to, () => run === spanRun && activeFeature() === k);  // stop on clear or switch
}
```

`ensureFrom` checks `keep()` before each `loadEarlier()`; no local loop.

- Called from C10-T02's `setFeature(k)` (k not null; one line), from `hook.js`
  `firstPaint()` and `repaint()` (after a resync) when `activeFeature()` is set,
  and from `url.js` `onServerURL` when `feature` changed (back/forward). C9-T01
  has no `onFirstPaint` hook; these are direct one-line calls.
- It runs whenever the feature's oldest member is older than the loaded window,
  not only when no member is loaded: a partial window would give a partial lock
  set (C9-T04 N-12).
- Paint first: the header, the dims and the columns appear at once; the earlier
  days arrive above with C9-T03's scroll anchor, so the viewport does not move.
  Each page relayouts and re-applies the columns, so the lock set grows to the
  design's set and then stays fixed.
- `before` / `from` stay server values; no client day arithmetic (C9-T03).
- The loop is sequential, one bounded server call per day, and stops on clear,
  switch, `more: false`, an error, no progress, or hook destroy. A long feature
  costs one request per active day. `ponytail:` no batch request. C9-T03
  Decision 2 explains why `ensureFrom` cannot use the `days` parameter (the
  client does not know how many active days lie between two times); C12-T06
  measures the cost. The `dense` dataset shows it: `d0` starts 2026-04-08, so
  focusing it pages about 180 days.
- **Paint first (settled 2026-10-08 with C9-T04).** There is no load before
  the first `applyCols` (Decision 5): holding the columns for one request per
  day (180 for `dense` `d0`) leaves the board on viewport columns for seconds.
  E8-D13 fixes the columns "while you scroll"; here they grow only while pages
  arrive, before any scroll.

### 4.6 Invariants

1. `activeFeature()` is `null` or a key of `D.features`. No branch dereferences a
   missing feature.
2. A figure the server marks unknown renders `—`, never `0`, `0%`, the last value
   or `total → total`.
3. In compact mode, every loaded member and every loaded ghost of the active
   feature is placed exactly once. In the timeline view every other loaded row is
   counted in exactly one gap marker (`rows()` J:406 or the wave marker J:506):
   sum of member + ghost items + gap `n` = loaded rows in the section. In the
   Gantt view the design counts a gap only in the break label whose span holds
   its `b` (J:450) and drops gaps inside a wave that has members (J:512); this
   ticket keeps that, so the sum holds only for the timeline.
4. `fmode` is `"focus"` whenever `S.feature` is null (J:1093; C3-T03 drops `fmode`
   without `feature`).
5. Focus-only changes do not relayout (J:1095, in C10-T02's `setFeature`): they
   redecorate and re-apply columns. Any change that enters or leaves compact
   relayouts.
6. At most one `loadFeatureSpan` loop pages at a time (`spanRun`), and it stops
   before its next request once the focused feature is cleared or changed.

## Decisions made without the owner

1. **Figures come from the server `stats`**, never a client `featStats` over loaded
   rows (C6-T05 Decision 1). Same numbers on every design dataset.
2. **Unknown figures render `—`** in the design's `.bd-kv b`, with the reason in
   `title` (C6-T05 Decision 6). DESIGN-E8 item S-26 covers this (C12-T08
   verifies it).
3. **No baseline renders `— → total`**, not `total → total`, because "original"
   is unknown. The design has no such state.
4. **An unknown or missing feature slug is treated as no feature** for layout and
   decoration, while the URL keeps it. The design would grey or fold the whole
   board.
5. **Focus pages history back to the feature's oldest member** whenever that day
   is older than the loaded window (not only when no member is loaded), paint
   first, with no cap. The design never needs this (it holds all history). The
   columns may grow while the pages arrive; after that they are fixed (E8-D13).
6. **The design window is aligned in parity checks** by scrolling the design page
   to the top until its history window equals the product's, instead of adding an
   allowlist entry.
7. **`aria-pressed` is not added** to the Focus/Compact buttons in this ticket:
   the design has the `.on` class only; C12-T05 adds `aria-pressed` in its
   accessibility pass (EC-19). The `#bd-fx` `aria-label` is kept from the design.
8. **The dead `#bd-feats` pill row** (J:1072–1073 under `if (false)`, and the
   J:1071 `fs` list only they read) is not ported.
9. **`dense` is left out of the top-of-history parity cell P-4.** Every `dense`
   feature starts between April and August 2026 (J:125–128), so aligning both
   pages would page 50–180 days one request at a time. P-3 still covers `dense`
   at the live position, and F-13 covers a `dense` focus through the URL.
10. **`setFeature` is reused from C10-T02, not ported a second time,** although
    the README row lists it here (Interface note 8).
11. **Unknown-figure titles use C10-T02's wording** ("at least N% weighted ·
    unknown: …"), and the Done title uses `done_min` as its lower bound, so the
    filter label and the header never disagree.
12. **`activeFeature` uses `Object.hasOwn`,** because shape-valid slugs such as
    `constructor` name `Object.prototype` members (N-22).
