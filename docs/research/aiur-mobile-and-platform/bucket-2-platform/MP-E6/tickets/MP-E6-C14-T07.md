# MP-E6-C14-T07 — Codex agent-native realtime option

Plan: [../plan.md](../plan.md) §19.3. Requirement R4 and KD4. Research: [../talk/research.md](../talk/research.md) §6.

Kevin, 2026-10-10 (verbatim): "… so they can just use the native end points and convo functionality of their agent if it exists without setting up new 3rd party deps."

## Identity and outcome

- **User value:** a Codex user can talk through Codex's own realtime voice (the TUI `/voice` feature, app-server `thread/realtime/*`), with Codex delegation, and the /talk page as the client. No new vendor.
- **Deliverable:** option `codex_realtime` (family `:agent_native`, experimental):
  - Availability: `codex features list` shows `realtime_conversation` enabled and the app-server answers `thread/realtime/listVoices`; else `unsupported` with the reason.
  - Session: fork the live thread read-only (C13-T07, `ephemeral: true`, `sandbox: read-only`), then `thread/realtime/start` on the **fork**, never on the live thread; relay page audio with `appendAudio` and text with `appendText`; map realtime events to the C2-T01 structs.
  - Confirmed drafts still go to the live thread only through C13-T06 (`codex queue`), after a page Confirm (V5).
  - Auth as Codex requires (record whether ChatGPT login works or an API key is needed; research says API key may be required, unverified).
- **Non-goals:** a stable contract (the methods are experimental; the option is off unless detected and is labelled experimental on the page and in `doctor`).

## Acceptance criteria

- [ ] With a stub app-server, `start` is called on a fork thread id, never on the parent id.
- [ ] Missing feature → option `unsupported` with the reason; `doctor` shows it, with the label "experimental". This ticket wires the probe into `talk doctor` (C13-T02).
- [ ] The adapter sends no JSON-RPC request that names the parent thread id, except `thread/fork`. No `turn/start`, `turn/steer`, `thread/queue/add` or `thread/realtime/*` on the parent (fake app-server records every request).
- [ ] `thread/realtime/start` uses `transport: {type: "websocket"}` and passes the briefing as `initialItems`. The adapter never sends an SDP offer.
- [ ] Output audio from `thread/realtime/outputAudio/delta` becomes `AgentAudio` with the rate from the chunk. Transcript deltas become `AgentTextTiming` through `from_text_deltas/2` (C13-T05), `estimated: true`.
- [ ] `stop/1` sends `thread/realtime/stop` on the fork and closes the app-server connection, so the ephemeral fork is discarded. No fork thread stays listed after the session.
- [ ] Event mapping passes the conformance cases the option declares in `capabilities/0`.
- [ ] Manual: one real Codex session, 2 minutes, recorded in the PR (auth mode, first audio time).

## Plan pass (2026-10-10)

**Key decisions**

- Use the app-server realtime WebSocket transport, not WebRTC. Reason: the protocol source (`realtime.rs`, `ThreadRealtimeStartTransport::Websocket`, read 2026-10-10 on `main`) has it, and audio then flows as JSON-RPC (`appendAudio` in, `outputAudio/delta` out). The host needs no WebRTC stack, and the daemon-relay rule of plan §19.1 holds.
- Fork once, at session start, through `AgentFork` (C13-T07) with `ephemeral: true`, `sandbox: "read-only"`, `approvalPolicy: "never"`. Start realtime on the fork id on the same app-server connection. Reason: an ephemeral thread lives only in that server's memory, and realtime V3 delegation then runs Codex turns on the read-only copy, never on the live thread.
- Give the briefing (C11-T08) as `initialItems` (limit: 128 items, 8,192 tokens) and the read-only and draft rules as `realtimeStartInstructions`. Reason: the voice model must answer from the briefing first (R16), and delegation to the fork is the "let me check" path (R17). Briefing refreshes go in by `appendText` as a labelled context note; the adapter does not re-fork during a session.
- Drafts: the start instructions tell the backing model to put a proposed instruction in one fixed marked block. The adapter parses the block from completed items and emits the core draft event. The core confirm rule and C13-T06 delivery stay as they are. Reason: the realtime session has no `draft_instruction` tool, and a read-only fork cannot apply a change, so a marked proposal is the only path to R14 and V5.
- Availability probe: `VoiceConverse.Provider.CodexRealtime.probe/1` runs `codex features list` and one `thread/realtime/listVoices`, both with a 5 s deadline, and returns the feature fact that C14-T01 reads from `Config`. Reason: `realtime_conversation` is stable and on in 0.160.0 (research §6), so the flag alone proves little; `listVoices` proves that the app-server answers.
- Pin the protocol: the request and notification names live in one module with a recorded fixture and the Codex version it came from. Reason: every method is EXPERIMENTAL, and the `main` source has rollout knobs marked for removal.

**Risks**

- Realtime with ChatGPT login fails (research §3.4.2, §3.6 gap 4, UNVERIFIED) → map the auth error to status `needs_credential` with reason `codex_realtime_needs_api_key`. Record the auth mode in the PR. Never pass a `.env` key to `codex` unless the user names it for this option.
- Protocol drift between Codex versions → probe the version; on an unknown version or an unknown method error, show `unsupported` with reason `codex_version`, never a crash. The fixture test fails loudly when the names change.
- The marked draft block is not reliable (the model paraphrases it or drops it) → the conformance draft case runs on fixtures only. The manual run counts how many asked-for drafts appeared. If fewer than 4 of 5 appear, `capabilities/0` declares no draft event, and the page keeps its typed-draft input for this option.
- The fork is a snapshot and goes stale while the live agent works → briefing notes by `appendText` cover new facts. The page says that answers come from a copy taken at session start.
- Cost cannot be metered by the host: Codex bills the user's account → the cost line shows "billed by Codex, not metered". The session time cap of plan §17.6 still applies.

**Test strategy**

- Unit, with fakes (CI, no keys): a fake Codex app-server (stdio JSON-RPC) records every request and plays recorded notification fixtures. Tests: realtime starts on the fork id; no parent-id request except `thread/fork`; websocket transport and `initialItems`; audio and transcript mapping; marked draft block to draft event; stop discards the fork; `listVoices` error and missing feature give `unsupported` with a reason; auth error gives `needs_credential`. A stub `codex` script covers `features list`.
- Conformance: run the speech-to-speech cases of `ProviderConformance` (C2-T01). `capabilities/0` declares the events that the option cannot emit (for example `Interruption` if the protocol has no interruption item), and the degraded cases must pass.
- Doctor: one test in the C13-T02 test file shows `codex_realtime` with status, reason and the experimental label, and never as `recommended`.
- Regression and mutation guard: start realtime on the parent id → "realtime starts on the fork, not the parent" and the parent-id request test fail. Drop `ephemeral: true` → the C13-T07 params test fails.
- Manual, recorded in the PR: one real Codex session of 2 minutes on the dev host. Record the auth mode, the first-audio time, the draft count (5 asked) and the parent thread state before and after. Cost cap: USD 3 (realtime audio on an API key); stop at the cap.

**Open points**

- If realtime fails with ChatGPT login and works only with an API key, Kevin decides if the option stays in v1 (it then needs `OPENAI_API_KEY`, and `openai_live` already covers that user). Recommendation: keep it, experimental and opt-in.
