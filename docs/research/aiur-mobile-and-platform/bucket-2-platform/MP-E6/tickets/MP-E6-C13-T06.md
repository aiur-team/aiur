# MP-E6-C13-T06 — Standalone agent bridge

Plan: [../plan.md](../plan.md) §19.7. Requirements: R15, R16, R18, R19. Research: [../talk/research.md](../talk/research.md) §3.

## Identity and outcome

- **User value:** the live agent keeps working; the assistant knows what it is doing; a confirmed instruction reaches the agent at its next checkpoint, and the user sees "applied" or "declined".
- **Deliverable (built on C11-T03 file ports):**
  - `talk brief [--file PATH | -]`: the agent writes or pipes a Markdown briefing with fixed headings (Summary, Doing now, Next, Waiting on, Questions for you); the host validates headings, stamps `observed_at`, and pushes a `Briefing` update (file watch already in C11-T03).
  - `talk inbox wait [--timeout S]`: blocks until one or more confirmed drafts or `ask` records exist for this project, prints them as JSON lines, and exits 0. Exit 2 on timeout with nothing. This shape lets Claude Code run it as a background task that wakes the agent on exit; other agents call it between steps (C13-T08 tells each agent how).
  - `talk inbox reply <id> --applied | --declined [--reason T] | --answer T`: writes the receipt / reply; the session speaks or shows it.
  - Records carry `id`, `kind: instruct | ask`, `text`, `draft_id`, `created_at`; delivery is at-least-once with idempotent `id`; replies to unknown ids are refused.
  - **Push delivery per harness** (research §3), tried first; the file inbox stays the record of truth and the fallback:
    - Claude Code: `talk serve` is started from the agent's Bash tool, so it inherits `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` (documented, v2.1.224+). On confirm, the host posts an own-child message (auth line, then one user line). Claude reads it between tool calls, or starts a turn when idle. The text is framed: "The user confirmed this instruction in the /talk voice page: …; reply with `talk inbox reply <id> …`". The line format is undocumented (seen in the 2.1.296 binary), so it sits in one module with a fixture and a probe; on any socket error the host falls back to the file inbox.
    - Codex: `codex queue --thread "$CODEX_THREAD_ID" --message <text>` (shared daemon, experimental). Falls back to the file inbox when the daemon or the command is absent.
    - Gemini CLI, OpenCode, others: file inbox plus the skill's instruction to call `talk inbox wait --timeout 0` between steps (Gemini hooks are an optional later improvement).
  - Socket and token values are kept in host memory only, never written to the state file or logs.
- **Non-goals:** pushing text into the agent's terminal or session file (never).

## Acceptance criteria

- [ ] An unconfirmed draft never appears in `inbox wait` output (core V5 invariant, end to end).
- [ ] `inbox wait` returns within 500 ms of a confirm.
- [ ] A reply `--applied` reaches the page as a receipt and the transcript.
- [ ] A briefing with a missing heading is accepted with a stated gap, not rejected.
- [ ] With a fake messaging socket, one confirm writes exactly one auth line and one user line; a socket error falls back to the file inbox with no lost record.
- [ ] With a stub `codex` on PATH, one confirm runs `codex queue --thread <id> --message …` once.
- [ ] A record that arrives by push and is also listed by `inbox wait` is applied once: a second reply to the same `id` is refused with a clear message and changes nothing.
- [ ] The socket path, the token and `CODEX_THREAD_ID` never appear in `<project>/.talk/` files, in `talk status --json` or in host logs (test greps all three).
- [ ] The `codex` stub receives the instruction text as one literal argument (no shell): text with quotes, `$(...)` and newlines arrives unchanged.
- [ ] Manual (recorded in the PR): a real Claude Code session receives a confirmed draft through the socket while it runs a long tool call, and applies it after the call.

## Plan pass (2026-10-10)

**Key decisions**

- Add MP-E6-C13-T01 to `blocked_by`. The verbs `talk brief` and `talk inbox` plug into the CLI that C13-T01 creates, and push delivery runs inside the `talk serve` process. C13-T02 and C13-T03 depend on C13-T01 for the same reason.
- `talk brief` parses with `VoiceConverse.Briefing.from_markdown/1` (C11-T08). It does not have its own parser. It writes `briefing.md` atomically (temp file, then rename), so the C11-T03 file watch never reads half a file.
- The files of C11-T03 stay the record of truth, in `<project>/.talk/`. The host appends and fsyncs the record before it tries a push. The CLI verbs are the only supported interface for agents. Agents do not read or write the ndjson files directly.
- `inbox wait` returns records that have no reply and that no earlier `wait` returned (a cursor in `.talk/`). `--all` lists every open record again. Delivery stays at-least-once; the agent uses the `id` to apply once.
- Receipts: the core port has only `:accepted | :delivered | :failed | :unknown` (plan §17.4). A reply maps to `{:receipt, id, :delivered}` plus `{:agent_reply, id, "applied" | "declined: <reason>" | <answer>}`. The page and the transcript show the reply text. This follows C12-T03 and needs no core change.
- Push adapters are one module each (`Talk.Push.ClaudeSocket`, `Talk.Push.CodexQueue`) behind one small behaviour. Each runs with a deadline (2 s socket, 5 s `codex`) and falls back to the file inbox on any error. `codex` runs through `System.cmd/3` with an argv list, never a shell.

**Risks**

- The Claude socket line format is undocumented (research §3.3.1, row 1a) → keep it in one module with a fixture; add `talk doctor --probe-push`, which sends one harmless line and reports the result; on error, fall back to the file inbox.
- Claude labels socket messages as from "another session" and may not act on them (research §3.3.1 trust note) → frame the text as a user confirmation from the page, with the `id` and the exact reply command; the manual run records how Claude treats it.
- Duplicate delivery (push plus `wait`) can cause a double apply → unique `id`, refusal of a second reply, and a skill rule (C13-T08) to check the `id` first.
- `codex queue` is experimental and its drain time is unknown (research §3.6, gap 3) → treat a zero exit as `:accepted`, not as applied; the file inbox still holds the record; the manual Codex check is optional and recorded if done.
- A Claude Code background `inbox wait` that times out (exit 2) wakes the agent with nothing → the skill (C13-T08) tells the agent to start it again; the default timeout is long (for example 25 min) to stay under the Monitor 30-minute limit.

**Test strategy**

- Unit, with fakes, in `test/voice_converse/talk/bridge_test.exs`: a fake Unix socket server (`:gen_tcp` on `{:local, path}`) that records lines; a stub `codex` script on a temporary `PATH`; a temporary project directory; the FakeProvider. Tests: unconfirmed draft not delivered; confirm wakes `wait` within 500 ms; one auth line and one user line per confirm; socket error falls back with no lost record; stub `codex` called once with literal argv; reply to an unknown `id` refused; second reply refused; briefing with a missing heading gives a gap; secret values absent from files, status and logs.
- Integration, in-process: page WebSock test client, propose, confirm, `inbox wait`, `inbox reply --applied`, then assert the page frame and the transcript record. C13-T09 repeats this as a shell e2e.
- Manual, recorded in the PR: one real Claude Code session receives a confirmed draft during a long tool call (for example `sleep 60`) and applies it after the call. Use the FakeProvider or `text_only` with the cheapest model. Cost cap USD 0.50.
- Mutation guards: deliver on `propose` (the unconfirmed test fails); remove the socket fallback (the fallback test fails); remove the `id` check on reply (the second-reply test fails).
