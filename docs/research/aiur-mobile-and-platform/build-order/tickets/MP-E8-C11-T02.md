## 1. Identity and outcome

- Bucket 2, feature MP-E8 (continuous build history), chunk C11 (ticket modal
  and agent chat), ticket T02.
- **User value.** The operator opens any ticket that has no agent conversation
  (a planned ticket, a not-queued ticket, a past ticket without an agent) and
  reads the real issue: who opened it and when, its body, why it waits, its
  queue facts and its dependencies. From a not-queued ticket the operator adds
  it to the build queue in one click, without the CLI.
- **Deliverable.**
  1. The `.bm-doc` body variant of the modal (J:1417–1440), ported into the
     home hook with real data. The design's mock text (`descOf`, J:1355–1364,
     and the random author `CV.people`, J:1427) is removed.
  2. A server read of the issue body through the existing
     `Aiur.BuildOrder.TicketDetailCoordinator`, rendered with the existing
     `AiurWeb.Markdown` renderer. The hook asks for it with its own
     `ticket-doc {id}` event when the doc view renders; the server replies
     with the first doc and pushes later ones as `build-ticket-doc`, each with
     an explicit state.
  3. The issue author's login added to `Aiur.BuildOrder.TicketDetail.Snapshot`
     (`author_login`), so `.bm-src` says "opened <date> by @login" from real data.
  4. **Add to queue** for not-queued (`sec: "nq"`) rows: the `queue-add {id}`
     event (named by C3-T02) calls MP-E1's queue add. Its hidden, disabled,
     pending, failed, outcome-unknown and success states follow S-14.
  5. Fixture data for the C1 parity runner: per-ticket body Markdown and author
     for the design datasets, so the product modal and the design modal render
     the same text.
  6. One row in `website/docs-app/guide/gui.md` "Writable controls".
- **Non-goals.**
  - The modal frame, header, links, close, focus trap, `?ticket=` and
    `data-goto` navigation (C11-T01). This ticket fills `#tk-body` only.
  - The conversation variant and the "Conversation not retained" note (C11-T03,
    S-6). C11-T03 calls this ticket's render function with a note (§4.6).
  - The pack source line "<pack path> · wave N · not filed yet" and the
    `pack:` id rules (C7-T02 patches this ticket's `.bm-src` site, as its
    ticket says).
  - Estimate values and the `estLabel` helper (C7-T03, which lands after this
    ticket). This ticket renders the unknown mark `—` and never ports the
    design's complexity fallback.
  - Any other queue verb (remove, reorder, hold). The design shows only "Add to
    queue".
  - Changes to `TicketContextPresenter` or the Build Order ticket context panel.
    That panel retires with Build Order (C12).

## 4. Chosen design

### 4.1 Where the data comes from

| Element | Source |
| --- | --- |
| Facts, cues, deps, unblocks, `created`, `sec` | the board row the hook already holds (C3-T02 row: `qpos wave cx est override deps cue created sec`; `D.children`) |
| Body, author, body freshness | `TicketDetailCoordinator` for the ticket's identity, pushed as `build-ticket-doc` |
| Add-to-queue visibility | payload `writable` and `sources.queue` (C7-T01 §4.5) |

The body is read only when a doc view opens, never per row (EC-32: no new
steady-state GitHub reads; the coordinator's reads go through `ResourceStore`).

### 4.2 Server: `AiurWeb.Build.TicketDoc` (PROPOSED `src/lib/aiur_web/build/ticket_doc.ex`)

```elixir
defmodule AiurWeb.Build.TicketDoc do
  @moduledoc "Issue body for the home modal's doc view. Pure present/2 plus socket helpers."

  @type doc :: %{v: 1, kind: "doc", id: String.t(),
                 state: "loading" | "available" | "empty" | "stale" | "unavailable"
                        | "identity_unknown",
                 body_html: String.t() | nil, author: String.t() | nil,
                 created: integer() | nil, observed_at: integer() | nil,
                 reason: String.t() | nil, retry_after: pos_integer() | nil}

  # Pure. input = {:ok, %TicketDetail.State{}} | {:error, %Failure{}} | {:error, term()} | :no_identity
  # (TrackerIdentity is Aiur.TrackerIdentity.)
  @spec present(String.t(), term()) :: doc()

  # Called from BuildLive's "ticket-doc" handler. Resolves the identity, subscribes,
  # requests, assigns :doc_identity and returns the first doc (the event's reply).
  @spec open(Phoenix.LiveView.Socket.t(), String.t()) :: {doc(), Phoenix.LiveView.Socket.t()}

  # Called from the "ticket-doc-close" handler and at the start of open/2.
  @spec close(Phoenix.LiveView.Socket.t()) :: Phoenix.LiveView.Socket.t()

  # Default identity lookup (the live DataSource delegates here; §4.3).
  @spec live_identity(String.t(), keyword()) :: {:ok, TrackerIdentity.t()} | :no_identity | {:error, term()}

  # BuildLive's handle_info for {:ticket_detail_updated, state} and the reset delegate here.
  @spec update(Phoenix.LiveView.Socket.t(), term()) :: Phoenix.LiveView.Socket.t()
end
```

`present/2` (one clause per row; each is a test in §8):

| Input | `state` | `body_html` | `reason` |
| --- | --- | --- | --- |
| `:no_identity` | `identity_unknown` | `nil` | `"identity_unknown"` |
| `{:ok, %State{health: :healthy, detail: %Snapshot{description: d}}}`, `d` binary | `available` | `Markdown.render(d) \|> safe_to_string` | `nil` |
| same, `description: nil` | `empty` | `nil` | `nil` |
| `{:ok, %State{health: :stale, detail: %Snapshot{}}}` | `stale` | rendered (or `nil` if no description) | failure kind, or `"not_fresh"` when `failure: nil` |
| `{:ok, %State{health: :unavailable, detail: nil, failure: nil}}` | `loading` | `nil` | `nil` |
| `{:ok, %State{health: :unavailable, failure: %Failure{kind: k}}}` | `unavailable` | `nil` | `Atom.to_string(k)` when `k` is a known kind, else `"unknown"` |
| `{:error, %Failure{kind: k, retry_after: r}}` | `unavailable` | `nil` | as above; `retry_after: r` |
| `{:error, _other}` (raise, exit, `:unavailable`) | `unavailable` | `nil` | `"unknown"` |

- `author` = `snapshot.author_login` (§4.4) or `nil`. `created` =
  `snapshot.created_at` in ms, or `nil` when there is no snapshot (the hook
  then uses the row's `created`). `observed_at` = `snapshot.observed_at` in ms,
  or `nil`. Never `0`, never the capture time.
- The body is `Snapshot.description`, which the normalizer already sanitised
  with the 16,384-byte limit. The presenter's 4,000-byte `safe_description/1`
  is **not** used: it turns a long body into `nil`, which would render as
  "No description" (§3).
- An unknown failure kind collapses to `"unknown"`, not to a specific cause
  (AGENTS.md "A collapsed cause names the collapse at the source").
- **HTML on the wire.** `body_html` is the only HTML the server sends, and
  only from `AiurWeb.Markdown.render/1` (escapes every run; `http`/`https`
  links only). C3-T02 lists it as an owner-validated exception. Checks:
  `body_html` is set only in `present/2`, and a source-scan test asserts that
  `"build-ticket-doc"` and `body_html` occur in no other file under `lib/`
  (§8.1). A JavaScript port would duplicate a security-sensitive parser (§10
  decision 1).

`open/2`:

1. `id` must match `^[1-9][0-9]{0,9}$` (the handler checks it first and
   replies `invalid_params`; a `pack:` id is never sent: C7-T02 owns unfiled
   rows and the hook renders them without a body read).
2. `close(socket)` (drop the previous identity's subscription).
3. Identity: `DataSource.call(socket.assigns.source, :ticket_doc_identity, [id])`
   (a new callback, §4.3). The live default, `live_identity/2`:
   - the `OpenTicketSource.snapshot/1` ticket whose `identifier == id` and
     whose `identity` is `TrackerIdentity.joinable?/1` → `{:ok, identity}`;
   - else, when the C4-T01 History row has a `node_id` (closed tickets) → the
     joinable identity built from it, `{:ok, identity}`;
   - else, when the snapshot `status` is `:unavailable` or it is
     `truncated?` → `{:error, :open_tickets_unavailable}` (we cannot tell; it
     renders `unavailable · unknown`, never "not loaded here");
   - else `:no_identity`.
   The call is wrapped like `call_context/3`: a raise or exit becomes
   `{:error, :unavailable}`.
4. Subscribe the identity's topic, then request (subscribe first, as
   `dashboard_live.ex:1920-1922` does, so no update is lost between the two).
   Request, subscribe and unsubscribe go through the existing
   `Endpoint.config/1` keys `:ticket_detail_request_fun`,
   `:ticket_detail_subscribe_fun` and `:ticket_detail_unsubscribe_fun`
   (`dashboard_live.ex:1922, 1954, 1984`), defaulting to
   `TicketDetailCoordinator.request/1` and the `Phoenix.PubSub` calls on
   `TicketDetailCoordinator.topic/1`, with the same rescue/catch. BuildLive's
   mount subscribes `TicketDetailCoordinator.reset_topic/0` once when
   connected (as `dashboard_live.ex:2025` does).
5. Assign `:doc_identity` and `:doc_id`; return `{present(id, result), socket}`.

`update/2`: an update whose identity differs from `:doc_identity` is ignored
(`maybe_update_ticket_context/3` rule, using the same `TrackerIdentity`
comparison as `same_identity?/2`); a matching one is pushed as
`build-ticket-doc`. A coordinator reset re-runs the request for the open
identity and pushes the result. With no `:doc_identity` (closed, or never
opened), both are no-ops.

### 4.3 Integration with C11-T01 and BuildLive

- **Client → server events (owned here; C3-T02 shared rules apply).**
  - `ticket-doc {id}`: sent by the registered doc body when it renders a
    ticket with a numeric id. The hook picks the variant (the design's
    `t.agent && t.start`, J:1377), so a ticket that shows a conversation
    never reads the body; C11-T03's S-6 path asks the doc view to render and
    so sends it. Handler: id guard → `{doc, socket} = TicketDoc.open(socket, id)`
    → `{:reply, doc, socket}`. A fallback clause replies
    `%{v: 1, kind: "error", reason: "invalid_params"}`. It is a read: not
    gated by `writable` (as C11-T01's `open-ticket`).
  - `ticket-doc-close {}`: sent from `onModalClose`. Handler:
    `{:noreply, TicketDoc.close(socket)}`.
- **Server → client.** The reply carries the first doc; later docs (updates,
  resets) are `push_event(socket, "build-ticket-doc", doc)`. Both have
  `v: 1, kind: "doc"` (C3-T02: every reply has `v: 1` and a `kind`).
- `BuildLive.handle_info({:ticket_detail_updated, state}, socket)` and
  `({:ticket_detail_coordinator_reset, _}, socket)` delegate to
  `TicketDoc.update/2`.
- **DataSource.** PROPOSED callback on `AiurWeb.Build.DataSource` (C3-T01;
  added in this PR, as C11-T01 adds `ticket/2`):
  `@callback ticket_doc_identity(id :: String.t(), opts :: keyword()) :: {:ok, TrackerIdentity.t()} | :no_identity | {:error, term()}`.
  The default body calls `TicketDoc.live_identity/2`; C8-T04's `IndexSource`

### 4.5 Add to queue

**Visibility (hook).** Only on rows with `sec === "nq"` (as the design).

| `writable` | `sources.queue.state` | Button |
| --- | --- | --- |
| `false` | any | hidden (EC-12: read-only hides writes) |
| `true` | `disabled` (any reason: `disabled`, `unsupported_tracker`, `not_installed`) | hidden: the feature is off |
| `true` | `unavailable` | shown, `disabled`, reason "Build queue unavailable · <reason>" |
| `true` | `ok` or `stale` | shown, enabled (a `reason` such as `writes_paused` goes in the `title`: the store still accepts the add, and MP-E1-C3-T04 applies the label when writes resume) |
| `true` | key missing, or any other value (C7-T03 also names `incomplete`) | shown, `disabled`, reason "Build queue state unknown" (never treated as `ok`) |

The reason is in the `title` of a wrapping `<span class="bm-qadd">` (the
`disabled` button has `pointer-events: none`, H:1362, so its own title never
shows) and in an `.sr-only` element the button names with
`aria-describedby` (EC-19: a disabled button is not focusable, so the reason
must also be in the accessible name tree). No pixel changes.

**Server event `queue-add {id}`** (event name from C3-T02):

1. `socket.assigns.writable and dashboard_writable?()` re-check inside the
   event (the C3-T02 rule) → reply `%{v: 1, kind: "error", reason: "read_only"}`,
   no call.
2. `id` must match `^[1-9][0-9]{0,9}$` → else `invalid_params`, no call. A
   fallback clause catches any other parameter shape (C3-T02 rule).
3. Single flight per id: if `assigns.queue_add_pending` holds the id, reply
   `%{v: 1, kind: "queue-add", id: id, state: "pending"}` and do nothing.
4. Otherwise reply `%{v: 1, kind: "queue-add", id: id, state: "pending"}`, put
   the id in `queue_add_pending`, and
   `start_async({:queue_add, id}, fn -> add_fun.([n], []) end)`.
   `add_fun` is `Endpoint.config(:build_queue_add_fun) || &Aiur.BuildQueue.add/2`
   (injection style of `dashboard_live.ex:2048-2049`). No `queue:` option: the
   item goes where `aiur queue add <id>` puts it without `--queue`. **Re-check
   at start:** if the merged `add/2` requires `queue:`, pass the CLI's name and
   record it here (§11 mismatch 7). Call the function that applies
   `DispatchAuthorization` (MP-E1-C6-T02); if only the CLI's RPC handler
   applies it, call that handler's server function (CR-E8-12).
5. `handle_async({:queue_add, id}, result, socket)` removes the id from
   `queue_add_pending` and pushes `build-queue-add`:

Every push is `%{v: 1, kind: "queue-add-result", id, …}`; the table lists the
other fields.

| Result | Push |
| --- | --- |
| `{:ok, {:ok, _}}` or `{:ok, :ok}` | `%{id, ok: true}` |
| `{:ok, {:error, {:already_queued, name}}}` | `%{id, ok: true, reason: "already_queued", queue: name}` |
| `{:ok, {:error, :closed}}` | `%{id, ok: false, reason: "closed"}` |
| `{:ok, {:error, :store_unavailable}}` | `%{id, ok: false, reason: "store_unavailable"}` |
| `{:ok, {:error, :unsupported_tracker}}` | `%{id, ok: false, reason: "unsupported_tracker"}` |
| `{:ok, {:error, other}}` | `%{id, ok: false, reason: "refused"}` |
| `{:exit, _}` (timeout, crash) | `%{id, ok: false, reason: "outcome_unknown"}` |

`outcome_unknown` is not "failed": the add may have happened. The hook says so
and lets the next diff decide (below).

**Hook states (S-14).**

| State | Look |
| --- | --- |
| idle | design button |
| pending (click until push) | `disabled`, `aria-busy="true"`, same label |

## 6. Non-happy paths

- **Read-only dashboard (EC-12).** Button hidden; the server refuses
  `queue-add` with `read_only` even if a stale client sends it.
- **Queue disabled, not installed, unsupported tracker.** Hidden. Unavailable
  or unknown queue state: disabled with a reason (§4.5).
- **Refusal texts** (escaped): `closed` → "the issue is closed";
  `store_unavailable` → "the queue store is unavailable"; `unsupported_tracker`
  → "this tracker has no build queue"; `refused` → "the queue refused it".
- **Concurrent writers (EC-13).** Two tabs or the CLI add the same ticket:
  the second is `already_queued`, shown as settled. Double click: single
  flight on the client (disabled) and the server (`queue_add_pending`).
- **Closed between render and click (EC-23).** `closed` refusal; the next
  diff moves the row to history (C8-T04).
- **Held with no actor (EC-23).** C7-T01 sends `"Held · no actor or reason
  recorded"`; the cue prints it escaped.
- **Unfiled pack item that is then filed (EC-23).** A `pack:` id never
  triggers a body read. When the filed ticket replaces it (C7-T02 `was`), the
  re-render for the real id sends `ticket-doc` and reads the body.
- **Untrusted text (EC-30).** Body: sanitised and redacted by the normalizer,
  then escaped by `AiurWeb.Markdown`; no `javascript:` links. Title, cue,
  override: `esc`. Login: shape check and `esc`. No new secret exposure (same
  text Build Order's ticket context shows today).
- **Body over the size limit.** `:validation` → "Issue body unavailable ·
  could not be read" (§10 decision 4).
- **GitHub rate limit, auth, timeout.** `unavailable` with the failure kind,
  plus "retry in Ns" from `retry_after`. A later coordinator update replaces
  it. A stale body keeps showing with its age and the reason.
- **Coordinator crash or reset.** The request function's exit becomes
  `{:error, :unavailable}` → `unavailable · unknown`. A reset re-requests.
- **Socket disconnect.** The rejoined LiveView has no `:doc_identity` or
  subscription, so `modal-doc.js` re-sends `ticket-doc {id}` from
  `reconnected()` when the doc view is open. Pending add → `outcome_unknown`.
- **Open-ticket source down or truncated.** An open issue missing from an
  `:unavailable` or `truncated?` snapshot renders `unavailable · unknown`
  (with "Issue body unavailable"), not "not loaded here", because the cause is
  not known (§4.2 step 3).
- **Authorization.** The dashboard add runs as the daemon, so it goes through
  the MP-E1 entry point that applies `DispatchAuthorization` (MP-E1-C6-T02);
  the `writable` re-check is the dashboard's own gate, not a substitute. The
  agent-workspace guard does not apply (not an agent process).
- **Modal switched while a doc is in flight.** `applyDoc` ignores a doc for
  another `id`; the server ignores an update for another identity.
- **Linear or memory tracker.** No joinable GitHub identity →
  `identity_unknown`; the queue is `disabled · unsupported_tracker` → no button.

## 10. Decisions made without the owner

1. **The server renders the body with `AiurWeb.Markdown`** and pushes it as
   `build-ticket-doc`: reuse the tested escaping renderer, not a second parser
   in JavaScript. A narrow C3-T02 exception: one field, one producer.
2. **The 16,384-byte normalizer body, not the presenter's 4,000-byte one.**
   Reason: the presenter turns a long body into `nil`, which would show as "No
   description".
3. **The doc view asks for the body with its own `ticket-doc {id}` event**
   when it renders, not through C11-T01's `open-ticket`. Reason: a ticket that
   shows a conversation does not need the body, and S-6 renders the doc view,
   so it reads the body too. The read goes through `ResourceStore`.
4. **A body over 16,384 bytes shows "unavailable · could not be read"**, not
   a truncated body: `sanitize/2` refuses rather than truncates, and changing
   that is outside this ticket.
5. **Real Markdown uses the design's article styles:** paragraphs as `.bm-sum`,
   all headings as `.bm-art h4`, ordered lists as `.bm-art ul`; code, quotes
   and links get the minimal rules in §4.8. Plan §10 item 13.
6. **Cues follow the body's first paragraph** (the design's position after the
   summary), or come first when the body does not start with a paragraph.
7. **Add to queue is hidden** when the dashboard is read-only or the queue is
   off, and **disabled with a reason** when the queue is unavailable or its
   state is unknown ("enabled" read as "configured"; "otherwise" as
   "configured but not usable now").
8. **The disabled reason sits in a wrapping span's `title`** plus
   `aria-describedby` text (`.btn:disabled` has `pointer-events: none`, H:1362;
   S-14 asks for a title reason).
9. **`already_queued` counts as success.** The ticket is in a queue, which is
   what the operator wanted; the one-owner rule names the queue.
10. **The default queue.** The add call passes no queue name, as the CLI does
    without `--queue`. Choosing a queue in the modal is not in the design.
11. **The author shows as `@login`** (the design prints `@maya`). A missing
    login drops "by …"; a missing date drops "opened …". No invented values.
12. **A dependency that is not loaded renders as "#N · not loaded"** without a
    swatch, and opens by id through C11-T01.
13. **An unknown prerequisite (C7-T01 `cue.unknown`) gets one cue line**, so
    the issue view does not look like a plainly queued ticket.
14. **No estimate fallback from complexity** on any row (R-G12): the
    interim site shows `—` until C7-T03 replaces it.
15. **GitHub App authors keep their login** (`dependabot[bot]`): the shape
    check allows the `[bot]` suffix; the value is still escaped.
16. **An unlisted `sources.queue.state` disables the button** as "state
    unknown"; a `writes_paused` reason keeps it enabled with the reason in the
    title, because the store still records the add.
17. **A miss in a down or truncated open-ticket snapshot is "unavailable"**,
    not "not loaded here": the cause is unknown, so it collapses to
    `unknown` (AGENTS.md collapsed-cause rule).
