# MP-N1-C10-T01 — Notification device validation

## Identity and outcome

- **Bucket / feature / chunk:** 3 / MP-N1 / MP-N1-C10 "Physical-device validation".
- **User value:** proof on real phones that a blocker notification shows its decrypted summary in
  every app state, falls back safely, and opens the right Command — not a simulator assumption.
- **Deliverable:** a results table (one row per DV row × slot) in the PR; failed required rows filed
  as tickets with their row ID. No production code.
- **Non-goals:** relay/privacy rows (MP-N4-C7 V-R*, V-S*, V-P1); meta-dashboard rows (MP-N3-C4-T06);
  transport rows (MP-N2-C10-T05); watch rows (MP-N7).

## Dependencies and blockers

Signed builds (MP-N1-C8-T01), push wiring (MP-N1-C6-T01), NSE and FCM service (MP-N4-C4-T02,
MP-N4-C5-T02), tap routing (MP-N6-C2-T02); OQ-N1-4 (devices), OQ-N4-1 (accounts). Run in the same
session as MP-N4-C7 to share setup; where an N4 row is the same observation, record it once and
cite both IDs.

Record per run: device model, OS build, app build + git SHA, aiur version, network path, timestamps.

| Row | Steps | Pass | Shared with |
|---|---|---|---|
| DV-P1 | For each state trigger a blocking Command on instance 1 (`aiur` test hook or a real agent ask). **Pass criteria are the canonical MP-N4 rows (Phase D feasibility M4); this row runs them, it does not redefine them.** | Foreground/background: decrypted summary (V-I1/V-A1). **System-terminated:** decrypted summary, pass required (V-I2/V-A2). **iOS app-switcher force-quit:** record only (V-I4, RQ-N4-3). **Android swiped from recents:** pass required on Pixel, record on Samsung (V-A2b). **Android Settings → Force stop:** expect **no** delivery, plus the MP-N4-C5-T03 warning on next launch (V-A4, required). | V-I1, V-I2, V-I4, V-A1, V-A2, V-A2b, V-A4 |

| DV-P3 (= MP-N4 V-I3/V-A3) | Reboot, do not unlock, trigger a Command; then unlock and tap | iOS: placeholder before unlock; tap after unlock opens the correct Command. Android: record behaviour | V-I3, V-A3 |
