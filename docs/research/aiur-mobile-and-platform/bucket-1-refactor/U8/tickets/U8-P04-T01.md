| PROPOSED path | Module | Takes | Est. lines |

| `src/lib/aiur/application/children.ex` | `Aiur.Application.Children` | `child_specs/1` and child helpers :506-:528, with every order comment | 290 |

Rationale: the child list is the one boot-order authority (proposal: `APP_BOOT` owns it).
A module of its own makes the order diff visible in review. The delegates keep the four
outside callers unchanged.

Tests: `application_test.exs` → `application/children_test.exs` (run-shape gating :91-:612,
which may split further into CLI and headless shapes if it stays above 500),
`application/supervision_contract_test.exs` (:613-), and `application_test.exs` for the rest.

## Implementation steps

   `mix run --no-start -e 'for o <- [...], do: IO.inspect(Enum.map(Aiur.Application.child_specs(o), &Supervisor.child_spec(&1, []).id))'`
   (the worker writes the four option lists from the tests at :91).
2. Move the list and helpers to `Children`; move checks to `StartupChecks`; add delegates.
3. Re-run the order capture at head; the four lists must be equal. Paste both in the PR body.
4. Split the test file.

## Non-happy paths

- Order is behavior here: a reordered child changes restart blast radius (#2525, #2531).
  The capture in steps 1 and 3 is the proof; a review that sees any id move rejects the PR.
- `child_specs/1` reads `Application.get_env/3` defaults at call time; keep the reads inside
  the function, not in module attributes (compile-time values would freeze test overrides).
- Signal handlers and distribution start stay in `Aiur.Application`, because they run in
  `start/2` before the supervisor exists.
