# U6-T03 - Usage aggregate re-subscribe

## Identity and outcome

- Bucket 1, prior unit U6.
- **User value:** usage numbers on the dashboard and `aiur usage` keep updating
  after the usage ledger process restarts, and say when they are stale.
- **Deliverable:** the aggregate monitors the ledger, re-subscribes and catches
  up on `:DOWN`, checks the subscribe result, and computes freshness at read time.
- **Non-goals:** no ledger change; no new periodic tick unless monitor is not possible.

## Dependencies and blockers

- U0-T01. Independent of other U6 tickets.

## Verified starting point (`58854d4c8`)

- `usage_aggregate/store.ex` (335): subscribes once in `bootstrap`, discards
  the result (`_ = safe(...)`, :79); no monitor, no `:DOWN` handler, no tick
  (:68-69); `freshness` returns a cached value (:65).
- Ledger keeps subscribers in memory (`usage_ledger/store.ex:82, 125-131`),
  one_for_one supervisor (`usage_ledger.ex:61`). A ledger restart drops the
  subscription silently.

## Chosen design

- After subscribing, `Process.monitor` the ledger pid. On `:DOWN`: schedule a
  re-subscribe with a short backoff (100 ms doubling to 5 s) until the ledger
  is back, then catch up from the ledger's read API the bootstrap already uses.
- Subscribe result `{:error, _}` → same retry path, logged.
- `freshness/0` computes from `last_event_at` at read time; while
  disconnected it reports `:stale` with since.

## Implementation steps

1. Monitor + `:DOWN` + retry; result check.
2. Read-time freshness.
3. Tests.

## Non-happy paths

- **Ledger never returns:** freshness stale, one alert after 60 s (existing
  alert style), retry continues at 5 s.
- **Duplicate events during catch-up:** aggregate dedupes by the ledger's event
  key (check the bootstrap's dedupe; reuse it).

## Compatibility and rollout

No config. Rollback: revert.

## Verification
