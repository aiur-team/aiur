# MPG-311 — Target one project on a multi-project gateway: research

Research ticket MPG-311R (#7624). Implementation contract: MPG-311 in `docs/plans/2026-11-06-multi-project-gateways/tickets-m3.md`.
Depends on MPG-306 (project registry, `Aiur.Project.Registry`), MPG-202 (`--gateway` selector). No code change in this PR.

## Outcome

On a gateway with several projects, a project-scoped command names its project with `--project <owner/repo>`.
Gateway-scoped commands never take it. Omitted:

- locally, the project is the repo of the current directory when the gateway has that project, else the only project;
- remotely, the project is the gateway's only project;
- otherwise the command exits 64 with `pick a project: o/a, o/b` and changes nothing.

`aiur set` / `unset` send `project` and stop depending on the caller's working directory for *which* project they edit.

## Design

### 1. Classification (the answer to "which commands are project-scoped")

Rule: a command is **project-scoped** if its data or effect lives in one tracker/repo (a queue, a ticket number, a lane,
an epic, a feature, a build order, a per-project setting). Ticket numbers are per-repo, so any command that takes a
ticket id is project-scoped. Everything about the daemon, the machine, credentials, or the executor/decision wake
stream is **gateway-scoped**. Source: `code-evidence.md` §3.3 Target column; "project" and "ticket/workspace/agents"
targets map to project-scoped, "daemon", "machine", "Decisions", "wake stream", "repo/client" map to gateway-scoped or local.

| Command | Scope | Reason / allowlist function |
|---|---|---|
| `queue show\|order\|add\|set\|remove\|reorder\|hold\|release\|recover\|clear` | **project** | `AgentControlCLI.queue/1` |
| `lane`, `epic`, `feature` (all verbs) | **project** | `lane/1`, `epic/1`, `feature/1` |
| `units` | **project** | `units/1` |
| `build-orders` | **project** | `build_orders/1` |
| `analytics` | **project** | `analytics/1` (reads one project's run logs) |
| `--todo <ids> [--only]` | **project** | `todo/2`; ids are repo-local |
| `take`, `release`, `reset-budget`, `workspace-recover`, `redispatch`, `park` | **project** | ticket-id commands |
| `pause <ids>` / `resume <ids>` | **project** | ids given |
| `pause` / `resume` (no ids) | **gateway** | `pause_global/0`, `resume_global/0`; pauses the whole daemon |
| `message <id>` | **project** | ticket id |
| `message --status`, `listen-mode` | gateway | agent-session level |
| `ticket estimate` | **project** | ticket id |
| `ticket-usage <id>` | **project** | ticket id |
| `set <key> <value>`, `unset <key>`, `set --list` | **project** | runtime override layer (L5) is per project; replaces `caller_cwd` |
| `set max-agents` | **project** | sets that project's ceiling (`projects[].max_agents`); the machine cap is `capacity.max_agents`, edited in `~/.aiur/machine` |
| `status`, `agents`, `alerts`, `watch`, `executor-sweep`, `capabilities`, `usage`, `accounts` | gateway | aggregate; they list projects themselves (MPG-306 adds `projects` to `status --json`) |
| `github-cost`, `github-usage` | gateway | budgets are per credential, not per repo |
| `command*`, `executor-*`, `operator-relay-answer`, `experiments` | gateway | Decisions and the wake stream belong to the executor, not a repo |
| `stop`, `restart`, `run`, `--bg`, `init`, `doctor`, `upgrade`, `token`, `login`, `pr`, `pre-pr`, `findings`, `ask*`, `listen`, `history` | local / refused remotely | unchanged |

Behaviour for the two scopes:

- Project-scoped + `--project` → resolved as below.
- Gateway-scoped + `--project` → exit 64 `status is gateway-scoped; --project does not apply`. Explicit beats a silently ignored flag.

### 2. Resolution (server side, `control_call.ex`)

New module `Aiur.ControlCall.Project` (`src/lib/aiur/control_call/project.ex`):

```elixir
@spec split(keyword() | term()) :: {String.t() | nil, String.t() | nil, term()}   # {project, hint, args_without_both}
@spec resolve(project :: String.t() | nil, hint :: String.t() | nil, repos :: [String.t()]) ::
        {:ok, String.t()} | {:error, {:ambiguous, [String.t()]} | {:unknown, String.t(), [String.t()]}}
```

Two keywords, because an implicit cwd default must never break today's single-project use:

- `project:` — explicit `--project`. Strict: must equal a registered project's `repo` (case-insensitive compare, returned in registry case).
- `project_hint:` — the CLI's cwd-derived repo. Used only to break a tie; ignored when it matches nothing.

`resolve/3`:

1. `repos == []` or one repo: explicit `project` equal to it or absent → that repo; explicit and different → `{:unknown, p, repos}`; hint ignored.
2. Several repos: explicit match → it; explicit no match → `{:unknown, p, repos}`; no explicit, hint matches → hint; else `{:ambiguous, repos}`.

Registry source: `Aiur.Project.Registry` (MPG-306) repo list. **Before MPG-306 lands there is no registry**; MPG-311 depends on it, so
the implementer reads `Aiur.Project.Registry.repos/0` (confirm the exact name at implementation; MPG-306 owns it). With `projects:` empty
the list is the single configured repo from `tracker`.

`ControlCall.parse/2` calls `Project.split/1` on the converted args **after** `Allowlist.fetch` (arity is taken from the raw call, so a call whose only
keyword was `project:` still matches the `{fun, 1, ..., [:keyword]}` row) and **before** `Literal.validate_arguments`, so no allowlist row needs a `project`
option. The stripped keyword is left as `[]` if nothing remains. `parse` returns `%{... project: repo | nil}` only for project-scoped functions;
`split` result for a gateway-scoped function with `project` present → `{:error, :project_not_applicable}`. Which functions are project-scoped is a literal
list `@project_scoped` in `project.ex` (`{module_segments, function}` tuples), checked by the parity test (Test 7).

`run/3` stores the resolved repo in the process dictionary before `execute/4` (same pattern as `put_actor/1`, key `{Aiur.ControlCall, :project}`), and
`Aiur.ControlCall.project/0` reads it. Project-scoped CLI modules call `ControlCall.project/0` to choose the orchestrator/tracker. Until MPG-306 makes the
orchestrator per-project, `project/0` is advisory in a single-project daemon and the existing code path is unchanged.

Errors map to exit **64** via a new `finish_failure(io, reason, code)` (today it hard-codes `1`; `run_control_rpc_dispatch` already forwards the code from `__AIUR_CONTROL_EXIT__:`):

- `{:ambiguous, repos}` → stderr line `pick a project: o/a, o/b` (repos sorted).
- `{:unknown, p, repos}` → `unknown project 'p'; this gateway has: o/a, o/b`.
- `:project_not_applicable` → `<cmd> is gateway-scoped; --project does not apply`.

Resolution failing happens in `parse` for remote HTTP and in `execute` for local RPC. To share it, resolution runs in `run/3` (both transports go through it); `parse` only extracts. A failed resolution runs no command.

### 3. Client side

`aiur-engine.sh` is 500 lines; the file must not grow. Put all new code in a new module `engine/project.sh` (add `project` to `AIUR_ENGINE_MODULES`, `aiur-engine.sh:68`) and keep the edit to `aiur_engine_main` net-zero by replacing the existing `--instance` case arms with one call (`aiur_parse_selectors "$@"`, which handles `--instance`, `--gateway` from MPG-202, and `--project`).

`--project` position: accepted **right after the selector, before the command** (as the ticket says), and also after the command name for the project-scoped commands that already parse flags themselves. The first is parsed by `aiur_parse_selectors` into `AIUR_PROJECT`; the second form is rewritten by each command's parser into the same variable.
Recommended default: support **only the leading position** in MPG-311 (`aiur --gateway nook --project o/b queue show`) plus the trailing position in `queue`, `lane`, `epic`, `feature`, which already own flag parsers. Other project-scoped commands take the leading form only. (Open question 2.)

`engine/project.sh` provides:

- `aiur_project_kw` — prints `, project: Base.decode64!("<b64>")` when `AIUR_PROJECT` is set, plus `, project_hint: Base.decode64!(...)` from `aiur_cwd_repo` when it is not; empty otherwise. Every project-scoped RPC expression appends it inside its keyword list (the same base64 quoting `queue_string` uses; never interpolate raw text).
- `aiur_cwd_repo` — `git -C "$PWD" remote get-url origin` reduced to `owner/repo` for `https://github.com/o/r(.git)` and `git@github.com:o/r(.git)`; empty on any failure. No network.
- `aiur_require_global` — called by gateway-scoped commands: if `AIUR_PROJECT` is set, print the `gateway-scoped` error and return 64. Hooked in the dispatch `case` so it lives in one place.
- `--project` value validated client-side with `^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$`; else exit 64 `--project expects owner/repo`.

`--gateway all` / `--instance all` with `--project`: exit 64 `--project names one project and cannot be used with 'all'`. (Open question 3.)

`set` / `unset` (`engine/commands.sh:348-412`): add the project keywords. `caller_cwd` must **not** simply be removed — it feeds `allow_mutation/1` (`src/lib/aiur/control_cli/settings.ex:103-125`), which refuses a `set` from inside an agent workspace. Plan:

- Local: keep sending `caller_cwd` (guard intact) and add `project`.
- Remote: `pwd` is a path on the wrong machine, so omit `caller_cwd`. The server marks calls that arrive over HTTP (`opts[:remote]` already exists in `parse/2`); `caller_evidence(opts, :caller_cwd)` accepts a missing cwd when the call is remote. `caller_agent_workspace_env` stays required.
- The allowlist rows `set_setting/3` and `unset_setting/2` (`allowlist.ex:202,206`) keep `caller_cwd` as an allowed option; no new `project` option is needed (stripped by `split`).

### 4. Single-project compatibility

- Single-project gateway: explicit `--project o/same` accepted and ignored; `--project o/other` → exit 64 `unknown project 'o/other'; this gateway has: o/same`.
- cwd hint never rejected on a single-project gateway, so running `aiur queue show` from any directory behaves as today.
- No `projects:` in `~/.aiur/machine` → registry has one repo; nothing changes.

## Risks

- **`caller_cwd` guard regression** (most serious). Dropping it from `set` lets an agent workspace edit settings. Mitigation above; Test 13's last assertion.
- **MPG-306 dependency.** `Aiur.Project.Registry` does not exist yet (`src/lib/aiur/project/` is absent). If its API differs, only `Project.resolve` callers change.
- **Hint/explicit confusion.** Sending the cwd repo as `project:` would turn today's cross-directory use on a single-project gateway into exit 64. The two-keyword split exists for this; Test 15 guards it.
- `aiur-engine.sh` (500) and `remote.sh` (497) are at the size gate; growing either fails `check-pr-structure.py`.
- Ticket-id commands rely on the project; before MPG-306 a daemon ignores it, so tests of "project B's data" can only be real once 306 is merged.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| 1. Is `set max-agents` project- or gateway-scoped? | Project (per-project ceiling); machine cap stays in `~/.aiur/machine` | If gateway, drop it from the project list and add a `set --machine` path (MPG-304 owns capacity) |
| 2. Accept `--project` after the command name, or only before it? | Before the command everywhere; also after for `queue`, `lane`, `epic`, `feature` | Universal trailing form needs every command's parser touched (~12 more edits) |
| 3. `--project` with `--gateway all`? | Exit 64 | Allowing it means fan-out with per-gateway "unknown project" tolerance |
| 4. Do `command request --ticket <id>` and `executor-*` take a project? | Gateway-scoped (Decisions are not per repo); a ticket id in a Decision is recorded with its project by MPG-407 | If project-scoped, `--ticket` becomes ambiguous on a multi-project gateway |
| 5. Do `github-cost` / `github-usage` accept `--project` as a filter? | No (gateway-scoped, rejects the flag) | If yes, the ledger needs a per-repo attribution column (not present) |
| 6. Strip `project` before allowlist validation vs add it to every row? | Strip (fewer edits, one place) | Row-by-row gives per-row type checking at the cost of ~25 edits and a drift risk |
| 7. Env var `AIUR_PROJECT` as a default? | No; flags only (an inherited variable was a bug class for `AIUR_REMOTE_INSTANCE`, see `aiur_engine_main`'s `unset`) | If wanted, unset it the same way and re-export only from the flag |
