# MPG-204 — Give remote writes request ids and replay-safe retries: research

Research deep dive MPG-204R (issue #7587). Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579),
contract `docs/plans/2026-11-06-multi-project-gateways/tickets-m2.md` § MPG-204, schema S5 in `state-schemas.md`.
Focus asked for: retention size limits, and restart behaviour of in-flight entries.

Method: the brainstorm questions are recorded below as open questions with defaults (no user questions asked).
No external question needed deep-research (see Prior art), so none was run.

## Outcome

A remote write (`POST /api/v1/control` carrying a `:write` call) sent with a `request_id` runs at most once per
(token, `request_id`) within 24 hours. A repeat with the same id and the same expression returns the stored response
without calling the function again. The same id with another expression returns 422 `request_id_reused`. A repeat
while the first is still running returns 409 `request_in_progress`. A repeat of a call whose outcome the daemon cannot
know (it crashed or restarted mid-call) returns 409 `outcome_unknown`; it never runs a second time. When the launcher
loses the answer (timeout, dropped connection), it prints the id and `retry with --request-id <id> is safe`.
Every audit line for a write carries `request_id`, `origin_gateway` and `actor`. Contract version 1 requests behave as
today.

## Design

### Current behaviour (read from the code)

- `AiurWeb.ControlController.run/2` validates `contract == "aiur.control.call"` and `contract_version == 1`
  (`request_contract/1`), parses with `ControlCall.parse/2`, checks scope, then `ControlCall.run/3` runs the call in a
  `Task.Supervisor.async_nolink` task. On timeout a write task is `Task.ignore`d, keeps running, and the controller
  answers 504 `timeout` with audit outcome `timeout_unknown` (`timed_out/5`).
- The audit line is appended after the run (`successful_call/6`); a failed append turns a finished write into 503
  `audit_unavailable`.
- Launcher `engine/remote.sh` `run_remote_rpc_with_timeout` posts with `contract_version: 1`, maps 504 to exit 124, and
  any curl failure (including `--max-time` expiry, curl exit 28) to exit 69 "could not reach", which hides that the
  write may have been applied. That mapping is the real gap this ticket closes.
- Persistent daemon state goes under `Aiur.Config.Paths.decision_state_dir/0` (instance-keyed, survives restart).
  `log_root_dir/0` is per-launch (`<cwd>/log`) and does **not** survive a restart, and the audit file lives there
  (`control-audit.ndjson`). The replay store therefore must not live next to the audit file.
- `Aiur.Journal` (`prepare/2`, `append/2`, `append_many/3`, `rewrite/2`, `replay/3`) is the existing fsync'd NDJSON
  primitive with torn-tail repair and `max_file_bytes` / `max_record_bytes` limits. Reuse it.

### Decisions

1. **Key = `{token_name, request_id}`.** A bare id would let one token probe or read another token's stored results.
   Tokens are already per-client (`conn.assigns.token_name`). A second gateway using its own token never collides.
2. **Only `:write` calls are stored.** Reads are idempotent; a `request_id` on a read is accepted and ignored. Refusals
   (403/422 parse, scope, dashboard read-only) are not stored: they never ran, a retry re-evaluates them.
3. **Body hash = sha256 of `expression` only.** `timeout_ms` and `max_scope` are transport hints; a retry may change
   them (a longer timeout is the usual reason to retry). `command` is a label only.
4. **Two durable records per call, begin before run.** `begin` is appended and fsync'd *before* `ControlCall.run`; `end`
   after it returns. This is what makes "in-flight at boot" detectable: a `begin` with no `end` after a crash means the
   function may or may not have run.
5. **Boot rule (as in the plan): an in-flight entry found at boot becomes `outcome_unknown`.** The store appends an
   `end` record with `status: "outcome_unknown"` for it and keeps it for the normal 24 h. A same-id retry gets 409
   `outcome_unknown`; the operator verifies state and sends a **new** id. Never auto-rerun: that is the double-apply
   this ticket exists to prevent.
6. **Timeout is terminal and stored.** The controller stores the 504 `timeout` response as the `end` record
   (`status: "timeout_unknown"`). The abandoned write task may still finish, but its output is discarded. A retry with
   the same id returns the stored 504 (no rerun), and the CLI says outcome unknown, verify, then use a new id. See open
   question 2 for the alternative.
7. **Replays are byte-equal to the original.** Stored: HTTP status plus the JSON response body (including
   `elapsed_ms`). A replay adds only the response header `x-aiur-replayed: true`, so "both responses are equal"
   (acceptance) holds for the body. Failed calls (exit marker non-zero, still HTTP 200) replay too.
8. **Fail closed on store errors.** If `begin` cannot be persisted, the write is not run: 503
   `replay_store_unavailable` (mirrors `audit_unavailable`). If `end` fails after a successful run, the response is
   still returned (the call ran and the caller has its answer); the entry stays in flight and becomes
   `outcome_unknown` at next boot; an alert-grade log line is written. Rationale: refusing the answer after the effect
   would be worse than a conservative retry result.
9. **Contract version.** `ControlCall.call_version/0` stays the *latest* (becomes 2); add
   `ControlCall.accepted_call_versions/0` returning `[1, 2]`. `request_contract/1` accepts both. `request_id` is
   honoured only on version 2; on version 1 it is ignored (today's behaviour). On version 2 `request_id` is optional on
   the server (absent: run as today, not replay-safe); the launcher always sends one for writes. **Result version stays
   1**: new fields (`request_id`) are additive, and the shipped launcher rejects `contract_version != 1`
   (`remote_json_output`, remote.sh ~line 353), so bumping it would break every old launcher against a new daemon.
10. **`request_id` format = UUIDv7**, validated by regex
    `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$` (lower case). Invalid: 422
    `invalid_request_id`. The launcher generates it in its existing Node snippet (48-bit ms timestamp plus
    `crypto.randomBytes`), since neither bash nor the Elixir deps in `src/mix.exs` provide UUIDv7.
11. **`origin_gateway` and `actor`.** `actor` is already `"token:" <> token_name` (passed to `ControlCall.run/3`).
    `origin_gateway` is an optional body string (`≤ 64` chars, `[A-Za-z0-9._-]`), recorded as *claimed*; it becomes
    authenticated only when MPG-205 binds a token to a peer. The audit line says so by carrying `peer: null` until
    then (S5 lists `peer`, owned by MPG-205/206; do not add it here beyond a null).
12. **Replay audit.** A replayed request appends its own audit line: `outcome: "replayed"`, `original_outcome`,
    same `request_id`. Reused-id and in-progress refusals are audited as `refused`.

### Retention and size limits (the focus)

All values are module attributes in `ReplayStore`, overridable through `Application.get_env(:aiur, :control_replay, [])`
for tests only. No operator config key: nothing here is a user-set knob, so no `configuration*.md` entry (and
`scripts/check-config-docs.py` is unaffected). Revisit if an operator asks for it.

| Limit | Value | Why | On breach |
|---|---|---|---|
| Retention | 24 h from `begin` (`ttl_ms = 86_400_000`) | Plan contract; far longer than any CLI retry loop | Entry dropped at compaction; a retry with that id runs as new (documented) |
| Max entries | 10_000 | A busy gateway issues well under 1/s of writes (24 h ≈ 86k worst case, realistically hundreds) | Evict oldest *completed* entry first |
| Max stored response per entry | 64 KiB | Control outputs are short status text | Entry stored with `status: "result_too_large"`, body omitted; replay returns 409 `result_not_retained` (not rerun) |
| Max file size | 16 MiB (`Journal.replay` `max_file_bytes`) | 10_000 × 64 KiB would be 640 MiB; the file cap is the real bound | Boot refuses to load an over-cap file: rotate it to `replay.ndjson.<ts>.bad`, start empty, log an alert. Never delete silently |
| Max record | 80 KiB (`max_record_bytes`) | 64 KiB body + envelope | Record rejected as above |
| In-flight entries | never evicted | Evicting one reopens the double-run window | If the table is full of in-flight entries: 503 `replay_store_full` |

Compaction: at boot, then every hour, rewrite the file with `Journal.rewrite/2` keeping only unexpired entries'
final state (one `begin` + one `end` each). Between compactions the file grows by two records per write; 16 MiB covers
that at the entry/response caps because compaction at the 1 h cadence plus the 10_000-entry cap keeps live size well
under it. If compaction itself would exceed the file cap, evict oldest completed entries until it fits.

### Restart behaviour (the focus)

| State found at boot | Result | Same-id retry returns |
|---|---|---|
| `begin` + `end` (any status) | restored as is | the stored response |
| `begin` only | append `end` `outcome_unknown`; kept 24 h | 409 `outcome_unknown` |
| torn final line | `Journal.replay` truncates the tail (repair on) | treated as `begin` only if its `begin` line was complete, else the call never ran: id unseen |
| file missing | empty store | runs as new |
| file over cap / unparsable record mid-file | rotate to `.bad`, start empty, alert | runs as new (honest: history lost; alert says so) |

A torn `begin` means the fsync did not return, which means `ControlCall.run` was never reached (begin precedes run),
so treating that id as unseen is safe.

The daemon's ETS table is rebuilt from the file; no other process owns it. `Aiur.ControlCall.ReplayStore` is a
`GenServer` started in the application supervision tree (after the paths/config it needs, before the endpoint).

### Alternatives rejected

- **Store only in ETS.** Loses the "never run twice across a restart" property; the restart case is the dangerous one.
- **Reuse `control-audit.ndjson`.** It lives in the per-launch log root, is not size-bounded, and must stay
  append-only evidence; mixing in lookup state breaks both.
- **Postgres lease store (`AIUR_LEASE_DATABASE_URL`).** Optional, multi-instance, and requires TLS Postgres; replay
  safety is per receiving daemon, so local durable state is the right scope.
- **Rerun an in-flight entry at boot.** Violates at-most-once.
- **Client-computed idempotency from the expression hash.** Cannot distinguish "send it again on purpose" from a retry.

## Prior art

None needed. The pattern (client-chosen key, stored response, 422 on key reuse with a different body, 409 while in
flight) is the standard HTTP idempotency-key contract; the code-owned parts (journal, state dirs, audit) are all
answered by the repo. No claim in this doc depends on an external guarantee. The prior-art reports in
`docs/research/multi-gateway/` (claim protocols, priority reconciliation, enrollment) concern ticket claims and
trust, not request replay; none contradicts this design. Marked as "pending evidence" only if a reviewer wants the
IETF idempotency-key draft's exact status codes cited: the codes here are chosen to match the plan's contract, not the
draft.

## Interfaces

- Consumes: `Aiur.Journal`; `Aiur.Config.Paths.decision_state_dir/0`; `conn.assigns.token_name` /
  `token_scope` (`AiurWeb.ControlController`); `Aiur.ControlCall.run/3`.
- Provides to MPG-205/206: audit fields `request_id`, `origin_gateway`, `actor` (S5), and a stable place
  (`execute_call/5`) where category/peer checks run *before* the store's `begin`, so a refused call is never stored.
- Provides to MPG-202/203 (launcher): `AIUR_REQUEST_ID` env var / `--request-id <uuidv7>` flag, exit 124 text.
- Provides to `remote_all.sh`: each per-instance write call gets its own fresh id; `--request-id` combined with
  `--instance all` is refused (exit 64): one id cannot be the key on several gateways.

## Data and assets

- Store file: `<decision_state_dir>/control-replay/replay.ndjson`, mode 0600 via `Journal.prepare/2`.
- Record schema (one JSON object per line):
  `{"v":1,"kind":"begin","token":"<name>","request_id":"<uuidv7>","expression_sha256":"<hex>","at_ms":1760000000000}` and
  `{"v":1,"kind":"end","token":"…","request_id":"…","at_ms":…,"status":"ok|timeout_unknown|outcome_unknown|result_too_large","http_status":200,"body":{…}}`.
  `body` holds the exact JSON response map; absent for `outcome_unknown` and `result_too_large`.
- Stored bodies contain control output, which may include ticket text: file mode 0600, under the decision state dir
  (daemon-private), never under an agent-writable workspace (matches AGENTS.md "daemon-owned records" rule).
- Known gap: `origin_gateway` is unauthenticated until MPG-205; documented, not hidden.

## Risks

- **Line budgets.** `aiur-engine.sh` is exactly 500 lines and `remote.sh` 497; growing either breaks the file-size
  gate. Mitigation: all new shell in `remote_request_id.sh`; move, don't add, in `aiur-engine.sh`. Check with
  `python3 scripts/check-pr-structure.py` after every change.
- **Write-ahead cost.** One extra fsync per remote write. Remote writes are operator actions (low rate); accepted.
- **Double result after timeout.** The abandoned task may still change state after the client was told "unknown".
  That is existing behaviour (`Task.ignore`); documenting it in the CLI text (`verify state`) is the mitigation.
- **Version bump to 2 with a v1-only daemon.** A new launcher against an old daemon gets 422 `parse_error` for
  `contract_version: 2`. Mitigation: on that exact 422 (no `unknown_on_build`, `error.build` present), the launcher
  retries once with `contract_version: 1` without `request_id` *only for reads*; for writes it fails with
  `<name> runs a build without replay-safe writes; upgrade it or pass --allow-unsafe-retry` (see open question 4).
- **Load-sensitive tests.** In-progress and timeout tests use latches and injected timeouts, never real CPU load.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| 1. Is `request_id` required on v2 writes? | Optional on the server, always sent by the launcher | Required: every non-launcher client (Stream Deck, scripts) breaks until updated |
| 2. After a timeout, keep the entry in flight until the abandoned task finishes, so a later same-id retry returns the real result? | No: store the 504 as terminal; retry never reruns; operator verifies | Yes: needs `ControlCall.run` to expose task completion (touches `control_call.ex` beyond the version change) and makes `request_in_progress` outlast the timeout |
| 3. Key by `{token, request_id}` or by `request_id` alone? | `{token, request_id}` | Alone: simpler, but one token can read another's stored output |
| 4. Writes against a daemon that does not know v2: refuse, or downgrade to v1 without replay safety? | Refuse with an upgrade message; `AIUR_ALLOW_UNSAFE_RETRY=1` downgrades (name pending, a new operator env var needs a docs entry in this PR) | Silent downgrade hides that a retry can double-apply |
| 5. Expose the retention numbers (24 h, 10_000, 64 KiB, 16 MiB) as config? | No, module attributes with a test-only env override | Yes: new keys in `Aiur.Config.Schema.*`, `configuration*.md`, the annotated examples, and `check-config-docs.py` entries |
