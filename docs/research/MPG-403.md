# MPG-403: Conflict ordering for shared intent

Plan: `docs/plans/2026-11-06-multi-project-gateways.md`, section "Reconciliation" (PR #7579). Schema: S4 in
`state-schemas.md`. This note confirms the eight rules and amends three. MPG-404 and MPG-405 build from the rules
as amended here.

**Q4 assumed (decided by Kevin, 2026-11-06):** an Executor may override a human dashboard change only with
`force: true` and a `reason`, and `supersedes` must name the human change that is current at that point in the fold.
The override is shown as a takeover. Nothing else lets an Executor displace a human value.

## Amendments

- **A1. Pause wins an exact HLC tie.** The plan's sort key is `(wall_ms, counter, origin_gateway, change_id)`.
  When two changes share `(wall_ms, counter)` and one is a pause, the origin name would pick the winner, so a
  gateway named `Z` could cancel an Executor's emergency pause. MPG-405's sort key becomes `(wall_ms, counter,
  pause_rank, origin_gateway, change_id)` where `pause_rank` is 1 for a `pause` field set to paused, else 0. The
  order stays total and deterministic. This is the only meaning of "pause-wins tie": a non-tied unpause still wins
  when it is later (row 10).
- **A2. A daemon never writes `pause`.** Rule 5 says any paused slot pauses. A paused `default` slot would
  therefore displace a human unpause, which breaks invariant 2 (row 13). Fold ignores `pause` changes in the
  `default` slot, and the writer API rejects them. A daemon that needs to stop work does so locally and does not
  publish it (rule 8).
- **A3. A held change does not move the local HLC.** The HLC receive rule takes the max of the remote wall time.
  Absorbing a change 90 s ahead would push every later local change 90 s ahead and poison the fleet. A held
  change is stored and re-checked as the clock advances; only an applied change merges into the HLC.

## Worked interleavings

Winner is the effective value after folding the whole set, and is the same for every arrival order. The model
asserts each row in both forward and reversed order. Walls are abbreviated (`@10`).

| # | Interleaving | Winner | Why |
|---|--------------|--------|-----|
| 1 | Human `a` @10; Executor `b` @20, no force | `a` | Executor slot is below human. The Executor value is kept beneath it. |
| 2 | Human H1 `a` @10; forced Executor E `b` @20 naming H1; human H2 `c` @30 | `c` | E clears H1, then H2 re-fills the human slot. |
| 3 | H1 @10; H2 `c` @20; forced E `b` @30 naming H1 | `c` | H2 is current, so E names a stale change and clears nothing. |
| 4 | H1 `a` @10; forced E `b` @20 naming H1, reason given | `b` | Takeover of the current human change. |
| 5 | H1 `a` @10; forced E `b` @20 naming H1, empty reason | `a` | A force without a reason is not honoured. |
| 6 | H1 `a` @10; forced E `b` @20 naming H1; late offline human `d` @15 arrives last | `d` | The fold puts `d` after H1, so at E the human slot is `d`, not H1. The takeover is cancelled retroactively. |
| 7 | Executor clock slow: forced E `b` @5 naming H1; H1 `a` @10 | `a` | At E there is no human slot to clear. H1 then fills it. A skewed Executor cannot take over. |
| 8 | Human `a` @10 and Executor `b` @20, each delivered twice, any order | `a` | Apply is idempotent by `change_id`. |
| 9 | Human unpause @10; Executor pause @20 | paused | Any paused slot pauses. |
| 10 | Executor pause @10; human unpause @20 | not paused | Human unpause clears every slot. |
| 11 | Human unpause and Executor pause, same `(wall, counter)`, origins `Z` and `A` | paused | A1: pause sorts last in a tie. |
| 12 | Human `a` @10; daemon `z` @99 | `a` | Daemon writes `default`, which is below human. |
| 13 | Human unpause @10; daemon pause @20 | not paused | A2: the daemon pause is ignored. |
| 14 | Two humans, same `(wall, counter)`, origins `A` then `B` | `B`'s value | Origin breaks the tie. Deterministic, not meaningful, so MPG-405 should surface a conflict marker when the losing change was concurrent. |
| 15 | Human change 90 s ahead of local time | old value, then the new one | Held until the local clock is within 60 s, then applied. Not dropped, not clamped. |

Row 6 is the cost of keeping a human edit that was made offline. The Executor's value is still in its slot and
shows again if the human clears theirs. The dashboard should render a "takeover superseded" note.

## Model and invariants

`docs/research/MPG-403/reconcile_model.py` is a stdlib-only executable model (run `python3 -I
docs/research/MPG-403/reconcile_model.py`). It folds a change set exactly as MPG-405 will, and checks:

1. **Same change set, same state on every gateway.** For 300 random sets of 2 to 6 changes, every permutation
   (with duplicate deliveries mixed in) folds to the same slots, and three gateways receiving in shuffled order
   agree. The random range is small, so HLC ties and stale `supersedes` references are frequent.
2. **A daemon change never displaces a human or Executor value.** Adding a `default`-slot change to any set that
   has a human or Executor value leaves the effective value unchanged, for `pause` and for a value field.
3. **Applying a remote change emits nothing to the outbox.** A gateway that authors one change and applies two
   remote changes (one duplicated) has an outbox of exactly one.

The model is an oracle for MPG-405's `reconciler_test.exs`: it should port the 15 rows and the permutation
property (StreamData) rather than invent new expectations.

## Limits

- The model uses integer walls and no real clock. HLC persistence and monotonicity across restarts belong to
  MPG-404's `hlc_test.exs`.
- Row 14 and row 6 lose a concurrent write by design. The research's version-vector conflict marker is not in the
  plan's S4 schema. Adding it is an MPG-405 decision, not required for convergence.
- The 60 s hold threshold is the plan's judgement; no source measured post-resume laptop skew.
- A forced Executor change has no rate limit in the plan. Two Executors can alternate takeovers; the research
  suggests one force per item per hour. Not decided here.
