# MPG-404 — Store shared intent changes with a local cache and outbox: research

Research deep dive MPG-404R (#7626). Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579), contract MPG-404 in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m4-m7.md`, schema S4 in `.../state-schemas.md`, rules in
`docs/research/MPG-403.md` (as amended A1-A3). No code is changed by this document.

## Outcome

After MPG-404, a gateway can author an intent change at any time, with or without the coordination database. The change
gets a persisted hybrid logical clock (HLC) stamp, lands in a local cache (`intent/changes.ndjson`) and a local outbox
(`intent/outbox.ndjson`), and is pushed to Postgres table `aiur_intent_changes` exactly once when the store is
reachable. Changes authored elsewhere are pulled by `seq` into the same local cache. Nothing folds registers yet
(MPG-405) and nothing schedules from them (MPG-406+). The only user-visible effects are the files and, when the store is
configured, rows in two new tables. Applying a pulled change never writes the outbox (rule 7).

## Design

### Pieces

| Module | Role | Process |
|---|---|---|
| `Aiur.Intent.Change` | Struct, validation and (de)serialisation of one change. Pure. | none |
| `Aiur.Intent.Hlc` | HLC state. `tick/0` for a local change; `observe/1` for an applied remote change. Persisted. | GenServer |
| `Aiur.Intent.Store` | Owns the three local files. All reads and writes go through it, so file access is serialised. | GenServer |
| `Aiur.Intent.Sync` | Pushes the outbox, pulls by `seq`, backs off when the store is down. | GenServer |
| `Aiur.Instance.LeaseStore.IntentState` | SQL for the two tables, called from the existing `LeaseStore` connection. | functions |

`Aiur.Intent.Writer.write/1` is the one entry point MPG-405+ callers use: validate, `Hlc.tick/0`, `Store.append_local/1`,
`Sync.nudge/0`. It is a thin function in `intent/writer.ex`. It returns `{:ok, change}` or `{:error, reason}`. It never
needs the database.

### Local files

Directory: `Path.join(Aiur.Identity.Store.dir(), "intent")`, i.e. `<machine dir>/intent/`. The machine dir is already the
per-machine, outside-Git, per-user location of `identity.json`, and `Aiur.Identity.Store.dir/1` already honours
`:machine_state_dir` for tests. The intent dir is overridable by `Application.get_env(:aiur, :intent_dir)` so tests never
touch a real path (AGENTS.md "Reading real state"). Directory mode 0700, files 0600 (`Aiur.Fs.atomic_write(..., mode: 0o600)`;
appends create the file with `File.open(path, [:append, :binary])` after a `chmod 0600` on first create).

One gateway is one machine (MPG-201 `Aiur.Gateway.Identity`), and all daemons of that machine share the machine dir. `Store`
and `Hlc` therefore hold an exclusive lock file `intent/.lock` for their lifetime (open question 2).

| File | Content | Write discipline |
|---|---|---|
| `changes.ndjson` | Every change this gateway knows (own and pulled), one JSON object per line, in arrival order. Append-only. Dedup by `change_id` happens on read through an in-memory `MapSet` built at `Store.init/1`. | `File.write(path, line, [:append])` then `:file.sync/1` |
| `outbox.ndjson` | Own changes not yet confirmed in Postgres. | Append + fsync on author. Rewritten with `Aiur.Fs.atomic_write(..., fsync: true)` after a push, with confirmed ids removed. |
| `registers.json` | `{"version":1,"pull_cursor":<seq>,"registers":{}}`. MPG-404 owns `pull_cursor` only; `registers` is `{}` until MPG-405 fills it. | `Aiur.Fs.atomic_write` with `fsync: true` |
| `hlc.json` | `{"version":1,"wall_ms":N,"counter":N}`. Not in the S4 list; see Decision D3. | `Aiur.Fs.atomic_write` with `fsync: true` |

A line that does not parse or fails `Change.validate/1` on load is skipped, counted, and logged once with the line
number and no value (`Logger.warning("intent cache: skipped N malformed lines in changes.ndjson")`). The file is not
rewritten. A torn final line (crash mid-append) is the usual cause and is harmless because the change is still in the
outbox or the database.

### Author path (order matters)

`Writer.write(attrs)`:

1. `Change.new(attrs)` fills `change_id` (UUIDv4 from `Ecto.UUID`-free code: `:crypto.strong_rand_bytes(16)` with version
   and variant bits set, formatted as 8-4-4-4-12 hex) and `origin_gateway` from `Aiur.Gateway.Identity.current().gateway_id`.
   If the identity is `"unavailable"` return `{:error, :gateway_identity_unavailable}`. An id is never invented.
2. `Change.validate/1` (below).
3. `Hlc.tick/0` returns `{wall_ms, counter}` **after** persisting it.
4. `Store.append_outbox/1` then `Store.append_changes/1`. Outbox first: a crash between the two leaves a change that
   will be published and then pulled back (harmless duplicate, deduped by id). The reverse order would leave a local
   change that is never published.
5. `Sync.nudge/0` (a `send` to the Sync process; a no-op if it is not running).

### HLC

State `{wall_ms, counter}`. `tick/0`: `now = System.os_time(:millisecond)`; if `now > wall_ms` then `{now, 0}` else
`{wall_ms, counter + 1}`. The new value is written to `hlc.json` (fsync) **before** it is returned, so a crash can never
reissue a value. At boot the persisted value is the floor: `wall_ms = max(now, persisted.wall_ms)`. A wall clock set back
5 minutes therefore yields `{persisted.wall_ms, persisted.counter + 1}` on the first tick: greater than the last
persisted value. A missing `hlc.json` starts at `{now, 0}`. A corrupt `hlc.json` is quarantined (`Aiur.Fs.quarantine/1`) and
the floor becomes the maximum `hlc_wall_ms`/`hlc_counter` found in `changes.ndjson` for this gateway's own changes, else
`{now, 0}`. An HLC counter above 2^31-1 is refused (`{:error, :hlc_counter_overflow}`), matching the Postgres `int` column.

`observe/1` takes a remote `{wall_ms, counter}`. Per MPG-403 A3 it must only be called for an **applied** change. It
returns `:held` and changes nothing when `wall_ms > now + 60_000` (rule 6). Otherwise it sets the HLC to the HLC receive
rule result and persists it. MPG-404 ships `observe/1` and its tests; MPG-405 calls it from the fold's apply step. The
60 s threshold is `Application.get_env(:aiur, :intent_hold_ms, 60_000)` (MPG-403 open question c leaves it constant;
the env hook exists for tests only and is not documented).

### Change validation (trust boundary)

`Change.validate/1` returns `:ok | {:error, atom}` and rejects:

| Rule | Error |
|---|---|
| `slot` not in `human`, `executor`, `default` | `:invalid_slot` |
| `entity_kind` not in `project`, `feature`, `ticket`, `gateway`, `fleet` | `:invalid_entity_kind` |
| `field` not allowed for the kind: `ticket` -> `order_key`; `gateway`, `fleet` -> `pause`; `project`, `feature` -> `priority`, `order_key`, `focus` (see D6) | `:invalid_field` |
| `field == "pause"` and `slot == "default"` (MPG-403 A2: a daemon never writes `pause`) | `:daemon_pause_rejected` |
| `force == true` and `reason` blank or longer than 500 bytes, or `force == true` with `supersedes == nil` | `:force_requires_reason_and_supersedes` |
| `force == true` and `slot != "executor"` | `:force_requires_executor_slot` |
| `entity_key` for `project` not `owner/name` (`~r/\A[A-Za-z0-9_.-]+\/[A-Za-z0-9_.-]+\z/`), or any `entity_key` starting with `/` or `~` or containing `..` | `:invalid_entity_key` (MPG-002 rule: shared intent keys on repo, never a checkout path) |
| `Jason.encode!(value_json)` over 8192 bytes | `:value_too_large` |
| `hlc_wall_ms < 0` or `hlc_counter` outside `0..2147483647` | `:invalid_hlc` |

Error messages are static atoms; no entity key, path or value is interpolated into a log or error (same rule MPG-002 set
for paths).

### Postgres (S4)

Added by `Postgres.create_tables/1` (same `CREATE TABLE IF NOT EXISTS` pattern; the function is 159 lines so one extra
`with` arm calling `IntentState.create_tables/1` keeps it small):

```sql
CREATE TABLE IF NOT EXISTS aiur_intent_changes (
  seq bigserial NOT NULL,
  change_id uuid PRIMARY KEY,
  hlc_wall_ms bigint NOT NULL,
  hlc_counter integer NOT NULL,
  origin_gateway text NOT NULL,
  slot text NOT NULL CHECK (slot IN ('human','executor','default')),
  author_id text NOT NULL,
  entity_kind text NOT NULL,
  entity_key text NOT NULL,
  field text NOT NULL,
  value_json jsonb NOT NULL,
  supersedes uuid NULL,
  force boolean NOT NULL DEFAULT false,
  reason text NULL,
  received_at timestamptz NOT NULL DEFAULT clock_timestamp()
);
CREATE UNIQUE INDEX IF NOT EXISTS aiur_intent_changes_seq ON aiur_intent_changes (seq);
CREATE TABLE IF NOT EXISTS aiur_intent_registers (
  entity_kind text NOT NULL, entity_key text NOT NULL, field text NOT NULL,
  winning_change_id uuid NOT NULL, value_json jsonb NOT NULL,
  PRIMARY KEY (entity_kind, entity_key, field)
);
```

`aiur_intent_registers` is created because S4 and the MPG-404 outcome say "Schema S4 exists". Nothing in MPG-404 reads or
writes it; MPG-405 decides whether to use it (Decision D4).

Push (`IntentState.publish/2`): one `Postgrex.transaction/2` per batch of up to 100 changes; each change is
`INSERT INTO aiur_intent_changes (...) VALUES ($1..$13) ON CONFLICT (change_id) DO NOTHING`. The result is the list of ids
the database now holds, which is all ids in the batch (inserted or already present), so a retry after a lost reply is
safe. `supersedes` and `change_id` bind as 16-byte binaries (Postgrex `uuid` takes raw binaries; `Change` keeps the string
form and converts at the edge). `value_json` binds as a decoded map.

Pull (`IntentState.changes_since/2`): `SELECT ... WHERE seq > $1 OR received_at > clock_timestamp() - interval '60 seconds'
ORDER BY seq LIMIT $2` with `$2 = 500`. See D2 for why the second predicate exists.

Both calls route through `LeaseStore`'s single connection as `{:shared_state, {:publish_intent_changes, list}}` and
`{:shared_state, {:intent_changes_since, cursor, limit}}`, so reconnect, the `system.instance.ownership_unknown` alert
and fail-closed behaviour are reused unchanged. Public wrappers `LeaseStore.publish_intent_changes/1,2` and
`intent_changes_since/2,3` go in `Delegates` (arities listed in Files). `SharedState` is already 237 lines; the new SQL
lives in the new `IntentState` module and `SharedState.handle_call/2` gets one clause that delegates to it. Net
change to `lease_store.ex` (496 lines, under the 500-line oversized-file rule): **zero lines**.

### Sync loop

`Sync` is a GenServer started only when `LeaseStore.configured?()`. It runs `sync_once/0` every 5000 ms (`:intent_sync_ms`,
test-only knob) and on `nudge/0` (coalesced: a pending timer is cancelled and replaced by a 50 ms one).

`sync_once/0`:

1. `outbox = Store.outbox(100)`. If non-empty: `LeaseStore.publish_intent_changes(outbox)`.
   - `{:ok, ids}` -> `Store.ack_outbox(ids)` (atomic rewrite of `outbox.ndjson` without them).
   - `{:error, {:store_unavailable, _}}` or `:disabled` -> leave the outbox, schedule the next run with exponential
     backoff 5 s to 60 s, return. No alert from Sync (LeaseStore already raises `system.instance.ownership_unknown`).
   - Other `{:error, reason}` -> log the atom once per 10 min and back off the same way.
2. Pull: `LeaseStore.intent_changes_since(Store.pull_cursor(), 500)` -> `{:ok, rows}` -> `Store.append_remote(rows)` which
   skips ids already known, appends the rest to `changes.ndjson`, and advances `pull_cursor` to the largest `seq`
   seen. Repeat while a full page (500) came back.
3. After either step, if `Store` appended any remote change, `Phoenix.PubSub`/`Aiur.AgentPubSub` broadcast is **not** done
   in MPG-404 (no consumer yet; MPG-405 adds the notify).

Applying a pulled change never touches `outbox.ndjson`: `append_remote/1` has no code path to it, and a test pins that
(rule 7, MPG-403 invariant 3).

### Boot pull, direct apply and freshness (for MPG-406R)

MPG-406R (PR #7713) gates dispatch on shared intent and needs three calls beyond the periodic loop. Names and arities
match that document.

- **`Sync.pull(timeout_ms: 5_000) :: :ok | {:error, reason}`.** Synchronous, time-bounded, pull half of `sync_once/0` only
  (never pushes). Called at boot before the first dispatch tick. The `Sync` process runs the paged pull in a `Task` and
  waits with `Task.yield/2` then `Task.shutdown/1` at the bound, so it returns `{:error, :timeout}` at the bound even when
  the connection hangs. `Store.append_remote/1` is only called with a complete, validated page, so a timeout never leaves
  a partial page: a timeout during the first page leaves the cache and `pull_cursor` untouched; pages that completed
  earlier stay (each advanced the cursor with its rows). Other errors: `{:error, {:store_unavailable, _}}`, `{:error,
  :disabled}` (store not configured, `Sync` not running). The call is serialised with `sync_once/0`, so a periodic run
  in flight is waited for, inside the same bound.
- **`Sync.apply_remote(change) :: {:ok, :applied | :duplicate} | {:error, atom}`.** One change delivered by a direct
  control call (no database). Runs `Change.validate/1` (the whole closed list, so a `slot = "default"` `pause` is
  `:daemon_pause_rejected` here too), skips a known `change_id` (`:duplicate`), else `Store.append_remote([change])`.
  Never writes the outbox (rule 7), never touches `pull_cursor` (a direct change has no `seq`), and does not call
  `Hlc.observe/1` (A3: only the fold's apply step does). It is a function on `Sync` that goes straight to `Store`, so it
  works when `Sync` is not running. If the same change later arrives by pull, `append_remote/1` dedups by id and the
  cursor advances with its `seq`.
- **`needs_pull` flag, `Sync.needs_pull?/0`, `Sync.ensure_fresh(timeout_ms \\ 5_000) :: :ok | {:error, reason}`.** The flag
  is `true` from `Sync` boot, set `true` by any failed or timed-out pull (periodic or bounded), and cleared only by a pull
  that reached a short page without error. It lives in a `:read_concurrency` ETS table owned by `Sync`, so
  `needs_pull?/0` is a table read: no `GenServer.call`, no store, no file. `ensure_fresh/1` returns `:ok` at once when
  the flag is `false`; otherwise it runs `pull/1`. After a failure it returns `{:error, :recently_failed}` without
  touching the network until the current backoff delay (5 s to 60 s) has passed, so a gate that calls it every tick pays at
  most one bound per backoff window. When the store is not configured, the flag is `false` and `ensure_fresh/1` is `:ok`
  (nothing to be fresh against).
- **The pause gate reads only the local cache and registers.** Once the boot `pull/1` has run, the gate (MPG-406R) reads
  `Store.changes/0` and the fold's registers: no network, no database call. An unreachable store delays boot by at most
  the bound (5 s default) and never blocks dispatch gating; on `{:error, _}` the gate proceeds on the local cache and
  `needs_pull?/0` stays `true` for `ensure_fresh/1` to retry.

The cache cap is not enforced in MPG-404 (see Risks). The outbox cap is 10 000 lines: `Writer.write/1` returns
`{:error, :outbox_full}` beyond that and `Store` raises `system.intent.outbox_full` once (needs_attention true).

### Decisions

- **D1. Plain files, not DETS/SQLite.** The plan fixes the three file names, they must be readable by a human and by the
  python oracle, and `Aiur.Fs` plus `Aiur.JsonStore` precedent covers atomic and fsync writes. Rejected: SQLite (new
  dependency for a few thousand lines).
- **D2. Pull cursor overlaps by a 60 s `received_at` window.** `bigserial` values are allocated at insert time, not commit
  time, so a transaction holding `seq 41` can commit after `seq 42` is visible; a pure `seq > cursor` pull would skip 41
  forever. Re-reading rows received in the last 60 s closes the gap for any transaction shorter than 60 s (ours last
  milliseconds) and costs nothing because apply dedups by `change_id`. The cursor still advances to the max `seq`.
  Rejected: advisory locks around the insert (serialises all publishers), and LISTEN/NOTIFY (extra connection, not needed).
- **D3. `hlc.json` is a fourth file.** S4 lists three files. The HLC must survive a restart even when no change is in
  `changes.ndjson` (everything pulled and compacted, or the cache deleted). Deriving it from the cache alone fails the
  "wall clock set back 5 minutes" acceptance after a cache reset. S4 and the plan table are amended to list `hlc.json`
  (a docs change in the PR that implements MPG-404, not in this PR).
- **D4. Registers are MPG-405's.** `registers.json` carries `pull_cursor` and an empty `registers` map. Nothing in
  MPG-404 folds. `aiur_intent_registers` (Postgres) is created but unused; MPG-405 may drop it from use and fold locally
  only, because a Postgres-side register cache would have to be rewritten on every late arrival (MPG-403 row 6).
- **D5. Sync rides the existing `LeaseStore` connection.** It inherits TLS, reconnect, timeouts and the fail-closed
  alert. A second Postgres pool would need its own reconnect and outage reporting.
- **D6. Allowed fields are a closed list.** `project`/`feature` fields (`priority`, `order_key`, `focus`) come from the plan's
  S3/S4 text and the MPG-402/407 tickets. MPG-404 can widen the list later without a schema change because `field` is `text`.
- **D7. Outbox before cache on write.** See Author path.
- **D8. No remote trust model in MPG-404.** Any holder of the shared database credential can insert any
  `origin_gateway`. That credential is already the trust root for leases (`AIUR_LEASE_DATABASE_URL`, removed from agent
  environments). Origin forgery is out of scope and recorded in Risks.

## Test scenarios

`Aiur.TestCleanup.rm_rf!/1`. Clocks are injected through the `:now_fun` option on `Hlc.start_link/1`, never the real
clock. The fixture gateway id is `"aaaaaaaaaaaaaaaaaaaaaaaaaa"` (26 chars of `[a-z2-7]`).

## Risks

- **Out-of-order `seq` (D2).** Detected by Y6. Fallback if a publisher ever holds a transaction over 60 s: raise the
  window; correctness is unaffected because apply is idempotent.
- **Unbounded cache growth.** `changes.ndjson` keeps every change forever. At human-edit rates (hundreds a day) it is
  megabytes a year. Detect: `Sync.status/0` exposes the line count; compaction belongs to MPG-405 after it defines which
  changes can be dropped without breaking fold results (a superseded takeover cannot be dropped, MPG-403 row 6).
- **Two daemons on one machine** share one outbox and may both push. The push is idempotent, so the result is correct;
  the cost is double work. Open question 2.
- **Origin forgery by a database writer (D8).** Out of scope; same trust root as leases.
- **Shared-database DDL.** `CREATE TABLE IF NOT EXISTS` runs at every connect on every instance, as today. A concurrent
  first run on two instances can fail one with a duplicate-name error; the existing `connect/1` already treats that as an
  `{:error, reason}` and retries with backoff, so the second attempt succeeds.
- **`lease_store.ex` at 496 lines.** Any edit that grows it breaks the oversized-file gate. The design adds zero lines
  there; `scripts/check-pr-structure.py` is the check.
- **Wall-clock set far forward.** A clock wrongly set a year ahead persists in `hlc.json` and every later tick sits a
  year ahead, even after the clock is fixed. Mitigation: `Hlc.start_link` refuses to boot from a persisted wall more than
  24 h ahead of `now` and instead raises `system.intent.hlc_ahead` (needs_attention) and uses the persisted value
  anyway, because lowering it would break the monotonic rule. The operator's repair is to delete `hlc.json` knowingly.
  This alert is the only reason the HLC is ever not strictly monotonic and is out of the acceptance scope.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| 1. Where do the intent files live: machine dir (`~/.config/aiur/machine/intent/`) or the daemon state root `<state root>/<instance key>/` | Machine dir. Intent is per gateway (machine), not per daemon, and survives an instance-key change | Per daemon state root gives two outboxes on a machine with two daemons and breaks "one gateway, one HLC" |
| 2. Two daemon nodes on one machine, both running `Sync` | Allow it; push is idempotent. Only `Store`/`Hlc` use a file lock (`:file.open` with `[:exclusive]` on `intent/.lock`, held for the process lifetime) so the second node's `Writer.write/1` returns `{:error, :intent_store_locked}` | Without the lock, two writers interleave `hlc.json` and can reissue an HLC value. With the lock, the second daemon cannot author intent until the first stops |
| 3. Pull overlap window | 60 s by `received_at` | A smaller window shortens re-reads but risks skipping a slow transaction; a larger one re-reads more. Fold results do not change |
| 4. Does a new internal component need `components/<name>.json` | Run `scripts/check-components.py --docs` on the implementation branch; add a component only if it fails. Recommend one `components/intent-sync.json` if the checker lists the new `Aiur.Intent.*` modules | Docs-only; no code change |
| 5. Outbox cap 10 000 lines | Keep; reject and alert beyond | An unbounded outbox hides a store that has been down for weeks; a lower cap rejects legitimate bursts only in absurd cases |
| 6. Hold threshold env hook (`:intent_hold_ms`) | Application env only, undocumented, tests only | Making it a config key adds a docs entry and `scripts/check-config-docs.py` coverage (MPG-403 open question c) |
| 7. Amend S4 to list `hlc.json` | Yes, in the MPG-404 PR | If not, the HLC floor must come from the cache and fails after a cache reset (H5 would be the only recovery) |
