# MPG-207 — Answer unauthenticated hello and list discoverable gateways: research

Research deep dive MPG-207R (issue #7590). Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579);
contract: MPG-207 in `docs/plans/2026-11-06-multi-project-gateways/tickets-m2.md`; schemas S2/S3 in `state-schemas.md`.
Paths are under `src/` unless they start with `packaging/` or `website/`. Facts marked **[probed]** were read from a
live `tailscale` 1.98.9 on the research host (2026-11-06); the rest come from the code at `origin/main` and the
prior-art report `docs/research/multi-gateway/gateway-enrollment-and-permissions.md`.

## Outcome

`GET /api/v1/gateway/hello` answers with no credential and returns exactly
`{gateway_id, gateway_label, build, tls_fingerprint_sha256, enrollment}` (`enrollment` is `"open"` or `"closed"`).
`aiur gateway discover` prints two kinds of row: tailnet peers that answered hello and are not in the registry
(`discovered (not enrolled)`) and registry entries that answered (`enrolled`). With no `tailscale` binary it lists the
registry entries only and prints `Tailscale not found; showing registered gateways only`. Discovery reads; it never
writes the registry, a token file or a grant. With `server.gateway_hello: false` the route answers 404.

## Design

### Findings from the code and the probe (corrections to the contract)

1. **`tailscale status --json` cannot filter peers by capability. [probed]** A peer object has `Tags`, `Online`,
   `DNSName`, `HostName`, `TailscaleIPs`, `ID`, `PeerAPIURL` and no `CapMap`. Only `Self` has `CapMap`. So the
   research report's "enrolment candidate only if its `WhoIs` `CapMap` holds the fleet capability" is a **receiver-side**
   check on an inbound caller; it cannot be used to *list* peers from the caller's side. Listing can filter only on
   `Tags` and `Online`.
2. **`tailscale whois --json <ip>` does return `CapMap`, `Node.Tags` and `UserProfile`. [probed]** The `CapMap` it
   returns is the capabilities the *queried node* holds, keyed by full name (`https://tailscale.com/cap/ingress`). It
   is not the capability set the queried peer holds toward the caller, which is the open question the report left
   ("unverified ... direction"). Do not use `CapMap` for direction; use it only to ask "is this node a fleet gateway".
3. **Tags are not a trust signal.** Tagged peers on the research tailnet are `tag:ingress` Funnel nodes. A `tag:gateway`
   string tells discovery which peers are worth probing, nothing more; hello is probed per peer and an answer from a
   non-gateway is simply no row.
4. **`public_bind` is `not loopback?(ip)`** (`lib/aiur/http_server.ex:147`), so a daemon bound to a tailnet address
   already counts as a public bind. The contract's default ("true on tailnet-bound or loopback, false on public bind")
   cannot be computed from `public_bind` alone. It needs a new predicate `tailnet_ip?/1`: IPv4 in `100.64.0.0/10` or
   IPv6 in `fd7a:115c:a1e0::/48`. Default is `true` when the bound ip is loopback or `tailnet_ip?`, and `false`
   otherwise (`0.0.0.0`, LAN, public). An explicit `true`/`false` always wins.
5. **The new route must be declared before the catch-all and outside every auth pipeline.** `routes/api.ex`
   `reads_and_catch_all` ends in `match(:*, "/*path", ... :not_found)` and every other `/api/v1` scope pipes through
   `:client_token_read` or `:client_token_write`. `ClientTokenAuth` treats every `/api/v1/*` path as needing a token
   (`client_token_auth.ex:48-60`), so hello needs its own scope with no auth pipe, like the webhook receiver
   (`GithubWebhook.receiver()` in `router.ex`). It still passes through the host allowlist plug on the endpoint.
6. **There is no `Aiur.Gateway` namespace and no `gateway/cli.ex` in the tree today.** MPG-001 creates
   `lib/aiur/gateway/identity.ex`; MPG-208 and MPG-209 add `invite`, `join`, `list`. The contract's "add `discover` to
   `src/lib/aiur/gateway/cli.ex`" therefore means MPG-207 **creates** `cli.ex` if it merges first. Dispatch is in the
   launcher: `aiur capabilities` is a case arm in `aiur-engine.sh:368` plus a sourced `aiur-capabilities.sh`; `gateway`
   needs the same pair (`cmd_gateway` + `aiur-gateway.sh`) and a help line. The rest of MPG-207 depends on this.
7. **Hello leaks nothing a probe could not already learn.** `gateway_id` is the machine id (public by design, it is the
   pin), label and build are display values, the fingerprint is public by construction, `enrollment` is a boolean-like
   string. Do not add hostnames, project names, agent counts or tailnet name; the contract's "and nothing else" is a
   test, not a hope.

### Decisions

- **Hello controller.** `AiurWeb.GatewayHelloController.show/2` builds the body from `Aiur.Gateway.Identity.current/0`
  (MPG-001), `to_string(Application.spec(:aiur, :vsn) || "unknown")` for `build` (the exact expression
  `Aiur.Identity.instance_section/0` in `src/lib/aiur/identity.ex` uses for `aiur_version`, which `aiur capabilities` reports;
  no new accessor; the value is the `mix.exs` `version:` string, e.g. `"0.0.9"`, or `"unknown"` if the app spec is absent), `Aiur.Gateway.Hello.tls_fingerprint/0` and `Aiur.Gateway.Hello.enrollment/0`. It
  sets `cache-control: no-store`. With identity unavailable (`identity.json` missing) it returns
  `gateway_id: null` and still 200, matching MPG-001; a null id is never invented and discovery shows it as
  `unidentified`.
- **`tls_fingerprint_sha256`** is the SHA-256 of the DER certificate the listener presents, when the daemon terminates
  TLS itself, and `null` otherwise (plain HTTP on loopback, or a tunnel that terminates TLS). MPG-208R already
  defaults to "pin disabled, token only, warn" for the tunnel case; hello reports the same `null`.
- **`enrollment`** is `"open"` when a non-expired, unused invite exists (MPG-208's `Aiur.Gateway.Invites`), else
  `"closed"`. Until MPG-208 lands, `Hello.enrollment/0` returns `"closed"`. It never carries invite data.
- **Route ordering and method handling.** `match(:*, "/api/v1/gateway/hello", ..., :method_not_allowed)` with
  `allow: GET`, same as `CapabilitiesController`.
- **Rate limiting: none in this ticket.** The body is static and cheap. If flooding matters, the host allowlist and the
  tailnet are the boundary; record as a risk, do not build a limiter.
- **Discovery source order.** (1) registry entries (`~/.aiur/remote-instances.yaml`, via the launcher parser) are
  probed at their `url`; (2) if `tailscale` exists, `tailscale status --json` yields peers where `Online` is true and
  either `Tags` contains `server.gateway_tag` (new, default `tag:gateway`) or no tag filter is configured;
  each is probed at `https://<DNSName without trailing dot>:<port>/api/v1/gateway/hello`.
- **Which port to probe.** A peer's daemon port is not in `status --json`. Default to the same port as the local
  daemon, plus an explicit `--port` flag; a port-0 daemon is not discoverable by this route and is said so. Registry
  entries use their own url.
- **`WhoIs`: do not use it in this ticket.** Hello is deliberately anonymous, so there is no inbound identity to
  resolve. `WhoIs` belongs to MPG-208's `enroll` (the receiver deciding whether a caller is a fleet node) and,
  optionally, to MPG-206 as the coarse gate. Using it here would add a LocalAPI dependency (a unix socket at
  `/var/run/tailscale/tailscaled.sock` the daemon user may not be able to read) for no behaviour the contract asks for.
  If MPG-208 later wants it, shell out to `tailscale whois --json <remote_ip>` with the existing bounded runner
  rather than speaking the LocalAPI socket directly.
- **Reuse the bounded Tailscale runner.** `Aiur.TailscaleFunnel` already has an executable lookup, a 5 s timeout and
  port cleanup (`tailscale_funnel.ex:160-340`), all private. Extract them to `Aiur.Tailscale.Cli.run/3` (new, tiny)
  and have `TailscaleFunnel` call it; do not copy 120 lines. The extraction changes no Funnel behaviour, and
  `tailscale_funnel_test.exs` is the guard.
- **Probe safety.** Each probe: `GET` only, 2 s timeout, redirects off, response body capped at 4 KiB, JSON must have
  exactly the five keys with string-or-null values, otherwise the row is `answered, unrecognised`. No credential is
  ever sent to a discovered peer. The probes run in parallel (`Task.async_stream`, max concurrency 8).
- **Registry mismatch.** A registry entry whose hello `gateway_id` differs from its pinned `gateway_id` shows
  `identity mismatch` and is not counted as `enrolled`. This reuses MPG-201's comparison, not a second one.

### Alternatives considered

- *Filter peers by capability from `status --json`.* Impossible (finding 1).
- *Use `WhoIs` to authenticate hello.* Defeats the endpoint's purpose (a joiner has no credential yet) and adds a socket
  dependency (above).
- *mDNS / DNS-SD LAN discovery.* The report allows it as an opt-in hint, but the plan scopes discovery to the tailnet
  and the registry; deferred.
- *Always-on hello.* Rejected by the plan (line 375: "can be turned off"); the bind-aware default is finding 4.

## Prior art

- `docs/research/multi-gateway/gateway-enrollment-and-permissions.md` § "Discovery yields candidates": discovery only
  produces candidates; tagged nodes plus a custom app capability; `WhoIs` for receiver-side identity; never put the
  control API on Funnel. This ticket follows the first and last points and corrects the second (findings 1-2).
- Syncthing / k3s join-string comparisons in the same report support a hello that exposes the fingerprint so a joiner
  can compare it with the code (MPG-208).
- Tailscale `status --json` and `whois --json` shapes: read from the live CLI (findings 1-2, **[probed]**). External
  docs were not fetched; no `deep-research` run was needed, since the prior-art report answers the remaining
  question and the probe answers the filtering question.

## Test scenarios

| Scenario | Input | Expected |
|---|---|---|
| **[fails without]** Hello with no credential | `GET /api/v1/gateway/hello`, no `authorization` | 200; JSON keys exactly `gateway_id, gateway_label, build, tls_fingerprint_sha256, enrollment`; `gateway_id` equals the fixture `identity.json` id |
| Hello off | `server.gateway_hello: false` | 404, body identical to any unknown path |

| No identity file | no `identity.json` | 200, `gateway_id: null`, no invented id |
| Enrollment state | no invite / one live invite (after MPG-208) | `"closed"` / `"open"` |
| Default by bind | ip `127.0.0.1` / `100.101.102.103` / `fd7a:115c:a1e0::1` / `0.0.0.0` / `192.168.1.5` | on / on / on / off / off |
| Explicit wins | `gateway_hello: true` with ip `0.0.0.0` | on |
| No Tailscale binary | runner returns `:tailscale_executable_not_found`, registry has `nook` answering | one `enrolled` row, line `Tailscale not found; showing registered gateways only`, exit 0 |
| Peer filtering | status JSON: 3 peers (`tag:gateway` online, `tag:gateway` offline, untagged online) | only the first is probed |
| Not enrolled vs enrolled | peer answers hello, id absent / present in registry | `discovered (not enrolled)` / `enrolled` |
| Identity mismatch | registry pin `A`, hello says `B` | row `identity mismatch`, not `enrolled` |
| Bad hello body | extra key `hostname`, or a 12 KiB body, or a redirect | `answered, unrecognised`; nothing from the body is displayed |
| Unreachable peer | probe times out at 2 s | row `unreachable` (not `offline`: absence of an answer is not proof of offline) |
| Discovery is read-only | snapshot `remote-instances.yaml`, token dir, grants before/after `discover` | byte-identical |
| Probe sends no credential | stub peer records request headers | no `authorization` header |
| Funnel unchanged | existing `tailscale_funnel_test.exs` | passes with no edits |

## Data and assets

- `tailscale status --json` fields used: `Peer[*].{DNSName, HostName, Tags, Online, TailscaleIPs}`; ignore the rest.
  The trailing dot on `DNSName` is stripped. `Tags` may be `null`. Treat any parse error as "no Tailscale data" and
  say so; do not crash.
- Peers on IPv6-only addresses are probed by `DNSName`, never by a bare IPv6 literal without brackets.
- Config: `server.gateway_hello: true|false` (default: bind-aware), `server.gateway_tag: string` (default
  `tag:gateway`; empty string disables the tag filter). The second key is an addition beyond the contract; if the
  operator prefers no new key, hard-code `tag:gateway` (open question 2).
- Machine-readable output for `--json`: `{gateway, connectivity, kind, gateway_id, observed_at, age_ms, freshness}`
  per row, following the freshness rule in `AGENTS.md`: a discovery result is `observed_at` now and `age_ms: 0`; an
  unreachable row carries no invented values.

## Risks

- **Port-0 daemons are undiscoverable by name.** Detect early: the test with `server.port: 0`. Fallback: registry
  entries carry a url, and `--port` is explicit.
- **`status --json` shape drift between Tailscale versions.** Probed on 1.98.9 only. Parse defensively; one test feeds
  JSON without `Tags`.
- **Hello advertises the machine id to anyone who can reach the port.** That is the same value a pin makes public; keep
  the default off on LAN and public binds, which is finding 4's reason for existing.
- **Merge order.** MPG-207 depends on MPG-001 and MPG-206 but also creates `cli.ex` that MPG-208/209 extend; whoever
  merges second resolves a one-file conflict. Serialize 207 before 208 and 209 as the plan already lists.
- **`public_bind` mismatch could silently expose hello on a LAN bind** if the predicate were written against
  `public_bind`. The bind table test guards it.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| Should discovery also use `WhoIs`-checked capability (`<domain>/cap/gateway`) to filter inbound callers? | No in MPG-207; decide in MPG-208/206 where there is a caller to check | Adds a `tailscale whois` shell-out per hello request and a configured capability domain |
| Add `server.gateway_tag` or hard-code `tag:gateway`? | Add the key, default `tag:gateway`, empty disables | Without the key, operators with other tag names cannot filter and probe every online peer |
| Which port to probe on a peer? | Local daemon port, override with `--port`; registry entries use their url | A fixed well-known gateway port would remove `--port` but needs a new listener |
| Should `unreachable` peers be listed? | Yes, as `unreachable`, only for registry entries; tailnet peers that do not answer are omitted | Listing every non-answering tailnet peer floods the output on a large tailnet |
| Where does `build` come from? | `to_string(Application.spec(:aiur, :vsn) \|\| "unknown")`, as in `Aiur.Identity.instance_section/0` (`aiur_version`) | Resolved; no accessor needed |
| Is `cli.ex` created here or by MPG-209? | Created here with only `discover` | If 209 lands first, MPG-207 appends one clause and the launcher arm |
