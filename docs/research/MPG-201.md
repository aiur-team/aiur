# MPG-201 — Pin gateway identity in the remote registry: research

Research deep dive MPG-201R (issue #7584). Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579);
contract: MPG-201 in `docs/plans/2026-11-06-multi-project-gateways/tickets-m2.md`; schema S2 in `state-schemas.md`.
Paths below are under `packaging/npm/aiur-cli/libexec/` (`engine/` = `libexec/engine/`) unless they start with `src/`,
`packages/` or `website/`.

## Outcome

An entry in `~/.aiur/remote-instances.yaml` may carry `gateway_id`, `label`, `tls_pin_sha256` and an `allows` block.
`aiur --instance <name> <cmd>` compares the `gateway_id` in every successful control response with the pinned one. A
mismatch exits 77 with `gateway identity mismatch for '<name>'` and prints no command output. An entry with no
`gateway_id` behaves as today, and the first successful call prints, on stderr, the id it saw and the exact YAML line
to pin it. **Pinning never writes the registry** (the answer to this ticket's focus question). A registry file
written by today's launcher parses unchanged in the shell parser and in the Stream Deck parser.

## Design

### Findings from the code (corrections to the contract)

1. **Today's parsers reject the new keys; they do not "ignore unknown keys".** `engine/remote.sh:177-181` fails with
   `unsupported instance field` for anything at indent 4 other than `url|token_file|token_env`, and indent 6 hits
   `expected zero, two or four spaces of indentation` (`remote.sh:206`). `packages/streamdeck/src/instances.ts:42`
   does the same. So MPG-201 must teach both parsers the new keys *and* skip the nested `allows:` block. A
   registry using the new keys is rejected by launchers older than this change; that cannot be fixed from here and
   is stated in the docs.
2. **`url` and a token reference are required today** (`remote.sh:128-129`, `instances.ts:23`), but S2 lets a peer
   entry omit `url` (inbound-only peer: the entry exists only so MPG-206 can read `allows`). Both parsers must accept
   an entry with no `url` and no token reference when it carries `allows` or `gateway_id`, and treat it as not
   callable: `--instance nook` exits 64 `remote instance 'nook' is inbound-only (no url)`, `--instance all` and the
   `*` listing skip it, and Stream Deck omits it from its targets.
3. **The response already has a place for the id.** `engine/remote.sh:453` reads `instance_id` from the 200 body
   with `remote_json_field`; MPG-001 adds `gateway_id` and `gateway_label` beside it in
   `control_controller.ex` `result/3`. MPG-201 reads `gateway_id` the same way. Both the single-target path and
   the `--instance all` fan-out go through `run_remote_rpc_with_timeout` (`remote_all.sh:91`, `:235`), so one check
   covers both; `remote_all.sh` needs no new logic.
4. **Error responses (401/403/422/504) carry no `gateway_id`**, so they cannot be checked. Only a 200 is checked.
   That is the right scope: the pin protects the *output* a user acts on.
5. **The pin cannot protect the bearer token.** The token is sent before the response is read. A DNS or Tailscale
   mix-up delivers the token to the wrong gateway; the response check then only refuses to show its output. Closing
   that gap is `tls_pin_sha256` (below) and the invite flow of MPG-207/MPG-208 (pin the target before any secret is
   sent). The docs say so plainly rather than claim the pin is a credential-theft control.

### Answer to the focus question: does pinning write the file automatically?

**No. Print the line.** Reasons:

- The registry is hand-edited, commented YAML, mode 0600, that other tools read (Stream Deck sidecar, MPG-206's
  receiver). The shell parser is an `awk` subset with no writer; a rewriter would drop comments and ordering or need
  a second YAML implementation.
- Automatic pinning on first contact is trust-on-first-use against exactly the wrong-host case the pin exists for
  (finding 5): the first answer might be the wrong gateway, and `--instance all` read fan-out would write several
  files in parallel.
- S2 says "no remote command can write it" and a pin is a trust decision; a human pasting a line is the explicit
  step. MPG-208's enrolment flow, which pins as part of a deliberate invite, is the right place for automatic
  writes, and it will use a real writer then.

Alternatives rejected: `aiur --instance nook --pin` writing in place (needs the writer above for one rarely used
flag); an `aiur gateway pin <name>` command (belongs to MPG-208/MPG-202 CLI surface, not this ticket).

### "Records the remote id": a seen-id marker, not the registry

The contract's Outcome says the first successful call "records" the id and the second acceptance item says it prints
the id "once". Both are met by a per-entry marker file, never the registry:

- Path: `${AIUR_REMOTE_STATE_DIR:-$HOME/.aiur/remote-state}/seen-gateway/<name>` (the engine already keeps
  per-instance state in `remote-state`, `remote_all.sh:107`; the name matches `^[A-Za-z0-9._-]+$`, so it is path
  safe). Directory mode 0700, file mode 0600, content = the 26-char id.
- Unpinned entry, no marker: after a successful 200 whose `gateway_id` is non-empty, write the marker and print to
  stderr:
  `aiur: 'nook' answered as gateway 7mq2...26chars (label Nook). To pin it, add under nook: in ~/.aiur/remote-instances.yaml:`
  `    gateway_id: 7mq2...`
- Unpinned entry, marker equals the id: silent.
- Unpinned entry, marker differs: **warn on stderr, do not refuse, update nothing** (`aiur: 'nook' now answers as
  gateway <new>; it answered as <old> before. Pin the one you trust.`). The contract's second acceptance item says an
  unpinned entry "works as today", which is incompatible with refusing on drift, so refusal is reserved for pinned
  entries. (Open question 1.)
- A failed marker write is non-fatal (the hint prints every time); a read-only home must not break a status call.
- Stderr only, so `--json` and piped stdout are unchanged. `aiur watch` would repeat a hint only until the first
  marker write succeeds.
- Fan-out: each instance has its own marker file, so parallel subshells never write the same path.

### The check (single place)

In `run_remote_rpc_with_timeout`, inside the `200)` branch, **before** `AIUR_CONTROL_RPC_OUTPUT` is assigned:

```text
seen="$(remote_json_field "$response_file" gateway_id)"        # empty when absent/null
if [ -n "$AIUR_REMOTE_GATEWAY_ID" ]; then
  if [ -z "$seen" ]      -> stderr "aiur: gateway identity unverified for '$name' (response carries no gateway_id)", status 77
  elif [ "$seen" != pin ] -> stderr "aiur: gateway identity mismatch for '$name'",                              status 77
else
  remote_gateway_seen_note "$name" "$seen"
fi
```

- Exit 77 matches the plan ("Registry pins aaaa…, server answers bbbb…: exit 77") and the existing "token rejected"
  class. The message must contain `gateway identity mismatch for 'nook'` verbatim (acceptance item 1); the extra
  detail (expected and seen ids, label) goes on a second stderr line so the first line stays greppable.
- **A pinned entry whose response has no `gateway_id` is refused** (exit 77, `unverified`): a pin is an assertion,
  and a build without MPG-001, or a machine whose `identity.json` is unavailable (`gateway_id: null`,
  `gateway_identity: "unavailable"`), cannot confirm it. Silently passing would turn the pin into decoration.
  (Open question 2.)
- `gateway_id` comparison is exact, case-sensitive string equality on the 26-char `[a-z2-7]` machine id
  (`src/lib/aiur/identity/store.ex:36`).
- `label` is display data. It is never compared; it is printed in the mismatch and hint lines and is read by
  MPG-202's resolver.
- A mismatch in `--instance all` marks that row failed with exit 77 and the standard error text; the other rows still
  print (the fan-out already isolates rows). The highest exit code wins as today.
- A timed-out or 5xx write is unchanged: the identity check never runs for non-200.
- Write commands: the check runs after the remote already acted. For a pinned entry that mismatches on a *write*,
  the output is withheld but the write happened on the other gateway. The error line therefore says
  `the command may have run on the gateway that answered` for write scope (`AIUR_REMOTE_MAX_SCOPE` is not the right
  signal; use the existing `control_command_label`/classification that already distinguishes timeout-unknown). Simpler
  and sufficient for this ticket: always append that sentence to the second line. Prevention before the write is the
  TLS pin or the hello check (MPG-207), not this ticket.

### Registry keys and validation

New optional keys at indent 4: `gateway_id`, `label`, `tls_pin_sha256`, and `allows:` (a key with no inline value,
followed by a nested block at indent 6 and deeper).

| Key | Validation in MPG-201 | Used by |
|---|---|---|
| `gateway_id` | `^[a-z2-7]{26}$`, else `invalid remote instance registry <file>:<line>: gateway_id must be 26 base32 characters` | the check above; MPG-202 resolver |
| `label` | 1-64 chars, no control characters (quoted-scalar rules of `scalar()` already forbid escapes) | display; MPG-202 resolver |
| `tls_pin_sha256` | `^[0-9a-f]{64}$` (lowercase hex; uppercase and `sha256//` forms rejected so there is one spelling) | curl pinning (below) |
| `allows` | **skipped, not validated**: lines at indent >= 6 under `allows:` are consumed and ignored; indent 6 anywhere else is still invalid | MPG-206 validates and enforces |

Duplicate keys are invalid, as for `url`. `awk` emits extra `gateway_id`, `label`, `tls_pin_sha256` lines in the
per-target record; `load_remote_instance` reads them into `AIUR_REMOTE_GATEWAY_ID`, `AIUR_REMOTE_LABEL`,
`AIUR_REMOTE_TLS_PIN` (reset to empty at the top, next to `AIUR_REMOTE_URL`). The `*` listing keeps its two-column
`name<TAB>url` shape so `remote_all.sh` callers are untouched; inbound-only entries are omitted from it.

### `tls_pin_sha256`

S2 and KTD-10 expect it for self-signed endpoints. Decision: **parse and validate it, and enforce it for the CLI in
this ticket. MPG-201 is the sole owner of enforcement**; MPG-208 only writes the key (from an invite) and never touches curl with curl's `--pinnedpubkey "sha256//<base64>"`, because a pin that is parsed and ignored gives false
assurance and the enforcement is three lines. The value is the SHA-256 of the server's *public key* (SPKI), the
quantity curl pins, written as hex; the shell converts hex to base64 with the Node runtime the script already
requires (`remote_js_runtime`). A certificate fingerprint (`openssl x509 -fingerprint`) is a different value and
would never match; the docs give the one-line `openssl` command that produces the right hex.

- With a pin present, curl is also given `--insecure` *only if* the endpoint is HTTPS and the pin is set, since the
  point of the pin is a self-signed certificate; pin match is then the sole authentication of the endpoint. Without a
  pin nothing changes: normal CA verification, no `--insecure`.
- Before relying on this, the implementer proves in a test that curl rejects a wrong pin and accepts the right one
  against a local self-signed HTTPS server with `--insecure` (the test scenarios below). If curl on a supported
  platform pins correctly only with CA verification on, fall back to: parse-only, and print `tls_pin_sha256 is not
  enforced by this client` on stderr whenever it is set. (Open question 3.)
- Stream Deck does not enforce the pin (browsers and its HTTP client cannot; the plan already says "Supported for
  CLI"). It parses and carries the value only.

### Stream Deck parser

`packages/streamdeck/src/instances.ts`: same keys, same skip of `allows:`, same inbound-only rule (entries without
`url` are dropped from `targets`, not an error). `InstanceTarget` gains optional `gatewayId?`, `label?`, `tlsPin?`
for MPG-202; nothing else in the switcher changes and the sidecar does **not** verify identity (the contract asks
only that the file parses). Unknown keys other than these four remain invalid in both parsers, matching "same
parser, same keys".

## Prior art

None needed for a new external question. The relevant prior art is already in `docs/research/multi-gateway/`
(`gateway-enrollment-and-permissions.md`, discovery and enrolment notes): identity pinned to the target before a
secret is sent, and no remote write of trust state. This ticket applies the same stance to an existing, already
authenticated registry: SSH `known_hosts` and `ssh-keygen -lf` show the same shape (print the fingerprint, the human
adds it; `StrictHostKeyChecking=ask` prompts rather than silently writing). The design above chooses "print, never
write" without the prompt because the CLI is frequently non-interactive (agents, `watch`, fan-out).

## Data and assets

- Fixture ids `A`, `B` above; real ids come from `identity.json` (`[a-z2-7]{26}`).
- Self-signed cert fixture for the TLS test: generate at test time with `openssl req -x509 -newkey ec ...` into the
  test temp dir; compute the SPKI hash with `openssl x509 -pubkey -noout | openssl pkey -pubin -outform der |
  openssl dgst -sha256 -binary | xxd -p -c 64`. If `openssl` is missing in CI the TLS pair is skipped with an
  explicit skip message, and the docs claim for pin enforcement is limited accordingly.
- Known gap: no gateway reports `gateway_id` until MPG-001 merges. MPG-201 is independent for tests (the fake server
  supplies it) but depends on MPG-001 for any live use, as the contract already states.

## Risks

- **Pinned-but-silent builds**: operators pin an id against a build without MPG-001 and every call exits 77. The
  message names the cause (no `gateway_id` in the response), and the docs note that pinning needs MPG-001's build.
- **`remote.sh` size** (497/500): the awk moves to `registry.awk` and the helpers to `remote_identity.sh`, otherwise the file-size gate
  fails the PR. Detect with `wc -l` before pushing.
- **Module list**: a new engine file not named in `AIUR_ENGINE_MODULES` is never sourced, and every remote call fails
  with `command not found`. The identity tests cover it because they run through the real engine.
- **Write already happened** on a mismatching gateway (finding 5): disclosed in the error text and the docs; real
  prevention is the TLS pin and MPG-207/MPG-208.
- **curl pin behaviour with `--insecure`** differs by TLS backend; guarded by the test pair and the documented
  fallback.
- **Older launchers reject registries that use the new keys**; documented, not fixable.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| 1. Should an *unpinned* entry refuse (not warn) when the id differs from the first one seen? The Outcome sentence reads as trust-on-first-use; the acceptance item says unpinned "works as today". | Warn only; refuse only when pinned. | Refuse-on-drift needs a way to reset a marker (delete the file or a flag) and makes unpinned entries stateful; it would also break an unpinned entry after a legitimate machine reinstall. |
| 2. Pinned entry, response without `gateway_id`: refuse or pass? | Refuse (exit 77, `unverified`). | Passing keeps old builds working with a pin but makes the pin a no-op exactly when identity is unavailable. |
| 3. Enforce `tls_pin_sha256` in this ticket, or parse only? | Enforce via `--pinnedpubkey` + `--insecure`, guarded by the two TLS tests; fall back to parse-only with a stderr notice if curl cannot pin on a supported backend. | Parse-only shrinks the ticket by one unit and would leave enforcement unowned (MPG-208 only writes the key), leaving self-signed peers unusable from the CLI until then. |
| 4. Where does the seen marker live? | `remote-state/seen-gateway/<name>` beside the existing per-instance state. | A single JSON file is simpler to inspect but needs locking under `--instance all`. |
| 5. Should Stream Deck verify the id? | No; parse only. | Verifying adds a fetch of `gateway_id` to the sidecar's connection path and belongs with MPG-202's resolver. |
| 6. Should `label` be unique across entries (MPG-202 resolves by label)? | Not validated here; MPG-202 refuses ambiguous labels at resolve time. | Validating here would reject a registry that is fine for `--instance <name>`. |
