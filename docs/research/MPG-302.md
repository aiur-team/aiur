# MPG-302 — Give each process a project context that config reads: research

Plan: [multi-project gateways](../plans/2026-11-06-multi-project-gateways.md). Contract: `tickets-m3.md` MPG-302.
Reads: [MPG-301](MPG-301.md) §3 (context resolution), §5 (migration order), §7 (`Aiur.ProjectCase`).
Focus of this memo (MPG-302R): the memo in `config/settings_snapshot.ex` and how every cache key on the config read
path must include the project id.

Code references are to `src/lib/aiur/` at `7d5cc6199`.

## Outcome

`Aiur.Project.Context.put/1` and `current/0` exist. `Aiur.Config.settings/0` and `settings!/0` return the settings of
the current process's project. `Aiur.Project.Task.async/1` copies the context. With no context, every function
behaves byte-for-byte as today. A test boots two projects (`o/a`, `o/b`) and sees
`Config.settings!().tracker.github.repo` return `o/a` in a process holding project A and `o/b` in one holding B.

## Design

### What actually memoizes config today (four places, not one)

The ticket names `config/settings_snapshot.ex`. Reading the read path shows **four** memos, and a project id has to
reach all of them or the contract test passes while a stale value leaks through the one that was missed.

| # | Memo | Where | Scope today | Key today | Wrong with two projects because |
|---|---|---|---|---|---|
| 1 | Process-dictionary snapshot | `config/settings_snapshot.ex:2-21` (`@key {__MODULE__, :settings}`) | one poll or status batch, one process | none (a single slot) | `run/1` stores `Config.settings()` once; `read/1` returns it without looking at the project. If a process switches context inside the batch, or a nested `run/1` is entered under another project, it serves the first project's settings. |
| 2 | Published workflow | `workflow_store/cache.ex:50-59` row `:current`, `put/3`, `fetch/1` | VM, one row | the config **path** (`{:stale, other}` when it differs) | One row. With project B's path, `fetch/1` returns `{:stale, path_of_A}`, and `WorkflowStore.current*/0` falls back to `Workflow.load()` — a disk read and YAML parse on **every** call (`workflow_store.ex:62-65,86-88,105-107`). Correct but unbounded cost on the most-called read in the system. |
| 3 | Parsed-settings memo | `cache.ex:86-95` row `:settings`, `config.ex:84-103` | VM, exactly one memo | `{{generation, publication_ref}, {env_epoch, catalog}}` | "Exactly one memo is kept" (`cache.ex` docs). Two projects each overwrite it, so every read is a miss. Correct, because `publication_ref` is unique per `put/3`, but it parses on every call. |
| 4 | Env-names memo | `cache.ex:118-130` row `:env_names`, `config.ex:127-135` | VM, one row | `cache_identity` | Same single-slot thrash as 3. |

Rows 2-4 are **not unsafe today only because `publication_ref` is a fresh reference per publish** (a hit needs an
identical ref). That is an accident of the key shape, not a project fence. The design below makes the fence explicit
instead of relying on it.

### Decision 1: the cache table stays one shared named table; rows are keyed by project id

Change the three row keys from atoms to tuples:

```elixir
{:current, project_id}   # {key, path, workflow, generation, publication}
{:settings, project_id}  # {key, memo_key, settings}
{:env_names, project_id} # {key, memo_key, names}
```

`project_id` is `nil`-safe: `Aiur.Project.Context.current/0 -> nil` maps to the atom `:default`
(`Cache.project_key/1`), so the no-context rows are `{:current, :default}` etc. and nothing changes for today's
callers. Every public function of `Aiur.WorkflowStore.Cache` gains a leading `project_id` argument, and keeps a
0-project arity that delegates with `Context.current_id()` where callers do not care (the 3-arity `put/3` at
`test/aiur/workflow_store_test.exs:216` keeps working unchanged).

Alternative rejected — unnamed per-project tables with the tid in `:persistent_term` (MPG-301 §3). That rule is for
**tables a project's own process owns**. This table is owned by the store and filled in by whichever *reader* needs the
parse (`cache.ex` moduledoc: "`:public` because the parsed-settings memo … is filled in by whichever reader"). A
per-project tid would need a `persistent_term` write (a global GC pause) per project at boot and a lookup per read,
for no isolation the row key does not already give. MPG-304 may still decide to move it; this memo keeps rows keyed
by project id so that move is a rename, not a redesign. Recorded as open question 2.

The `{:stale, other_path}` fence in `fetch/1` is **kept**, per project: a row for project B whose path differs from
the path B's context resolves to is stale. Cross-project reads can no longer produce `{:stale, ...}` (they hit
different rows) and so no longer degrade to disk reads.

### Decision 2: the snapshot memo is keyed by project id

`SettingsSnapshot` stores `{project_id, settings}` in the process dictionary. `read/1` returns the stored settings only
when the stored project id equals `Context.current_id()`; otherwise it calls `load.()` (live). `run/1` nests by
project: a nested `run/1` under the **same** project reuses the outer snapshot (today's behaviour, pinned by
`test/aiur/idle_cpu_hot_paths_test.exs:19-28` and `daemon_idle_work_test.exs:37-64`); under a **different** project it
takes its own snapshot for the duration of the call and restores the outer one in `after`. The `try/after` that
deletes the key becomes a restore of the previous value.

Why not drop the snapshot: it saves one ETS lookup plus an `env_epoch/2` sample per read across ~300 call sites per
status render (`config.ex:111-123` comment), and `with_cached_roots/1` rides on the same boundary.

### Decision 3: where the project's config path comes from

`Workflow.workflow_file_path/0` (`workflow.ex:37-42`) is the single seam. New precedence:

1. per-process override pinned by `set_workflow_file_path/1,2` (tests; unchanged, still wins);
2. **the current project's `config_path`** (new);
3. VM-global `:workflow_file_path` app env;
4. run-folder discovery.

The project sits *below* the per-process pin so an existing test that pins a path keeps its view, and *above* the VM
global so a project tree is not redirected by an unrelated `Application.put_env`. With no context, step 2 is skipped
and the function is identical to today.

Twenty-five call sites outside `workflow.ex` read `workflow_file_path/0` (`workflow_store.ex`, `model_discovery.ex`,
`global_config_startup.ex`, `cli.ex`, `config.ex`, `model_availability.ex`, `client_tokens_cli.ex`,
`config/tracker_settings.ex`, `github/ci_readiness*.ex`, `init/github.ex`, `github/config.ex`, `workflow_store/reload.ex`,
`alerts/config.ex`, `cli/runtime_deps.ex`, `mix/tasks/aiur.test.reset.ex`). They all pick the project path up for
free; none is edited. MPG-302 must read each once to confirm none runs in a **machine-level** process that would now
see a project path (see Risks).

### Decision 4: the store is untouched in behaviour; project stores arrive in MPG-304

MPG-302 does not start a second `WorkflowStore`. Under a non-default project the read path is:
`Workflow.current_with_cache_identity/0` → `WorkflowStore.current_with_cache_identity/0` → `Cache.fetch(project_id,
path)` → miss (`:error`) → falls to the existing "store alive, ask it" branch, which `GenServer.call`s the default
store and would return **the default project's** workflow. That is wrong for project B and is the one real
correctness hole in the code path. So:

- `WorkflowStore.current*/0` (`workflow_store.ex:56-68,80-93,99-117`): when `Context.current_id()` is non-nil and
  the row is a miss, **load from disk** (`Workflow.load/0`, which reads `workflow_file_path()` = the project path) and
  return identity `:unknown`. Never call the singleton store for a non-default project.
- `Config.cached_settings/2` already treats `:unknown` identity as `settings_from({:ok, workflow})`
  (`config.ex:62-64`), so settings are correct and uncached for a project that has no store yet.
- The cost is a YAML parse per read for non-default projects until MPG-304 gives each project a store that publishes
  rows under its project id. MPG-302 ships with that cost on purpose: nothing in production sets a context until
  MPG-306, and the alternative (a stopgap per-project cache) would be thrown away by MPG-304.

`Reload.reload_state/1` (`reload.ex:49-57`) compares `Workflow.workflow_file_path()` with `state.path` **in the
store process**, so a context in a *caller* never re-points the store. Keep it so: MPG-302 must not make the store
read its caller's context. The store process holds no context (it is a machine/default child), so `Cache.put/4`
from `Reload.commit/2` (`reload.ex:264`) publishes under `Context.current_id()` = `:default`. MPG-304 gives each
project store its own context via `$ancestors`, which publishes under that project with no further change.

### Decision 5: `Aiur.Project`, `Context`, `Task` (shapes)

```elixir
# src/lib/aiur/project.ex
defmodule Aiur.Project do
  @enforce_keys [:id, :repo, :config_path, :state_root]
  defstruct [:id, :repo, :config_path, :state_root]
  @type id :: String.t()
  @type t :: %__MODULE__{id: id(), repo: String.t(), config_path: Path.t(), state_root: Path.t()}
  @spec from_machine_entry(map()) :: t()   # id == repo; config_path/state_root Path.expand'ed
end
```

`id` is `repo` (`"o/a"`): `Aiur.Machine.Settings.Schema.Project` has only `repo` and `config` and validates `owner/name`
(`machine/settings/schema/project.ex:22-23`), and MPG-301 §4 keys ledger rows, tokens and tables by project id. A
second id scheme would need a mapping table. `config` may begin with `~/` (schema line 23), so `from_machine_entry/1`
calls `Path.expand/1`. `state_root` defaults to `Path.join(Aiur.Config.Paths.state_root(), "projects/#{repo}")` —
MPG-302 only stores the field; the real layout is MPG-201/MPG-306.

```elixir
# src/lib/aiur/project/context.ex
@key {Aiur.Project.Context, :project}
@spec put(Aiur.Project.t()) :: :ok          # explicit, process dictionary
@spec current() :: Aiur.Project.t() | nil   # MPG-301 §3 order
@spec current_id() :: Aiur.Project.id() | nil
@spec delete() :: :ok
```

`current/0` implements MPG-301 §3 steps 1, 3 and 4 in 302: pdict, then `$callers`, then `$ancestors`, caching a
resolved answer in the calling process. "A pid resolves to a project" needs `Aiur.ProjectRegistry`; MPG-302 defines the
lookup as `Registry.lookup(Aiur.ProjectRegistry, {:root, pid})` guarded by `Process.whereis(Aiur.ProjectRegistry)`
(absent registry → `nil`, i.e. today). Starting the registry in production is MPG-306 (open question 1). The cache is
**not** keyed by anything else: it stores the resolved `%Project{}` and is invalidated by `put/1` and `delete/0`.

```elixir
# src/lib/aiur/project/task.ex
@spec async((-> result)) :: Task.t()
def async(fun), do: (project = Context.current(); Task.async(fn -> project && Context.put(project); fun.() end))
```

`async/1` exists for a *machine* process starting work for a project (MPG-301 §3, "Task children"). Plain `Task.async`
already gets the context from `$callers` once step 2 is implemented, so `Project.Task.async/1` is the explicit form:
it copies the **parent's** resolved project. Add `async_stream`-style variants only when a caller needs one (YAGNI).

### Alternatives considered for the context carrier

- **`Logger` metadata / `ProcessLabel`:** not inherited by `Task`, and not readable cheaply. Rejected.
- **Pass the project into every `Config.settings/1` call:** touches 142 files / 311 call sites
  (`code-evidence.md` §5). Rejected by MPG-301 rule 2.
- **A single global `:persistent_term` of the "current" project:** wrong the moment two projects run, which is the
  whole point. Rejected.

## Prior art

None needed. The `prior-art` reports in `docs/research/multi-gateway/` concern gateway/daemon topology, not an
in-process config cache, and the question is fully answered by the code above. The pattern (process-dictionary context
inherited via `$callers`/`$ancestors`) is the one OTP's `Logger`, `Ecto.Repo` dynamic repo and `Phoenix.PubSub` caller
tracking already use; it is stated in MPG-301 §3, not re-derived here.

## Test scenarios

All new tests use `Aiur.ProjectCase` with a `tmp_dir`; none touches `~/.aiur`. Dates are not involved.

| Scenario | Input | Expected |
|---|---|---|
| **[fails without]** per-process repo | Projects A (`o/a`) and B (`o/b`) configs; process 1 `Context.put(a)`, process 2 `put(b)`, each calls `Config.settings!()` | `tracker.github.repo` is `"o/a"` in 1 and `"o/b"` in 2. Fails if the path seam (unit 4) or the cache rows (unit 5) are reverted: the second process gets A's settings. |
| Cache rows are per project | Publish A then B via `Cache.put(project_id, …)`; read both | `Cache.fetch("o/a", path_a)` returns A's `{generation, publication}`; `fetch("o/b", path_b)` returns B's; neither is `{:stale, _}`. With single-row `:current` the second is `{:stale, path_a}`. |
| Settings memo does not thrash | `Config.settings/0` ×50 in alternating A/B processes with a counter on `Schema.parse/1` (via `Config.settings_from/1` telemetry or a `BackendCatalog` stub) | Parse count is 2 after warm-up for projects with a published row; with the single memo it is 50. |

The mutation rule (`AGENTS.md`): for each of the first, second, fourth and sixth rows, revert the matching unit in a
worktree, confirm the named test fails, restore, and report the command in the PR body.

## Data and assets

- Project id: the `owner/name` string. ETS and `persistent_term` keys use it verbatim. `Cache.project_key(nil) ==
  :default`; the string `"default"` is not a valid project id (`owner/name` requires a `/`), so the two cannot collide.
- Config fixtures: two memory-tracker `.aiur/config` files written by `ProjectCase`, whose only difference is
  `tracker.github.repo`.
- Gap: the config schema field that holds the repo for a memory tracker. Confirm at pickup which key
  `tracker.github.repo` resolves from when `tracker.kind: memory`; if the memory tracker ignores the repo, use
  `tracker.kind: github` with a stubbed client instead. The contract's acceptance line names `tracker.github.repo`.

## Risks

- **Machine process reads a project path.** `workflow_file_path/0` now varies with context. A machine process (HTTP
  endpoint, usage ledger) that inherits a project through `$callers` and then reads config would see that project's
  config. Mitigation: MPG-301 rule 3 (machine processes never read an ambient context); the 25 sites are read once at
  pickup and any machine-level one is made explicit. Detect early: the "no context" suite plus a grep audit in the PR.
- **`$callers` walks on a hot path.** `current/0` resolving through `$callers`/`$ancestors` on every `settings/0` is
  O(depth). Mitigation: cache the resolved project in the process dictionary (Decision 5) and let the `nil` no-project
  answer short-circuit when `Process.whereis(Aiur.ProjectRegistry)` is `nil`. Measure with the existing bench.
- **Stale context cache.** A process that cached project A and is later handed to B (e.g. a pooled worker) keeps
  serving A. Mitigation: `put/1` and `delete/0` always overwrite the cache; pooled workers (the `Task.Supervisor`
  children) are not reused across tasks. Add the pooled-worker case to MPG-305R's inventory.
- **Single table owner.** One named table owned by the default store: if no default store exists (projects mode,
  MPG-306), nothing creates it. `Cache.init!/0` is idempotent and `safe/1`-wrapped, so a project's own store creates
  it on boot, and an absent table is a disk read. Open question 2 decides whether that is acceptable.
- **The uncached non-default read is a YAML parse per call** until MPG-304. Not reachable in production before MPG-306.
  Detect: the throughput bench with a context set.
