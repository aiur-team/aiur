# MPG-308 — Pause, reload and hand off one project without touching others: research

Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (rows 9, 10, 11). Contract: MPG-308 in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m3.md`. Reads the ADR [MPG-301](MPG-301.md) (§10 pause and reload,
§11 agents across a restart). Neighbours: MPG-302 (project context), MPG-304 (per-project `WorkflowStore`), MPG-306
(`Aiur.Project.Supervisors`, `aiur gateway reload`), MPG-309 (gateway key), MPG-406 (fleet pause), MPG-602 and MPG-604
(read and write pause). Code references are to `src/lib/aiur/` at `7d5cc6199`.

## Outcome

In a gateway with `projects:` set:

- `aiur pause --project o/r` stops new starts in that project only. `aiur resume --project o/r` lifts it. Bare
  `aiur pause` sets the **gateway** pause and stops new starts in every project. Running agents are never stopped (as
  today). Both switches persist and an unreadable file holds dispatch paused (the existing invariant).
- A change to one project's `.aiur/config` reloads that project's `Aiur.Config.settings/0` and wakes only that
  project's config subscribers.
- `aiur restart --keep-agents` writes one handoff record per project and each project judges its own config
  fingerprint. If project A changed `workspace.root`, A's agents fall back to a resumed session; B's are adopted.
- With `projects:` empty nothing changes: bare `aiur pause` still writes `global-pause.json`, `Protection` and
  `Record.path/1` behave as today.

## Design

### D1. What is already per project, and what is not

Binding Executor decisions (MPG-304R, PR 7725): a project id is the repository `owner/name` downcased; each project's
state leaf is built from its own downcased id with today's leaf rule, so the daemon's own repo resolves to exactly
today's leaf; two entries that resolve to the same leaf are a boot error raised by MPG-306. `Paths.decision_state_dir/0`
stays **machine-level and never reads the context**; a new `Paths.project_state_dir/0` (context first, falls back to
`decision_state_dir/0`) is used only by per-project paths. MPG-304's T6b asserts the `GlobalPauseStore` default path is
the same with and without a context, so MPG-308 must not change `resolve_path/0`'s default.

Once MPG-302 makes `Aiur.Config.settings/0` read the project context, two things become per project, and a third needs
an explicit call:

- **Project flag path (explicit).** `GlobalPauseStore.resolve_path/0` (`global_pause_store.ex:85-96`) stays
  machine-level. The project flag is read and written with the `path:` option D3 adds:
  `Path.join(Paths.project_state_dir(), "global-pause.json")`, called from the project's orchestrator (T1 and T5 revert
  checks point at this call). Because the daemon's own repo resolves to today's leaf, today's `global-pause.json` is read
  as that project's flag on upgrade: a project paused today boots paused. That removes the upgrade concern behind open
  question 2.
- **Handoff record path (explicit).** `Handoff.Record.path/1` (`handoff/record.ex:23-26`) resolves through
  `Paths.project_state_dir/0` rather than `runtime_state_dir/0` (`paths.ex:321-326`), so each project's record lives in
  its own leaf (`<project state dir>/handoff/current.json`). It is a small edit plus context passing and tests, not a
  file move; with no context the fallback is `decision_state_dir/0`, today's path.
- `Handoff.config_fingerprint/0` (`handoff.ex:55-62`) hashes `{tracker.kind, tracker.github.repo,
  tracker.linear.project_slug, workspace.root, worker.ssh_hosts}` from `Config.settings/0`. Called in a project's
  process it is that project's fingerprint. `Compatibility.check/3` (`handoff/compatibility.ex:8-30`) compares each
  agent's stored fingerprint to the adopting process's fingerprint. If each project's orchestrator adopts its own
  record, the comparison is already per project.
- `Adopter.adopt/2` runs from the orchestrator's `init` (`orchestrator/lifecycle.ex:174`), which is a project process.

### D2. Two flags, and which state field each uses

Keep `State.globally_paused` as it is: **"this orchestrator's own switch"**. Its 125 references, its persistence
(`global-pause.json`), `GlobalPause.set_global_pause_call/4` and the existing tests stay unchanged. In projects mode
that switch is the **project flag**; with `projects:` empty it is the only flag (today's behaviour).

Add `State.gateway_paused :: boolean()`, default `false`. It mirrors the gateway flag and is never persisted by the
orchestrator. Dispatch is stopped when `globally_paused or gateway_paused`:

- New module `orchestrator/dispatch_pause.ex` defines `defguard dispatch_paused(state)` and
  `dispatch_paused?/1`. MPG-406 adds its `fleet_paused` term here and nowhere else.
- The four dispatch gates switch to it: `dispatcher.ex:217` and `:408` (function heads, so the guard), and
  `retry_engine/lookup.ex:26` and `:82`. Same line count, so no oversized file grows.
- The other readers of `globally_paused` are display or secondary gates. Update only these four more:
  `pause_resume/control_calls.ex:111` (resume refused during pause), `override_resume.ex:128`,
  `optimistic_guard_effects.ex:142`, `tracker_health.ex:254`. `snapshot_payload.ex:87-89` and
  `agent_statuses.ex:488` gain `gateway_paused` next to `globally_paused`. `issue_sync/dependencies.ex:318` stays: a
  paused project still detects circular waits.

Alternatives rejected:
- *One flag per project, set on all projects for a gateway pause.* A new project added while the gateway is paused
  would dispatch, and a gateway resume would clear project pauses an operator set on purpose.
- *Reuse `globally_paused` for the gateway flag and add a project field.* It renames the meaning of the field that the
  persisted file, the CLI and 125 sites use.

### D3. Gateway flag: file, entry point, delivery

- **File:** `<gateway state root>/gateway-pause.json`, same JSON shape as `global-pause.json`.
  `Paths.gateway_state_dir/0` (new) is `Path.dirname(Paths.decision_state_dir())` — the `<state root>/<AIUR_INSTANCE_KEY>` parent of the leaf; it is defined from the machine-level `decision_state_dir/0`, never from a context.
  It exists before and after MPG-309 renames the instance key.
- **Deviation from the ADR (§10):** the ADR names `pause.json` for both files and says the project flag lives at
  `<project state root>/pause.json`. This note keeps the project flag in **`global-pause.json`**. Renaming would, on
  upgrade, make a project that is paused today boot unpaused, and the file's four tests and its recovery invariant
  (`global_pause_store.ex:43-47`) would move for no benefit. The gateway file is new, so its name is free. If the
  ADR must stay literal, see open question 2.
- **Store:** `GlobalPauseStore.load/1` and `save/2` gain an optional `path:` option (default: today's
  machine-level `resolve_path/0`; the project flag passes an explicit project path). No new storage module.
- **Entry point:** `Aiur.Gateway.Pause.set(on?, source)` (new, `gateway/pause.ex`, the function the ADR names). It saves
  the file with `GlobalPauseStore.save(state, path: gateway_path())`, then
  `Phoenix.PubSub.broadcast(Aiur.PubSub, "gateway:pause", {:gateway_pause, on?, meta})`. A save failure returns
  `{:error, {:global_pause_persistence_failed, reason}}` and broadcasts nothing.
- **Orchestrator side** (`orchestrator/lifecycle.ex`, new helper module `orchestrator/gateway_pause_sync.ex` to keep
  `lifecycle.ex`, 446 lines, short): `init` calls `GatewayPauseSync.load/0` (reads the file; an unreadable file gives
  `gateway_paused: true`) and subscribes to `"gateway:pause"`; `handle_info({:gateway_pause, on?, _}, state)` sets the
  field and, on resume, calls `Lifecycle.request_refresh_state/1` exactly as `maybe_refresh_after_global_pause_change/4`
  does today for the project flag (`global_pause.ex:128-141`), so dispatch resumes within one base interval.
  The `Application.put_env(:aiur, :instance_globally_paused, …)` at `lifecycle.ex:113` and `global_pause.ex` stays the
  project-or-single switch; the heartbeat's `instance.ex:224` reads it. Open question 3 covers whether the heartbeat
  should report the gateway flag.
- **Routing, so there is one place that decides:** `Aiur.AgentControlCLI.pause_global/0` and `resume_global/0`
  (`agent_control_cli.ex:82-83`) call `Aiur.Gateway.Pause.set/2` when `Aiur.Project.Supervisors.which_projects()` is
  non-empty, and today's `Orchestrator.set_global_pause/2` otherwise. MPG-604's `POST /api/v1/gateway/pause`
  and MPG-406's local author step must call `pause_global/0`, not the orchestrator directly (see Interfaces).
- **Project verb:** `Aiur.AgentControlCLI.pause_project(project_id)` and `resume_project(project_id)` delegate to
  `Aiur.Project.Pause.set(project_id, on?, source)` (new, `project/pause.ex`). It resolves that project's orchestrator
  with MPG-306's registry lookup and calls the existing `Orchestrator.set_global_pause/3` on it. Unknown id returns
  `{:error, {:unknown_project, id}}`. With `projects:` empty it returns `{:error, :no_projects_configured}`.
- **Effective state for MPG-602:** `Aiur.Project.Pause.status(project_id) :: {:ok, %{paused: boolean(), project: boolean(),
  gateway: boolean(), paused_at: DateTime.t() | nil, source: String.t() | nil}} | {:error, :unknown_project |
  :orchestrator_unavailable}`; `paused` is `project or gateway`. It reads the published global-pause snapshot
  (`SnapshotStore.publish_global_pause/3`), not the orchestrator mailbox, so a busy orchestrator cannot block the
  dashboard.
- **CLI (engine):** `commands.sh` `cmd_pause_resume` (77-100) parses a leading `--project <owner/name>` before the
  target parser. Valid id: `^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$`, else exit 64; the id is downcased before lookup, so `--project O/R` selects project `o/r`. `Protection` keys, the reload topic suffix and `Project.Pause.status/1` all use the downcased id. `--project` with issue ids or `--all` exits
  64 (`--project cannot be combined with issue ids yet`; open question 4). Expressions:
  `Aiur.AgentControlCLI.pause_project("o/r")`, `resume_project("o/r")`. `park` does not accept `--project`.
- **Remote control allowlist** (`control_call/allowlist.ex:198-199`): add `{:pause_project, 1, :write, [:string], %{}}`
  and `{:resume_project, 1, :write, [:string], %{}}` next to `pause_global`. MPG-205 assigns the `agents` category to
  both; MPG-308 follows whatever category map MPG-205 shipped (open question 5).
- **Output:** `aiur: project o/r pause ON — no agents will be provisioned in o/r`; on resume while the gateway is
  paused: `aiur: project o/r pause OFF — gateway pause is still ON, o/r stays held`. Exit 0 for both.
- **Resume of a project while gateway paused** succeeds and clears only the project flag. Refusing would leave an
  operator unable to fix a project flag during a gateway pause.

### D4. Handoff: one `prepare` per project, one `Protection` entry per project

- `Aiur.Handoff.Protection` keeps its API and adds a project key: `store/5` writes `{__MODULE__, :prepared,
  project_id}` where `project_id = Context.current().id` (the downcased id of the `%Aiur.Project{}`; `nil` with no context, which is today's key
  value under a new key shape). `protected?/1`, `prepared/0`, `take_expired/3` and `reset/0` read the caller's own
  project. New `active?(:any)` and `prepared_all/0` list every project's entry. `Shutdown` (`shutdown.ex:188`) and
  `Guardian` (`workspace/ownership/guardian.ex:191`) run in machine or per-ticket processes; `Shutdown` uses
  `prepared_all/0`, `Guardian` passes the ticket's project (it already has the lease, `state.lease.ticket`, which gains
  the project id from MPG-107's key `owner/repo#N`; if the lease key is bare, MPG-308 reads the project from the
  context of the guardian's start — open question 6).
- `Aiur.Handoff.prepare_all(opts)` (new, in `handoff/all.ex` to keep `handoff.ex`, 382 lines, from growing):
  for each project in `which_projects()`, run `Handoff.prepare(orchestrator: pid)` inside that project's context in a
  `Task.async_stream` with `timeout: 110_000` (prepare's own budget is 100 s, `handoff.ex:12-14`; the shell RPC
  envelope is 120 s, `handoff/cli.ex:9-12`), so projects prepare in parallel and the sum cannot exceed the envelope.
  Result: `{:ok, %{projects: %{id => {:ok, result} | {:error, reason}}, handoff_ids: [..]}}`.
- **Partial failure rule:** a project whose `prepare` fails has already aborted its runners and cancelled its dispatch
  hold (`handoff.ex:107-120`). Its agents are not protected, so `terminate/2` reaps them (`lifecycle.ex:218-233`) and
  they resume from their workspaces. The other projects proceed. `Handoff.CLI.prepare` prints
  `Handoff project o/r failed: <reason>; its agents restart from their workspaces` and exits 0 unless **every**
  project with agents failed (exit 1, restart refused, same message as today). The marker line becomes one
  `__AIUR_HANDOFF__:<id>` per prepared project, joined with commas (`engine/handoff.sh:25` stores one string in
  `AIUR_RESTART_HANDOFF_ID`, used only for display and rollback evidence, `restart.sh:20`,
  `restart_rollback.sh:81,128,135`). With one project the output is byte-identical to today.
- **Reap on terminate:** `ProcessReaper.handoff(refs)` (`handoff.ex:97`) is a machine-level list today and one project's
  `ProcessReaper.handoff([])` at `lifecycle.ex:97` would clear another project's refs. MPG-301 §11 gives
  `ProcessReaper` project-keyed entries; MPG-308 passes the project id to `handoff/1` the same way (MPG-305 owns the
  key; open question 7 if MPG-305 shipped without it).
- **`restart_project(id, handoff: true)`** (ADR §10): implemented in `project/handoff_restart.ex`, called by
  `Aiur.Project.Supervisors.restart_project/2`. Steps: `Handoff.prepare` in that project's context, stop only that
  project's runner tasks with `Task.Supervisor.terminate_child(Aiur.TaskSupervisor, pid)` (the pattern at
  `agent_teardown.ex:263`), stop and start the project tree, and let `Adopter.adopt/2` run from the new orchestrator's
  `init`. No CLI command triggers it in this ticket (open question 8).

### D5. Record carries the project; adoption checks it

`Handoff.record/2` (`handoff.ex:371`) adds `"project_id" => id | nil`. `Record.valid_envelope?/1` ignores extra keys,
so `@schema` stays `1` and an old daemon reads a new record. `Adopter.consume/3` compares `record["project_id"]` to the
adopting process's project: equal, or both `nil`, is fine; a mismatch makes every agent in that record fall back with
reason `:project_mismatch` and raises `system.handoff.incompatible` (the existing alert, `adopter.ex:233-243`). A
record with no `project_id` read by a project process (upgrade across the first multi-project start) is adopted as
today: the fingerprint still protects it, because the repo is part of the fingerprint.

This is the defence for G6. Even if two projects ever resolved the same file, the second to read would find the wrong
`project_id` and fall back instead of adopting another repository's agents.

### D6. Reload: per-project topic, no per-project reload code

`WorkflowStore.Reload.configuration_topic/0` (`reload.ex:24-25`) returns `"workflow_store:configuration"` when
`Context.current()` is `nil` and `"workflow_store:configuration:" <> project_id` otherwise; `broadcast_configuration/1`
(`reload.ex:312-318`) uses it. Every subscriber calls `Reload.configuration_topic/0` or `WorkflowStore.subscribe/1`
(`workflow_store.ex:214`) from its own `init`, which runs in its project tree, so none of the five subscribers changes.
A machine-level subscriber (`AllowedContributors` if MPG-305 classifies it machine) subscribes explicitly to each
project's topic — a MPG-305/306 decision, listed in open question 9.

Which changes need more than an in-place reload? None are rebuilt automatically in this ticket. `workspace.root`,
tracker repo/kind and `ssh_hosts` (the fingerprint inputs) already apply live to new dispatches today; they matter only
across a restart, where D1 handles them. A tree rebuild stays an operator action (`aiur gateway reload`, MPG-306).

## Test scenarios

All use `Aiur.ProjectCase.start_projects!/2` (MPG-301 §7; memory tracker, `tmp_dir` state root, never `~/.aiur`) and

## Risks

- **R1 Shared state directory (G6).** Two repos with one leaf are a boot error in MPG-306 (binding decision), so they never run together. D5's `project_id` check stays as defence in depth. Detect: MPG-306's boot test and T2.
- **R2 Terminate order.** `terminate/2` runs per orchestrator and calls `ProcessReaper.reap` (`lifecycle.ex:218-233`).
  If MPG-305 has not project-keyed the reaper, project A's terminate kills B's agents and T10 fails. Detect early: T10 is
  the first test to write. Fallback: MPG-308 blocks on MPG-305 for that one call (open question 7).
- **R3 Parallel prepare load.** Several projects snapshot at once on a loaded host. Mitigation: `max_concurrency: 4` on the
  `Task.async_stream`; per-project timeout unchanged.
- **R4 Pause ordering at boot.** An orchestrator that starts before the gateway file is readable would dispatch for one
  poll. `init` reads the file synchronously before `schedule_initial_tick` (`lifecycle.ex:183`), the same place the project
  flag loads, so there is no window.
- **R5 Oversized files.** `commands.sh` (427), `dispatcher.ex` (494), `lifecycle.ex` (446) and `handoff_test.exs` (483)
  must not grow past 500. Plan: same-line edits in `dispatcher.ex`; new modules for everything else; no new test cases in
  `handoff_test.exs`.
