## Outcome
`aiur ownership migrate --map agent=<gateway> --map nuc=<gateway>` lists open tickets of the configured repository and,
for each one whose **state** labels name exactly one mapped prefix, plans a claim of `refs/aiur/owners/<ticket>` for that
gateway (S1, `reason: "migration"`). Tickets with state labels from two mapped prefixes are reported `ambiguous`; tickets
with no mapped state label are `skip`. Without `--apply` it writes nothing. With `--apply` it claims through the MPG-102
adapter, paced by the GitHub budget broker, and prints the write count. A second `--apply` writes nothing because every
planned claim now reads as already owned by the same gateway.

## Design
**Plan is pure.** `Aiur.Ownership.Migration.plan(tickets, opts)` takes `[%{ticket: String.t(), labels: [String.t()],
owner: nil | owner_record}]` and `opts.map :: %{prefix => gateway}`, returns `[action]` in ticket order, one per input,
where `action` is one of:
- `{:claim, ticket, gateway}`: exactly one mapped prefix has a state label and no record exists (or it is `released`).
- `{:already, ticket, gateway}`: a record exists and names that same gateway. Zero writes. This is what makes re-runs
  idempotent.
- `{:conflict, ticket, labelled: gateway, owner: gateway}`: a record exists naming a different gateway. Never overwritten.
- `{:ambiguous, ticket, [prefix]}`: state labels from two or more mapped prefixes.
- `{:skip, ticket, reason}`: reason `:no_state_label` (covers `[]`, parked-only, and unmapped prefixes).

State-label detection reuses `Aiur.GitHub.StatePolicy.normalize_state/1` and the known-state list in
`Aiur.GitHub.StateLabels` (made public as `known_states/0`) rather than a second list; the existing
`foreign_state_label?/3` is the same "prefix + known state" test inverted. Prefix compare is trimmed and downcased, as
there. The `:claim` branch runs only after the plan has read the record, so plan input carries `owner`.

**Apply is the only impure function.** `apply(actions, opts)` handles `:claim` actions one at a time through the MPG-102
adapter (`Aiur.Ownership.GitHubRef.claim/3`, `src/lib/aiur/ownership/github_ref.ex`, create-if-absent `updateRefs` with zero `beforeOid`; the outcomes `won | lost |
unknown`). `won` counts a write; `lost` re-reads and reports the winner (a daemon or other migrator got there first);
`unknown` is reported and not retried in the same run (MPG-101: a loser has no distinguishable signature, so inference
is forbidden). Each write goes through the budget broker as a GraphQL write so the migration cannot starve dispatch.
Returns `%{claimed: n, already: n, lost: n, unknown: n, ambiguous: [...], skipped: n, writes: n}`; the CLI prints
`writes: <n>`.

**Gateway name resolution.** `--map prefix=<gateway>`: `<gateway>` resolves to a 26-char `gateway_id` and label. For
the local gateway use the machine identity; for a peer use the S2 registry entry (`gateway_id`, `label`). A name that
resolves to neither is a usage error before any read. `daemon_key` in S1 is not knowable for a peer, so migration
records the **local** `daemon_key` only for the local gateway and `null` for a peer; see Open question 1.

**Which labels to read.** The tracker already lists open issues for dispatch; migration reuses that listing via the
read cache (`Aiur.GitHub.Issues`) rather than a new query. One uncached ref listing (`matching-refs/aiur/owners/`, MPG-101
step 8) supplies existing owners in one call instead of 831 reads.

**Dry run is the default.** No flag, no write. Output is the action table plus the counts above for the live repo, so an
Executor can compare with this document's table before `--apply`.

**Alternatives rejected.** (a) Treat any `<prefix>:*` label as a claim: claims 433 parked tickets. (b) Remove the old
labels after claiming: not asked, irreversible, and the plan keeps `gateway:<label>` projection and state labels
(KTD-2 "label is a projection"). (c) Infer a loss from the GraphQL error text: MPG-101 shows losers are
indistinguishable from server errors.

## Risks
- **Mass write against live ownership.** 134 GraphQL writes; a mapped-wrong gateway would hand PC's tickets to Nook.
  Mitigation: dry run default; `--apply` prints the table and requires the mapping; the claim is create-if-absent so a
  mistake is fixed by an explicit transfer, not by re-running.
- **A running ticket is claimed while a daemon claims it too.** Both use create-if-absent; the loser is `lost`.
- **Label drift mid-run.** The listing is a snapshot; a ticket relabelled during apply is claimed by its old label. The
  fence and the "ref wins" rule (KTD-2) make this recoverable.
- **Budget.** 134 writes plus 1 list is small; the pacing test above guards the principle, not a measured saving. This
  PR claims no saving.
- **`daemon_key` for peers** (Open question 1).

## Open questions
| Question | Recommended default | What changes if answered differently |
|---|---|---|
| 1. What is `daemon_key` for a record written on behalf of a peer gateway? | `null`; the peer's daemon fills it on its first epoch advance | If S1 requires it, migration must run on each gateway for its own prefix only |
| 2. Claim tickets whose only mapped label is a non-state label (`parked`, `paused`)? | No (433 tickets); they get a claim when someone un-parks them | Claiming them adds ~433 writes and owns idle work |
| 3. Claim `done`/`cancelled` open tickets? | Yes, if still open, with the same rule; 0 appear in today's count | A skip rule would add a `:terminal` skip reason |
| 4. Remove or relabel `agent:`/`nuc:` state labels after claiming? | No, they stay (labels are the state machine, ownership is separate) | Would need a rollback path and touch dispatch |
| 5. Project the `gateway:<label>` label during migration? | No, migration writes refs only; the daemon projects best-effort on next dispatch (protocol step 4) | +134 label writes |
| 6. May one gateway run migration for the other's prefix? | Yes, if the registry resolves the peer; an Executor token needs the `tickets` category on the peer | Otherwise each gateway migrates its own prefix and `--map` accepts one entry |
| 7. Where is `epoch` initialised? | `1`, `previous_epoch` `0`, per S1 | Fix in the test fixtures only |
| 8. Does this ticket unify the `agent:`/`nuc:` state prefixes (plan row 28a, Q1)? | No. Row 28a is a separate dry-run migration that runs only after the first ownership test (MPG-109) passes.
