# MPG-402 — Dispatch by cross-project priority within machine capacity: research

Date: 2026-11-06. Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (KTD-5, KTD-7). Contract: MPG-402 in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m4-m7.md`. Policy input: `docs/research/MPG-401.md` (the
algorithm, 19 cases and the property test are copied from it, not redesigned here). Neighbour contracts read:
MPG-307 (`Aiur.Gateway.Capacity`, first-come grants), MPG-403/405 (reconciled priority, a later source of
`priorities`), MPG-306 (per-project orchestrators).

## Outcome

With `projects:` set in `~/.aiur/machine`, every project's orchestrator asks `Aiur.Gateway.Capacity` before it
starts an agent. Capacity answers by running the pure `Aiur.Gateway.Allocation.allocate/5` over the machine's
current demand, running counts and priority order. Project A (priority 1) fills to its maximum before B gets a slot;
when A has no ready work, B uses every free slot; no running agent is ever stopped. With `projects:` empty nothing
changes: Capacity is not consulted and `slots.ex` behaves as it does today.

## Design

### Decisions

1. **`allocate/5` is exactly MPG-401's function.** It lives in `gateway/allocation.ex` with the types, the reference
   implementation and nothing else but `order_groups/3` (decision 4). No I/O, no clock, no process state.
2. **Capacity stays the single owner of counts and serialises every decision.** One GenServer holds `running`,
   the last `demands` per project, and a `pending` set of grants not yet turned into agents. A grant is counted in
   `running` the moment it is returned (MPG-401 "Dispatch races"), so two orchestrators cannot take the same slot.
3. **The orchestrator asks per ticket, not per batch.** `Capacity.request(project_id, group, issue_id)` returns
   `:granted | :denied`. Capacity recomputes `allocate/5` with the caller's group included in `demands`, and grants
   when `grants[group] >= 1`. It is idempotent per `issue_id` (a retry of the same ticket does not double-count).
   A per-ticket ask fits the existing dispatch loop, which already walks candidates in order and starts what it can
   (`dispatcher/launch.ex` `dispatch_to_worker/5`), and it gives MPG-401 open question (e) its answer for free: a
   grant is permission for one start, never a held slot. A start that fails calls `Capacity.release/2`.
4. **Priority order is built outside the allocator and injected.** `Allocation.order_groups(project_priorities,
   feature_orders, groups)` returns the `priorities` list: projects ascending by `projects[].priority` (ties by repo
   id), then within each project its features in that project's `build_order.feature_order` order, then
   `{project, :none}`. Capacity takes a `priority_fun` (default: the function above fed from machine config), so
   MPG-405's shared-intent source replaces the default without touching `allocate/5` or Capacity's callers.
5. **Demand is published by the orchestrator once per poll, from what dispatch would actually start.** After the
   candidate list is final and before `HoldsAndAlerts.dispatch_or_hold`, the orchestrator calls
   `Capacity.report_demand(project_id, demands)`. `Aiur.Gateway.Demand.from_issues/3` builds it from the same
   filtering dispatch uses (`DispatchCandidates.partition/3` `:chain` tier, `DispatchPolicy.should_dispatch_issue?/2`
   true, no pending retry per `RetryEngine`). Counting a ticket the orchestrator then refuses would hold a higher
   group's share idle, which breaks "no slot idle while eligible work exists" (MPG-401 P3) in practice.
6. **A demand snapshot expires.** Each snapshot carries `observed_at_ms`. A snapshot older than
   `3 × poll interval` counts as `ready: 0` for its project, and Capacity emits one `system.gateway.demand_stale`
   alert per project per stale episode. Reason: a hung or crashed orchestrator must not hold slots back from others.
   This reads as unknown, not as zero, in status output (see Interfaces).
7. **Group = (project, feature).** A ticket's feature is the first `feature:<slug>` label in sorted order that
   `Aiur.BuildOrder.Features.LabelRules.parse/1` accepts; no such label gives `:none`. Sorting makes a ticket with two
   feature labels deterministic.
8. **Limits are project maximums only.** `limits = %{project_id => min(projects[].max_agents, agent.max_concurrent_agents)}`;
   no feature maximum has a config source (S3 has none), so group-keyed limits stay unused in v1 though `allocate/5`
   supports them. Capacity builds `limits` without reading priority (MPG-401 P1/P2).
9. **`promoted` is 0 until an operator action exists** — see "Finding: `--todo` is not a promotion". The promotion pass
   stays in `allocate/5` and is tested there; the demand builder passes `promoted: 0`.
10. **Capacity ignores global dispatch constraints; it adds one.** Host-pressure holds, spend cap, optimistic-share
    and queue-set gates in `DispatchPolicy` still apply per ticket before the ask. Capacity only answers "is a
    machine slot mine, by priority"; it does not replace `Slots.dispatch_slots_available?/2`, it is called after it.

### Finding: `--todo` is not a promotion

MPG-401's recommended default for open question (b) is to map `promoted` to tickets queued with `--todo`. The code
does not support that. `Orchestrator.TodoCLI.queue_fetched_todo_issue/5` (`orchestrator/todo_cli.ex:155`) applies the
`agent:todo` label (and with `--only` removes it from others). A ticket in `agent:todo` is an ordinary candidate;
there is no front-of-line marker to read, so "promoted" would equal "every dispatchable ticket" and the promotion pass
would run ahead of the priority pass for all of them, deleting cross-project priority. Recommended default: `promoted: 0`
in MPG-402; a real signal (an explicit `aiur promote <n>` action writing a marker) is a separate, later ticket. Test
cases 9 to 11 still run against `allocate/5` directly.

### Why this shape (alternatives rejected)

| Alternative | Why not |
|---|---|
| Orchestrator asks for a batch `request(project, n)` | The ticket's group is unknown to a batch ask, so feature focus cannot be applied; it also lets one project take a grant it cannot use. |
| Capacity polls trackers for demand itself | Duplicates the candidate fetch and GitHub budget (see `website/docs-app/apis/`); the orchestrator already has the fetched list. |
| Hold a grant per project between polls (reservation) | MPG-401 forbids reservations; it idles slots. |
| Re-run `allocate` in each orchestrator | Counts are machine-wide; only one process may own them. |
| Preempt to give A its slots back | Rejected in MPG-401 and KTD-5. Capacity has no stop path: its API has no function that messages a holder. |

## Prior art

None needed beyond MPG-401's reading of `docs/research/multi-gateway/priority-reconciliation.md` ("Focus with
borrowing has direct scheduler precedent"). This ticket adds no external question: it wires a settled pure function
to a serialised owner. The serialised-owner pattern is the one the repository already uses for `Aiur.Orchestrator`
state and `BuildQueue` hints.

## Interfaces

- Consumes from MPG-307: `Aiur.Gateway.Capacity` GenServer with `request/…`, `release/2`, holder monitors, machine
  `capacity.max_agents`, `projects[].max_agents`; `orchestrator/slots.ex` call site. **MPG-402 changes the arity of
  `request`**: MPG-307's `request(project_id, n)` is first-come and batch-shaped. MPG-402 replaces it with

- Consumes from MPG-401: `allocate/5`, its types, 19 cases, the property test, rules H1 to H4, P1 to P3.
- Consumes from MPG-306: one orchestrator per project, each knowing its `project_id`; `projects[]` config.
- Provides to MPG-403/405: `priority_fun` injection point on `Capacity.start_link/1`.
- Provides to MPG-501/502 (Executors, status): `Capacity.snapshot/0 -> %{capacity, running_by_group, demands_by_project
  (with observed_at_ms, age_ms, stale?), last_decision}` for `aiur status --json` and the dashboard.

Public API after MPG-402:

```elixir
# gateway/allocation.ex (new, pure)
@spec allocate(capacity(), demands(), priorities(), limits(), running()) :: grants()
@spec order_groups([{project_id(), integer()}], %{project_id() => [String.t()]}, [group()]) :: priorities()

# gateway/demand.ex (new, pure)
@spec group(project_id(), Aiur.Issue.t()) :: Allocation.group()
@spec from_issues(project_id(), [Aiur.Issue.t()], MapSet.t()) :: Allocation.demands()   # promoted: 0

# gateway/capacity.ex (MPG-307, modified here)
@spec report_demand(project_id(), Allocation.demands()) :: :ok          # cast
@spec request(project_id(), Allocation.group(), issue_id :: String.t()) :: :granted | :denied
@spec release(project_id(), issue_id :: String.t()) :: :ok
@spec snapshot() :: map()
```

## Test scenarios

Allocation (unit 9): the 19 cases in MPG-401 `## Cases` pass verbatim; expected grants are in that table and are not
repeated here so the two cannot diverge. Plus the 2,000-input property check (P1, P2, P3, `sum(grants) <= free`).

Demand (unit 10):

| Scenario | Input | Expected |
|---|---|---|
| Feature label | issue labels `["agent:todo","feature:mpg-m4"]` | group `{"o/r", "mpg-m4"}` |
| No feature label | labels `["agent:todo"]` | `{"o/r", :none}` |
| Two feature labels | `["feature:b","feature:a"]` | `{"o/r", "a"}` |
| Invalid slug | `["feature:Bad Slug"]` | `:none` |
| Held by open blocker | blocked issue in `:held` tier | not counted |
| Ready counts | 3 chain issues, 2 in `mpg-m4`, 1 unlabelled | `%{{"o/r","mpg-m4"} => %{ready: 2, promoted: 0}, {"o/r", :none} => %{ready: 1, promoted: 0}}` |
| Pending retry backoff | one chain issue with a retry attempt scheduled | not counted |

Order (unit 1, `order_groups/3`):

| Scenario | Input | Expected |
|---|---|---|
| Projects by priority | `[{"B",2},{"A",1}]` | A groups before B groups |
| Equal priority | `[{"B",1},{"A",1}]` | A before B (repo id) |
| Features then none | A order `["f2","f1"]`, groups `{A,:none},{A,"f1"},{A,"f2"}` | `{A,"f2"},{A,"f1"},{A,:none}` |
| Unknown feature | group `{A,"zzz"}` not in feature_order | after listed features, before `:none` |

Capacity integration (unit 11; fake orchestrators are test processes that call `request/3`):

| Scenario | Input | Expected |
|---|---|---|
| Saturated, A > B | capacity 12, A max 8, B max 8, both report 10 ready; each process asks for 10 tickets in alternating order | A granted 8 then denied; B granted 4; running total 12 |
| A idle, B borrows | A reports ready 0; B asks 10 | B granted 8 (its max); with B max 12, all 12 |
| A wakes up later | B holds 8, A reports ready 5 | A's first asks denied until B releases; after one `release`, A's next ask granted, B's next denied |
| No stop | any of the above | Capacity sends no message to holder pids except `:DOWN` handling; assertion: holders' mailboxes are empty |
| Grant counted at once | two processes ask in the same instant for the last free slot | exactly one `:granted` |
| Idempotent ask | same `issue_id` asked twice | second returns `:granted`, `snapshot().running_by_group` counts it once |
| Release | `release/2` after a granted start | the slot is askable again |
| Holder crash | granted holder process dies | its counts return within one second (MPG-307 invariant retained) |
| Stale demand | A's snapshot older than 3 poll intervals, B asks | A counts as ready 0 (B granted); `snapshot` reports `stale?: true`; one `system.gateway.demand_stale` alert |
| Fresh demand overrides | A reports ready 5 after being stale | stale flag clears; alert resolves |
| Priority swap | `priority_fun` returns B before A | B filled first; running unchanged (no stop) |
| Single project | `projects:` has one entry | grant total equals `min(ready, capacity - running, max)`, same as `slots_test` expectations |
| Empty `projects:` | no Capacity | `GatewayDemand.publish/2` and `admit/2` return without calling a process (test uses no Capacity pid) |
| Unavailable demand | no snapshot ever reported for a project that asks | treated as that caller's own ask only (demand `ready: 1` for its group), never as a priority hold on others |

The last row is the unknown-path guard AGENTS.md requires: replacing "no snapshot" with an assumed large
demand makes another project's ask fail, so the test fails if the branch is mis-defaulted.

## Data and assets

No new files, state or schema. In-memory only (Capacity state is rebuilt from `report_demand` casts on the next poll
and from MPG-307's holder registrations after a restart). Group key is `{repo :: String.t(), feature :: String.t() | :none}`.

Known gap: after a daemon restart `running` is rebuilt only from adopted agents. During the first poll interval Capacity
sees no demands, so each caller is granted on its own ask (the "unavailable demand" row), which is first-come, not
priority, for at most one poll. Fallback: accept it; it is bounded and equals today's behaviour.

## Risks

- **Demand over-count idles slots** (decision 5). Detect: `snapshot()` shows `ready > 0` for a project with free
  slots and zero grants for more than one poll. Fallback: the ask is per ticket, so a ticket the orchestrator
  refuses is simply not asked; the over-count then lasts only until the next poll.
- **Stale or lost `report_demand` casts** starve nobody (decision 6) but make the priority look wrong. Detect: the
  `demand_stale` alert.
- **Per-ticket ask frequency.** Each dispatch tick asks once per candidate considered, bounded by free slots and the
  candidate list; Capacity does O(groups) work per ask. For 3 projects × 20 features the call is microseconds.
  Measure in the integration test with 1,000 asks; expect under 100 ms in total.
- **Size gates.** `dispatcher.ex` (494) and `launch.ex` (487) are one change from 500. Hence the glue module and the
  "net zero lines" instruction in units 5 and 6.
- **MPG-307 API drift.** Unit 3 assumes MPG-307's final GenServer shape; if it renames `release/2`, MPG-402 follows.
  Re-read `gateway/capacity.ex` when starting.
- **Priority input changes mid-run** (MPG-405). By H1 it moves only future starts; no code here reacts to it.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| What is `promoted` in v1? `--todo` only applies a label (finding above). | `promoted: 0`; no signal until a dedicated promote action ships. | MPG-401's default (b) is overridden; adding a signal means a new CLI verb, a marker store and docs, ahead of MPG-402 or as its follow-up. |
| Should feature focus also apply to a gateway with exactly one project? | Yes whenever `projects:` is non-empty; no change when it is empty. | Skipping it for one project would make single-project gateways dispatch in a different order from multi-project ones. |
| Is there a per-feature maximum? | No; S3 has no key, so `limits` carries projects only. | A key would need config schema, docs and the machine-config page; `allocate/5` already supports it. |
| Demand staleness window | `3 × poll interval`. | A longer window holds slots for a hung project longer; a shorter one flaps on a slow poll. |
| Which module owns the retry-backoff exclusion (MPG-401 (c))? | `Aiur.Orchestrator.RetryEngine`; `Demand.from_issues` leaves out any ticket with a pending retry. | If backoff is not queryable per ticket, Demand over-counts until the retry fires; add a read function to the retry engine. |
| `system.gateway.demand_stale` as a new alert name | Add it, informational (`needs_attention: false`). | If alert names are fixed by an allowlist, extend it in the same PR. |
| Where does MPG-307 call `release/2` per agent end? | Verify in MPG-307's merged code; MPG-402 reuses that site. | If 307 releases per orchestrator rather than per agent, MPG-402 adds the per-agent release in `orchestrator/agent_teardown.ex`. |
