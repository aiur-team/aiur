# MPG-209 — Show gateway status from the CLI: research

Research ticket MPG-209R (#7592). Inputs: `docs/plans/2026-11-06-multi-project-gateways.md` and `tickets-m2.md`,
`code-evidence.md`, `state-schemas.md` (all from PR #7579, not yet on `main`), plus the code read below. No code change.

## Outcome
`aiur gateway list` prints one row per registry entry: name, `registered`, connectivity (`online|offline|unknown|error`),
workload (`idle|active|saturated|paused|unknown`), last-seen age, gateway id, projects, running agents, owned tickets,
Executor presence and grants both ways where known. `aiur gateway status <g>` prints one gateway in detail. An offline
gateway shows cached values with their age and workload `unknown`; it is never `idle` and never `0`.

## Design
**Source of truth.** MPG-209 does not depend on the S6 endpoint (`GET /api/v1/gateway/summary`): that is MPG-602, which
needs MPG-407 and MPG-601 and lands after MPG-209. MPG-202 is only the `--gateway` selector and MPG-207 only the
unauthenticated hello. Per registry entry the CLI reads, in parallel through `remote_all.sh`:
1. `GET /api/v1/gateway/hello` (MPG-207): `gateway_id`, `gateway_label`, `build`; connectivity and the id-pin check.
2. `aiur agents --json` (existing, read-scope, envelope `aiur.agents` v1): the running count and per-agent rows.
Note `aiur status --json` is not usable: it requires `--handoff` (`commands.sh` `cmd_status`) and reports handoff state,
and plain `status` is text. v1 shows projects and owned tickets as `unknown`: neither `agents --json` nor `aiur capabilities --json`
(`Aiur.Capabilities.to_wire/1`: machine, instance, repository, executor, capability states) reports them, and they stay
`unknown` until MPG-602. Executor presence is the `executor.state` string from `capabilities --json`, shown verbatim; an
absent or null `executor` section renders `unknown`. The collector's `state` enum is not pinned in this research, so unit 3
reads it from `Aiur.Capabilities.Collector` and names the value that counts as present before mapping anything to a
yes/no. A field the peer does not report renders `unknown`, never `0`. Capacity (`max`) and pause state are not exposed
by any existing read command, so v1 cannot derive `saturated` or `paused`. When MPG-602 lands, the CLI prefers the S6
body (which carries both) and the table below applies in full; until then a missing `capacity` yields only
`idle|active|unknown`. Unavailable at MPG-209's level, so shown as `unknown` (never `0`/`false`): S6 `capacity`, per-project `paused`, gateway-level
pause, `pending_decisions`. Gateway pause has no read source until MPG-602 (`aiur pause` is a local control command with
no read-side report); this is a declared soft dependency, not a hidden one.
The workload function is shared so CLI, dashboard (MPG-603) and JSON agree.

**Workload derivation** (pure function `Aiur.Gateway.Workload.derive/1`). It has two rules; the switch is whether the
peer's S6 body (MPG-602) supplied `capacity`. v1 has none, so v1 always uses the first.

*v1 rule* (running count from `agents --json` only):

| Order | Condition | Result |
|---|---|---|
| 1 | connectivity is not `online` | `unknown` |
| 2 | running count `> 0` | `active` |
| 3 | otherwise | `idle` |

*S6 rule* (once MPG-602 lands and the peer reports `capacity`; takes over for that peer):

| Order | Condition | Result |
|---|---|---|
| 1 | connectivity is not `online` | `unknown` |
| 2 | gateway-level pause set, or `projects` non-empty and every project `paused` | `paused` |
| 3 | `capacity.max > 0` and `capacity.running >= capacity.max` | `saturated` |
| 4 | `capacity.running > 0` | `active` |
| 5 | otherwise | `idle` |

Reasons: pause outranks load because a paused gateway with leftover running agents is draining and the operator needs to
see "not taking work". Saturated outranks active because it is the actionable state (plan A4: lower-priority work uses
idle slots, so saturation means no slack). `idle` means "reachable, unpaused, zero running" and says nothing about ready
work. `max = 0` is never saturated. Rejected: a percentage threshold (a made-up number; `running >= max` is the cap the
orchestrator already enforces in `src/lib/aiur/orchestrator/slots.ex`); an `offline` workload value (connectivity
already carries it).

**Connectivity.** `online`: hello and `agents --json` both answered. `offline`: transport failure or timeout. `error`: answered
but refused or invalid (401/403, bad JSON, gateway id differs from the registry pin). `unknown`: never reached (no cache).

**Cache.** After each fully successful read, write `~/.aiur/remote-state/<name>.json` (temp file + rename, mode 0600)
with the fields actually read (hello `gateway_id`, `gateway_label`, `build`; the running count and per-agent rows from
`agents --json`; the `executor` section from `capabilities --json`; and the S6 body once MPG-602 supplies it) plus
`observed_at`. On failure read it: `age_ms = now - observed_at`; `freshness` is `fresh` (answered now),
`stale` (from cache) or `none` (never reached). Row text: `agents: 3 (12m ago)`. Totals sum only known numbers; any
`none` entry renders the total as `12 + unknown`.

**Fan-out.** Reuse `packaging/npm/aiur-cli/libexec/engine/remote_all.sh`: it already runs read commands in parallel with
per-instance result files (`run_remote_all_instance`) and forces `max_scope=read`. `agents` and `capabilities` are already in its read-command
allow-list (the `case` near line 37), so v1 adds no command there; the hello call is the only new read, and the S6 summary
joins the list when MPG-602 lands. No new fan-out. Per-entry timeout default 5 s so one dead peer cannot
stall the table.

**JSON.** One object per row: `{gateway, connectivity, workload, last_seen_at, age_ms, freshness}` (the acceptance
shape) plus `last_workload`, the cached value when offline. The text table must render the age too (AGENTS.md "Computed
ages" rule).

## Interfaces
- Consumes: hello (MPG-207), `--gateway` resolution (MPG-202), `agents --json` and `capabilities --json` (existing); S6 summary (MPG-602) later, not required; registry entries and tokens (MPG-206/207); `remote_all.sh`.
- Provides: `Aiur.Gateway.Workload.derive/1`; the `~/.aiur/remote-state/<name>.json` cache; `aiur gateway list|status [--json]` for MPG-210 and dashboard MPG-603.

4. Launcher: `packaging/npm/aiur-cli/libexec/engine/remote_all.sh` plus the engine dispatcher route for `gateway list|status`.
5. Docs: `website/docs-app/reference/cli-gateways.md` (commands, workload table, cache path, `12 + unknown`).

## Test scenarios
| Scenario | Input | Expected |
|---|---|---|
| Offline uses cache | stubs: A answers, B times out; B cache has 3 agents observed 12 min ago | B row `offline`, `agents: 3 (12m ago)`, workload `unknown`, freshness `stale` |
| Never reached | no cache, unreachable | `unknown`, freshness `none`; totals `12 + unknown` |
| Idle, no S6 | online, `agents --json` empty, no capacity | `idle` |
| Active | running 2 (max 4 if S6) | `active` |
| Saturated (S6 present) | running 4, max 4 | `saturated` |
| Max zero | running 0, max 0 | `idle` |
| Paused beats saturated (S6 present) | running 4, max 4, gateway pause | `paused` |
| All projects paused (S6 present) | running 0, every project paused | `paused` |
| Error | peer returns 403 | connectivity `error`, workload `unknown` |
| JSON shape | `--json` | each row has the six keys plus `last_workload` |
| Corrupt cache | truncated file | treated as never reached, no crash |
| Unknown-branch mutation | replace the offline `unknown` with `idle` | the offline test fails |

## Data and assets
Cache path `~/.aiur/remote-state/<name>.json`. Tests point the state root at a temp dir (AGENTS.md: never read real
`~/.aiur`). Known gap: heartbeat `agent_count`/`agent_capacity`
(`src/lib/aiur/orchestrator/instance_heartbeat_metadata.ex`) is display-only and carries no pause or project data, so S6
must be built from orchestrator state, not the roster.

## Risks
- S6 field names may move in MPG-602. Detect: tests use the S6 literal from `state-schemas.md`; v1 tests use real `agents --json` output.
- Plan acceptance names `saturated|paused`, which v1 cannot produce without MPG-602. Fallback: state this in the CLI docs; the states appear when S6 is present.
- One slow peer stalls output. Fallback: per-entry timeout and parallel fan-out.
- Stale cache read as live. Fallback: always print age; JSON carries `freshness`.

## Open questions
| Question | Recommended default | What changes if answered differently |
|---|---|---|
| Paused with running agents: `paused` or `draining`? | `paused` | A fifth state touches the enum in the plan and MPG-603 |
| Offline: show last-known workload as the workload? | No: `unknown`, last value in `last_workload` | Plan item 16 forbids offline reading as idle; a cached `active` risks the same lie |
| Per-entry timeout | 5 s, `--timeout` flag | Longer slows `list` when a peer is down |
| `idle` when ready work exists but gateway is unpaused? | Yes; ready count is a separate column | A `starved` state needs a ready-vs-slots rule |
| Derive in the CLI when the peer lacks `workload`? | Yes, same function | Older peers would show `unknown` |
