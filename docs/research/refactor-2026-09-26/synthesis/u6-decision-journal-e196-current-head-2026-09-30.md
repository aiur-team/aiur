## Current source distinction

- `DecisionLog.append/2` writes a complete newline-terminated record before `:file.sync/1` (`decision_log.ex:127-145`). A sync error returns an error even when the bytes are readable. The request and lifecycle callers keep their old in-memory state on append error (`decision_store.ex:2426-2462,2483-2507`), so a same-process retry can reserve a new event ID before reconciling the journal. A pre-write error and an uncertain post-write sync outcome need different policies. The `filesystem_sync_fun` option only covers journal creation, not each append's `:file.sync`.
- After a confirmed append, `repair_projection/1` marks the store read-only on `decisions.json` failure (`decision_store.ex:733-751`). Request acceptance then calls `notify/3` unconditionally (`:2458`), while enrichment and lifecycle paths suppress notification when `writable?` is false (`:2153,2509-2527`). `blocked_ticket_ids/1` also treats repair health as unreadable (`:1064-1094,1771-1778`). Boot reconciliation scans requested/deferred executor notifications; it is not a general event-ID replay for withheld lifecycle topics (`:597-611,2589-2613`).
- The `follow_up_required` and `follow_up_handled` append-error branches still call `fatal_lifecycle_append_failed/3` (`:4057-4069,4072-4090,4365-4368`), which latches the store read-only without the action-scoped alert/retry used by other background lifecycle append errors (`:4287-4327`). This is the `loose-1-02` boundary; the projection and notification split is `loose-1-03`.

## Minimal deterministic witnesses before extraction

1. **Known pre-write failure.** In isolated temporary state, fail journal open/write before a complete record exists. Assert no accepted transition, no notification, no new journal record, and an explicit error or action-scoped hold. For the follow-up branches, assert a visible alert and recoverable retry policy rather than an unexplained fleet-wide read-only latch. A reserved but unused event ID is not proof of acceptance.
2. **Ambiguous sync.** Let the full record reach the temporary journal, then make sync report an error. Assert an uncertain outcome, reconcile by the original event ID before a same-process logical retry, and prove only one accepted transition and one side effect after restart. This needs a narrow injectable append file-operations seam or equivalent controlled fault; chmod/ENOSPC alone cannot prove that bytes were written before the sync failure. Reading bytes after a synthetic sync error is not a power-loss durability claim.
3. **Accepted append, failed projection.** Confirm journal fsync, then fail the derived JSON replacement. Cover both a new request and an answer/lifecycle event: assert one durable event ID, accepted journal authority, explicit stale cause and observed age, and the chosen notification/dispatch hold policy. Restore projection writing, rebuild from the journal, and assert any withheld notification is published once with its original event ID. Restart before and after repair to catch duplicate or lost delivery. Current tests assert repair health and answer-dispatch suppression, but not request/lifecycle publication parity or event-ID replay (`decision_store_test.exs:3284-3297,4571-4589`).
4. **Corrupt complete record.** Append a malformed or semantically invalid *newline-terminated* record after a valid prefix. Replay must keep the first bad line and following bytes, serve validated-prefix reads, alert, and reject mutations until explicit repair. Existing log/store tests cover this shape (`decision_log_test.exs:153-188`, `decision_store_test.exs:4408-4422,4532-4553`); retain them as characterization tests.
5. **Unacknowledged torn tail.** Append a final fragment without a newline. Replay must truncate and sync only that fragment, preserve the complete prefix, and return writable health; a truncation/sync error must stay visible without overwriting the prefix. Existing tests cover the ordinary repair and the `repair_torn_tail: false` read-only probe (`decision_log_test.exs:113-150`, `decision_store_test.exs:4555-4568`).

Do not promote U6 beyond `requirements-only` on these static observations. The implementation contract remains: a confirmed fsynced journal event has one stable identity; an uncertain append waits for reconciliation; projection freshness and withheld side effects are visible and replayable by that identity. New regression tests must fail when their guarded production repair is removed.
