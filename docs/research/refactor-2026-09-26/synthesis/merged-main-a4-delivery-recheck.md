# Queue and parked-entry recheck on `a4e5f70acdd208743cd4b98fc1c92c8c1c22545f`

This narrows P1 `agent-runtime-04` against the release head; it does not reproduce a real failed send or assert incidence. `CheckpointDelivery` claims an immediate or safe-checkpoint queue item and provides an `on_failure` callback. For immediate Executor text, the callback calls `Orchestrator.restore_queue_item_pending/2` after ordinary send errors, or `mark_queue_item_failed/3` for invalid native responses. Both queue APIs return `:ok | {:error, term()}`. Claude REPL `OperatorInject.deliver_immediate_operator_message/2` invokes `on_failure.(reason)` and discards its result; AppServer `OperatorDelivery` invokes it through `TurnState.safe_invoke_failure_callback/2`, whose caller also ignores the result. The focused tests verify callback invocation, not failed restore or mark-failed settlement.

On a successful parent turn, `TurnLoop` calls `consume_delivered_queue_items/2` before the boundary drain. Thus a claimed item whose failed send cannot be restored can be consumed by that sweep while the original delivery never reached the provider. This is conditional on a queue RPC failure after the claim; the source path is present. A new test should use a queue server that accepts claim, rejects restore, then permits consume, asserting the item is never represented as successfully delivered and remains recoverable or visibly failed. The production policy must distinguish provider-send failure from queue-settlement failure and keep the latter's result observable across Claude, AppServer and Muse callbacks.

The #2858 packaging change does not touch these paths. The frozen finding's broader wording should not be read as saying every ordinary send failure loses a message: when restore returns `:ok`, the item is pending for retry.

P1 `orch-b-02` remains a separate lifecycle path. `RateLimitFallback.redispatch_safety_entry/2` keeps identifier, host, retry and prior-work fields, but drops `started_at` and `completion_totals_recorded`; `retain_redispatch_safety/3` leaves that entry in `state.running` if no replacement Task pid appears. `AgentTeardown.terminate_running_issue/3` matches the parked map even with nil pid/ref and passes it to `TokenAccounting.record_session_completion_totals/2`, which accesses `running_entry.started_at` directly unless `completion_totals_recorded: true`. An explicit terminate or equivalent teardown of a parked failed fallback can therefore raise `KeyError` before cleanup. An existing fallback test constructs the nil-pid parked entry and verifies retry scheduling, but does not pass it through teardown. A decisive test should force attempted fallback dispatch to return without a Task, then terminate/deactivate that parked entry and assert no Orchestrator crash, preserved claim/fence and correct accounting. The intended accounting for a non-running safety entry must be decided before adding fields blindly.

P1 `orch-a-10` still has an unbounded in-memory shape: `AgentQueueStore.put_item/2` only writes into `items`, and action/message ID indexes only gain mappings; no eviction path exists in that module. `OperatorMessages.reject_already_queued_events/2` scans every retained item to rebuild a set of historic digest event IDs for each enqueue. This establishes growth and increasing per-enqueue work with lifetime item count, but not a measured production rate or memory cost. Exact replay/idempotence depends on those retained IDs, so a blind trim would break behavior. Before a bounded design, measure queue population and enqueue time on a running daemon, define the replay horizon and durable tombstone authority, then test duplicate delivery across restart and compaction.
