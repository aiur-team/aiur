# P2/P3 reconciliation overlay: parts 2 and 3

This overlay resolves the five conflict groups in [the parts 2–3 cross-review](p2p3-triage-cross-review-parts-2-3.md), covering nine finding IDs. The [part-1 overlay](p2p3-part-1-reconciliation.json) resolves eight further IDs. All three raw partition artifacts stay intact. I reread the full cited flows on public main `3339b887` and compared the affected paths with the clean pre-release integration candidate `7bce08f36`; none of those paths changed in that candidate. The later candidate `b2d38b15` changes CommandRunner and launcher pidfile cleanup, not these cited paths; that candidate is interim. Recheck each decision on **merged main after release** before opening implementation work.

**Consistent rule:** `source-supported` means the checked source establishes the *mechanism*, including a plausible failure path; it does not mean a live incident, frequency or saving has been observed. `unknown` is for a mechanism that still depends on an untraced call, missing branch, or unresolved source contradiction. `fix` means a concrete correctness or operator-contract repair should be queued, but implementation is ready only when its named owner supplies a test that fails on the existing behavior and passes with the repair. `defer` needs an explicit missing evidence condition. Every row below is **source-supported / fix** under that rule; every runtime-incidence claim remains unknown.
