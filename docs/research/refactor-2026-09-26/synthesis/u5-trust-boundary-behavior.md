# U5 trust boundary: current behavior and contract gates

Source snapshot: combined release candidate `0299daca28383a336682374e19e90d6434aa4e1a` (before merged-main acceptance). This is source and existing-test evidence, not a production incidence count or a proposed implementation. It sharpens the frozen `github-a-01`, `github-a-02`, and `github-a-07` conflict in [report-wide contradictions](report-wide-contradictions.md).

## Two consumers, different answers

`Aiur.GitHub.CodeOwners` constructs the repository-wide event allowlist by collecting every `@user` and expanding every `@org/team`; it ignores path patterns for that purpose. It refreshes on a timer and publishes `trusted`, `codeowners`, `source`, `degradation`, and `drift` in `trust_snapshot/1` (`src/lib/aiur/github/code_owners.ex:17-45, 181-203, 322-331, 447-485`). `Aiur.Codeowners` separately parses path patterns and decides whether a particular commenter owns a path or any changed PR path (`src/lib/aiur/codeowners.ex:113-155, 158-203`). This split is intentional today; merging it requires an explicit compatibility contract.

## Additional boundary evidence

* The path authority helper also fetches only the first 100 changed PR files and ignores pagination (`codeowners.ex:477-494`). On a larger PR, this can undercount relevant paths and ownership. A U5 contract must cover both team-member and changed-file pagination.
* Successful team lookups in the path helper are memoized in the caller's process dictionary; failures are retried, and no snapshot version ties them to the event allowlist (`codeowners.ex:409-425`). A refactor cannot assume both consumers observed one GitHub membership version.
* `Aiur.GitHub.CodeOwners` only marks parse/read failures as `degradation`; team resolution errors are logged then omitted. Its module comment says resolution failures preserve the previous allowlist, while `do_refresh/1` recomputes whenever direct/configured accounts remain. Treat the code, not that comment, as current behavior (`code_owners.ex:36-39, 181-238, 475-485`).

## Implementation-readiness gates

1. Product/Executor decision: documented policy for incomplete or unavailable team membership, stale trust expiration, absent/empty file fallback, and trust-server crash. The policy must distinguish *unknown* from a proven empty owner set.
2. Behavior tests on current merged main: multi-page team success, later-page failure after a prior healthy snapshot, owner removal on refresh, missing file without repo identity after prior trust, and >100 changed PR paths. Assert the event allowlist, path authority, `trust_snapshot`, alert, digest, and command/rework result for each relevant case.
3. One versioned trust owner and paginated lookup contract can then be designed; validate all consumers against that contract before splitting the oversized CODEOWNERS files. No measured production population or live failure frequency is available from this source review.
