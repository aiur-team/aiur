**Research base:** `research/refactor-current-head-refresh-20260929@f7e40220f`; source checked against `origin/main@f9dabd3e` on 2026-09-30. The five named production/test files below have identical Git blobs at both refs. This is a read-only source finding, not a behavior test, incident count, or implementation approval.

## The unresolved planning gap

[U3 in the current plan](../../../plans/2026-09-29-001-refactor-production-readiness-plan.md#u3-preserve-event-and-claim-ordering) is one unit with a hard U2 dependency. It combines three paths with different state owners: per-ticket subscription cursor and buffer, cross-process Executor lease claims, and the durable wake inbox. The high-priority ledger already assigns `events-webhooks-executor-01` to Event exchange/subscriptions and `events-webhooks-executor-02` to Executor attention. Leaving these as one worker ticket would make its review boundary ambiguous and unnecessarily serialize the two independent fixes behind all of U2. The following is a **proposed planning correction**, subject to behavior witnesses at the implementation SHA.

## Dependency correction

Create two separately reviewable U3 tickets from the first two rows. Both can start after U0 freezes the implementation SHA and source/owner rows; neither source repair requires U2's full lifecycle rewrite. The Event ticket consumes the existing Orchestrator enqueue result contract (`set_enqueue_fn/1` is already the test seam); the Claims ticket uses its existing locked file mutation. If U2 changes either public contract, record that as a reviewed-contract dependency or a file conflict at scheduling time, rather than a global U2 merge prerequisite. The wake receipt ticket depends on the reviewed Claims contract because it calls `Claims.record_acknowledgement/3`.

U4 should depend on the Event delivery contract only where agent turn delivery consumes it; U6 should depend on the wake receipt contract only for shared status or Decision side-effect work that actually reads it. Recheck those exact callers when converting the plan into tickets. This changes scheduling, not the plan's accepted behavior or its final U9 acceptance gate.

**Evidence limits:** The mailbox loss and former-owner revival are source-reachable hypotheses, not measured production incidence. The proposed split does not claim a LOC or latency saving. Run the focused witnesses on the implementation head before selecting a repair, then apply the repository's production-hunk red/green rule in a clean worktree.
