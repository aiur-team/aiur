# MPG-601: project-first dashboard and browser sign-in

Design for [MPG-601](https://github.com/aiur-team/aiur/issues/7601), milestone M6 of
[the multi-project gateways plan](../plans/2026-11-06-multi-project-gateways.md) (PR #7579). It sets the
contracts that MPG-602 (summary API), MPG-603 (home screen) and MPG-604 (gateway view, pause) build to. Their
research tickets (MPG-602R..604R) refine file lists. They do not reopen the decisions below.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Every gateway serves the same home screen at `/` on its own `https://<host>.<tailnet>.ts.net` name. `aiur.dev` is the single entry URL: a static launcher that opens the last gateway used, or lists the gateways. | Keeps the decided browser-to-daemon architecture over Tailscale, with no Local Network Access prompt and no third-party cookies (D3, D4) |
| D2 | The browser fetches each peer's summary directly, cross-origin: `fetch(url, {credentials: "include"})`. No gateway proxies another's data. | Each gateway answers for itself. A human acts on each gateway with that gateway's own session, so peer grants (KTD-9) never come into play and nothing can raise a principal |
| D3 | The human proof is a **session on each gateway**: the existing Google or passkey sign-in, in a host-only `SameSite=Lax`, `Secure` cookie. One Google sign-in signs every gateway in, by chained top-level redirects. | `ts.net` is on the Public Suffix List, so all gateways in one tailnet are one *site*. Lax cookies ride same-site cross-origin fetches in every browser, Safari included |
| D4 | Tailscale identity headers (`Tailscale-User-Login`) are **not** an authorization source. | `tailscale serve` proxies to the loopback listener. Any process on that host (agents and Executors included) can call `127.0.0.1` with forged headers. Tagged devices get no headers. A device being logged in as Kevin says nothing about whether Kevin is at the keyboard |
| D5 | CORS answers credentialed requests only for an exact origin that is listed: registry peer URLs (S2) plus `server.dashboard_origins`. Writes also need a preflighted request and an `Origin` that passes the same check. | Reads stay private to the gateway's own tailnet. Writes cannot be forged by a simple cross-site form or `fetch` |
| D6 | Connectivity and workload are two separate fields with separate icon slots. The browser never turns "no answer" into `offline`, and never turns it into `idle`. | Plan R12 and the AGENTS.md rule on collapsed causes |
| D7 | Off-tailnet gateways get a link-out card on the home. Their data is not shown. The proxy alternative is laid out for Kevin and **not adopted** (section "Gateways off the tailnet"). | The scope asks for the limitation to be stated without changing the architecture |

## Home screen

### Order

Plan decision 13 puts projects and features first and machines second. MPG-603 lists the sections, and the home
uses that order:

1. **Projects**, each row expanding to its **focus features**
2. **Current agents**, across gateways
3. **Queue entry**: the next tickets to get a free slot
4. **Gateway health**
5. **Pending Decisions**

A one-line header holds the totals, pause-all and a link to each pending Decision count. Totals that leave a gateway
out are marked: `Running 7 of 12+ · 1 gateway unknown`. A total never silently drops the unknown part.

```

1. Filters live in the query string (`?gateway=nook&state=ready`), so a filtered view can be shared and
   bookmarked. The `owner` filter is the ownership ref's gateway (S1), not the state label.
2. Project row: counts by state bucket and the gateways that serve the project. `⠿` is the later drag handle (see
   "Later: drag-and-drop"); the MVP renders it disabled with the title "Reordering comes later". `[⏸]` pauses this
   project on every gateway that runs it (MPG-308).
3. Feature row: progress `done/total`, live counts, and a link to the existing Build page. That keeps decision 14,
   "keep detailed project views".
4. One line per running agent: the gateway label comes first, so machines stay visible but secondary.
5. For an unknown gateway, the list shows its last-known agents, prefixed with its age. It never shows an empty
   list.
6. Read-only in the MVP. Order comes from the allocation function (MPG-401) via each gateway's summary. Order across
   gateways uses shared intent (S4) when known. Otherwise it falls back to each project's L1/L3 priority, as the plan's
   config table says.
7. Connectivity and workload each have an icon slot `[◌]` (see "States").
8. The unreachable form required by MPG-603: `unreachable · last seen 5m ago`, with the workload marked
   `last known`.
9. The off-tailnet form (D7).
10. A Decision opens on its own gateway, since its confirmation needs that gateway's session (plan 34b).

### 1,000+ tickets: grouping, collapse, filter

- **Group** by project, then feature (Build Order feature, else `(no feature)`), then state bucket. The buckets are
  `running`, `ready`, `blocked`, `review` (human-review, ci-wait, merging), `paused` and `done`. `done` stays
  hidden unless the state filter asks for it.
- **Collapse by default.** Projects start expanded and show feature rows only. Feature rows start collapsed and show
  counts only. A home screen over 1,000 tickets therefore renders about one row per feature, not one per ticket.
  Expand state is kept per browser in `localStorage`.
- **Load lazily.** S6 carries counts, not tickets. Expanding a feature fetches its tickets from the owning gateway
  50 at a time, with `Show 50 more`. MPG-603R names the endpoint; the existing Build data is the candidate.
- **Search** with `#1234` jumps to that ticket. Free text matches titles among loaded rows, and the result says
  "loaded rows only" until every group has loaded. It never implies a full search.
- **Filter** by gateway, project, feature, state bucket, owner gateway and lane. A filter that removes every row
  says which filter did so.

│ Capacity  ████████ 4/4 · ready waiting 9                                                    │
│ Projects  aiur-team/aiur 4 running (cap 4)                                                  │
│ Agents    #7590 work 60% 40m · #7611 review 90% 5m · #7612 work 20% 2m · #7615 ci-wait      │
│ Local queue  #7640 · #7641 · #7652 …                                                        │

│ Owned tickets 23 · last ownership write 2m ago                                              │

```

The view is reached from a gateway-health row or a `?gateway=` filter. It holds no data the summary lacks, except
the agent list. When the gateway is not online, every field shows its last-known value and age.

## States

Two fields, each rendered as icon slot + text. The text is always present, so the separate icon work can land at any
time without layout changes. Slot ids: `gw-conn-<state>` and `gw-load-<state>`, each a 16 px inline box with
`data-icon-slot`. Colours come from `packages/aiur-style` tokens.

### Connectivity (the browser's view of one gateway)

| State | Set when | Text |
|---|---|---|
| `connecting` | First fetch in flight, nothing cached | `connecting…` |
| `online` | Summary answered 2xx within 3 s, and `gateway_id` matches the registry | `online` |
| `error` | Answered, but unusable: 401/403 (`signed out`), 5xx, schema or `gateway_id` mismatch. The reason is shown | `error: signed out` |
| `unknown` | No answer (timeout or `TypeError`). The browser cannot tell network, TLS, CORS and browser blocks apart, so it names no cause | `unreachable · last seen 5m ago` |
| `offline` | `unknown` **and** a server-side source agrees: the home gateway's liveness (MPG-408) reports the peer silent beyond `offline_after_seconds` | `offline · last seen 5m ago` |

`unreachable` is display text for `unknown` (plan R12). It is not a sixth state. A gateway never contacted on this
device and absent from cache reads `unknown · never seen on this device`. Last-known summaries are cached per
gateway in `localStorage` with their `observed_at`, so a reload during an outage still shows an age.

### Workload (from S6 `workload`, computed by the gateway)

| State | Rule |
|---|---|
| `paused` | The gateway is paused (local or pause-all). Takes precedence; running agents still show |
| `saturated` | `running >= capacity.max` |
| `active` | `0 < running < capacity.max` |
| `idle` | `running == 0` |

Workload is shown live only when connectivity is `online`. In any other state it is prefixed `last known` and its
age. It is never shown as `idle` and never omitted. The MPG-603 mutation test, replacing the unknown branch with
`0 agents`, must fail against this rule.

## Pause controls

- **Gateway pause** (`[Pause Nook]`) calls that gateway directly with its own session.
- **Project pause** (`[⏸]` on a project row) calls each gateway that runs the project.
- **Pause all** writes the shared-intent `fleet.pause` change (S4, slot `human`) through the home gateway when the
  store is up. It also calls every reachable gateway directly. It then shows a delivery report:

```text
Pause all — 3 gateways
  PC     paused ✓
  Nook   will pause on reconnect   (unreachable; fleet pause is in shared intent)
  Lab    not paused: off tailnet, pause it from its own dashboard ↗
```

`will pause on reconnect` is shown only when the shared-intent write succeeded. If the store is also down, it reads
`not paused: unreachable and no shared store`. A12 depends on that difference. Resume mirrors pause. Per
reconciliation rule 5, a human resume clears every slot.

## Later: drag-and-drop (out of MVP)

The handles `⠿` exist from day one, disabled. When the editor lands:

- Projects, features and tickets in the queue reorder by drag. A drop writes one shared-intent change (slot `human`)
  setting `order_key` to a fractional index between the two neighbours. No other row is rewritten.
- A row whose order an Executor forced (rule 3) shows a `takeover` badge naming the change it superseded.
- Keyboard: `Space` picks up a row, arrows move it, `Space` drops it, `Esc` cancels. A live region announces each
  position.
- Dropping onto an unreachable gateway's project is allowed. The change lives in shared intent, and the row shows
  `applies on reconnect`.

## Browser sign-in

### Flow (one sign-in across gateways)

```text
aiur.dev ──navigate──▶ https://pc.<tailnet>.ts.net/        (home; PC session cookie, Google sign-in)
   │                       │ fetch(nook/api/v1/gateway/summary, credentials: include)
   │                       ▼
   │                   401 from Nook → card "Nook: signed out [Sign in]"
   │                       │ [Sign in to all] → top-level navigation, one gateway at a time:
   │                       ▼
   │      https://nook.<tailnet>.ts.net/auth/google?return_to=https://pc.<tailnet>.ts.net/
   │                       │ Google already signed in → no prompt (login_hint carries the account)
   │                       ▼
   └──────────────── back on PC home; Nook's fetches now carry Nook's cookie
```

- **One interactive sign-in.** The first gateway's Google sign-in is the only prompt. Each further gateway costs a
  redirect, which Google usually completes without a prompt while its session lives (an account chooser may show). A passkey sign-in stays per gateway: its
  credential is stored per gateway today.
- **`return_to` is new.** The Google callback today returns to its own home. MPG-602 adds `return_to`. It is accepted
  only when it is an exact origin from the D5 list, so it cannot become an open redirect.
- **Each gateway's Google redirect URI** (`https://<host>.<tailnet>.ts.net/auth/google/callback`) must be registered
  on the shared Google client. This is a one-time operator step per gateway, documented with MPG-602.
- **Writes** from the home to a peer carry that peer's cookie, `Content-Type: application/json` and
  `x-aiur-request-id` (KTD-12). That forces a preflight, and the peer checks `Origin` against D5 before it acts. The
  peer records the write as a local human action by the signed-in account (S5 `actor`), with `origin_gateway` set
  to the page's gateway. No peer grant is consulted or widened.
- **Grant confirmations** (plan 34b) open on the target gateway's own page. They are never a cross-origin write.

### CORS

The summary route (MPG-602) and every route the home calls answer:

```text
Access-Control-Allow-Origin: <the request Origin, if listed>   # never "*" (credentials)
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST          # POST only on write routes
Access-Control-Allow-Headers: content-type, x-aiur-request-id
Access-Control-Max-Age: 600
Vary: Origin
```

An unlisted origin gets no CORS headers, which matches MPG-602's acceptance test. Existing write routes keep their
same-origin rule until they are added to the home on purpose.

### Private Network Access / Local Network Access

- Chrome's Private Network Access preflights were replaced by the **Local Network Access** permission prompt (Chrome
  142). Mozilla reports shipping LNA in Firefox 151. Safari status is unconfirmed.
- The LNA spec classes `100.64.0.0/10` (Tailscale addresses) as **local**. A prompt fires only when a request goes
  to a *less public* address space than the page.
- Under D1 the page is served from a tailnet address, and its peers have tailnet addresses: local to local, **no
  prompt** in any browser. The launcher step is a top-level navigation from `aiur.dev`. The spec notes that Chromium
  applies LNA only to iframe navigations today. If it starts gating main-frame navigations, the launcher's fallback
  list of plain links still works after one prompt.
- Rejected alternative: a page hosted on `aiur.dev` calling gateways directly. That is public to local, so it raises
  a per-browser LNA prompt. It also runs into cross-site cookies: blocked by Safari, partitioned by Firefox. Writes
  would then need bearer tokens held in a public page's JavaScript, and one XSS on `aiur.dev` would reach every
  gateway.

### Phone access

- The phone joins the tailnet with the Tailscale app. MagicDNS resolves `*.ts.net`, and the certificates are
  publicly trusted, so the phone's browser works unchanged. Sign-in is the same Google flow.
- The home collapses to one column below 640 px, in the same order. Gateway health moves into the header as one
  status chip per gateway: icon slot + label + state text.
- iOS Safari's handling of tailnet addresses under LNA is not documented. MPG-603's post-deploy check covers it.

## Gateways off the tailnet

This section states a limitation. It does not change D1-D7.

- A browser reaches a gateway only through a **publicly trusted certificate** (a tunnel, or a real domain with
  ACME). A pinned self-signed endpoint (`tls_pin_sha256`) works for the CLI and **cannot be shown in a browser**.
- With a trusted certificate, the gateway is a **different site** from the tailnet home. Its session cookie is
  cross-site: blocked by Safari, partitioned by Firefox. Its card cannot carry a signed-in session.
- The home therefore shows such a gateway as a link-out card (⑨). The card holds its label and a link to its own
  dashboard. It has no counts and no pause button. Totals mark it as unknown.
- **The alternative, for Kevin to decide, not adopted:** route peers through the page's own gateway (browser → own
  gateway → peer), as the enrolment research proposes. It reaches any gateway the CLI can reach, pinned ones
  included. The cost: it changes the decided browser-to-daemon architecture. It also needs a forwarded human principal
  that a peer must trust its neighbour to assert, which plan 34b currently forbids for grants.
