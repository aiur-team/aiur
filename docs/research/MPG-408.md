# MPG-408 — Alert once when a gateway goes offline: research

Research ticket MPG-408R (#7598). Plan: `docs/plans/2026-11-06-multi-project-gateways.md` (PR #7579); contract: MPG-408 in
`docs/plans/2026-11-06-multi-project-gateways/tickets-m4-m7.md`. Focus: the alert channel (existing push) and the dedupe key.
No code changes. Brainstorm questions are recorded under Open questions with a recommended default.

## Outcome

A gateway whose heartbeat (store up) or hello (store down or not configured) has been silent longer than
`coordination.offline_after_seconds` (default 180) raises exactly one `needs_attention` alert for that outage. It does
not alert again while the outage lasts, nor when the gateway recovers; recovery only closes the open attention
silently. A later, separate outage raises a new alert. A restart of the observing daemon in the middle of an outage does
not re-alert.

## Design

**Alert channel.** There is no separate "push" module in the tree (the only `push` code is
`lib/aiur/push/crypto/primitives.ex`). The operator-facing push is the alert path:
`Aiur.Signal.alert(topic, opts)` -> `Aiur.Alerts.emit_system/2` -> alert feed and ledger, whose `needs_attention: true`
records are what wake the Executor and the dashboard. MPG-408 uses that path exactly as `Aiur.Orchestrator.FeatureSupply`
does (`lib/aiur/orchestrator/feature_supply.ex:28-56`):

```elixir
Aiur.Signal.alert("system.gateway.<id>.offline",
  message: "Gateway Nook silent for 4 min (last heartbeat 12:03:10Z)",
  reason: "no heartbeat for 240 s; threshold 180 s",
  needs_attention: true, severity: "warning", durable: true, central: true,
  exchange_payload: %{gateway_id: id, silent_ms: ms, last_seen_at: iso, source: "store" | "hello"})
```

`durable: true` keeps the latch until publication succeeds (`alerts.ex` `do_emit`), so a failed publish retries on the
next tick instead of losing the outage. `central: true` keeps it in the central feed (as `landing_watch.ex:305` does).

**Topic and dedupe key.** `Aiur.AlertTopic.attention_key/1` maps `system.<rest>` to `{:system, rest}`, so the topic string
*is* the attention identity. A single `system.gateway.offline` topic would merge two gateways' attentions into one (the
second never shows). So the topic carries the gateway: `system.gateway.<gateway_id>.offline`, the same wildcard shape
already used for `system.claude_account.*.usage_probe_failing`. The catalogue gets `{"system.gateway.*.offline", ...}` and
`{"system.gateway.*.offline.resolved", ...}` in `lib/aiur/events/catalog/system_entries.ex`. (This refines the ticket's
`system.gateway.offline`; see Open question 1.)

The **outage key** is `{gateway_id, last_seen_ms}`: the gateway id plus the `heartbeat_at` of the last row seen live
(store) or the observer's last successful hello time (direct). It is stable for the whole outage and changes only after
the gateway has been seen live again, so "online, then offline an hour later" is a new key and a second alert. It is held
in memory only. Across a daemon restart the open outage is recovered from the ledger, not from a file:
`AlertFeed.condition_state("system.gateway.<id>.offline")` returns `:firing | :resolved | :unknown`
(`alert_feed.ex`, `condition_state/2`); `:firing` seeds the state as already alerted. No new persistence.

**Recovery.** Plan requirement R13 / decision row 21: alert on going offline, not on return. On the first live
observation after an alert, emit `system.gateway.<id>.offline.resolved` with `needs_attention: false, severity: "info"`,
which only closes the attention (it has no sound; `Alerts.do_emit` already drops repeat resolutions via
`repeat_resolution?`). If the feed ever turns a resolved record into a push, see Open question 2.

**Observers and the store.** With the store up, every daemon reads the same roster, so N observers would raise N alerts for
one outage. Dedupe without new schema: only the repository leader alerts (roster rows already carry `leader?`,
`instance/roster.ex:60-66`, from `LeaseStore.leader/1`). With the store down or unset there is no leader and no shared
state; each observer alerts for its own peers from hello. If the leader changes during an outage the new leader alerts once
more; accepted as rare (Open question 3 for the claim-table alternative).

**Detection.**
- Store mode: `Aiur.Instance.Roster.list/1` already returns `age_ms` per row from the store's `heartbeat_at`
  (`roster.ex:74-90`). A row is offline when `age_ms > offline_after_seconds * 1000`. The roster's own `state: :stale`
  (30 s default) is a display threshold and is not used. Rows for this daemon (`current?`) and rows with `removed?: true` are skipped.
- Direct mode: `GET /api/v1/gateway/hello` (MPG-207) per registry peer (MPG-205). Offline when the time since the last
  successful hello exceeds the threshold. A peer never seen has no baseline: the clock starts when the observer starts watching.
- If the store call errors, no store verdict is made and the tick falls through to hello for peers that have one. An
  observer whose probes all fail in one tick, with no store, cannot tell its own network outage from theirs: it skips
  alerting and logs (Open question 4).

**Process.** `Aiur.Gateway.Liveness`, a GenServer under the daemon supervisor, ticks every 30 s (module attribute,
overridable via `start_link` opts for tests; not a public key in the MVP). The decision is a pure function
`Aiur.Gateway.Liveness.Core.evaluate(observations, prior_state, now_ms, threshold_ms) :: {actions, new_state}` so tests need
no clock or processes. `actions` is a list of `{:alert, id, details} | {:resolve, id}`. The GenServer applies actions and
only commits `new_state` for an action whose emit returned `:ok`.

**Alternatives rejected.**
- One global `system.gateway.offline` topic: merges attentions (above).
- A new Postgres claim table for cross-observer dedupe: a migration for a case the leader gate covers.
- Persisting outage state in a JSON file: the ledger already holds it.
- Alerting from the roster's 30 s `:stale`: flaps on one missed heartbeat; the ticket asks for 180 s.

## Test scenarios

Threshold 180 s, tick 30 s, all times from an injected `now_ms`. Alerts are asserted from the returned actions.

| Scenario | Input | Expected |
|---|---|---|
| Silent 4 minutes | row `age_ms` 240_000, then ticks at +30 s and +60 s with the same outage | exactly one `{:alert, id, _}` with `silent_ms` 240_000; none on later ticks |
| Silent 2 minutes, back | `age_ms` 120_000, then 5_000 | zero actions |
| Exactly at threshold | `age_ms` 180_000 | none (strictly greater) |
| Recovery | alerted, then `age_ms` 5_000 | one `{:resolve, id}` and no `:alert`; the next tick yields nothing |
| Second outage | alerted, live, then `age_ms` 240_000 an hour later (new `last_seen_ms`) | a second `:alert` with a different outage key |
| Two gateways | A and B both silent 240 s | two alerts, topics `system.gateway.<A>.offline` and `system.gateway.<B>.offline` |
| Not the leader | this daemon's row has `leader?: false` | zero actions although a peer is silent |
| Restart mid-outage | state seeded from ledger `:firing` for A; A still silent | zero actions; when A is live, one `:resolve` |
| Restart, ledger `:unknown` | A silent 240 s | one alert (fail toward telling the operator) |
| Row vanishes while alerted | A absent from rows | no resolve (absent is not recovered); attention stays open |
| Direct mode, never seen | hello fails, `now - observer_start` = 100 s | zero actions |
| Direct mode, silent 4 min | last hello success 240 s ago | one alert, `source: "hello"` |
| All probes fail, no store, 2+ peers | every hello fails | zero actions and a log line |
| Emit fails | `emit` returns `{:error, _}` | state not committed; the next tick emits; one alert in total once it lands |
| Mutation check | `evaluate/4` replaced by `fn _, s, _, _ -> {[], s} end` | the 4-minute and second-outage rows fail |

Process test (`liveness_test.exs`): start the GenServer with injected `:roster_fun`, `:hello_fun`, `:emit` and `:now`,
send `:tick`, and `assert_receive` the emit with `needs_attention: true` and `durable: true` for the exact topic.

## Data and assets

- Topics: `system.gateway.<gateway_id>.offline` and `.offline.resolved`; `gateway_id` is the 26-character base32 id of S1/S2.
- Outage key `{gateway_id, last_seen_ms}`; never written to disk.
- Config: `coordination.offline_after_seconds`, integer, default 180.
- Known gap: how long a silent row stays in the roster is heartbeat TTL + `instance.roster_stale_retention_ms` (default
  300 000, `config/schema/instance.ex:59`). If TTL + retention is below the threshold the row vanishes before the alert.
  Fallback: treat a previously live row that disappears as silent since its last `heartbeat_at`, and warn at startup
  (Open question 5).

## Risks

- An observer partitioned from the store sees every peer as stale; only a store *error* is distinguishable from silence.
  Detect with a tick log line naming the verdict source; the all-probes-failed skip covers direct mode.
- Leader gate: if no daemon holds leadership, nobody alerts. The tick logs `leader: none`; fallback is to alert locally when the store is up but the leader is unheld.
- A topic per gateway grows the attention list, bounded by the gateway count.
- MPG-407 may rename roster fields: the core takes a normalised `%{id, age_ms, leader?}` map, so only the reader adapts.

## Open questions

| Question | Recommended default | What changes if answered differently |
|---|---|---|
| 1. Topic: per-gateway `system.gateway.<id>.offline`, or the ticket's `system.gateway.offline` with the id in the payload? | Per-gateway (the topic string is the attention identity) | One topic means one open attention per fleet, so a second gateway's outage is invisible while the first is open; ticket wording and acceptance text keep the old name |
| 2. Does a `needs_attention: false` `.resolved` record cause a push or sound? | No; emit it so the attention closes | If it does, drop the resolve emit and let the attention age out, leaving a stale open attention |
| 3. Cross-observer dedupe: repository leader gate or a claim table keyed `(gateway_id, outage_key)`? | Leader gate (no schema) | A claim table needs a migration in `lease_store/postgres.ex` and removes the repeat alert on leader change |
| 4. No store, every probe fails: alert or stay silent? | Stay silent and log | Alerting blames peers for the observer's own outage |
| 5. Check `offline_after_seconds` against heartbeat TTL + retention at startup? | Warn, do not reject | Rejecting makes a bad machine file unbootable |
| 6. A gateway runs several projects, each with a repository leader: which leader gates? | The leader of the first project in `projects:` order; none configured, no gate | Per-project gating repeats one outage once per project |
