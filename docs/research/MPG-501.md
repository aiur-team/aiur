# MPG-501 — Delegate a ticket to another gateway through ownership: research

Research ticket MPG-501R (#7599). Implementation ticket: MPG-501 (#7664). Focus: the waiting-label name and its
clearance rule. Inputs read: the plan (`docs/plans/2026-11-06-multi-project-gateways.md`, PR #7579, branch
`plan/multi-project-gateways`), `code-evidence.md`, `state-schemas.md`, the MPG-501 contract in `tickets-m4-m7.md`,
the contracts of MPG-102, 103, 104, 106, 202, 207, 306 and 407, and the code listed under "Implementation units".
Nothing in `src/lib/aiur/ownership*` exists on `main` yet; every path below marked *(MPG-nnn)* is created by the named
neighbour and MPG-501 extends it.

## Outcome

`aiur ticket assign <n> --to pc --reason <r>` run from Nook's Executor is the whole delegation (R14, KTD-11). Before
writing, it checks PC's project list. PC lacks `owner/repo` (fresh evidence): exit 64 `pc does not run owner/repo`,
nothing written. PC unreachable and no usable cached list: the transfer is written and the CLI warns. Later, Nook's
poll notices that PC reports the repo missing and adds one label, `gateway-waiting:project-missing`, to the issue. The
label clears when it stops being true. While PC is offline the ticket stays owned by PC and Nook never dispatches it
(already true under the ownership protocol; MPG-501 adds the test that pins it).

## Design

### D1. Label name: `gateway-waiting:project-missing` (keep the plan's name)

- Not under the `agent:`/`nuc:` prefix. The prefix is per gateway (`github.label_prefix`), and this label is read by
  the delegator and the owner, which may use different prefixes. A prefixed marker would be invisible to one of them.
- Not `gateway:<slug>`. MPG-104 owns `gateway:<label-slug>` as the ownership projection and treats every label that
  starts with `gateway:` as a possible owner. A gateway whose label slugs to `waiting-project-missing` would collide.
  `gateway-waiting:` has a different prefix before the colon, so MPG-104's parser never sees it.
- Safe against the existing cross-prefix guard. `Labels.foreign_state_label?/3`
  (`src/lib/aiur/github/state_labels.ex:35-47`) only trips when the text after the first colon normalizes to a state
  slug (`todo`, `in-progress`, …). `project-missing` is none of them, and the prefix `gateway-waiting` is not
  `agent`/`nuc`. A test pins this (scenario T9).
- The suffix names the cause, so a later cause can add `gateway-waiting:<cause>` beside it without renaming.
  Only `project-missing` exists in MPG-501. No other value is written.
- It is a **projection**, like `gateway:<label>`: the ownership ref decides, the label informs. Dispatch never reads
  it (see D6), so a human deleting it changes nothing about who owns the ticket.

### D2. Who adds it, and exactly when

Add only when all hold, evaluated by the **delegating** gateway on its poll, in `Aiur.Ownership.Projection`
*(MPG-104)*:

1. The ownership ref for the ticket names another gateway `G` (not self), and the ref's `reason` is `transfer`.
2. This gateway is the delegator: the local delegation record (D4) holds `{repo, ticket, to_gateway_id, epoch}` with
   `epoch` equal to the ref's epoch. (A ticket transferred by someone else, or re-transferred since, is not ours to
   label.)
3. `G`'s project list is known and fresh (≤ `@fresh_ms` = 10 minutes) and **does not contain** `repo`.
4. The issue does not already carry the label (the poll's issue list already has the labels; no extra read).

Unknown never labels. Unreachable, no list, or a stale list: do nothing and keep the record. The reason is the
AGENTS.md rule on collapsed causes: "PC is offline" and "PC does not run the repo" are different causes, and the label
states only the second. Offline is shown by the gateway-offline alert (MPG-408) and the roster, not by this label.

Writes use the governed GitHub client and the budget broker (one `POST /issues/{n}/labels`). The call is additive and
idempotent (`POST /issues/{n}/labels` adds without replacing, per `github-claim-protocols.md`), so two gateways racing
it is harmless. The label is created in the repo on first use by the same ensure-label step MPG-104 adds for
`gateway:<slug>` (colour and creation details are MPG-104R's); if that helper is absent, MPG-501 calls it with the new
name rather than creating labels itself.

### D3. Clearance rule

Remove `gateway-waiting:project-missing` on any poll by **any** gateway that sees it, when one of these is true.
Removal is idempotent (`DELETE /issues/{n}/labels/{name}`; a 404 is success), so no election is needed:

| Condition | Why it clears |
|---|---|
| The ref's owner is this gateway | The ticket reached a gateway that runs the repo. Covers PC after it adds the project and its poll sees its own ticket. |
| The ref's owner is another gateway `G'` whose fresh list contains `repo` | Re-delegated, or the owner added the project. |
| The ref is `released`, or the ref's epoch is higher than the delegation record's and the owner changed | The delegation the label described no longer exists. |
| The issue is closed (terminal state) | Housekeeping; the label must not outlive the work. |
| The owner's fresh list now contains `repo` | The condition is no longer true. |

It does **not** clear because the owner went offline, a list went stale, or an hour passed. A label that stays while
unknown is the honest state (it was true when written); a timer would clear a still-true label.

If the label is present but the ref is unreadable (`:unknown`), leave it alone and let the existing
`ownership_unknown` handling skip the ticket.

### D4. Delegation record and peer project cache (local state)

Two small files under the gateway state root (`Aiur.Config.Paths` ownership dir, `ownership/`), written atomically:

- `ownership/delegations.json`: `[{"repo","ticket","to_gateway_id","to_label","epoch","at"}]`. `assign` appends after
  a successful `:won` transfer; the projection pass drops entries that cleared (D3). Bounded: at most 500 entries,
  oldest dropped with a log line. This is what makes "we are the delegator" decidable without extending S1.
- `ownership/peer-projects.json`: `{ "<gateway_id>": {"observed_at","projects":["owner/name",...]} }`. Written by
  `assign` (from the CLI fetch, D5) and by any later fetch. It is the "last cached one".

S1 is not changed (see open question Q3 for the alternative).

### D5. Where the peer's project list comes from

The contract says "S6 summary", but S6 (`GET /api/v1/gateway/summary`) is MPG-602, which is **not** a dependency of
MPG-501 (MPG-501 depends on MPG-106, MPG-306, MPG-501R). Without a source MPG-501 cannot be built or accepted. The
sources that exist at MPG-501's dependency level:

| Source | Available after | Verdict |
|---|---|---|
| `aiur --gateway pc status --json`, whose `projects` list MPG-306 adds (acceptance: "lists both under `projects`") | MPG-306 + MPG-202 | **Use.** Read-only, existing remote transport, no new endpoint. |
| Heartbeat `projects` key (MPG-407) | MPG-407, store up only | Optional second source. Not a dependency; read if present. |
| `gateway/hello` (MPG-207) | MPG-207 | Rejected: exactly five keys, no projects, by contract. |
| S6 summary (MPG-602) | MPG-602 | Not available; the fetcher takes a function so S6 can replace it later with no other change. |

Division of labour: Elixir has no outbound peer client (the HTTPS call is the launcher: `engine/remote.sh`,
`code-evidence.md` §3.1). So:

- **`assign` (CLI path):** the shell verb `ticket assign` first runs the remote read for the `--to` gateway
  (`status --json` through the `--gateway` path, 5 s timeout), extracts `projects[].repo`, and passes it to the RPC as
  `peer_projects: [..], peer_observed_at: <iso8601>`. If the fetch fails it passes nothing and the RPC falls back to
  the cache. The RPC rewrites the cache on any fresh value.
- **Poll path (daemon):** the daemon reads only the cache and the heartbeat `projects` key. It never calls a peer. So
  after PC goes offline the delegator's last cached list ages out of `@fresh_ms` and the label is not added; it is
  added only when a fresh list says "missing". Fresh data arrives whenever an Executor or a scheduled
  `aiur gateway status --refresh`-style read runs; if the plan wants this automatic, that is MPG-209's gateway status
  call writing the same cache (open question Q2).

`assign` gate decision (pure function `Delegation.check_target/3`):

| Cached/fetched list for target | Result |
|---|---|
| Fresh (live fetch, or ≤ 10 min) and contains repo | proceed |
| Fresh and lacks repo | refuse, exit 64 `<to> does not run <repo>` |
| Stale (> 10 min) and lacks repo | proceed, warn `<to> did not answer; its last list (age) lacked <repo>` |
| Stale and contains repo | proceed, no warning |
| No list at all (never fetched, unreachable) | proceed, warn `<to> unreachable; project list unknown; transfer written` |

A stale negative never refuses: PC may have added the project since, and the refusal would be a confident statement
the evidence no longer supports.

### D6. Dispatch is untouched

`Aiur.Orchestrator.DispatchPolicy` (`src/lib/aiur/orchestrator/dispatch_policy.ex:385-403`) needs no change. The
requirement "while PC is offline the ticket stays owned by PC and Nook does not dispatch it" is satisfied by
ownership protocol step 2 (owner is another gateway: skip), which MPG-103 implements. The contract's file list names
`orchestrator/dispatch_policy.ex`; this research withdraws it. MPG-501 adds a test that exercises the existing skip
for a transferred ticket carrying the waiting label, and one that proves the label alone does not skip a ticket this
gateway owns (the label is a projection, never a gate). Adding a skip reason to `dispatch_policy.ex` would turn the
projection into a second source of ownership truth, which KTD-2 forbids.

### Alternatives considered

- Refuse in every case where the list is unknown: contradicts the settled decision ("refuse or wait with a visible
  label") and breaks delegation whenever PC sleeps. Rejected.
- Label on the receiving gateway (PC): PC cannot add it because it does not run the repo and does not poll it.
  Rejected.
- Comment on the issue instead of a label: not filterable, not removable by rule. Rejected. (A comment would also
  spend a write per transition.)
- Timer-based clearance: clears true labels. Rejected (D3).

## Prior art

None needed. The external questions (GitHub label write semantics, no atomicity for labels, ref-based ownership) are
answered by `docs/research/multi-gateway/github-claim-protocols.md`, which says label writes are additive,
unconditional and not a claim primitive, so the label must stay a mirror of the ref. The plan's decided rule (Q2:
refuse or wait with a visible label; no auto-clone) settles the product question. No `deep-research` run.

## Risks

- **Dependency drift.** `cli.ex`, `projection.ex` and `ticket.sh` belong to MPG-106/104 and do not exist yet. If their
  function names differ from the contracts, MPG-501 adapts at implementation time; detect early by reading those
  merged files first. Fallback: keep the new logic only in `delegation.ex` and call it from one line in each.
- **No automatic refresh of the peer list** (D5, Q2): the label could lag the fact. Detect: T5 passes but the live
  proof shows no label. Fallback: MPG-209 writes the cache.
- **Cache poisoning via a remote `assign`.** `peer_projects` arrives from the caller. A caller with `tickets` rights
  could claim a list. Mitigation: it only changes whether a check refuses or warns, never ownership, and it is
  validated (T11); the daemon-side poll pass trusts only the cache it wrote itself from an `assign` that came over a
  local socket. Open question Q4 asks whether remote callers may supply it at all.
- **Label created in the repo on first use** by a token that may lack label-create rights: failure is logged and the
  pass retries next poll; no dispatch effect.
- **`cli-operations.md` growth.** Under 400 lines now; MPG-106 also adds to it. Re-count before editing.
