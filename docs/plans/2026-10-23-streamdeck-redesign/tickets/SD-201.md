# SD-201 — View state and dial/key input model (server-side per-deck navigation)

**Complexity:** 3
**Phase hint:** 2
**Area:** area:daemon
**Depends on:** SD-101 — the reducer lives under the Deck shell (`AiurWeb.Streamdeck.Deck`) and reads list sizes from its sections.
**Serializes with:** SD-102 (both wire into the Deck shell (`AiurWeb.Streamdeck.Deck`) and `streamdeck_channel.ex`), SD-103 (removes the TS routing this replaces), SD-104 (`streamdeck_live.ex` assigns)

## Outcome

One pure Elixir reducer owns deck navigation for both the physical deck and the
`/streamdeck` emulator: which view is shown (Ticket, Feature, Epic, Fleet), the page in
each view, the selected ticket, the drill-in stack and the dial-1 scroll offset. The deck
sends raw gestures; the server keeps the state per connected deck.

## Context and evidence

- Three navigation machines exist: dead `packages/streamdeck/src/mode.ts` (tests only),
  the live `packages/streamdeck/src/controller.ts:45-352`, and the emulator's assigns in
  `src/lib/aiur_web/live/streamdeck_live.ex:62-90` + `live/streamdeck_live/modes.ex`.
  See `evidence/B-findings.md` §1-3.
- The channel already holds per-deck state in assigns (`streamdeck_channel.ex:41`).
- There is no long-press detection (`input.ts:36-50` emits rising edges only).
- Server rendering (decision 2) needs the view state on the server.

## Scope

- New module `AiurWeb.Streamdeck.Deck.Nav` (`src/lib/aiur_web/streamdeck/deck/nav.ex`): struct + `reduce(nav, input, sizes) :: {nav, [effect]}`.
- Input model (dial N = hardware index N-1):
  - dial 4 press: cycle Ticket -> Feature -> Epic -> Fleet -> Ticket (clears the drill stack);
  - dial 4 turn: page the current list by one page (8 keys) per detent, clamped;
  - dial 4 long press: pop the drill stack (back); at the root, no-op;
  - dial 1 turn: scroll (list rows or chat, whichever the current surface declares scrollable); dial 1 press: no-op (reserved);
  - dial 2 turn: emit `{:priority, id, :up | :down, detents}` for the selected ticket (action owned by SD-206);
  - dial 3: not handled by the server (sidecar-local instance switch, SD-207); the reducer ignores it;
  - key press: drill in (feature/epic -> its tickets; fleet category -> filtered tickets; ticket -> `{:open_ticket, id}` for SD-301).
- Channel event `input` (device -> Aiur) in `AiurWeb.StreamdeckChannel`, validated (kind allowlist, index 0..7 keys / 0..3 dials, ticks -32..32); state kept in assigns as `:deck_nav`; reply `{:ok, %{"view" => ..., "page" => ...}}`.
- `/streamdeck` LiveView keeps its own `Nav` in assigns and routes its existing dial and key events through `reduce/3` (render stays as today until SD-104).
- Long-press classification is defined here as a contract for SD-103/SD-104: the client fires `dial_long_press` once when the button has been held 500 ms, and then sends no `dial_press` on release.

## Non-goals

- Rendering any view (SD-102, SD-202..205). Ticket page (SD-301..304).
- Switching the sidecar's own input over to `input` (SD-103) or the emulator's pixels (SD-104).
- Persisting nav across reconnects. Settings for default view (SD-406).
- Mic hold, voice, Commands answer flow (they keep their current paths).

## Existing owner and reuse target

- Per-socket assigns pattern: `StreamdeckChannel.handle_in("focus")` (`streamdeck_channel.ex:47-55`).
- Clamp/paging math to port: `packages/streamdeck/src/dial.ts:127-195` (column paging) and `controller.ts:177-217` (one detent = one step, clamp before step).
- Pure-state precedent: `mode.ts:130-199` (`transitionMode` returning `{state, effects}`).

## Contract and invariants

- `reduce/3` is pure: no process calls; effects are data returned to the caller.
- `sizes` = `%{ticket: n, feature: n, epic: n, fleet: n, drill: n | nil}` from the Deck sections; a page never points past the last item after a list shrinks (clamp on every reduce).
- Cycling views never loses a view's page; drilling pushes, long press pops.
- Unknown input kinds are refused with `{:error, %{reason: "invalid_input"}}`, never ignored silently.

Worked shape:

```elixir
# input frame from the device
%{"kind" => "dial_press", "index" => 3}

# state before / after
%Nav{view: :ticket, pages: %{ticket: 2, feature: 0, epic: 0, fleet: 0}, stack: [], selected: "5998", scroll: 0}
%Nav{view: :feature, pages: %{ticket: 2, feature: 0, epic: 0, fleet: 0}, stack: [], selected: "5998", scroll: 0}

# key press on feature key 1 in Feature view
{%Nav{view: :feature, stack: [{:feature, "f-bo-2573-home"}], ...}, []}
# key press on a ticket key
{nav, [{:open_ticket, "5998"}]}
# dial 2 turn, ticks -1, with a selected ticket
{nav, [{:priority, "5998", :up, 1}]}
```

## Acceptance criteria

1. Dial 4 press cycles Ticket -> Feature -> Epic -> Fleet -> Ticket and keeps each view's page.
2. Dial 4 turn of +3 on a 30-item list moves the page from 0 to 3 (clamped at `ceil(30/8)-1 = 3`); a further +1 stays at 3.
3. Key press in Feature view pushes a drill entry; dial 4 long press pops it; long press at the root returns the same state.
4. Dial 2 turn with no selected ticket emits no effect.
5. Dial 3 input returns the state unchanged with no effect.
6. Channel `input` with `"kind" => "bogus"` or an index out of range replies `invalid_input`.
7. Two channel connections hold independent nav states.
8. The emulator's dial and key events go through `Nav.reduce/3`.
