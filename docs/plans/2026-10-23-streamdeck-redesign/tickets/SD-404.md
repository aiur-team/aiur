# SD-404 — Meter press: per-account 5h and weekly windows

**Complexity:** 3
**Phase hint:** 3
**Area:** area:ui
**Depends on:** SD-403 — provides `Deck.Meters` and the chosen-account rule; SD-201 — input model (key press and back); SD-102 — server renderer for the detail page.
**Serializes with:** SD-403 and SD-405 (`deck/meters.ex`), SD-205 (Fleet page key layout)

## Outcome
Pressing a provider meter opens a detail page. It shows one key per account, and each key has
two bars, 5h and weekly, with remaining percent and reset time. The touch strip shows the
provider summary. Long press on dial 4 returns.

## Context and evidence
`evidence/D-findings.md` §4. `Build.Usage` keeps per-account `acc` values but only the earliest
`reset_at` (`build/usage.ex:206-209`). Per-account readings with their own `resets_at` live in
`Aiur.Accounts.UsageReadings.snapshot/2`. There is no touch decoding in the sidecar (`input.ts:13-33`),
so the "press" is a key on the Fleet page.

## Scope
- `Deck.Meters.detail(provider)` returns one entry per account: `name`, `session` and `weekly`
  with `remaining_percent`, `reset_at`, and `freshness`.
- Add per-account `reset_at` to the shared model: in `Build.Usage.account_window/4`, keep a
  `resets` list beside `acc` (additive and optional, so the Build page can use it later). Add it to `PayloadSchema` as optional.
- A single-account provider shows one key with its two windows.
- The view state `{:meter_detail, provider}` in the SD-201 reducer. Entry: press a meter key on the Fleet
  page (SD-205). Exit: long press on dial 4.
- Render: an account key = name, two bars, "12% left · 2h". Unknown = "—" with a hatched bar.

## Non-goals
- No account switching or selection from the deck.
- No touch-strip tap decoding (see Open points).

## Existing owner and reuse target
- `Build.Usage` multi-account branch (`usage.ex:162-175,206-209`), `Aiur.Accounts.UsageReadings`,
  and `AiurWeb.RemainingMeter` (#5589).

## Contract and invariants
- `acc[i]` and `resets[i]` refer to the same account `names[i]`.
- Unknown remaining is never drawn as full or empty (#5589 rule 4).
- A stale account reading is dimmed and labelled "stale". Its value is not hidden.

```elixir
%{provider: "claude", accounts: [
   %{name: "personal", session: %{remaining_percent: 50, reset_at: 1761260000000}, weekly: %{remaining_percent: 70, reset_at: 1761600000000}, freshness: "fresh"},
   %{name: "work", session: %{remaining_percent: 12, reset_at: 1761250000000}, weekly: %{remaining_percent: nil, reset_at: nil}, freshness: "stale"}]}
```

## Refreshable implementation notes
- `src/lib/aiur_web/build/usage.ex:206-209` (`account_window/4`): add `resets`.
- `src/lib/aiur_web/build/payload_schema.ex` and the `payload.ex` moduledoc: an optional `resets` window field.
- `src/lib/aiur_web/streamdeck/deck/meters.ex`: `detail/1`.
- View: the SD-102 key renderer and the SD-201 reducer.

## Acceptance criteria
1. With two Claude accounts, `detail("claude")` lists both, sorted by name, with their own `reset_at`.
2. An account with no weekly reading shows weekly "—" and a hatched bar, not 0% and not 100%.
3. A meter key press on the Fleet page opens the detail. A long press on dial 4 returns to the Fleet page.
4. The Build page payload still validates with `resets` present and with it absent.
