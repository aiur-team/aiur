# SD-203 — Feature view with % progress and drill-in (#5998 data)

**Complexity:** 3
**Phase hint:** 4
**Area:** area:ui
**Depends on:** #5998 — its server block `feature_progress` is the data; it does not exist on main. SD-102 — renderer. SD-201 — paging and drill. SD-202 — drill-in shows tickets with `Tickets.keys(rows, {:feature, key})`.
**Serializes with:** SD-202, SD-204, SD-205 (Deck shell (`AiurWeb.Streamdeck.Deck`) section list)

## Outcome

The Feature view shows one key per feature with the same percentage as the Build home
Features view (#5998): closed / total, rounded down, with a ci_wait marker. A key press
shows that feature's tickets in the Ticket layout; dial 4 long press goes back.

## Context and evidence

- #5998 (OPEN, `agent:todo`, blocked by #5996) defines snapshot block `feature_progress`
  keyed by feature-local epic: `{closed, open, ci_wait, unpublished, total}` (integer or
  nil) + `observed_at`, percentage = closed / total rounded down, unknown never 0.
- Not on main (no `feature_progress` in `src/lib`). The existing
  `features[slug].stats` (`src/lib/aiur/build_order/index/catalogue.ex:24-28`) is
  complexity-weighted (`feature_stats.ex:15-21`) — a different number. Do not use it.
- Feature membership: a row's `epic` is one of `features[slug].epics` (`catalogue.ex:28`).
- Details: `evidence/B-findings.md` §5.

## Scope

- Section `AiurWeb.Streamdeck.Deck.Features` (`src/lib/aiur_web/streamdeck/deck/features.ex`): one key per `feature_progress` entry, in the snapshot `order` (wave order when #5997 metadata is present).
- Key model: label (from `features[slug].label`), percentage (`floor(closed*100/total)`), three-layer bar values (closed, open, unpublished), `ci_wait` count badge when > 0 and known.
- Unknown: any nil count -> "—" and a hatched/empty bar; never "0%".
- Drill-in: push `{:feature, slug}`; the drill list = `Tickets.keys(rows, {:feature, slug})` (rows whose `epic` is in that feature's `epics`).
- Strip line for the view: "<closed>/<total> closed · <unpublished> not published · age <n>m" from `observed_at` (AGENTS.md: a computed age is rendered).

## Non-goals

- The browser Features view and `feature_progress` itself (#5998).
- Feature icons (#5997); use a text key until then.

## Existing owner and reuse target

- Data: `feature_progress` block in `AiurWeb.Build.Payload` (added by #5998), read through the SD-101 adapter.
- Bar layering: same three layers as #5998's meter.

## Contract and invariants

- The deck percentage equals the Build Features view percentage for the same snapshot.
- Pages hold 8 features; turning dial 4 pages (SD-201).

Worked shape:

```elixir
# feature_progress entry (from #5998)
%{"f-bo-2573-home" => %{closed: 12, open: 5, ci_wait: 2, unpublished: 3, total: 20}, observed_at: 1_792_000_000_000}
# key model
%{key: "f-bo-2573-home", label: "Home / Build page", pct: 60, bar: %{closed: 12, open: 5, unpublished: 3}, ci_wait: 2}
# unknown closed
%{key: "f-bo-2573-cli", label: "CLI", pct: :unknown, reason: "states unavailable", bar: :unknown, ci_wait: nil}
```

## Acceptance criteria

1. Fixture with two features (12/20 closed; 0/4 closed) renders 60% and 0%.
2. A feature whose `closed` is nil renders "—" with its reason, not 0%.
3. `ci_wait` badge shows only when the count is known and > 0.
4. Key press drills into exactly the rows whose `epic` belongs to that feature; long press returns to page and feature view as before.
5. The strip shows the data age from `observed_at`.
6. On the real deck, one feature's % equals `/?view=list&list=features` for the same moment.
