# SD-301 — Deck ticket page: status, PR/CI, agent state

**Complexity:** 3
**Phase hint:** 2
**Area:** area:daemon
**Depends on:** SD-101 (the ticket page is one section module of the deck adapter shell)
**Serializes with:** SD-201, SD-302, SD-303, SD-304 (shared `packages/streamdeck/src/mode.ts`, `controller.ts`, `surface.ts`, `streamdeck_channel.ex` focus handler)

## Outcome

Pressing a ticket key opens a deck ticket page. It shows the same status, PR/CI and agent state
as the desktop Build modal header for that ticket at the same instant.

## Context and evidence

See `evidence/C-findings.md` §1, §2, §5. Today cmd mode (`touchStrip/agentDetail.ts`) shows the
`StreamDeckGrid` agent DTO, not the Build row. The desktop modal header reads the Build row via
`AiurWeb.Build.Ticket.open/2` → `DataSource.call(source, :ticket, [id, opts])` and labels it in
`priv/static/build-home/modal/header.js:13-41`. The Build row carries `pr` only for merged PRs
(`build_order/index/rows.ex:158-159`); open-PR and CI-green evidence is in
`Aiur.StartTrigger.ProgressStore.lookup/1`; CI-red / CI-wait / merge-queued are in
`agent.state` / `agent.pause` from `Build.NowRows`.

## Scope

- Add a ticket-page section to the SD-101 adapter (suggested `AiurWeb.Streamdeck.Deck.TicketPage`)
  that builds one DTO from the Build row (`DataSource :ticket`), `Controls.read_body/2`-equivalent
  control state (`TicketControl.encode/3`), and the open PR.
- Add the open PR to the shared Build row: `pr` = `%{num, state: "open", ci: stage}` from
  `ProgressStore.lookup/1` for non-hist rows, so the desktop modal gets the PR link too.
  Extend `Build.PayloadSchema` `pr` with optional `ci`.
- On `focus`, push a `ticket` event with the DTO; re-push on `:build_changes` /
  `:fleet_changed` for the focused id.
- Sidecar: cmd mode strip and keys read the `ticket` DTO instead of the grid agent for status,
  PR and CI. Keep existing painters (current renderer).

## Non-goals

- Actions (SD-302), chat (SD-303/SD-304), server-side images (SD-102).
- New status vocabulary: labels come from the Build taxonomy only.

## Existing owner and reuse target

- Row: `AiurWeb.Build.DataSource` / `Build.IndexSource` / `Build.Payload.ticket/3`.
- Status taxonomy: `Build.NowRows` (9 states) + `now-state.js` `AST` labels.
- Control: `AiurWeb.Build.TicketControl.encode/3`.
- PR/CI: `Aiur.StartTrigger.ProgressStore.lookup/1`, `Aiur.BuildOrder.Index.Rows.pr/1`.

## Contract and invariants

- Unknown stays `nil`; never a fabricated "no PR" or "CI green".
- Status label for a value matches the desktop label for the same row (one mapping, server-side).
- Read-only dashboard → control `state: "disabled"`.
- The DTO carries an `observed_at` and the deck renders its age when stale (AGENTS.md rule 1).

## Acceptance criteria

1. Focusing ticket N pushes one `ticket` event whose `status.label` equals the desktop header label for N.
2. A ticket with an open PR shows `#<num>` and its CI stage on the strip; the desktop modal shows the same PR link.
3. A ticket in `ci_wait`, `ci-red`, `merge-queued`, `usage_limited` and `parked` shows the matching Build label.
4. With `ProgressStore` empty, `pr` is `nil` and the strip shows no PR (not "no PR").
5. A stale DTO renders its age.

## Test that fails without the change

- ExUnit: a row in `now` with a `ProgressStore` entry `%{pr_number: 77, stage: :pr_opened}` →
  `Rows` emits `pr: %{num: 77, state: "open", ci: "pr_opened"}`. Fails on main (open PR is `nil`).
- Channel test: `focus` → `assert_push "ticket", %{"status" => %{"label" => "Waiting for CI"}}`
  for a `ci_wait` fixture. Fails on main (no `ticket` event).
