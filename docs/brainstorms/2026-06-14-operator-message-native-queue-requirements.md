# Operator-message parity: opencode pane == claude RC (native queue)

- **Date:** 2026-06-14
- **Status:** Requirements (brainstorm complete; ready for `/ce-plan`)
- **Scope tier:** Deep — feature (existing product shape; this refines delivery semantics)
- **Branch:** `kevin/repl-dualchat`

## Problem

An operator can talk to a `claude-repl` agent from two surfaces:

- **RC** — claude's own remote-control UI (`https://claude.ai/code/session_…`). Sends raw text to claude's native input. Works: "respond exactly 456" is answered in <10s.
- **opencode** — the aiur agent's tmux pane → opencode binary → aiur bridge → pane paste. Broken: "respond exactly 123" is delivered but never answered, and the `QUEUED` indicator clears before the agent reads it.

The goal is that these are **two views of one conversation** with **identical consumption semantics**, so operator messages land as fast and as reliably as native claude/codex CLI — regardless of which surface they're typed in.

## Root cause (verified in source + live `--test3` 2026-06-14)

The queueing is **already unified** on claude's native queue for `claude-repl`:
`coding_agent.ex:80-94` declares `immediate_delivery: true, safe_checkpoints: []` — operator text is typed straight into the pane and claude's native queue folds it in at the next turn boundary. The bespoke `AgentQueue`/`AgentQueueStore` is a **thin immediate pass-through** for this backend, not a competing queue.

Two narrow defects, not a queueing-architecture problem, cause the divergence:

1. **opencode wrapper corrupts the message.** The opencode binary wraps mid-stream operator text as
   `<system-reminder>The user sent the following message: <text>  Please address this message and continue with your tasks.</system-reminder>`
   (string is **not** in the aiur repo — generated by opencode). aiur pastes it verbatim into the pane (`repl_agent.ex:1007-1019`, control bytes collapsed to spaces). The "continue with your tasks" instruction makes claude keep working instead of stopping to answer. RC sends raw text and is obeyed.
2. **Ack at accept-time, not read-time.** The bridge closes the operator SSE with `finish_reason: stop` as soon as `AgentChat.send` is *accepted* (`chat_completions.ex:638-662`), so opencode clears `QUEUED` within ~1s — before claude has consumed the message. This is the "shown read before it is read" bug (task #37).

## Goals

1. A message typed in the opencode pane reaches claude as the operator's **raw text**, identical to what the RC UI sends — so claude obeys it the same way.
2. The opencode `QUEUED` indicator persists until claude **actually consumes** the message (UserPromptSubmit hook), then clears.
3. RC-typed and opencode-typed messages each appear **once**, with correct attribution, in **both** surfaces (two views of one convo).
4. Default mid-turn behavior stays **native**: queue and fold at the next turn boundary; never cut the agent off mid-work. Interrupt (Ctrl+C to the pane) remains the explicit out-of-band stop.

## Non-goals / out of scope

- **Codex and non-RC/headless claude delivery** — untouched (scope decision). Tasks #25/#27 stay pinned.
- **No new queue, and no removal of the shared `AgentQueue`** — it's a pass-through for repl and shared with codex. We change *what text is delivered* and *when the ack fires*, not the queue.
- **No programmatic RC-channel send** — aiur has no handle on claude's RC channel (it only parses the session URL: `remote_control.ex`). RC stays the user-driven claude.ai UI.

## Decisions (from brainstorm)

| Decision | Choice |
|---|---|
| Mid-turn default | Queue, fold at next boundary (native) |
| Architecture | Unify on claude's native queue — realize it by removing the two defects above |
| Scope | `claude-repl` RC↔opencode parity only |

## Key risk / open question (for planning spike)

**How does claude receive the operator's RAW text, given the opencode binary wraps mid-stream interjections?** Candidate directions to evaluate in `/ce-plan`:
- (a) Strip opencode's known wrapper boilerplate in the bridge before paste (simple; fragile if opencode changes the format).
- (b) Understand *why* opencode wraps (it appears to be opencode's "you typed while the assistant was streaming" format) and avoid triggering it — e.g., the bridge not appearing mid-stream when the operator submits.
- (c) Extract the operator's raw substring deterministically from the wrapper.
A short spike should confirm which is robust before committing.

## Spike results (wrapper question — resolved 2026-06-14)

Confirmed in the opencode binary (`~/.local/share/mise/installs/opencode/1.15.6/opencode`):

- opencode wraps operator text in `<system-reminder>` envelopes and uses **two** formats by its view of whether the assistant (our bridge) is busy on submit:
  - **idle:** `<system-reminder>Message sent at <UTC>.</system-reminder>\n<RAW>` — raw instruction follows; claude obeys (the "456 works" case).
  - **mid-stream:** `<system-reminder>\nThe user sent the following message:\n<RAW>\n\nPlease address this message and continue with your tasks.\n</system-reminder>` — instruction buried + softened; claude keeps working (the "123 fails" case). Template is verbatim in the binary.
- opencode ships its own `SYSTEM_REMINDER_RE = /<system-reminder>([\s\S]*?)<\/system-reminder>/g` and uses `<system-reminder>` for its own scaffolding (cwd change, file open, selection, goal) — none of which the real agent (claude) needs.
- The bridge currently **double-sends** an operator message: wrapped (~182B) via the primary `stream_turn`/`send_operator` path **and** raw (~49B) via `dispatch_shadowed_operator_texts` (the coalesce path). Claude receives both.

**Chosen direction: (c) deterministic extraction in the bridge.** Strip `<system-reminder>…</system-reminder>` envelopes and forward only the operator's genuine raw text, exactly once — matching what the RC UI sends. Robust because opencode is version-pinned and both formats are `<system-reminder>`-delimited. Rejected (b) "avoid triggering opencode's mid-stream format" — it requires reworking the bridge's held-open turn-stream model (high risk). Extraction also eliminates the double-send.

## Success criteria (verifiable)

1. Typing `pause and respond exactly "123"` in the opencode pane while the agent is mid-turn → agent answers `123` at the next turn boundary, **identical** to typing it in the RC UI.
2. The text claude receives for an opencode message contains **only** the operator's raw text (no `<system-reminder>`/"continue with your tasks" wrapper).
3. opencode `QUEUED` stays until the matching UserPromptSubmit hook fires, then clears (no premature clear).
4. A message sent from either surface renders once, attributed correctly, in both the RC transcript view and the opencode pane.
5. Codex and non-RC claude operator-message behavior is unchanged (regression check).
